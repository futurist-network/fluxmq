1. Скорость (потреблено сообщений/с, от продюсера до консьюмера). Один узел, group commit (fsync перед каждым подтверждением): 1 KiB — 231k (1×1) / 320k (4×4), 100 B — 427k / 632k. По сравнению с Kafka по умолчанию (подтверждение из page cache) это хуже при 1 KiB (0,44× / 0,55×) и при 100 B 1×1 (0,66×) и в 3 раза лучше при 100 B 4×4 (консьюмеры Kafka отстают: 210k; второй повтор Kafka упёрся в клиента и исключён). По сравнению с Kafka с fsync на каждое сообщение (равная надёжность): 0,81× / 0,73× при 1 KiB, 0,63× при 100 B 1×1, наравне при 100 B 4×4 (632k против 638k). Три узла RF=3: 1 KiB — 217k / 207k, 100 B — 622k / 328k: в 2,6 раза быстрее Kafka по умолчанию и в 1,7 раза быстрее Kafka с fsync при 1 KiB 4×4 (строки Kafka 3 узла 100 B 4×4 упёрлись в клиента и исключены), 0,86× Kafka по умолчанию при 1 KiB 1×1 (1,36× Kafka с fsync), наравне при 100 B 1×1. RabbitMQ: 11–38k (1 узел), 6–11k (3 узла) — FluxMQ быстрее в 16–85 раз. На одном узле продюсеры FluxMQ обгоняют его консьюмеров (публикуют в 1,7–2 раза больше, чем потребляется): при 1 KiB упираемся в 2 CPU брокера, при 100 B 1×1 — в SDK консьюмера (см. «Улучшения»). Пропускная способность, равная надёжность, по умолчанию против по умолчанию. После одного быстрого исправления, измеренного в конце (отложенное уплотнение «сырых» доставок, см. После быстрых исправлений): 1 узел 1 KiB — 277k / 476k, 100 B 1×1 — 545k; при 1 KiB 4×4 это уже быстрее Kafka с fsync (1,09×) и 0,82× Kafka по умолчанию; 3 узла 1 KiB — 239k / 297k.
  2. Задержка (от продюсера до консьюмера, 1 KiB, 4×4). Один узел, p50 / p99 / p99.9: 1,5 / 3,6 / 19 мс при 1k сообщ./с, 1,7 / 3,5 / 9,5 мс при 10k, 2,4 / 8,2 / 18 мс при 50k — лучший хвост среди всех систем (Kafka по умолчанию p99 12 / 16 / 22 мс, Kafka с fsync 40 / 44 / 57 мс, RabbitMQ 2,6 / 49 мс, 50k недостижимо). Три узла, p50 / p99: 2,7 / 7,5 мс, 7,6 / 19 мс, 14 / 131 мс: p99 лучше Kafka по умолчанию при 1k и 10k (8,3 / 84 мс) и намного лучше Kafka с fsync (100 / 259 / 601 мс), p50 выше, чем у Kafka по умолчанию (2,5–2,8 мс), а p99 при 50k немного хуже (131 против 110 мс) — FluxMQ делает fsync на каждой реплике ISR до подтверждения, Kafka по умолчанию — нет. Задержка.
  3. Надёжность (подтверждённые, но потерянные сообщения после сбоя). FluxMQ в режиме по умолчанию (group commit) потерял 0 подтверждённых сообщений во всех случаях: kill -9 и имитация отключения питания (грязный page cache сброшен, проверено canary-файлом при каждом сбое) — на одном узле, на лидере кластера из 3 узлов и на всех 3 узлах сразу; 12 сбоев, проверено 1,16M подтверждённых id. Kafka с настройками по умолчанию потеряла 90 094 подтверждённых сообщения в 2 из 2 отключений питания одного узла и 119 178 в 2 из 2 отключений всех 3 узлов (0 после kill -9 и 0, когда питание терял только лидер — уцелела реплика) — FluxMQ надёжнее Kafka в поставке по умолчанию. Kafka с fsync на каждое сообщение потеряла 0 (равная надёжность), а FluxMQ с fsync=os ‡ теряет так же, как Kafka по умолчанию (95 606 на одном узле, 104 374 при отключении всех 3 узлов) — поэтому этот режим не по умолчанию. Надёжность.
  4. Отказоустойчивость (узел падает под нагрузкой 5k сообщ./с, 3 узла). kill -9 брокера — лидера партиции 0, узел выключен на 30 с, продюсеры и консьюмеры работают: FluxMQ возобновил подтверждения через 5,9 с (5,4–6,4 с; обнаружение — node_timeout), консьюмеры — через те же 5,9 с; Kafka — через 11,4 с (8,7–14,0 с) — переключение примерно в 2 раза быстрее. 0 ошибок у клиентов (оба клиента повторяют внутри себя) и 0 потерянных подтверждённых у обоих. Когда узел возвращается, публикация у FluxMQ замирает на 38 мс против 178 мс у Kafka, а перезапущенный узел FluxMQ готов за 0,1–0,5 с против 11–22 с у Kafka (перезапуск в 20–100 раз быстрее). RabbitMQ здесь не измерялся (в инструменте сбоев нет клиента AMQP). Отказоустойчивость.
  5. Перегрузка и медленные консьюмеры. Продюсеры без ограничений 60 с. 100 B, 1 узел: консьюмеры FluxMQ по-прежнему получают 606k сообщ./с (37 % от 1,65M опубликованных; в 0.6 было 36k) — в 3 раза больше Kafka по умолчанию (201k), наравне с Kafka с fsync (628k, она и публикует меньше). 3 узла, 100 B: FluxMQ — 324k; строки Kafka 3 узла 100 B в перегрузке упёрлись в клиента (1,5k потреблено; у Kafka с fsync растянулось окно измерения), поэтому соотношение не приводим. 1 KiB: консьюмеры FluxMQ успевают (363k на 1 узле, 213k на 3), потому что CPU брокера ограничивает продюсеров; Kafka успевает на 616k на одном узле (FluxMQ 0,59×), но отстаёт на трёх (76k из 195k: FluxMQ в 2,8 раза больше). Брокер оставался отзывчивым (без ошибок); сообщения, удалённые лимитом размера до того, как их прочитала медленная группа, считаются и сопровождаются предупреждением, никогда не молча (после исправления ниже — 0 необъяснённых во всех прогонах). Перегрузка.
  6. Чтение вдогонку (большой накопленный объём). 100 B, 10,7M сообщений (1 GiB): FluxMQ 1,35M сообщ./с (8,0 с; 3 узла — 1,45M, 7,4 с) против Kafka 0,61–0,69M (17,7 с; 3 узла — 0,50M, 21,5 с) — примерно в 2 раза быстрее. 1 KiB, 1M сообщений: FluxMQ 477k сообщ./с, 2,2 с; скорость чтения Kafka после первого сообщения выше (1,9M сообщ./с), но вход в группу консьюмеров у неё дольше, поэтому по общему времени наравне (2,7 с). RabbitMQ: 44k (объём 100 MiB). Чтение вдогонку.
  7. Ресурсы. В простое: FluxMQ 0,02 ядра / 28 MiB (1 узел), 78 MiB на 3 узла; Kafka 0,06 / 436 MiB, 1,4 GiB на 3 узла; RabbitMQ 134 / 319 MiB — FluxMQ в покое занимает в 15–18 раз меньше памяти. Под нагрузкой 1 KiB 4×4 FluxMQ занимает весь лимит в 2 CPU: 155k сообщений на CPU-секунду брокера против 310k у Kafka по умолчанию и 423k с fsync — Kafka в 2–2,7 раза экономнее по CPU при 1 KiB (отдаёт консьюмерам через sendfile, FluxMQ копирует). Память под нагрузкой: FluxMQ 631 MiB против 1,47 GiB у Kafka (в 2,3 раза меньше). Ресурсы.

Цена TLS (только FluxMQ). 1 узел: −47 % при 1 KiB 1×1 (122k против 231k), −46 % при 4×4, −16 % / −17 % при 100 B; p99 при 1k/10k/50k — 7,3 / 19 / 8,5 мс. 3 узла (TLS клиентов + mTLS между узлами): −40 % / −47 % при 1 KiB, −7 % / −13 % при 100 B, p99 47 / 114 / 133 мс. TLS считается на тех же 2 CPU брокера, которые 1 KiB уже загружает полностью. Kafka и RabbitMQ с TLS не измерялись. TLS.
  9. Цена функций. lz4 (1 узел): потреблено +7 % при 1 KiB 4×4 и +8 % при 100 B 1×1, −3 % / −8 % в остальных; продюсеры заметно быстрее (1,33M против 354k сообщ./с при 1 KiB 4×4), CPU брокера падает до 1,3 ядра; p99 2,8–3,5 мс (лучшее из всех). Нагрузка бенчмарка сжимается очень хорошо; реальные данные — по-разному. Cumulative-подтверждения: от 0 до −7 % пропускной способности и хуже хвосты задержки (p99 27–33 мс при 10k–50k) в этом harness — выигрыша не измерено; индивидуальные подтверждения остаются по умолчанию и рекомендуются. Функции.
  10. Масштабирование 1 → 3 узла. Здесь три узла добавляют репликацию (RF=3, fsync на каждой реплике ISR), а не мощность: все три делят одну VM и один SSD. FluxMQ теряет от 6 % (1 KiB 1×1) до 35 % (1 KiB 4×4) и выигрывает при 100 B 1×1 (+46 %: на одном узле упирались в клиента); Kafka по умолчанию теряет 51 % (1×1) и 86 % (4×4, консьюмеры отстают) при 1 KiB, RabbitMQ — 34–72 %. FluxMQ сохраняет больше всего от своей пропускной способности на одном узле. Масштабирование.
  11. Итог. Лучше Kafka: хвосты задержки на одном узле (p99 3,5–8 мс против 12–22 мс) при fsync перед каждым подтверждением; пропускная способность 3 узлов при 1 KiB 4×4 (2,6×); консьюмеры в перегрузке (100 B: 3× на одном узле; 1 KiB: 2,8× на трёх); насыщение одного узла при 100 B 4×4 (3×); чтение вдогонку при 100 B (2×); память (в 2,3 раза меньше); ноль потерь подтверждённых после отключения питания там, где Kafka по умолчанию теряет 90–119k; переключение при отказе в 2 раза быстрее, перезапуск в 20–100 раз быстрее. Наравне: 100 B 1×1 на трёх узлах; общее время чтения вдогонку при 1 KiB; 100 B 4×4 против Kafka с fsync на одном узле. Хуже: насыщение одного узла при 1 KiB (0,44–0,55× Kafka по умолчанию, 0,73–0,81× Kafka с fsync) и 100 B 1×1 (0,66× / 0,63×) — это инженерный разрыв, а не плата за надёжность, ведь Kafka с fsync на каждое сообщение тоже быстрее: брокер копирует каждый байт консьюмерам (нет sendfile) и упирается в свои 2 CPU, а один консьюмер FluxMQ при 100 B ограничен ~430k сообщ./с в SDK. Также хуже: p50 задержки на трёх узлах (плата за надёжность: fsync на каждой реплике до подтверждения) и скорость 3 узлов при 1 KiB 1×1 (0,86×). Найдено и исправлено этим бенчмарком до публикации: отстающая группа консьюмеров могла пропустить хранящиеся, ещё не доставленные сообщения, когда retention по размеру её догоняла (нарушение at-least-once; теперь покрыто регрессионным тестом; все строки FluxMQ здесь — с исправленной сборки).
Методика и ограничения. Один MacBook Pro (M1 Pro, 8 ядер, 32 ГБ), VM Docker Desktop (8 CPU, 9,7 ГБ), каждый контейнер брокера ограничен 2 CPU / 2 GiB, клиент — 4 CPU (1 узел) или 2 (3 узла); три «узла» делят одну VM и один SSD, поэтому результаты 3 узлов показывают цену репликации, а не горизонтальное масштабирование. Тот же harness и настройки, что в v0.6 (окно 20 000, сегменты 16 MiB, retention 512 MiB на партицию, окна по 30 с), FluxMQ в режиме по умолчанию (group commit). Чтобы уложиться во время, в этом наборе 2 повтора насыщения (в v0.6 — 3 на одном узле), чтение вдогонку и перегрузка — только для основных систем, строки lz4 / cumulative — только на одном узле, по 2 итерации сбоев на режим. Объём для чтения вдогонку у RabbitMQ — 100 MiB (не 1 GiB). Прогоны Kafka при 100 B 4×4, где harness упёрся в CPU клиента и окно измерения растянулось, исключены из медиан (сохранены в наборе).

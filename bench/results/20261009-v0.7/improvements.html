Evidence: perf record -g --call-graph dwarf (499 Hz, 12 s inside the measured window) on the broker and the harness containers, built with symbols (fluxmq:prof, same source as the matrix), plus broker/client CPU from docker stats for every run. Profiles and reports: investigation/profile/ (runs) and the scratch reports quoted below. Shares are of the sampled process's CPU. None of the proposals weakens durability: fsync before ack, per-message acks, redelivery and DLQ stay as they are.

  1. Zero-copy outbound frames (vectored writes). Gap: one node, 1 KiB saturation, 0.44× / 0.55× Kafka default and 0.73–0.81× Kafka-fsync; the broker is CPU-bound (2.0 of 2 cores; 155k msg per CPU-second vs Kafka 310k / 423k). Root cause: 16.9 % of broker CPU is memcpy inside postcard::Serializer::serialize_field::<Bytes> ← FrameCodec::encode ← net::connection::feed / write_loop (crates/fluxmq-server/src/net/codec.rs, connection.rs): every raw DeliverRecords envelope is copied into the write buffer, plus 3.1 % BytesMut::reserve_inner (buffer growth copies). Kernel copy_to_user 12 % / copy_from_user 10 % (pread, writev) come on top. Kafka serves consumers with sendfile. Fix: encode only the frame header with postcard and hand the envelope Bytes to the socket as separate IoSlices (write_vectored), reserving the header buffer once; later, sendfile/splice for plaintext reads that come from disk. Expected gain: −15 to −20 % broker CPU per message at 1 KiB, i.e. +15–25 % consumed at 1 KiB on one node (more with TLS, where the same copies run before encryption). Risk: none for durability; wire format unchanged.
  2. Raw-run compaction in the middle of an ack batch (quick fix done, see "After quick fixes"). Gap: same rows, and 100 B 1×1. Root cause: GroupState::ack_at (crates/fluxmq-core/src/group.rs) compacts a raw in-flight run as soon as 7/8 of it is acked, calling Run::materialize, which decodes and CRC-checks the whole envelope chunk to keep the last 1/8 — which the same AckRanges settles a moment later. Profile: crc32c ← ChunkRecords::next ← Run::materialize ← ack_at ← Group::ack_ranges = 10 % of broker CPU at 1 KiB 4×4 and ~23 % (materialize + record iteration + varints + CRC) at 100 B 1×1. Fix (≤ 40 lines, done): collect candidates during the batch and compact only runs still mostly settled after it. Measured gain: +49 % consumed at 1 KiB 4×4 on one node (320k → 476k; consumers now keep up), +20 % at 1 KiB 1×1, +28 % at 100 B 1×1, +43 % / +10 % at 1 KiB on 3 nodes; 100 B 4×4 within noise (+2 % / −5 %); latency unchanged. Risk: none (memory-only optimization; the straggler compaction test still passes).
  3. Per-message attempt history on first deliveries. Gap: 100 B 1×1 (0.66× Kafka default) and part of the 1 KiB gap. Root cause: AttemptHistory::on_deliveries 10.3 % of broker CPU at 100 B 1×1 (2.4 % at 1 KiB), on_finishes 1.2 % (crates/fluxmq-core/src/history.rs): the retry timeline records every first delivery and its finish. Fix: record history only for messages that are redelivered, nacked or dead-lettered (first attempts are implied by the offset and the run's delivery time), or sample it. Expected gain: up to +10 % at 100 B. Risk: none for durability; changes what the retry-timeline UI shows for messages delivered once — product decision.
  4. Inbound copy of PublishBatch bodies. 3.5 % Bytes::copy_from_slice in ClientFrame::decode_frame (net/codec.rs): the batch body is copied out of the read buffer. Fix: BytesMut::split_to(n).freeze() for the body (zero-copy). Expected: −3 % broker CPU at 1 KiB. Risk: none (buffer lifetime only).
  5. SDK consumer cost per message. Gap: 100 B 1×1, where a single consumer task is the limit (broker at 0.55 cores). Harness profile: Delivery::ack future per message 2 %, malloc/free 5.4 %, Records::next 1.2 %, plus harness work common to all systems (a clock read per message, 17 %; the consumer closure, 9 %). Fix: an SDK batch-ack helper (ack a Vec<Delivery> / a whole frame in one call) and fewer per-Delivery allocations (shared header maps, no per-message Arc clone where avoidable). Expected: +15–25 % for one consumer at 100 B. Risk: none.
  6. TLS cost at 1 KiB (−46 to −47 % on one node, −40 to −47 % on 3 nodes). Same CPU budget as item 1: the copies and the encryption share the 2 broker CPUs that 1 KiB already saturates. Item 1 helps directly; kTLS would remove the user-space encryption copy (out of scope). Not separately profiled in this run.
  7. 3-node latency at 50k msg/s (p99 131 ms; v0.6 61 ms; p50 14 ms vs Kafka default 2.7 ms). Durability trade-off in part (fsync on every in-sync replica before the ack, three replicas sharing one SSD), but the p99 regression vs v0.6 is not explained yet: not profiled in this run (time budget). Next step: profile the leader and a follower at 50k msg/s (fetch long-poll wake-ups, group-commit interval, the overlapped follower fsync).
  8. Paced retention cannot keep up at saturation. The background pass removes at most 16 segments per second per channel (RETENTION_MAX_SEGMENTS_PER_TICK, broker.rs). Natively, at ~830 MB/s ingest with 4 MiB segments it removed ~64 MB/s, so the log overshoots its size cap without bound while producers saturate; in Docker (16 MiB segments, ~500 MB/s) it keeps up only barely. Fix: scale the per-tick budget with the overshoot (bytes over the cap / segment size), keeping the stepwise shrink. Risk: none for acked data (retention only removes what the cap allows; skips stay counted).
  9. Producers outrun consumers on one node. Under saturation FluxMQ publishes 1.7–2× what its consumers receive (Kafka publishes and consumes the same), so a closed-loop run turns into a growing backlog and, with a size cap, retention skips. The product rule says producers are never throttled by consumers; an opt-in per-channel "consumer-paced" admission (bounded lag) would make the default behaviour explicit for users who prefer it. Product decision.
  10. Harness. The Kafka 3-node 100 B 4×4 rows were client-bound (2 client CPUs saturated by librdkafka; the measurement window stretched); give the client 4 CPUs on 3-node runs next time. The FluxMQ audit cap was raised to 600 s during this run (a compressed backlog holds tens of millions of messages).

Erratum (added after the run; measurements unchanged). The "not drained" FluxMQ run (3 nodes, TLS, 1 KiB 4×4, repeat 2: 250 of 3.27 M acknowledged messages not received) was real data loss, not slow redelivery. Size retention deleted the newest closed segment. The harness's per-partition cap (128 MiB) equalled FluxMQ's default segment size, so right after a segment roll, closed + active segment exceeded the cap and the just-closed segment was deleted. Retention then kept almost nothing, and a consumer group whose next undelivered offset was still inside that segment skipped past it. In this run the skipped data was one producer batch of 250 messages (2000 window ÷ 8 partitions) that the producer had already had acknowledged. Fixed in v0.6: retention deletes a segment only while what remains still holds the cap, which is Kafka's rule. Regression test in fluxmq-core. The v0.6 harness checks delivery by message id and reports late vs missing messages.

Conclusions

  • Kafka is 2.5–5× faster than FluxMQ on throughput, on one node and in a 3-node cluster, at both message sizes. In the 4×4 runs Kafka saturated its 4-CPU client container (4.0 cores), so its real broker ceiling is higher still. FluxMQ is clearly behind here; this report does not dress that up.
  • FluxMQ is 10–25× faster than RabbitMQ (classic queues on one node, quorum queues on three), and RabbitMQ's broker was CPU-bound (≈ 2.2 of 2 cores) in every saturation run.
  • At low rates FluxMQ's latency is competitive: p99 6.4 ms at 1k msg/s on one node (Kafka 10.0, RabbitMQ 3.1) and 8.5 ms in the cluster (Kafka 6.1, RabbitMQ 8.3), with a p50 of about 4 ms. That floor comes from FluxMQ's group-commit fsync before every ack; Kafka acks from the page cache.
  • At 50k msg/s FluxMQ has a severe tail (p99 0.4–0.6 s on one node, 1.5–1.8 s in the cluster), caused by segment deletion under retention (next section). Kafka keeps p99 at 7 ms (one node) and 64 ms (cluster).
  • Footprint: FluxMQ idles at ~126 MiB per node and stays under ~600 MiB summed across 3 nodes under load. Kafka's 3 JVMs use 1.4 GiB idle and ~4.4 GiB under load.
  • TLS costs FluxMQ 0–10 % of throughput (largest with 4×4 at 1 KiB: −8 % on one node, −10 % in the cluster), with no measurable change in low-rate latency.
  • v0.5 batched delivery vs v0.4: +14 % (1 KiB) and +15 % (100 B) closed-loop throughput, and the same p99 at 1k msg/s (3.4–3.6 ms; one outlier at 20 ms).

Why FluxMQ loses to Kafka (best technical explanation)

  1. What an ack costs. A FluxMQ ack waits for the batch to be fsynced (group commit, 2 ms window). In the cluster it waits for every ISR member to have it, and each follower also fsyncs. Kafka with acks=all acks once the followers have the batch in memory, with no fsync anywhere. On this Docker VM disk an fsync costs several milliseconds, which sets FluxMQ's ~4 ms p50 floor and caps how many commits per second each partition log can do.
  2. The single-node ceiling is a serialized ack path, not CPU. At saturation FluxMQ's broker used only 1.3–1.9 of its 2 cores and the client wasn't saturated. Going from 2,000 to 8,000 messages in flight (1×1 → 4×4) raised throughput only 13 % (150k → 169k) while p50 latency tripled (14 → 46 ms). That is queueing in front of a fixed-rate stage: the per-partition append + group-commit pipeline. By Little's law, 2,000 in flight ÷ 14 ms ≈ 143k msg/s, which matches the 1×1 result.
  3. Work per message. FluxMQ parses every message, writes an index entry per message, and tracks per-message delivery state for consumer groups: acks, redelivery, retries and DLQ, which are its queue semantics. Kafka stores the producer's record batches as opaque blobs, serves consumers with sendfile, and consumers only commit offsets. Measured efficiency: Kafka ≈ 445k msg per broker CPU-second (1 KiB, 4×4), FluxMQ ≈ 100k, RabbitMQ ≈ 8k.
  4. Replication. FluxMQ followers pull through a fetch loop and fsync before the leader can advance the high watermark. Going from 1 to 3 nodes cost FluxMQ 37 % (150k → 94k, 1 KiB 1×1); Kafka lost 44 % but from a much higher base. Three "nodes" on one VM and one disk also share fsync bandwidth, which hurts the fsync-per-replica design most.

The 50k msg/s tail: cause

Every FluxMQ 50k msg/s run shows a single 0.5–1 s dip in publish acks, about 24 s into the run; nothing similar happens at 1k or 10k msg/s. Publish RTT p99 equals E2E p99, so the stall is on the ack path, not in the consumers. The open-loop harness correctly charges the backlog to every message scheduled during the stall: ~1 s × 50k msg/s ≈ 3 % of the window, which lands squarely in p99.

A/B test (same image and limits; FluxMQ 1 node, 50k msg/s, 1 KiB, 4×4): with the harness's 128 MiB/partition retention cap, p99 was 633 ms and 457 ms (two runs); with a cap the run never reaches (4 GiB/partition), p99 was 17.6 ms. So it is not the harness backlog and not steady-state fsync; it is retention deleting segments. Both capped runs dip exactly once, at t = 24 s (to 20–23k acks/s); the uncapped run never dips. Raw JSON: investigation/ in this result set.

Mechanism. FluxMQ's default segment size is 128 MiB, the same as the per-partition cap, and retention deletes only whole closed segments. So nothing is deleted until each partition has a second segment. Then all 8 partitions delete a 128 MiB segment at almost the same moment (~1 GiB, at ≈ 20–25 s at 50 MB/s). The segment-list lock is released before the unlinks, so the likely cause is the filesystem: on ext4 in the Docker VM, unlinking about 1 GiB makes the concurrent group-commit fsync wait behind the journal commit of the freed extents.

How this applies outside the benchmark. This is a real broker behaviour at high write rates, not a harness artifact: any deployment where retention removes large segments under load will see it. Kafka here deletes 16 MiB segments (and 1 GiB by default) continuously. Remedies: smaller default segments, and staggered or rate-limited deletion (or truncating large files in steps). These are listed as remaining work.

Anomalies and exclusions

  • Kafka, 3 nodes, 1 KiB 1×1, repeat 3: the consumer never received a message (its group never got an assignment), while the producer ran normally at 220k msg/s. It is excluded from the median, which is therefore over 2 runs (211k / 222k).
  • FluxMQ, 3 nodes TLS, 1 KiB 4×4, repeat 2: "not drained": 250 of 3.27 M messages acknowledged in the window weren't received within the 15 s drain. Consumption stopped near the end of the drain. The run's channel is deleted after each run, so slow redelivery can't be told apart from loss after the fact. This is reported as is and listed for investigation. The live integration checks (decommission under load, forget, controller kill) consumed every acknowledged message, and the other 2 repeats drained fully.
  • Batching drain rows are missing for v0.4: the v0.5 SDK's drain mode can't connect to a v0.4 broker ("unsupported protocol version 3 (broker speaks 2)"): the SDK does not negotiate down. Only the closed-loop and 1k msg/s rows compare the two versions. This is also a real compatibility limit: upgrade brokers before clients.
  • Reproducibility: the first full measurement (20261009-full, frozen, aborted at Kafka when the host disk filled) ran the same broker code as this one (its image is labelled 8df5f55-dirty: the working tree later committed as a02a18b). The FluxMQ single-node saturation medians agree within −3 … +7 %; see the History section.
  • Wall-clock gaps between some runs (the laptop likely slept). The in-run timelines are clean and windows are measured on the harness's monotonic clock, so measurements are unaffected; total durations are not meaningful.

Methodology

One harness for every system. bench/harness (mq-harness, Rust) drives FluxMQ through its SDK, Kafka through librdkafka (rdkafka crate, built from source) and RabbitMQ through lapin (AMQP 0-9-1), with one engine: the same producer loop, the same consumer accounting and the same HDR histograms. The first 8 bytes of every payload carry the send time on the harness's monotonic clock; producers and consumers run in one process, so end-to-end latency has no clock skew. The official perf tools (kafka-producer-perf-test, RabbitMQ perf-test) were not used for the comparison because they measure latency differently (Kafka's tool reports produce latency only, perf-test uses its own timestamping and a JVM client), which would mix tool differences into broker differences.

  • Topology per run: a fresh topic / channel / set of queues with 8 partitions (RabbitMQ: 8 queues used like partitions, producers round-robin over them, each consumer owns a share). Deleted after the run; retention capped at 128 MiB per partition / queue to bound disk use.
  • Producers: one connection each, messages sent one by one through the library's async API with at most 2000 unacknowledged per producer. Client-side batching is the library's own: FluxMQ BatchingProducer and Kafka linger.ms both linger 5 ms in saturation and 1 ms in the latency runs; AMQP has no producer batching (frames are pipelined, confirms are asynchronous).
  • Consumers: one connection each, one group (Kafka group / FluxMQ consumer group / queue share), starting at the beginning of the fresh topic; every message is acknowledged (FluxMQ ack, AMQP basic.ack; Kafka commits offsets automatically every 5 s, its normal mode).
  • Saturation: closed loop, 10 s warm-up discarded, 30 s measured, then up to 15 s for consumers to receive everything sent in the window ("drained").
  • Fixed-rate latency: open loop, sends scheduled evenly across producers; latency from the scheduled send time (30 s measured). Not sustained = publish or consume below 95 % of the target, or not drained.
  • Idle footprint: broker containers after start-up settle, no clients; under load: the same docker stats samples during the saturation window.
  • Fairness: every broker container has the same CPU and memory limit; clients run in their own container with their own limit on the same Docker network. Each system's stack is created fresh (empty volumes) and destroyed after its runs, so systems never run at the same time.
  • Repeats: every saturation configuration ran several times, interleaved (repeat 1 of every configuration, then repeat 2, …) so slow drift spreads evenly; the report shows the median and the min–max range.
  • Client resources: the single-node systems were driven by a 4-CPU client container, the 3-node systems by a 2-CPU one (3 × 2 broker CPUs + 2 = the VM's 8); every system within one comparison had the same client.
  • Batched delivery (FluxMQ only): fluxmq-bench of the v0.4 baseline image and of the current image, each against its own single broker, plus the current bench's drain mode against both brokers; rounds interleaved, a fresh broker per round.

Reproduce: bench/run.sh (everything) or e.g. bench/run.sh --systems fluxmq,kafka --scenarios saturation; raw JSON per run plus stats.jsonl and env.json are in the results directory.

Durability settings per system

What "acknowledged" means differs per system; that difference is part of the result.

  • FluxMQ: --fsync group-commit (default): a publish is acked after its batch is fsynced (commit window 2 ms). In the cluster: RF=3, --min-isr 2, acked once every ISR member has the batch (acks=all); followers also group-commit.
  • Kafka: producer acks=all, enable.idempotence=true. Brokers keep the default flush policy: no fsync per message; data reaches disk via the page cache, durability comes from replication. Cluster: RF=3, min.insync.replicas=2.
  • RabbitMQ 1 node: durable classic queues, persistent messages, publisher confirms (sent once the message is persisted, fsync batched). 3 nodes: quorum queues (Raft, 3 members), confirm after a majority has the entry fsynced to its write-ahead log.

Caveats

  • macOS Docker VM. All containers share one Linux VM (Docker Desktop, Apple Virtualization) on one laptop. Disk I/O goes through the VM's virtual disk; fsync cost there is neither macOS F_FULLFSYNC nor a server NVMe's. Networking is the VM's bridge, not a real network: no RTT, no bandwidth limit.
  • Single laptop, noisy neighbours. Brokers, clients and the host OS (and anything else running on the laptop, including builds) compete for the same cores, memory bandwidth and SSD. Thermal state matters. Each saturation configuration ran 3× (interleaved); bars show the median, whiskers the range. Latency, idle and resource figures come from one run each (resources: the median saturation repeat).
  • Not a production cluster. "3 nodes" are 3 containers on one VM and one disk: replication costs CPU and disk bandwidth that real separate machines would not share, and a node failure is not independent.
  • Client limits. One client container with a CPU limit drives every system (4 CPUs for the single-node systems, 2 for the 3-node systems so brokers + client fit the VM's 8 CPUs; the same within each comparison); check "Client CPU" in the resource table before attributing a ceiling to a broker.
  • Defaults, not tuned. Each broker runs close to its defaults (Kafka heap 1 GiB, RabbitMQ defaults, FluxMQ defaults) and each client library with mostly default settings. Expert tuning would change every number.
  • Different durability semantics (see the table above): faster acknowledgement can mean weaker guarantees.
  • Short runs. 30 s windows do not show segment rolling, retention, compaction, GC pauses over hours, or long-run steady state. TLS was measured for FluxMQ only, not for Kafka or RabbitMQ.

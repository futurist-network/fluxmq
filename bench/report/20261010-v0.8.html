FluxMQ в режиме по умолчанию — group commit (fsync перед каждым подтверждением, на каждой синхронной реплике). «◦ v0.7» — строка Kafka/RabbitMQ, взятая из набора v0.7 без перемера (Kafka не менялась). Под нагрузкой 1 KiB 4×4 брокер FluxMQ тратит 0,85 ядра на 511k msg/s (v0.7: 2,01 ядра, весь контейнер, на 310k — теперь в 3,9 раза больше сообщений на CPU-секунду; на 3 узлах — в 1,6 раза). Kafka тратит 1,73 ядра на 538k. В 1,9 раза больше сообщений на CPU-секунду на одном узле и в 2,1 раза на трёх; в 2,5 раза меньше памяти под нагрузкой (396 против 989 MiB). Ресурсы.

В v0.8.0 — свой слой записей поверх рукопожатия rustls (расшифровка на месте, независимые половины, AES-128 первым). A/B на этой же машине: 1 KiB 1×1 −63 % → −17 % (199k → 438k), 1 KiB 4×4 −14 % → −7 %, 3 узла −16 % → −3 %. Цель ≤ 15 % выполнена, кроме 1 KiB 1×1 (не хватает 2 п.). FluxMQ с TLS в 1,5 раза (1×1) и 2,7 раза (4×4) быстрее Kafka с TLS. A/B быстрого TLS, цена TLS v0.7 → v0.8.
  9. Масштабирование 1 → 3 узла (RF=3, одна машина). 1 KiB: −43 % / −50 %, как у Kafka (−46 % / −53 %). 100 B 4×4: +46 % (на 1 узле там упираются консьюмеры). Три «узла» делят одну VM и один SSD, так что это цена репликации, а не горизонтальное масштабирование. Масштабирование.
  10. Retention при насыщении. Каталог данных остался в пределах лимит + 2 сегмента в 21 из 21 прогона FluxMQ (пик 4 232 MiB при границе 4 352 MiB, до 32 GiB записано за прогон). Kafka выходила за лимит до 9,3 GiB в своём темпе retention. v0.7 превышал лимит на гигабайты. Retention.
  11. Вердикт. v0.8 выполняет продуктовую цель по большинству осей. Она надёжнее Kafka «из коробки» (0 против 90–119k потерянных при отключении питания) и при 1 KiB на одном узле не медленнее её, делая fsync перед каждым подтверждением. Она быстрее на трёх узлах, при перегрузке, в догоняющем чтении и в failover, тратит вдвое меньше CPU на сообщение и в разы меньше памяти. Где ещё проигрывает: цена TLS при 1 KiB на одном узле (−56 %), p50 на 3 узлах (fsync на каждой реплике), p99 на 3 узлах при 50k (наравне с Kafka, цель 20 мс не достигнута), перегрузка 1 KiB на 1 узле (0,91×), 3 узла 100 B 1×1 (0,95×) и догоняющее чтение 1 KiB на 1 узле против Kafka с fsync. Надёжностью нигде не жертвовали.

  6. Catch-up (1 GiB backlog, 4 consumers). 1 node: 1 KiB 1.28M msg/s, 100 B 2.51M (v0.7: 477k / 1.35M). Kafka ◦ v0.7: 395k / 608k, 3.2× / 4.1×. Kafka-fsync ◦ v0.7 was faster at 1 KiB on one node (1.69M). 3 nodes: 1.44M / 2.28M vs Kafka ◦ v0.7 568k / 499k (2.5× / 4.6×). Catch-up.
  7. Resources. Idle memory: 15 MiB on one node and 69 MiB on three, vs Kafka's 436 MiB and 1,428 MiB. Under 1 KiB 4×4 load the FluxMQ broker uses 0.85 cores for 511k msg/s (v0.7: 2.01 cores, the whole container, for 310k: 3.9× more messages per CPU-second now; 3 nodes 1.6×). Kafka uses 1.73 cores for 538k. 1.9× more messages per CPU-second on one node and 2.1× on three; 2.5× less memory under load (396 vs 989 MiB). Resources.
  8. TLS cost. v0.8.0: −17 % / −7 % / −3 %. In the main set (old TLS) 1 node 1 KiB 1×1 cost −56 %: rustls' buffered stream copied every byte three times. v0.8.0 ships FluxMQ's own record layer on the rustls handshake (in-place decrypt, independent halves, AES-128 first). Same-host A/B: 1 KiB 1×1 −63 % → −17 % (199k → 438k), 1 KiB 4×4 −14 % → −7 %, 3 nodes −16 % → −3 %. The ≤ 15 % goal is met except at 1 KiB 1×1 (2 points short).   9. Scaling 1 → 3 nodes (RF=3, one machine). 1 KiB: −43 % / −50 %, similar to Kafka's −46 % / −53 %. 100 B 4×4: +46 % (1-node consumers are saturated there). Three "nodes" share one VM and one SSD, so this is the cost of replication, not horizontal scaling. Scaling.
  10. Retention at saturation. The data directory stayed within cap + 2 segments in 21 of 21 FluxMQ runs (peak 4,232 MiB, bound 4,352 MiB, up to 32 GiB written per run). Kafka overshot to 9.3 GiB at its own retention pace. v0.7 overshot by gigabytes. Retention.
  11. Verdict. v0.8 meets the product goal on most axes: it is more reliable than Kafka as shipped (0 vs 90–119k lost on power cuts) and at least as fast at 1 KiB on one node while fsyncing every ack. It is faster on three nodes, under overload, in catch-up and in failover, and uses half the CPU per message and a fraction of the memory. Where it still loses: TLS cost at 1 KiB on one node (−56 %), 3-node p50 latency (fsync on every replica), the 3-node p99 at 50k (a tie with Kafka, 20 ms goal missed), 1-node 1 KiB overload (0.91×), 3-node 100 B 1×1 (0.95×) and 1-node 1 KiB catch-up vs Kafka-fsync. Durability was not traded anywhere.

What improved vs v0.7: 1-node throughput +71–112 % at 1 KiB (+64 % at 100 B 1×1) with drained consumers; broker CPU per message 3.9× lower on 1 node; catch-up 2–3×; overload consumption +17 % (100 B) / +54 % (1 KiB); bounded retention; lower 3-node tails at 1k–10k. 3 nodes vs the v0.7 set: +28–32 % at 1 KiB and 3.3× at 100 B 4×4, but the client got 4 CPUs instead of 2. The same-host A/B with 4 client CPUs puts the broker's share at +8 % (1 KiB 4×4: v0.7 image 251k → v0.8 273k). Same: durability (0 lost), failover (~5.6 s), 3-node p99 at 50k.

How this set was measured

Build. fluxmq:dev and fluxmq-harness:dev from HEAD 95107b0 (v0.8 part 1: zero-copy hot path, follower fetch-ahead with durable-progress reports, paced retention), built with deploy/build.sh --harness. Crash images were rebuilt from it with bench/crash/build.sh. The v0.7 control image is fluxmq:v07-base (cac69af, the published v0.7 plus its quick fix). Harness settings are as in v0.7: window 20 000, max in flight 32, 16 MiB segments, 512 MiB per partition retention (4 GiB per broker over 8 partitions), 30 s windows, group commit. The broker still reports version "0.7.0" because the crate version is bumped at release.

Host. Same MacBook (M1 Pro, Docker Desktop, 8 VM CPUs, broker containers 2 CPUs / 2 GiB). Free disk was 34–43 GB throughout; the previous v0.8 attempts ran with 8–13 GB free and saw multi-second fsync stalls. Sanity check first: the v0.7 image at 1 node, 1 KiB 1×1 gave 280k / 286k consumed (v0.7 after its quick fix: 274k / 280k), publish p99 62 / 67 ms (v0.7: 77 / 74 ms). An idle container measured 0.55 ms per 64 KiB O_DSYNC write (v0.7 notes: 0.9–1.3 ms). The host was not quiet: macOS StorageManagement / Storage services re-indexed the freed disk at 50–90 % CPU for the whole session (load average about 7 with no benchmark running), and an IDE was open. That shows up in latency tails, not in throughput (see "Host health").

Client CPUs. 4 for every system, on 1 node and (new in v0.8) on 3 nodes. With 2 CPUs, v0.7's Kafka 3-node 1 KiB 4×4 run was client-bound (80k); with 4 it reaches 251k. Kafka 3-node rows reused from v0.7 keep their 2 CPUs (column "Client CPUs").

Reductions to fit about 2–2.5 h (architect's trim).

  • FluxMQ saturation: 2 repeats for 1 KiB 1×1 and 4×4 (1 node and 3 nodes). The other cells have 1 repeat, except the 1-node 100 B cells, which got 2 because that pass was already running when the trim arrived.
  • FluxMQ TLS: 1 node 1 KiB and 100 B 1×1, 3 nodes 1 KiB 4×4, 1 repeat each, saturation only (no TLS code changed in v0.8).
  • Overload and catch-up: 1 KiB and 100 B, 4×4, 1 node and 3 nodes, 1 repeat, FluxMQ only. Kafka and RabbitMQ overload / catch-up rows are reused from v0.7.
  • Kafka re-measured with 1 repeat. On 1 node: saturation 1 KiB 1×1 and 4×4 and 100 B 4×4, latency 10k / 50k, both for the default and the fsync-per-message config. On 3 nodes: default saturation 1 KiB 4×4, default latency 10k / 50k, and fsync latency at 50k. Every other Kafka row is reused from 20261009-v0.7 (Kafka unchanged, same image apache/kafka:3.7.0), marked "◦ v0.7 run" in every table.
  • RabbitMQ: not re-run; every row is reused from v0.7.
  • Crash matrix: FluxMQ group commit only, 1 iteration per mode and target (6 crashes). v0.7 had 2 iterations (12 crashes), and the v0.8 replication agent ran 8 more on this code (771,160 acked, 0 lost). The Kafka crash rows are reused from v0.7, with evidence in 20261009-v0.7/crash/runs/.

  • Not run: fsync=os, lz4 and cumulative-ack rows (v0.7 has them) and the idle scenario for the TLS systems.

Sampler. During saturation, overload and catch-up runs a script ran du on every broker's data directory and read FluxMQ's fsync histogram (/metrics) every ~2 s via docker exec. That gives the retention check and the fsync columns (samples-summary.json, raw reduced samples in samples.jsonl.gz). It was off during latency runs, because docker exec every 2 s visibly worsened latency tails. The first 1-node latency pass ran with it on (p99 113–173 ms); those runs are kept in investigation/latency-tails/matrix-sampler-on/ and were re-measured with the sampler off.

Excluded runs: none. Every FluxMQ run passed the id check (0 missing). Runs where producers outran consumers are reported as measured ("not drained": every miss was still stored or a counted retention skip).

Method: what each crash simulates, and its limits

kill9: SIGKILL of the broker's whole process group inside its container (crashctl kill9). The kernel and its page cache survive: everything the broker had written with write(2) is still there after the restart, fsynced or not. Simulates a broker process crash (OOM kill, panic, kill -9), not a machine crash.

powercut: Simulated power loss of the broker's machine (crashctl powercut). The data directory is an ext4 filesystem on a device-mapper device over a loop device backed by a sparse file in a Docker volume. At the cut the dm device is suspended without flushing and switched to the dm `error` target, then the broker gets SIGKILL (before the device resumes, so it never sees the I/O errors). The filesystem is unmounted: dirty pages (written but not yet written back or fsynced) fail against the error target and the device's cache is dropped. Then the linear mapping is restored and ext4 is mounted again (journal replay), exactly the bytes that had reached the device at the cut. Only data that was fsynced (or written back by the kernel's periodic writeback before the cut) survives. A per-crash canary proves it: a file created just before the cut must be gone, a file synced before the workload must be there.

Canary. Before each crash the tool writes a file that is never fsynced and checks after the restart: after kill9 it must survive (page cache intact), after powercut it must be gone while a file synced before the workload must be there. A run whose canary disagrees is marked invalid.

Limits. The device below the cut is trusted (the Docker VM does not crash); kernel writeback that happened before the cut survives, which favours page-cache systems (Kafka defaults, FluxMQ fsync=os), never fsync-before-ack systems; torn sectors inside one write are not emulated (covered by the storage engine's torn-tail tests); one laptop, one SSD, three "nodes" on one VM; recovery time is until the readiness probe passes (Kafka's probe starts a JVM, adding seconds).   • Both images show them. The v0.7 image shows them as often and as large as v0.8 when the runs alternate (A/B rows), so they are not caused by v0.8 changes.

  • The storage engine's fsyncs are healthy inside the spiky windows. In the sampler-on 1-node runs the fsync mean was 0.6–1 ms and p99 ≤ 2.5–10 ms, while the publish p99 was 110–223 ms.

Methodology

One harness for every system. bench/harness (mq-harness, Rust) drives FluxMQ through its SDK, Kafka through librdkafka (rdkafka crate, built from source) and RabbitMQ through lapin (AMQP 0-9-1), with one engine: the same producer loop, the same consumer accounting and the same HDR histograms. The first 8 bytes of every payload carry the send time on the harness's monotonic clock; producers and consumers run in one process, so end-to-end latency has no clock skew. The official perf tools (kafka-producer-perf-test, RabbitMQ perf-test) were not used for the comparison because they measure latency differently (Kafka's tool reports produce latency only, perf-test uses its own timestamping and a JVM client), which would mix tool differences into broker differences.

  • Topology per run: a fresh topic / channel / set of queues with 8 partitions (RabbitMQ: 8 queues used like partitions, producers round-robin over them, each consumer owns a share). Deleted after the run; retention capped at 512 MiB per partition / queue to bound disk use. Segment size 16 MiB for FluxMQ (broker FLUXMQ_SEGMENT_BYTES) and Kafka (topic segment.bytes); RabbitMQ has no equivalent setting.
  • Producers: one connection each, messages sent one by one through the library's async API with at most 20000 unacknowledged per producer (FluxMQ: up to 32 Publish requests pipelined per producer). FluxMQ producers run with stamp_producer=false: no flux-producer header per message, like the Kafka and RabbitMQ clients, which send no header either. Client-side batching is the library's own: FluxMQ BatchingProducer and Kafka linger.ms both linger 5 ms in saturation and 1 ms in the latency runs; AMQP has no producer batching (frames are pipelined, confirms are asynchronous).
  • Consumers: one connection each, one group (Kafka group / FluxMQ consumer group / queue share), starting at the beginning of the fresh topic; every message is acknowledged (FluxMQ ack, AMQP basic.ack; Kafka commits offsets automatically every 5 s, its normal mode).
  • Saturation: closed loop, 10 s warm-up discarded, 30 s measured, then up to 15 s for consumers to receive everything sent in the window ("drained"). Checked by message id (producer + sequence number in the payload): every message the broker acknowledged must arrive at least once. On a miss the harness keeps waiting 45 s more and reports each missed message as late or missing.
  • Fixed-rate latency: open loop, sends scheduled evenly across producers; latency from the scheduled send time (30 s measured). Not sustained = publish or consume below 95 % of the target, or not drained.
  • Idle footprint: broker containers after start-up settle, no clients; under load: the same docker stats samples during the saturation window.
  • Fairness: every broker container has the same CPU and memory limit; clients run in their own container with their own limit on the same Docker network. Each system's stack is created fresh (empty volumes) and destroyed after its runs, so systems never run at the same time.
  • Repeats: every saturation configuration ran several times, interleaved (repeat 1 of every configuration, then repeat 2, …) so slow drift spreads evenly; the report shows the median and the min–max range.
  • Client resources: the single-node systems were driven by a 4-CPU client container, the 3-node systems by a 2-CPU one (3 × 2 broker CPUs + 2 = the VM's 8); every system within one comparison had the same client.
  • Batched delivery (FluxMQ only): fluxmq-bench of the v0.4 baseline image and of the current image, each against its own single broker, plus the current bench's drain mode against both brokers; rounds interleaved, a fresh broker per round.

Reproduce: bench/run.sh (everything) or e.g. bench/run.sh --systems fluxmq,kafka --scenarios saturation; raw JSON per run plus stats.jsonl and env.json are in the results directory.

Durability settings per system

What "acknowledged" means differs per system; that difference is part of the result.

  • FluxMQ: --fsync group-commit (default): a publish is acked after its batch is fsynced (commit window 2 ms). In the cluster: RF=3, --min-isr 2, acked once every ISR member has the batch (acks=all); followers also group-commit.
  • Kafka: producer acks=all, enable.idempotence=true. Brokers keep the default flush policy: no fsync per message; data reaches disk via the page cache, durability comes from replication. Cluster: RF=3, min.insync.replicas=2.
  • RabbitMQ 1 node: durable classic queues, persistent messages, publisher confirms (sent once the message is persisted, fsync batched). 3 nodes: quorum queues (Raft, 3 members), confirm after a majority has the entry fsynced to its write-ahead log.

Caveats

  • macOS Docker VM. All containers share one Linux VM (Docker Desktop, Apple Virtualization) on one laptop. Disk I/O goes through the VM's virtual disk; fsync cost there is neither macOS F_FULLFSYNC nor a server NVMe's. Networking is the VM's bridge, not a real network: no RTT, no bandwidth limit.
  • Single laptop, noisy neighbours. Brokers, clients and the host OS (and anything else running on the laptop, including builds) compete for the same cores, memory bandwidth and SSD. Thermal state matters. Each saturation configuration ran 2× (interleaved); bars show the median, whiskers the range. Latency, idle and resource figures come from one run each (resources: the median saturation repeat).
  • Not a production cluster. "3 nodes" are 3 containers on one VM and one disk: replication costs CPU and disk bandwidth that real separate machines would not share, and a node failure is not independent.
  • Client limits. One client container with a CPU limit drives every system (4 CPUs for the single-node systems, 2 for the 3-node systems so brokers + client fit the VM's 8 CPUs; the same within each comparison); check "Client CPU" in the resource table before attributing a ceiling to a broker.
  • Defaults, not tuned. Each broker runs close to its defaults (Kafka heap 1 GiB, RabbitMQ defaults, FluxMQ defaults) and each client library with mostly default settings. Expert tuning would change every number.
  • Different durability semantics (see the table above): faster acknowledgement can mean weaker guarantees.
  • Short runs. 30 s windows do not show segment rolling, retention, compaction, GC pauses over hours, or long-run steady state. TLS was measured for FluxMQ only, not for Kafka or RabbitMQ.

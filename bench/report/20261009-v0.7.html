Ключевые вопросы — ответы / Key questions — answers

  1. Скорость (потреблено сообщений/с, от продюсера до консьюмера). Один узел, group commit (fsync перед каждым подтверждением): 1 KiB — 231k (1×1) / 320k (4×4), 100 B — 427k / 632k. По сравнению с Kafka по умолчанию (подтверждение из page cache) это хуже при 1 KiB (0,44× / 0,55×) и при 100 B 1×1 (0,66×) и в 3 раза лучше при 100 B 4×4 (консьюмеры Kafka отстают: 210k; второй повтор Kafka упёрся в клиента и исключён). По сравнению с Kafka с fsync на каждое сообщение (равная надёжность): 0,81× / 0,73× при 1 KiB, 0,63× при 100 B 1×1, наравне при 100 B 4×4 (632k против 638k). Три узла RF=3: 1 KiB — 217k / 207k, 100 B — 622k / 328k: в 2,6 раза быстрее Kafka по умолчанию и в 1,7 раза быстрее Kafka с fsync при 1 KiB 4×4 (строки Kafka 3 узла 100 B 4×4 упёрлись в клиента и исключены), 0,86× Kafka по умолчанию при 1 KiB 1×1 (1,36× Kafka с fsync), наравне при 100 B 1×1. RabbitMQ: 11–38k (1 узел), 6–11k (3 узла) — FluxMQ быстрее в 16–85 раз. На одном узле продюсеры FluxMQ обгоняют его консьюмеров (публикуют в 1,7–2 раза больше, чем потребляется): при 1 KiB упираемся в 2 CPU брокера, при 100 B 1×1 — в SDK консьюмера (см. «Улучшения»). Пропускная способность, равная надёжность, по умолчанию против по умолчанию. После одного быстрого исправления, измеренного в конце (отложенное уплотнение «сырых» доставок, см. После быстрых исправлений): 1 узел 1 KiB — 277k / 476k, 100 B 1×1 — 545k; при 1 KiB 4×4 это уже быстрее Kafka с fsync (1,09×) и 0,82× Kafka по умолчанию; 3 узла 1 KiB — 239k / 297k.
  2. Задержка (от продюсера до консьюмера, 1 KiB, 4×4). Один узел, p50 / p99 / p99.9: 1,5 / 3,6 / 19 мс при 1k сообщ./с, 1,7 / 3,5 / 9,5 мс при 10k, 2,4 / 8,2 / 18 мс при 50k — лучший хвост среди всех систем (Kafka по умолчанию p99 12 / 16 / 22 мс, Kafka с fsync 40 / 44 / 57 мс, RabbitMQ 2,6 / 49 мс, 50k недостижимо). Три узла, p50 / p99: 2,7 / 7,5 мс, 7,6 / 19 мс, 14 / 131 мс: p99 лучше Kafka по умолчанию при 1k и 10k (8,3 / 84 мс) и намного лучше Kafka с fsync (100 / 259 / 601 мс), p50 выше, чем у Kafka по умолчанию (2,5–2,8 мс), а p99 при 50k немного хуже (131 против 110 мс) — FluxMQ делает fsync на каждой реплике ISR до подтверждения, Kafka по умолчанию — нет. Задержка.
  3. Надёжность (подтверждённые, но потерянные сообщения после сбоя). FluxMQ в режиме по умолчанию (group commit) потерял 0 подтверждённых сообщений во всех случаях: kill -9 и имитация отключения питания (грязный page cache сброшен, проверено canary-файлом при каждом сбое) — на одном узле, на лидере кластера из 3 узлов и на всех 3 узлах сразу; 12 сбоев, проверено 1,16M подтверждённых id. Kafka с настройками по умолчанию потеряла 90 094 подтверждённых сообщения в 2 из 2 отключений питания одного узла и 119 178 в 2 из 2 отключений всех 3 узлов (0 после kill -9 и 0, когда питание терял только лидер — уцелела реплика) — FluxMQ надёжнее Kafka в поставке по умолчанию. Kafka с fsync на каждое сообщение потеряла 0 (равная надёжность), а FluxMQ с fsync=os ‡ теряет так же, как Kafka по умолчанию (95 606 на одном узле, 104 374 при отключении всех 3 узлов) — поэтому этот режим не по умолчанию. Надёжность.

Отказоустойчивость (узел падает под нагрузкой 5k сообщ./с, 3 узла). kill -9 брокера — лидера партиции 0, узел выключен на 30 с, продюсеры и консьюмеры работают: FluxMQ возобновил подтверждения через 5,9 с (5,4–6,4 с; обнаружение — node_timeout), консьюмеры — через те же 5,9 с; Kafka — через 11,4 с (8,7–14,0 с) — переключение примерно в 2 раза быстрее. 0 ошибок у клиентов (оба клиента повторяют внутри себя) и 0 потерянных подтверждённых у обоих. Когда узел возвращается, публикация у FluxMQ замирает на 38 мс против 178 мс у Kafka, а перезапущенный узел FluxMQ готов за 0,1–0,5 с против 11–22 с у Kafka (перезапуск в 20–100 раз быстрее). RabbitMQ здесь не измерялся (в инструменте сбоев нет клиента AMQP). Отказоустойчивость.
  5. Перегрузка и медленные консьюмеры. Продюсеры без ограничений 60 с. 100 B, 1 узел: консьюмеры FluxMQ по-прежнему получают 606k сообщ./с (37 % от 1,65M опубликованных; в 0.6 было 36k) — в 3 раза больше Kafka по умолчанию (201k), наравне с Kafka с fsync (628k, она и публикует меньше). 3 узла, 100 B: FluxMQ — 324k; строки Kafka 3 узла 100 B в перегрузке упёрлись в клиента (1,5k потреблено; у Kafka с fsync растянулось окно измерения), поэтому соотношение не приводим. 1 KiB: консьюмеры FluxMQ успевают (363k на 1 узле, 213k на 3), потому что CPU брокера ограничивает продюсеров; Kafka успевает на 616k на одном узле (FluxMQ 0,59×), но отстаёт на трёх (76k из 195k: FluxMQ в 2,8 раза больше). Брокер оставался отзывчивым (без ошибок); сообщения, удалённые лимитом размера до того, как их прочитала медленная группа, считаются и сопровождаются предупреждением, никогда не молча (после исправления ниже — 0 необъяснённых во всех прогонах). Перегрузка.
  6. Чтение вдогонку (большой накопленный объём). 100 B, 10,7M сообщений (1 GiB): FluxMQ 1,35M сообщ./с (8,0 с; 3 узла — 1,45M, 7,4 с) против Kafka 0,61–0,69M (17,7 с; 3 узла — 0,50M, 21,5 с) — примерно в 2 раза быстрее. 1 KiB, 1M сообщений: FluxMQ 477k сообщ./с, 2,2 с; скорость чтения Kafka после первого сообщения выше (1,9M сообщ./с), но вход в группу консьюмеров у неё дольше, поэтому по общему времени наравне (2,7 с). RabbitMQ: 44k (объём 100 MiB). Чтение вдогонку.
  7. Ресурсы. В простое: FluxMQ 0,02 ядра / 28 MiB (1 узел), 78 MiB на 3 узла; Kafka 0,06 / 436 MiB, 1,4 GiB на 3 узла; RabbitMQ 134 / 319 MiB — FluxMQ в покое занимает в 15–18 раз меньше памяти. Под нагрузкой 1 KiB 4×4 FluxMQ занимает весь лимит в 2 CPU: 155k сообщений на CPU-секунду брокера против 310k у Kafka по умолчанию и 423k с fsync — Kafka в 2–2,7 раза экономнее по CPU при 1 KiB (отдаёт консьюмерам через sendfile, FluxMQ копирует). Память под нагрузкой: FluxMQ 631 MiB против 1,47 GiB у Kafka (в 2,3 раза меньше). Ресурсы.

Цена TLS (только FluxMQ). 1 узел: −47 % при 1 KiB 1×1 (122k против 231k), −46 % при 4×4, −16 % / −17 % при 100 B; p99 при 1k/10k/50k — 7,3 / 19 / 8,5 мс. 3 узла (TLS клиентов + mTLS между узлами): −40 % / −47 % при 1 KiB, −7 % / −13 % при 100 B, p99 47 / 114 / 133 мс. TLS считается на тех же 2 CPU брокера, которые 1 KiB уже загружает полностью. Kafka и RabbitMQ с TLS не измерялись. TLS.
  9. Цена функций. lz4 (1 узел): потреблено +7 % при 1 KiB 4×4 и +8 % при 100 B 1×1, −3 % / −8 % в остальных; продюсеры заметно быстрее (1,33M против 354k сообщ./с при 1 KiB 4×4), CPU брокера падает до 1,3 ядра; p99 2,8–3,5 мс (лучшее из всех). Нагрузка бенчмарка сжимается очень хорошо; реальные данные — по-разному. Cumulative-подтверждения: от 0 до −7 % пропускной способности и хуже хвосты задержки (p99 27–33 мс при 10k–50k) в этом harness — выигрыша не измерено; индивидуальные подтверждения остаются по умолчанию и рекомендуются. Функции.
  10. Масштабирование 1 → 3 узла. Здесь три узла добавляют репликацию (RF=3, fsync на каждой реплике ISR), а не мощность: все три делят одну VM и один SSD. FluxMQ теряет от 6 % (1 KiB 1×1) до 35 % (1 KiB 4×4) и выигрывает при 100 B 1×1 (+46 %: на одном узле упирались в клиента); Kafka по умолчанию теряет 51 % (1×1) и 86 % (4×4, консьюмеры отстают) при 1 KiB, RabbitMQ — 34–72 %. FluxMQ сохраняет больше всего от своей пропускной способности на одном узле. Масштабирование.
  11. Итог. Лучше Kafka: хвосты задержки на одном узле (p99 3,5–8 мс против 12–22 мс) при fsync перед каждым подтверждением; пропускная способность 3 узлов при 1 KiB 4×4 (2,6×); консьюмеры в перегрузке (100 B: 3× на одном узле; 1 KiB: 2,8× на трёх); насыщение одного узла при 100 B 4×4 (3×); чтение вдогонку при 100 B (2×); память (в 2,3 раза меньше); ноль потерь подтверждённых после отключения питания там, где Kafka по умолчанию теряет 90–119k; переключение при отказе в 2 раза быстрее, перезапуск в 20–100 раз быстрее. Наравне: 100 B 1×1 на трёх узлах; общее время чтения вдогонку при 1 KiB; 100 B 4×4 против Kafka с fsync на одном узле. Хуже: насыщение одного узла при 1 KiB (0,44–0,55× Kafka по умолчанию, 0,73–0,81× Kafka с fsync) и 100 B 1×1 (0,66× / 0,63×) — это инженерный разрыв, а не плата за надёжность, ведь Kafka с fsync на каждое сообщение тоже быстрее: брокер копирует каждый байт консьюмерам (нет sendfile) и упирается в свои 2 CPU, а один консьюмер FluxMQ при 100 B ограничен ~430k сообщ./с в SDK. Также хуже: p50 задержки на трёх узлах (плата за надёжность: fsync на каждой реплике до подтверждения) и скорость 3 узлов при 1 KiB 1×1 (0,86×). Найдено и исправлено этим бенчмарком до публикации: отстающая группа консьюмеров могла пропустить хранящиеся, ещё не доставленные сообщения, когда retention по размеру её догоняла (нарушение at-least-once; теперь покрыто регрессионным тестом; все строки FluxMQ здесь — с исправленной сборки).
Методика и ограничения. Один MacBook Pro (M1 Pro, 8 ядер, 32 ГБ), VM Docker Desktop (8 CPU, 9,7 ГБ), каждый контейнер брокера ограничен 2 CPU / 2 GiB, клиент — 4 CPU (1 узел) или 2 (3 узла); три «узла» делят одну VM и один SSD, поэтому результаты 3 узлов показывают цену репликации, а не горизонтальное масштабирование. Тот же harness и настройки, что в v0.6 (окно 20 000, сегменты 16 MiB, retention 512 MiB на партицию, окна по 30 с), FluxMQ в режиме по умолчанию (group commit). Чтобы уложиться во время, в этом наборе 2 повтора насыщения (в v0.6 — 3 на одном узле), чтение вдогонку и перегрузка — только для основных систем, строки lz4 / cumulative — только на одном узле, по 2 итерации сбоев на режим. Объём для чтения вдогонку у RabbitMQ — 100 MiB (не 1 GiB). Прогоны Kafka при 100 B 4×4, где harness упёрся в CPU клиента и окно измерения растянулось, исключены из медиан (сохранены в наборе).   1. Speed (consumed msg/s, end to end). One node, group commit (fsync before every ack): 1 KiB 231k (1×1) / 320k (4×4), 100 B 427k / 632k. Against Kafka's default (page-cache acks) that is worse at 1 KiB (0.44× / 0.55×) and 100 B 1×1 (0.66×), 3.0× better at 100 B 4×4 (Kafka's consumers fall behind: 210k; its second repeat was client-bound and is excluded). Against Kafka with fsync per message (equal durability): 0.81× / 0.73× at 1 KiB, 0.63× at 100 B 1×1, on par at 100 B 4×4 (632k vs 638k). Three nodes RF=3: 1 KiB 217k / 207k, 100 B 622k / 328k: 2.6× Kafka default and 1.7× Kafka-fsync at 1 KiB 4×4 (Kafka's 3-node 100 B 4×4 rows are client-bound and excluded), 0.86× Kafka default at 1 KiB 1×1 (1.36× Kafka-fsync), on par at 100 B 1×1. RabbitMQ: 11–38k (1 node), 6–11k (3 nodes) — FluxMQ is 16–85× faster. On one node FluxMQ's producers outrun its consumers (they publish 1.7–2× what is consumed); the limit is the broker's 2 CPUs at 1 KiB and the consumer SDK at 100 B 1×1 (see Improvements). Throughput, equal durability, default vs default. After one quick fix measured at the end (deferred raw-run compaction, see After quick fixes): 1 node 1 KiB 277k / 476k and 100 B 1×1 545k — 1 KiB 4×4 then beats Kafka-fsync (1.09×) and reaches 0.82× Kafka default; 3 nodes 1 KiB 239k / 297k.
  2. Latency (end to end, 1 KiB, 4×4). One node p50 / p99 / p99.9: 1.5 / 3.6 / 19 ms at 1k msg/s, 1.7 / 3.5 / 9.5 ms at 10k, 2.4 / 8.2 / 18 ms at 50k — the best tail of all systems (Kafka default p99 12 / 16 / 22 ms, Kafka-fsync 40 / 44 / 57 ms, RabbitMQ 2.6 / 49 ms, 50k not reachable). Three nodes p50 / p99: 2.7 / 7.5 ms, 7.6 / 19 ms, 14 / 131 ms: p99 better than Kafka default at 1k and 10k (8.3 / 84 ms) and far better than Kafka-fsync (100 / 259 / 601 ms), p50 higher than Kafka default (2.5–2.8 ms) and p99 at 50k slightly worse (131 vs 110 ms) — FluxMQ fsyncs on every in-sync replica before the ack, Kafka's default does not. Latency.
  3. Reliability (acked-but-lost after a crash). FluxMQ in its default group commit lost 0 acknowledged messages in every case: kill -9 and a simulated power cut (dirty page cache dropped, verified by a canary on every crash), on one node, on the leader of a 3-node cluster and on all 3 nodes at once — 12 crashes, 1.16M acked ids checked. Kafka with its default flush lost 90,094 acked messages in 2 of 2 power cuts on one node and 119,178 in 2 of 2 power cuts of all 3 nodes (0 after kill -9, and 0 when only the leader lost power, since a replica survived) — FluxMQ is more reliable than Kafka as shipped. Kafka with fsync per message lost 0 (equal durability), and FluxMQ with fsync=os ‡ loses like Kafka's default (95,606 on one node, 104,374 when all 3 nodes lose power), which is why it is not the default. Reliability.
  4. Fault tolerance (a broker dies under 5k msg/s, 3 nodes). Kill -9 of the broker leading partition 0, kept down 30 s, live producers and consumers: FluxMQ resumed acks after 5.9 s (5.4–6.4 s; detection = node_timeout) and the consumers after the same 5.9 s; Kafka after 11.4 s (8.7–14.0 s) — about 2× faster failover. 0 client errors (both clients retry internally) and 0 acked lost on both. When the node comes back FluxMQ's publishing pauses for 38 ms vs Kafka's 178 ms, and a restarted FluxMQ node is ready in 0.1–0.5 s vs 11–22 s for Kafka (20–100× faster restart). RabbitMQ was not measured here (the crash tool has no AMQP client). Fault tolerance.
  5. Overload and slow consumers. Producers unthrottled for 60 s. 100 B, 1 node: FluxMQ consumers still get 606k msg/s (37 % of 1.65M published; v0.6: 36k) — 3× Kafka default (201k), on par with Kafka-fsync (628k, which publishes less). 3 nodes, 100 B: FluxMQ 324k consumed; Kafka's 3-node 100 B overload rows are client-bound (1.5k consumed; Kafka-fsync's window stretched), so no ratio is quoted. 1 KiB: FluxMQ consumers keep up (363k on 1 node, 213k on 3 nodes) because the broker's CPU caps the producers; Kafka keeps up at 616k on 1 node (FluxMQ 0.59×) but falls behind on 3 nodes (76k of 195k: FluxMQ 2.8×). The broker stayed responsive (no errors, latency runs between scenarios unaffected); messages removed by the size cap before a slow group read them are counted and warned, never silent (0 unexplained in every run after the fix below). Overload.
  6. Catch-up (read a backlog). 100 B, 10.7M messages (1 GiB): FluxMQ 1.35M msg/s (8.0 s; 3 nodes 1.45M, 7.4 s) vs Kafka 0.61–0.69M (17.7 s; 3 nodes 0.50M, 21.5 s) — about 2× faster. 1 KiB, 1M messages: FluxMQ 477k msg/s, 2.2 s; Kafka's read rate after its first message is higher (1.9M msg/s) but its consumer-group join takes longer, so the wall time is on par (2.7 s). RabbitMQ: 44k (100 MiB backlog). Catch-up.
  7. Resources. Idle: FluxMQ 0.02 cores / 28 MiB (1 node), 78 MiB for 3 nodes; Kafka 0.06 / 436 MiB, 1.4 GiB for 3 nodes; RabbitMQ 134 / 319 MiB — FluxMQ uses 15–18× less memory at rest. Under 1 KiB 4×4 load FluxMQ uses its whole 2-CPU limit: 155k messages per broker CPU-second vs Kafka's 310k (default) and 423k (fsync) — Kafka is 2–2.7× more CPU-efficient at 1 KiB (it serves consumers with sendfile; FluxMQ copies). Load memory: FluxMQ 631 MiB vs Kafka 1.47 GiB (2.3× less). Resources.
  8. Cost of TLS (FluxMQ only). 1 node: −47 % at 1 KiB 1×1 (122k vs 231k), −46 % at 4×4, −16 % / −17 % at 100 B; p99 at 1k/10k/50k 7.3 / 19 / 8.5 ms. 3 nodes (client + node mTLS): −40 % / −47 % at 1 KiB, −7 % / −13 % at 100 B, p99 47 / 114 / 133 ms. TLS runs on the broker's 2 CPUs, which 1 KiB already saturates. Kafka and RabbitMQ were not measured with TLS. TLS.
  9. Cost of features. lz4 (1 node): consumed +7 % at 1 KiB 4×4 and +8 % at 100 B 1×1, −3 % / −8 % elsewhere; producers get much faster (1.33M vs 354k msg/s published at 1 KiB 4×4) and broker CPU drops to 1.3 cores; latency p99 2.8–3.5 ms (best of all). The bench payload compresses very well; real ratios vary. Cumulative acks: −0 to −7 % throughput and worse latency tails (p99 27–33 ms at 10k–50k) in this harness — no benefit measured; individual acks stay the default and the recommendation. Features.
  10. Scaling 1 → 3 nodes. Here three nodes add replication (RF=3, fsync on every in-sync replica), not capacity: all three share one VM and one SSD. FluxMQ loses 6 % (1 KiB 1×1) to 35 % (1 KiB 4×4) and gains at 100 B 1×1 (+46 %, the 1-node run was client-bound); Kafka default loses 51 % (1×1) and 86 % (4×4, consumers fall behind) at 1 KiB, RabbitMQ 34–72 %. FluxMQ keeps the most of its 1-node throughput. Scaling.
  11. Verdict. Better than Kafka: latency tails on one node (p99 3.5–8 ms vs 12–22 ms) with fsync before every ack; 3-node throughput at 1 KiB 4×4 (2.6×) and at 100 B with 4 consumers; consumers under overload (100 B: 3× on 1 node; 1 KiB: 2.8× on 3 nodes); one-node 100 B 4×4 saturation (3×); catch-up at 100 B (2×); memory (2.3× less); zero acked loss after power cuts where Kafka's default loses 90–119k; failover 2× faster and restarts 20–100× faster. On par: 100 B 1×1 on 3 nodes; catch-up wall time at 1 KiB; 100 B 4×4 vs Kafka-fsync on one node. Worse: one-node saturation at 1 KiB (0.44–0.55× Kafka default, 0.73–0.81× Kafka-fsync) and 100 B 1×1 (0.66× / 0.63×) — an engineering gap, not a durability trade-off, because Kafka with fsync per message is also faster: the broker copies every byte to consumers (no sendfile) and runs out of its 2 CPUs, and a single FluxMQ consumer tops out at ~430k msg/s at 100 B in the SDK. Also worse: 3-node p50 latency (a durability trade-off: fsync on every replica before the ack) and the 1 KiB 1×1 3-node rate (0.86×). Found and fixed by this benchmark before publishing: a lagging consumer group could skip stored, undelivered messages when size retention overtook it (at-least-once violation, now covered by a regression test; all FluxMQ rows here are from the fixed build).
Method and limits. One MacBook Pro (M1 Pro, 8 cores, 32 GB), Docker Desktop VM (8 CPUs, 9.7 GB), every broker container limited to 2 CPUs / 2 GiB, the client to 4 CPUs (1 node) or 2 (3 nodes); three "nodes" share one VM and one SSD, so 3-node results show replication cost, not horizontal scaling. Same harness and settings as v0.6 (window 20 000, 16 MiB segments, 512 MiB/partition retention, 30 s windows), FluxMQ in its default group commit. To fit the time budget this set uses 2 saturation repeats (v0.6: 3 on one node), catch-up and overload only on the headline systems, the lz4 / cumulative rows on one node only, and 2 crash iterations per mode. RabbitMQ's catch-up backlog is 100 MiB (not 1 GiB). Kafka runs at 100 B 4×4 where the harness container was CPU-bound and its measurement window stretched (5 of 6 at 3 nodes, 1 of 2 at 1 node) are excluded from the medians and kept in the set. How this set was measured (and what stopped it)

  • Data-loss bug found and fixed mid-run. The first FluxMQ 1-node pass (build acba45c) stopped on its own id check: in fluxmq-single-sat-1024B-1p1c-r3, 1,069,078 acknowledged messages were neither delivered nor counted as retention skips. Root cause: when a lagging group's catch-up read-ahead was continued by the next prefetch, install_fetch dropped the held read-ahead and the dispatcher skipped the gap as "a hole in the log" — stored, undelivered messages skipped silently. Fixed in 4533c6c with a property test (crates/fluxmq-core/tests/retention_overtake.rs); every skip of undelivered messages is now warned and counted. All FluxMQ rows of this set were measured again from scratch on the fixed build; the pre-fix rows are kept in investigation/v07-pre-fix-retention-skip/.
  • Harness audit cap. One lz4 run stopped because the FluxMQ audit (re-reading the log to classify misses) hit its 120 s cap before the end of a ~56M-message compressed backlog; nothing had been removed and the consumer was still draining. The cap was raised to 600 s and the lz4/cumulative rows were rerun; the aborted run is in investigation/audit-cap-120s/.
  • Disk guard. The 3-node fsync=os rows stopped once at 9.9 GB host free (the Docker VM disk grows faster than it is given back); they were rerun after freeing space (investigation/cluster-os-disk-abort/).
  • Crash matrix in two parts. The device-cleanup helper hung on a package download after the FluxMQ group-commit systems; the remaining systems (FluxMQ 3-node fsync=os, all Kafka) ran in a second invocation into the same directory (crash/env.json records the second command). The helper now uses the crash image (no download).
  • Excluded runs. Kafka at 100 B 4×4 where the harness container was CPU-bound and its measurement window stretched past 1.5× the plan (5 of 6 at 3 nodes, 1 of 2 at 1 node) are excluded from medians and kept on record. FluxMQ's 1 KiB / 100 B rows where producers outran consumers are reported as measured ("not drained": every miss was either still stored or a counted retention skip — 0 unexplained).
  • Reductions to fit the time budget: 2 saturation repeats (v0.6: 3 on one node), catch-up and overload only on the headline systems (FluxMQ, Kafka ± fsync, RabbitMQ), lz4 / cumulative rows on one node only, 2 crash iterations per mode and target, RabbitMQ catch-up backlog 100 MiB, failover 2 runs per system, pipeline A/B 2 repeats in one order.
  • After quick fixes. One small fix found by profiling (raw-run compaction deferred to the end of an ack batch) was measured afterwards in after-quick-fixes/; the headline tables stay on the matrix build.
  • Commit pipeline A/B (investigation/pipeline-ab/, 1 KiB 4×4, 2 repeats; 10k msg/s latency, one run): pipeline on published +22 % (440k vs 368k) but consumed −11 % (268k vs 303k), p99 22 vs 14 ms. Recommendation: keep FLUXMQ_COMMIT_PIPELINE off.

Method: what each crash simulates, and its limits

kill9: SIGKILL of the broker's whole process group inside its container (crashctl kill9). The kernel and its page cache survive: everything the broker had written with write(2) is still there after the restart, fsynced or not. Simulates a broker process crash (OOM kill, panic, kill -9), not a machine crash.

powercut: Simulated power loss of the broker's machine (crashctl powercut). The data directory is an ext4 filesystem on a device-mapper device over a loop device backed by a sparse file in a Docker volume. At the cut the dm device is suspended without flushing and switched to the dm `error` target, then the broker gets SIGKILL (before the device resumes, so it never sees the I/O errors). The filesystem is unmounted: dirty pages (written but not yet written back or fsynced) fail against the error target and the device's cache is dropped. Then the linear mapping is restored and ext4 is mounted again (journal replay), exactly the bytes that had reached the device at the cut. Only data that was fsynced (or written back by the kernel's periodic writeback before the cut) survives. A per-crash canary proves it: a file created just before the cut must be gone, a file synced before the workload must be there.

Canary. Before each crash the tool writes a file that is never fsynced and checks after the restart: after kill9 it must survive (page cache intact), after powercut it must be gone while a file synced before the workload must be there. A run whose canary disagrees is marked invalid.

Limits. The device below the cut is trusted (the Docker VM does not crash); kernel writeback that happened before the cut survives, which favours page-cache systems (Kafka defaults, FluxMQ fsync=os), never fsync-before-ack systems; torn sectors inside one write are not emulated (covered by the storage engine's torn-tail tests); one laptop, one SSD, three "nodes" on one VM; recovery time is until the readiness probe passes (Kafka's probe starts a JVM, adding seconds). Full description: bench/crash/README.md.

Improvements: where FluxMQ loses, why, and what to do

Evidence: perf record -g --call-graph dwarf (499 Hz, 12 s inside the measured window) on the broker and the harness containers, built with symbols (fluxmq:prof, same source as the matrix), plus broker/client CPU from docker stats for every run. Profiles and reports: investigation/profile/ (runs) and the scratch reports quoted below. Shares are of the sampled process's CPU. None of the proposals weakens durability: fsync before ack, per-message acks, redelivery and DLQ stay as they are.

  1. Zero-copy outbound frames (vectored writes). Gap: one node, 1 KiB saturation, 0.44× / 0.55× Kafka default and 0.73–0.81× Kafka-fsync; the broker is CPU-bound (2.0 of 2 cores; 155k msg per CPU-second vs Kafka 310k / 423k). Root cause: 16.9 % of broker CPU is memcpy inside postcard::Serializer::serialize_field::<Bytes> ← FrameCodec::encode ← net::connection::feed / write_loop (crates/fluxmq-server/src/net/codec.rs, connection.rs): every raw DeliverRecords envelope is copied into the write buffer, plus 3.1 % BytesMut::reserve_inner (buffer growth copies). Kernel copy_to_user 12 % / copy_from_user 10 % (pread, writev) come on top. Kafka serves consumers with sendfile. Fix: encode only the frame header with postcard and hand the envelope Bytes to the socket as separate IoSlices (write_vectored), reserving the header buffer once; later, sendfile/splice for plaintext reads that come from disk. Expected gain: −15 to −20 % broker CPU per message at 1 KiB, i.e. +15–25 % consumed at 1 KiB on one node (more with TLS, where the same copies run before encryption). Risk: none for durability; wire format unchanged.
  2. Raw-run compaction in the middle of an ack batch (quick fix done, see "After quick fixes"). Gap: same rows, and 100 B 1×1. Root cause: GroupState::ack_at (crates/fluxmq-core/src/group.rs) compacts a raw in-flight run as soon as 7/8 of it is acked, calling Run::materialize, which decodes and CRC-checks the whole envelope chunk to keep the last 1/8 — which the same AckRanges settles a moment later. Profile: crc32c ← ChunkRecords::next ← Run::materialize ← ack_at ← Group::ack_ranges = 10 % of broker CPU at 1 KiB 4×4 and ~23 % (materialize + record iteration + varints + CRC) at 100 B 1×1. Fix (≤ 40 lines, done): collect candidates during the batch and compact only runs still mostly settled after it. Measured gain: +49 % consumed at 1 KiB 4×4 on one node (320k → 476k; consumers now keep up), +20 % at 1 KiB 1×1, +28 % at 100 B 1×1, +43 % / +10 % at 1 KiB on 3 nodes; 100 B 4×4 within noise (+2 % / −5 %); latency unchanged. Risk: none (memory-only optimization; the straggler compaction test still passes).
  3. Per-message attempt history on first deliveries. Gap: 100 B 1×1 (0.66× Kafka default) and part of the 1 KiB gap. Root cause: AttemptHistory::on_deliveries 10.3 % of broker CPU at 100 B 1×1 (2.4 % at 1 KiB), on_finishes 1.2 % (crates/fluxmq-core/src/history.rs): the retry timeline records every first delivery and its finish. Fix: record history only for messages that are redelivered, nacked or dead-lettered (first attempts are implied by the offset and the run's delivery time), or sample it. Expected gain: up to +10 % at 100 B. Risk: none for durability; changes what the retry-timeline UI shows for messages delivered once — product decision.
  4. Inbound copy of PublishBatch bodies. 3.5 % Bytes::copy_from_slice in ClientFrame::decode_frame (net/codec.rs): the batch body is copied out of the read buffer. Fix: BytesMut::split_to(n).freeze() for the body (zero-copy). Expected: −3 % broker CPU at 1 KiB. Risk: none (buffer lifetime only).
  5. SDK consumer cost per message. Gap: 100 B 1×1, where a single consumer task is the limit (broker at 0.55 cores). Harness profile: Delivery::ack future per message 2 %, malloc/free 5.4 %, Records::next 1.2 %, plus harness work common to all systems (a clock read per message, 17 %; the consumer closure, 9 %). Fix: an SDK batch-ack helper (ack a Vec<Delivery> / a whole frame in one call) and fewer per-Delivery allocations (shared header maps, no per-message Arc clone where avoidable). Expected: +15–25 % for one consumer at 100 B. Risk: none.
  6. TLS cost at 1 KiB (−46 to −47 % on one node, −40 to −47 % on 3 nodes). Same CPU budget as item 1: the copies and the encryption share the 2 broker CPUs that 1 KiB already saturates. Item 1 helps directly; kTLS would remove the user-space encryption copy (out of scope). Not separately profiled in this run.
  7. 3-node latency at 50k msg/s (p99 131 ms; v0.6 61 ms; p50 14 ms vs Kafka default 2.7 ms). Durability trade-off in part (fsync on every in-sync replica before the ack, three replicas sharing one SSD), but the p99 regression vs v0.6 is not explained yet: not profiled in this run (time budget). Next step: profile the leader and a follower at 50k msg/s (fetch long-poll wake-ups, group-commit interval, the overlapped follower fsync).
  8. Paced retention cannot keep up at saturation. The background pass removes at most 16 segments per second per channel (RETENTION_MAX_SEGMENTS_PER_TICK, broker.rs). Natively, at ~830 MB/s ingest with 4 MiB segments it removed ~64 MB/s, so the log overshoots its size cap without bound while producers saturate; in Docker (16 MiB segments, ~500 MB/s) it keeps up only barely. Fix: scale the per-tick budget with the overshoot (bytes over the cap / segment size), keeping the stepwise shrink. Risk: none for acked data (retention only removes what the cap allows; skips stay counted).
  9. Producers outrun consumers on one node. Under saturation FluxMQ publishes 1.7–2× what its consumers receive (Kafka publishes and consumes the same), so a closed-loop run turns into a growing backlog and, with a size cap, retention skips. The product rule says producers are never throttled by consumers; an opt-in per-channel "consumer-paced" admission (bounded lag) would make the default behaviour explicit for users who prefer it. Product decision.
  10. Harness. The Kafka 3-node 100 B 4×4 rows were client-bound (2 client CPUs saturated by librdkafka; the measurement window stretched); give the client 4 CPUs on 3-node runs next time. The FluxMQ audit cap was raised to 600 s during this run (a compressed backlog holds tens of millions of messages).

Methodology

One harness for every system. bench/harness (mq-harness, Rust) drives FluxMQ through its SDK, Kafka through librdkafka (rdkafka crate, built from source) and RabbitMQ through lapin (AMQP 0-9-1), with one engine: the same producer loop, the same consumer accounting and the same HDR histograms. The first 8 bytes of every payload carry the send time on the harness's monotonic clock; producers and consumers run in one process, so end-to-end latency has no clock skew. The official perf tools (kafka-producer-perf-test, RabbitMQ perf-test) were not used for the comparison because they measure latency differently (Kafka's tool reports produce latency only, perf-test uses its own timestamping and a JVM client), which would mix tool differences into broker differences.

  • Topology per run: a fresh topic / channel / set of queues with 8 partitions (RabbitMQ: 8 queues used like partitions, producers round-robin over them, each consumer owns a share). Deleted after the run; retention capped at 512 MiB per partition / queue to bound disk use. Segment size 16 MiB for FluxMQ (broker FLUXMQ_SEGMENT_BYTES) and Kafka (topic segment.bytes); RabbitMQ has no equivalent setting.
  • Producers: one connection each, messages sent one by one through the library's async API with at most 20000 unacknowledged per producer (FluxMQ: up to 32 Publish requests pipelined per producer). FluxMQ producers run with stamp_producer=false: no flux-producer header per message, like the Kafka and RabbitMQ clients, which send no header either. Client-side batching is the library's own: FluxMQ BatchingProducer and Kafka linger.ms both linger 5 ms in saturation and 1 ms in the latency runs; AMQP has no producer batching (frames are pipelined, confirms are asynchronous).
  • Consumers: one connection each, one group (Kafka group / FluxMQ consumer group / queue share), starting at the beginning of the fresh topic; every message is acknowledged (FluxMQ ack, AMQP basic.ack; Kafka commits offsets automatically every 5 s, its normal mode).
  • Saturation: closed loop, 10 s warm-up discarded, 30 s measured, then up to 15 s for consumers to receive everything sent in the window ("drained"). Checked by message id (producer + sequence number in the payload): every message the broker acknowledged must arrive at least once. On a miss the harness keeps waiting 45 s more and reports each missed message as late or missing.
  • Fixed-rate latency: open loop, sends scheduled evenly across producers; latency from the scheduled send time (30 s measured). Not sustained = publish or consume below 95 % of the target, or not drained.
  • Idle footprint: broker containers after start-up settle, no clients; under load: the same docker stats samples during the saturation window.
  • Fairness: every broker container has the same CPU and memory limit; clients run in their own container with their own limit on the same Docker network. Each system's stack is created fresh (empty volumes) and destroyed after its runs, so systems never run at the same time.
  • Repeats: every saturation configuration ran several times, interleaved (repeat 1 of every configuration, then repeat 2, …) so slow drift spreads evenly; the report shows the median and the min–max range.
  • Client resources: the single-node systems were driven by a 4-CPU client container, the 3-node systems by a 2-CPU one (3 × 2 broker CPUs + 2 = the VM's 8); every system within one comparison had the same client.
  • Batched delivery (FluxMQ only): fluxmq-bench of the v0.4 baseline image and of the current image, each against its own single broker, plus the current bench's drain mode against both brokers; rounds interleaved, a fresh broker per round.

Reproduce: bench/run.sh (everything) or e.g. bench/run.sh --systems fluxmq,kafka --scenarios saturation; raw JSON per run plus stats.jsonl and env.json are in the results directory.

Durability settings per system

What "acknowledged" means differs per system; that difference is part of the result.

  • FluxMQ: --fsync group-commit (default): a publish is acked after its batch is fsynced (commit window 2 ms). In the cluster: RF=3, --min-isr 2, acked once every ISR member has the batch (acks=all); followers also group-commit.
  • Kafka: producer acks=all, enable.idempotence=true. Brokers keep the default flush policy: no fsync per message; data reaches disk via the page cache, durability comes from replication. Cluster: RF=3, min.insync.replicas=2.
  • RabbitMQ 1 node: durable classic queues, persistent messages, publisher confirms (sent once the message is persisted, fsync batched). 3 nodes: quorum queues (Raft, 3 members), confirm after a majority has the entry fsynced to its write-ahead log.

Caveats

  • macOS Docker VM. All containers share one Linux VM (Docker Desktop, Apple Virtualization) on one laptop. Disk I/O goes through the VM's virtual disk; fsync cost there is neither macOS F_FULLFSYNC nor a server NVMe's. Networking is the VM's bridge, not a real network: no RTT, no bandwidth limit.
  • Single laptop, noisy neighbours. Brokers, clients and the host OS (and anything else running on the laptop, including builds) compete for the same cores, memory bandwidth and SSD. Thermal state matters. Each saturation configuration ran 2× (interleaved); bars show the median, whiskers the range. Latency, idle and resource figures come from one run each (resources: the median saturation repeat).
  • Not a production cluster. "3 nodes" are 3 containers on one VM and one disk: replication costs CPU and disk bandwidth that real separate machines would not share, and a node failure is not independent.
  • Client limits. One client container with a CPU limit drives every system (4 CPUs for the single-node systems, 2 for the 3-node systems so brokers + client fit the VM's 8 CPUs; the same within each comparison); check "Client CPU" in the resource table before attributing a ceiling to a broker.
  • Defaults, not tuned. Each broker runs close to its defaults (Kafka heap 1 GiB, RabbitMQ defaults, FluxMQ defaults) and each client library with mostly default settings. Expert tuning would change every number.
  • Different durability semantics (see the table above): faster acknowledgement can mean weaker guarantees.
  • Short runs. 30 s windows do not show segment rolling, retention, compaction, GC pauses over hours, or long-run steady state. TLS was measured for FluxMQ only, not for Kafka or RabbitMQ.

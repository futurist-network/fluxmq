Methodology

One harness for every system. bench/harness (mq-harness, Rust) drives FluxMQ through its SDK, Kafka through librdkafka (rdkafka crate, built from source) and RabbitMQ through lapin (AMQP 0-9-1), with one engine: the same producer loop, the same consumer accounting and the same HDR histograms. The first 8 bytes of every payload carry the send time on the harness's monotonic clock; producers and consumers run in one process, so end-to-end latency has no clock skew. The official perf tools (kafka-producer-perf-test, RabbitMQ perf-test) were not used for the comparison because they measure latency differently (Kafka's tool reports produce latency only, perf-test uses its own timestamping and a JVM client), which would mix tool differences into broker differences.

  • Topology per run: a fresh topic / channel / set of queues with 8 partitions (RabbitMQ: 8 queues used like partitions, producers round-robin over them, each consumer owns a share). Deleted after the run; retention capped at 128 MiB per partition / queue to bound disk use.
  • Producers: one connection each, messages sent one by one through the library's async API with at most 2000 unacknowledged per producer. Client-side batching is the library's own: FluxMQ BatchingProducer and Kafka linger.ms both linger 5 ms in saturation and 1 ms in the latency runs; AMQP has no producer batching (frames are pipelined, confirms are asynchronous).
  • Consumers: one connection each, one group (Kafka group / FluxMQ consumer group / queue share), starting at the beginning of the fresh topic; every message is acknowledged (FluxMQ ack, AMQP basic.ack; Kafka commits offsets automatically every 5 s, its normal mode).
  • Saturation: closed loop, 10 s warm-up discarded, 30 s measured, then up to 15 s for consumers to receive everything sent in the window ("drained").
  • Fixed-rate latency: open loop, sends scheduled evenly across producers; latency from the scheduled send time (30 s measured). Not sustained = publish or consume below 95 % of the target, or not drained.
  • Idle footprint: broker containers after start-up settle, no clients; under load: the same docker stats samples during the saturation window.
  • Fairness: every broker container has the same CPU and memory limit; clients run in their own container with their own limit on the same Docker network. Each system's stack is created fresh (empty volumes) and destroyed after its runs, so systems never run at the same time.
  • Repeats: every saturation configuration ran several times, interleaved (repeat 1 of every configuration, then repeat 2, …) so slow drift spreads evenly; the report shows the median and the min–max range.
  • Client resources: the single-node systems were driven by a 4-CPU client container, the 3-node systems by a 2-CPU one (3 × 2 broker CPUs + 2 = the VM's 8); every system within one comparison had the same client.
  • Batched delivery (FluxMQ only): fluxmq-bench of the v0.4 baseline image and of the current image, each against its own single broker, plus the current bench's drain mode against both brokers; rounds interleaved, a fresh broker per round.

Reproduce: bench/run.sh (everything) or e.g. bench/run.sh --systems fluxmq,kafka --scenarios saturation; raw JSON per run plus stats.jsonl and env.json are in the results directory.

Durability settings per system

What "acknowledged" means differs per system; that difference is part of the result.

  • FluxMQ: --fsync group-commit (default): a publish is acked after its batch is fsynced (commit window 2 ms). In the cluster: RF=3, --min-isr 2, acked once every ISR member has the batch (acks=all); followers also group-commit.
  • Kafka: producer acks=all, enable.idempotence=true. Brokers keep the default flush policy: no fsync per message; data reaches disk via the page cache, durability comes from replication. Cluster: RF=3, min.insync.replicas=2.
  • RabbitMQ 1 node: durable classic queues, persistent messages, publisher confirms (sent once the message is persisted, fsync batched). 3 nodes: quorum queues (Raft, 3 members), confirm after a majority has the entry fsynced to its write-ahead log.

Caveats

  • macOS Docker VM. All containers share one Linux VM (Docker Desktop, Apple Virtualization) on one laptop. Disk I/O goes through the VM's virtual disk; fsync cost there is neither macOS F_FULLFSYNC nor a server NVMe's. Networking is the VM's bridge, not a real network: no RTT, no bandwidth limit.
  • Single laptop, noisy neighbours. Brokers, clients and the host OS (and anything else running on the laptop, including builds) compete for the same cores, memory bandwidth and SSD. Thermal state matters. Each saturation configuration ran 3× (interleaved); bars show the median, whiskers the range. Latency, idle and resource figures come from one run each (resources: the median saturation repeat).
  • Not a production cluster. "3 nodes" are 3 containers on one VM and one disk: replication costs CPU and disk bandwidth that real separate machines would not share, and a node failure is not independent.
  • Client limits. One client container with a CPU limit drives every system (4 CPUs for the single-node systems, 2 for the 3-node systems so brokers + client fit the VM's 8 CPUs; the same within each comparison); check "Client CPU" in the resource table before attributing a ceiling to a broker.
  • Defaults, not tuned. Each broker runs close to its defaults (Kafka heap 1 GiB, RabbitMQ defaults, FluxMQ defaults) and each client library with mostly default settings. Expert tuning would change every number.
  • Different durability semantics (see the table above): faster acknowledgement can mean weaker guarantees.
  • Short runs. 30 s windows do not show segment rolling, retention, compaction, GC pauses over hours, or long-run steady state. TLS was measured for FluxMQ only, not for Kafka or RabbitMQ.

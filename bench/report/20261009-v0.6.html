Conclusions

  • FluxMQ v0.6 roughly doubles v0.5's throughput: +71 to +155 % at 1 KiB on 1 and 3 nodes, still with an fsync before every ack. Broker efficiency at 1 KiB 4×4 went from about 100k to about 180k messages per broker CPU-second. This gain mixes three things: the broker work, the SDK work, and the fairer harness (window 2000 → 20000, no producer header). A broker-only check, the same v0.5 harness against both broker images at window 2000, gave 134k → 162k msg/s (+21 %, one run each). The rest of the gain comes from the client side.
  • Kafka is still faster at saturation on one node: 1.7–2.1× at 1 KiB and 1.7× at 100 B 1×1. Kafka acks from the page cache. Even FluxMQ with fsync=os (the same durability point as Kafka) reached 291k / 537k at 1×1, against Kafka's 534k / 696k. The 3-node gap could not be measured in v0.6.
  • Low-rate latency is now on par with or better than Kafka while keeping fsync-before-ack: p50 1.96 ms at 1k msg/s (Kafka 3.1, RabbitMQ 1.7) and p99 6.4 ms at 10k msg/s (Kafka 6.4).
  • Weakness: consumers starve under producer overload at 100 B 4×4. The window no longer throttles the producers, so 4 FluxMQ producers publish about 1.4–1.5M msg/s. On 1 node the consumers then manage only 29–43k msg/s; on 3 nodes, 11–14k. Most of the backlog stays stored, and the rest is removed by the 512 MiB/partition retention cap. Kafka shows the same pattern but degrades far less (374k consumed against 1.31M published). FluxMQ needs fair scheduling between publish and fetch, or producer backpressure, before it holds up under overload. This is open work.
  • The 50k msg/s tail is much smaller, but the target is not reliably met. The retention stall is gone (A/B below: v0.5 p99 572 / 1208 ms against v0.6 12.6–64 ms with the same 128 MiB/partition cap). Without any retention, though, single runs still show 0.1–0.3 s tails at random moments: 155 ms in the headline run, 10.2 ms in an earlier identical run.
  • No data loss. Every FluxMQ run passed the id-level check, with 0 true missing messages. Every id that did not arrive was either still stored (the audit found it in the log) or provably removed by size retention. For the latter, the audit did not find it, and the broker's v0.6 "retention removed messages a consumer group had not consumed" counter covers at least that many messages. The tables report such ids as "dropped by retention (backlog > cap)", separately from "missing". Kafka's 100 B 4×4 gaps are classified the same way, inferred from consumer lag against the cap (Kafka has no audit). The cap could not be raised enough for Kafka at 100 B: holding its backlog would need more than 6 GB per broker, above the 5 GB volume guard.
  • SDK bug found and fixed (also present in v0.5). PublishFuture wrapped a tokio oneshot, which spends the awaiting task's coop budget. With about 20k sends outstanding in one FuturesUnordered, as in the harness at window 20000, completed sends kept coming back Pending, and the cost per message grew with the window. Measured at 1 KiB 1×1, FluxMQ throughput by window: 2000 → 215k msg/s, 3000 → 215k, 5000 → 191k, 10000 → 105k, 20000 → 50k. The v0.5 SDK did the same (42k at window 20000). The fix uses futures::channel::oneshot, with a regression test. After the fix: 389k msg/s published at window 20000. The rows measured with the buggy SDK are kept in investigation/sdk-coop-bug-window20000/ and are not used here.
  • TLS costs 21–31 % at saturation on 1 node and 2 % on 3 nodes at 1×1. It costs 56 % at 3 nodes, 1 KiB 4×4 (307k → 134k), where the TLS consumers fell behind and retention dropped part of the backlog. TLS latency p99 was noisy in this set (cluster TLS: 106 ms at 1k msg/s, a single run).

With 8 partitions v0.6 needs about 45 % less broker CPU at the same rate. Not measured

  • Commit pipeline on vs off (FLUXMQ_COMMIT_PIPELINE): not run, because the set was stopped first. The runner has the fluxmq-single-pipeline system for it (bench/run.sh --systems fluxmq-single,fluxmq-single-pipeline). No basis to change the default: it stays off.
  • The v0.5 broker under the v0.6 harness (with the fixed SDK), and repeated 50k msg/s runs to bound the remaining tail.

Method changes since v0.5, and anomalies

  • Window 20000 (was 2000), FluxMQ max_in_flight 32, 16 MiB segments for FluxMQ and Kafka, retention 512 MiB per partition/queue (was 128), FluxMQ stamp_producer=false.
  • Late drain 35 s and idle settle 15 s for the FluxMQ reruns and the 3-node phase, to save time (Kafka/RabbitMQ 1 node: 45 s and 30 s). The 3-node FluxMQ idle memory (336 MiB) was probably measured before start-up had settled.
  • Kafka/RabbitMQ 1 node were measured with the harness image from before the SDK fix. Their client paths do not use the FluxMQ SDK.
  • Runner hardening added during this set: the drain-miss classification; the audit now holds missing ids as per-producer bitsets (an OOM at 12M missing ids left a 4.4 GB channel behind); orphaned bench channels/topics are deleted after a failed run; a FluxMQ run with true missing messages stops the matrix.
  • Single-node FluxMQ saturation with a large window has wide ranges, because the producers outrun the consumers in some repeats (marked "not drained"). The bars show medians with min–max whiskers.

Computed verdicts

  • Throughput, single, 1024 B 1×1: FluxMQ is in the middle (255.8k/s vs Kafka · 1 node 534.4k/s, RabbitMQ · 1 node classic 11.2k/s).
  • Throughput, single, 1024 B 4×4: FluxMQ is in the middle (355.2k/s vs Kafka · 1 node 587.2k/s, RabbitMQ · 1 node classic 10.6k/s).
  • Throughput, single, 100 B 1×1: FluxMQ is in the middle (403.9k/s vs Kafka · 1 node 695.6k/s, RabbitMQ · 1 node classic 11.2k/s).
  • Throughput, single, 100 B 4×4: FluxMQ is in the middle (35.9k/s vs Kafka · 1 node 374.1k/s, RabbitMQ · 1 node classic 29.5k/s).
  • p99 at 1,000/s, single: FluxMQ 4.18 ms is the middle (vs RabbitMQ · 1 node classic 3.49 ms, Kafka · 1 node 6.56 ms).
  • p99 at 10,000/s, single: FluxMQ 6.43 ms is the middle (vs Kafka · 1 node 6.38 ms, RabbitMQ · 1 node classic 40.7 ms).
  • p99 at 50,000/s, single: FluxMQ 155 ms is the highest (vs Kafka · 1 node 9.01 ms).
  • 50,000/s, single: not sustained or skipped by RabbitMQ · 1 node classic.
  • These verdicts are computed from this run's data (median of 3 runs per saturation configuration, one run per latency rate) on one laptop. Read them together with the durability table: the systems do not pay the same durability cost per acknowledged message (FluxMQ and RabbitMQ fsync before confirming; Kafka relies on replication and the page cache by default).

Methodology

One harness for every system. bench/harness (mq-harness, Rust) drives FluxMQ through its SDK, Kafka through librdkafka (rdkafka crate, built from source) and RabbitMQ through lapin (AMQP 0-9-1), with one engine: the same producer loop, the same consumer accounting and the same HDR histograms. The first 8 bytes of every payload carry the send time on the harness's monotonic clock; producers and consumers run in one process, so end-to-end latency has no clock skew. The official perf tools (kafka-producer-perf-test, RabbitMQ perf-test) were not used for the comparison because they measure latency differently (Kafka's tool reports produce latency only, perf-test uses its own timestamping and a JVM client), which would mix tool differences into broker differences.

  • Topology per run: a fresh topic / channel / set of queues with 8 partitions (RabbitMQ: 8 queues used like partitions, producers round-robin over them, each consumer owns a share). Deleted after the run; retention capped at 512 MiB per partition / queue to bound disk use. Segment size 16 MiB for FluxMQ (broker FLUXMQ_SEGMENT_BYTES) and Kafka (topic segment.bytes); RabbitMQ has no equivalent setting.
  • Producers: one connection each, messages sent one by one through the library's async API with at most 20000 unacknowledged per producer (FluxMQ: up to 32 Publish requests pipelined per producer). FluxMQ producers run with stamp_producer=false: no flux-producer header per message, like the Kafka and RabbitMQ clients, which send no header either. Client-side batching is the library's own: FluxMQ BatchingProducer and Kafka linger.ms both linger 5 ms in saturation and 1 ms in the latency runs; AMQP has no producer batching (frames are pipelined, confirms are asynchronous).
  • Consumers: one connection each, one group (Kafka group / FluxMQ consumer group / queue share), starting at the beginning of the fresh topic; every message is acknowledged (FluxMQ ack, AMQP basic.ack; Kafka commits offsets automatically every 5 s, its normal mode).
  • Saturation: closed loop, 10 s warm-up discarded, 30 s measured, then up to 15 s for consumers to receive everything sent in the window ("drained"). Checked by message id (producer + sequence number in the payload): every message the broker acknowledged must arrive at least once. On a miss the harness keeps waiting 35 s more and reports each missed message as late or missing.
  • Fixed-rate latency: open loop, sends scheduled evenly across producers; latency from the scheduled send time (30 s measured). Not sustained = publish or consume below 95 % of the target, or not drained.
  • Idle footprint: broker containers after start-up settle, no clients; under load: the same docker stats samples during the saturation window.
  • Fairness: every broker container has the same CPU and memory limit; clients run in their own container with their own limit on the same Docker network. Each system's stack is created fresh (empty volumes) and destroyed after its runs, so systems never run at the same time.
  • Repeats: every saturation configuration ran several times, interleaved (repeat 1 of every configuration, then repeat 2, …) so slow drift spreads evenly; the report shows the median and the min–max range. 1-node saturation = median of 3 repeats; 3-node saturation = median of 2 repeats.
  • Client resources: the single-node systems were driven by a 4-CPU client container, the 3-node systems by a 2-CPU one (3 × 2 broker CPUs + 2 = the VM's 8); every system within one comparison had the same client.
  • Batched delivery (FluxMQ only): fluxmq-bench of the v0.4 baseline image and of the current image, each against its own single broker, plus the current bench's drain mode against both brokers; rounds interleaved, a fresh broker per round.

Reproduce: bench/run.sh (everything) or e.g. bench/run.sh --systems fluxmq,kafka --scenarios saturation; raw JSON per run plus stats.jsonl and env.json are in the results directory.

Durability settings per system

What "acknowledged" means differs per system; that difference is part of the result.

  • FluxMQ: --fsync group-commit (default): a publish is acked after its batch is fsynced (commit window 2 ms). In the cluster: RF=3, --min-isr 2, acked once every ISR member has the batch (acks=all); followers also group-commit.
  • Kafka: producer acks=all, enable.idempotence=true. Brokers keep the default flush policy: no fsync per message; data reaches disk via the page cache, durability comes from replication. Cluster: RF=3, min.insync.replicas=2.
  • RabbitMQ 1 node: durable classic queues, persistent messages, publisher confirms (sent once the message is persisted, fsync batched). 3 nodes: quorum queues (Raft, 3 members), confirm after a majority has the entry fsynced to its write-ahead log.

Caveats

  • macOS Docker VM. All containers share one Linux VM (Docker Desktop, Apple Virtualization) on one laptop. Disk I/O goes through the VM's virtual disk; fsync cost there is neither macOS F_FULLFSYNC nor a server NVMe's. Networking is the VM's bridge, not a real network: no RTT, no bandwidth limit.
  • Single laptop, noisy neighbours. Brokers, clients and the host OS (and anything else running on the laptop, including builds) compete for the same cores, memory bandwidth and SSD. Thermal state matters. Each saturation configuration ran 3× (interleaved); bars show the median, whiskers the range. Latency, idle and resource figures come from one run each (resources: the median saturation repeat).
  • Not a production cluster. "3 nodes" are 3 containers on one VM and one disk: replication costs CPU and disk bandwidth that real separate machines would not share, and a node failure is not independent.
  • Client limits. One client container with a CPU limit drives every system (4 CPUs for the single-node systems, 2 for the 3-node systems so brokers + client fit the VM's 8 CPUs; the same within each comparison); check "Client CPU" in the resource table before attributing a ceiling to a broker.
  • Defaults, not tuned. Each broker runs close to its defaults (Kafka heap 1 GiB, RabbitMQ defaults, FluxMQ defaults) and each client library with mostly default settings. Expert tuning would change every number.
  • Different durability semantics (see the table above): faster acknowledgement can mean weaker guarantees.
  • Short runs. 30 s windows do not show segment rolling, retention, compaction, GC pauses over hours, or long-run steady state. TLS was measured for FluxMQ only, not for Kafka or RabbitMQ.

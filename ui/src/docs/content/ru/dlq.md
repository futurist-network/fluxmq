Сюда попадают сообщения, которые исчерпали все попытки доставки (nack или тайм-аут подтверждения `max attempts` раз), и те, которые получатель отклонил с `retry = false`. Каждое хранится вместе с **последней причиной** ошибки, поэтому экран устроен как почтовый ящик: сначала причина, потом сообщения.

## Причины {#reasons}

Вверху — карточки причин: текст причины (`PostgreSQL timeout`, `HTTP 503`, `Invalid schema`, `route target unavailable: …`), сколько сообщений с ней и когда было последнее. «Все причины» показывает всё сразу. Число в боковом меню у «Недоставленных» — сколько всего сообщений в DLQ.

> [!TIP]
> Пишите в `nack` короткие и **стабильные** причины: «PostgreSQL timeout», а не текст исключения с id запроса. Тогда одинаковые ошибки соберутся в одну карточку и их можно будет повторить одной кнопкой.

## Список сообщений {#entries}

| Колонка | Что значит |
|---|---|
| Сообщение | тип (`flux-type`) и id записи DLQ |
| Канал | ссылка на канал |
| Группа | какая группа получателей не справилась; `router` — неудачные пересылки маршрутов (`$router`), `$webhook:<имя>` — вебхук |
| Причина | показывается, если выбраны «Все причины» |
| Ключ | ключ сообщения |
| Попытки | сколько раз доставлялось |
| В DLQ | когда попало в очередь |

Клик по строке открывает панель: причина, содержимое, заголовки и история доставки, кнопки **Повторить** и **Удалить** для одного сообщения.

## Действия {#actions}

| Кнопка | Что делает | Роль |
|---|---|---|
| Повторить все (N) | вернуть все сообщения выбранной причины (или все) исходной группе с новым запасом попыток | оператор |
| Повторить выбранные | то же для отмеченных галочками | оператор |
| Удалить все / Удалить выбранные | удалить безвозвратно (с подтверждением; пишется в журнал аудита) | оператор |
| Экспорт NDJSON | скачать сообщения в формате NDJSON (по строке JSON на сообщение) | оператор |

Повторённое сообщение возвращается **той же группе**, которая с ним не справилась, — другие группы канала его повторно не получат.

> [!WARNING]
> Сначала устраните причину (поднимите базу, исправьте схему, верните удалённый канал-цель), потом нажимайте «Повторить все». Иначе сообщения пройдут все попытки заново и вернутся сюда.

## Через REST {#rest}

```bash
H=http://localhost:7421
curl -s $H/api/dlq/summary                                   # сводка по причинам
curl -s "$H/api/dlq?reason=PostgreSQL%20timeout&limit=50"     # сообщения
curl -s -X POST $H/api/dlq/retry -H 'content-type: application/json' \
  -d '{"reason":"PostgreSQL timeout"}'                        # повторить причину
curl -s "$H/api/dlq/export?channel=orders" > dlq.ndjson       # выгрузка (роль оператора)
```

## Что нормально {#normal}

Пустая DLQ — норма. Единичные сообщения с «плохими данными» (`Invalid schema`) — повод исправить отправителя и удалить их. Растущая DLQ открывает оповещение «Рост DLQ» и красит карточку «Ошибки» на [Обзоре](/docs/dashboard). Пошагово — [Разобрать DLQ](/docs/howto-handle-dlq).

Оповещения брокер открывает сам — настраивать нужно только **куда** их слать. Нужна роль администратора.

## Telegram за пару минут {#telegram}

1. **Создайте бота.** В Telegram откройте @BotFather, отправьте `/newbot`, задайте имя и username (оканчивается на `bot`). Он пришлёт токен вида `7123456789:AAH…` — храните его как пароль.
2. **Добавьте бота в чат.** Личный чат — напишите боту `/start`. Группа — добавьте бота и отправьте `/start@имя_бота`. Канал — сделайте бота администратором с правом публикации и опубликуйте пост.
3. **Узнайте ID чата:**

   ```bash
   curl -s "https://api.telegram.org/bot<ТОКЕН>/getUpdates"
   ```

   В ответе найдите `"chat":{"id":…}`: у личного чата — положительное число, у групп — отрицательное, у супергрупп и каналов — вида `-1001234567890`. Для группы с темами номер темы — `message_thread_id`. Пустой `result` — отправьте в чат ещё сообщение и повторите.
4. **Добавьте канал уведомлений**: Настройки → Уведомления → **Подключить Telegram** (или «Добавить канал» → Telegram) → токен бота, ID чата, при необходимости ID темы → **Отправить тест**. Сообщение должно прийти в чат.
5. **Создайте правило**: **Новое правило** → имя «Критичное — дежурным», отправлять в этот канал, минимальная важность «Критично», группировка 30 с, повтор раз в 4 часа, сообщение о восстановлении — включено.

Типичные ошибки теста: `HTTP 401` (неверный токен бота), `HTTP 400 … chat not found` (неверный ID чата или бот не добавлен), `HTTP 403 … bot was blocked by the user`.

Так выглядит сообщение:

```text
🔴 CRITICAL · Email queue is growing rapidly
Lag increased from 1.2k → 18k in 6 min
Possible reason: Consumers processing slower than producers.
Channel: email · Group: workers · Open for: 6m
Open in console
```

Ссылка «Open in console» появляется, если брокер запущен с `--public-url`.

## PagerDuty {#pagerduty}

В сервисе PagerDuty: Integrations → Add integration → **Events API V2**, скопируйте Integration Key. В FluxMQ добавьте канал уведомлений PagerDuty с этим ключом. Открытое оповещение создаёт инцидент, закрытое — закрывает его; ключ дедупликации — id оповещения, поэтому напоминания не плодят инциденты. Тестовая отправка создаёт и сразу закрывает инцидент уровня `info`.

## Свой HTTP-адрес {#webhook}

Тип **Webhook**: URL, необязательный секрет подписи и заголовки. Брокер отправляет JSON:

```json
{
  "id": "gfznwqk01b",
  "cluster": "local",
  "sent_at_ms": 1791447236768,
  "rule": "Удаление каналов",
  "status": "event",
  "alerts": [],
  "events": [{"id": 4, "ts": 1791447231765, "kind": "channel_deleted", "title": "Channel deleted",
              "subject": "orders.tmp", "severity": "warning"}],
  "console_url": "http://127.0.0.1:7421"
}
```

`status`: `firing`, `resolved`, `event` или `test`; `id` одинаков у повторов одной отправки — дедуплицируйте по нему. С секретом запрос подписан `X-FluxMQ-Signature` по той же схеме, что у [HTTP-вебхуков](/docs/webhooks#request).

## Правила без шума {#rules}

| Задача | Правило |
|---|---|
| Дежурным — только то, что будит ночью | важность «Критично», без событий, группировка 30 с, повтор 4 ч |
| Команде заказов — всё по своим каналам | важность «Внимание», маски `orders` и `orders.*`, виды `lag_growth`, `consumer_stalled`, `no_consumers`, `dlq_growth` |
| Аудит опасных действий | событие `channel_deleted`, группировка 5–10 с, в канал аудита |
| Кластер | виды `node_down`, `under_replicated_partitions`, `offline_partitions` **без масок каналов** — иначе оповещения без канала не подойдут |

- События по умолчанию выключены (их много) — включайте явно нужные.
- **Группировка** сворачивает всплеск в одно сообщение и не шлёт ничего, если оповещение открылось и закрылось внутри окна.
- **История доставки** покажет, что ушло, что упало (с причиной) и что подавлено выключенным каналом.

Через REST то же самое: `POST /api/notify/notifiers`, `POST /api/notify/notifiers/{id}/test`, `POST /api/notify/rules` — см. [REST API](/docs/ref-rest).

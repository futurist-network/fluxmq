## Общий порядок {#rolling}

Обновляйте узлы **по одному**:

1. (По желанию) **Снять лидерство** с узла на экране [Узлы](/docs/nodes) — или просто остановите его через `SIGTERM`: штатная остановка сама передаёт лидерство и выходит из ISR.
2. Остановите процесс, замените бинарник (или образ), запустите с **тем же** `--data-dir` и теми же флагами.
3. Дождитесь, пока узел станет «Работает», а **недореплицированных разделов станет 0** (сводка на экране «Узлы» или `GET /api/cluster/status` → `under_replicated_partitions = 0`).
4. Переходите к следующему узлу. Контроллер обновляйте последним — его остановка стоит одних выборов Raft (1–3 с).

Одиночный брокер: остановите, замените бинарник, запустите с тем же каталогом данных. Перед обновлением полезно сделать [резервную копию](/docs/howto-backup-restore).

Если не хотите, чтобы реплики переезжали во время обновления, переведите ребалансировку в режим `off` (панель «Ребалансировка» → настройки) и верните `full` после.

## 0.6 → 0.7: пачки записей {#v07}

В 0.7 брокер хранит сообщения **пачками записей** (record batches): пачка продюсера записывается в лог как есть, её можно сжать (lz4/zstd), реплицировать и отдавать целиком. Узел 0.6 такие пачки прочитать не может, поэтому переход устроен так:

- **Каталог данных 0.6 открывается без изменений**: старые записи читаются, новые пишутся в новом формате; в одном сегменте могут быть оба формата.
- **В кластере** лидер раздела начинает писать пачки, только когда **все** реплики раздела объявили поддержку нового формата (то есть обновлены до 0.7). Пока в кластере есть узел 0.6, публикации хранятся в старом формате — с теми же смещениями и подтверждениями.
- Лидер никогда не отправляет пачку реплике, которая не умеет её читать: такая реплика получает только старый префикс, а брокер пишет громкую ошибку — порчи данных нет.
- **Пока часть лидеров ещё на 0.6**, у их разделов возможны две ошибки ISR 0.6 (в 0.7 исправлены): ISR может «мигать», а вернувшаяся реплика — остаться вне ISR в метаданных, хотя данные она догнала (раздел висит недореплицированным). Данные не теряются: подтверждения по-прежнему требуют `--min-isr` реплик. Если раздел, которым руководит узел 0.6, остаётся недореплицированным дольше ~30 с при ISR ≥ min ISR, продолжайте: обновление (перезапуск) этого лидера снимает проблему.
- Проверено поочерёдным обновлением трёх процессов под нагрузкой с `kill -9` лидеров: 0 потерянных подтверждённых сообщений.

> [!WARNING]
> **Откат на 0.6 после записи пачек не поддерживается.** Как только последний узел обновлён до 0.7 (или одиночный брокер принял первую публикацию в 0.7), в логах появляются пачки, которые 0.6 не читает. Если откат может понадобиться, сделайте резервную копию до обновления последнего узла.

**Новые флаги 0.7** (значения по умолчанию подходят большинству): `--partition-cache-bytes` (16 MiB недавних пачек на раздел в памяти, чтобы догнавшие получатели читали без диска) и `--delivery-threads` (2 потока отдельного рантайма доставки, чтобы получатели не голодали, когда отправители загружают брокер). См. [Флаги и переменные](/docs/ref-cli).

## Клиенты {#clients}

- **SDK 0.7** работает с брокерами 0.4–0.7: предлагает протокол v4, а со старым брокером сразу переходит на поддерживаемую версию. Поэтому клиентов 0.7 можно обновлять в любом порядке относительно брокеров; выигрыш от пачек, сжатия и cumulative-подтверждений появится, когда брокер станет 0.7.
- **Старые SDK** (протоколы v2/v3) продолжают работать с брокером 0.7 без изменений.
- Исторически (0.4 → 0.5): SDK 0.5 не умел понижать протокол, поэтому тогда правило было «сначала все брокеры, потом клиенты». С SDK 0.7 это ограничение снято.

## Более ранние переходы {#older}

- **0.3 → 0.4**: узел 0.4+ удаляет локальные копии разделов, репликой которых больше не является; первый контроллер 0.4 записывает настройки ребалансировки из `--auto-rebalance` (по умолчанию `full`). Чтобы реплики не начали переезжать сразу, запускайте узлы с `--auto-rebalance off`.
- **0.4 → 0.5, 0.5 → 0.6**: формат данных не менялся, обновление по одному узлу. В 0.6 размер сегмента по умолчанию стал 64 MiB (вместо 128 MiB) — старые сегменты читаются как прежде.

## После обновления {#verify}

- [Узлы](/docs/nodes): все «Работает», 0 недореплицированных и 0 недоступных разделов, у всех узлов новая версия.
- [Обзор](/docs/dashboard): задержка и отставание вернулись к привычным значениям.
- `curl -s http://<узел>:7421/api/health` — `version` новая.

Все операции — роль администратора, на любом узле (выполняет контроллер). Состояние видно на экране [Узлы](/docs/nodes).

## Добавить узел {#add}

1. Запустите новый процесс с **новым** `--node-id`, тем же `--cluster-secret` (и теми же cluster TLS-флагами) и `--peers`, перечисляющим существующие узлы:

   ```bash
   ./target/release/fluxmq --node-id n4 --peers n1@10.0.0.1:7422,n2@10.0.0.2:7422,n3@10.0.0.3:7422 \
     --cluster-secret "$FLUXMQ_CLUSTER_SECRET" --advertise-host 10.0.0.4 --data-dir /var/lib/fluxmq
   ```

2. Контроллер добавит его в Raft сначала learner'ом, потом голосующим (до 5 голосующих). На экране «Узлы» он появится как «Подключается», затем «Работает».
3. Новые каналы сразу используют новый узел. Существующие реплики в режиме `full` переедут на него сами примерно через 10 с после `Up` (плюс до 30 с до ближайшей проверки) — в панели «Ребалансировка» появится план с причиной `node n4 joined`. В режимах `off` и `repair` нажмите **Ребалансировать сейчас**.

## Перезапустить узел для обслуживания {#maintenance}

1. На карточке узла — **Снять лидерство** (или просто остановите процесс через `SIGTERM`: штатная остановка делает то же самое сама).
2. Остановите, обслужите, запустите с тем же `--data-dir` и флагами.
3. Узел догонит лидеров, вернётся в ISR, станет `Up` через ~10 с и заберёт свои предпочтительные лидерства. Короткий простой (меньше `replace_after_secs`, по умолчанию 10 минут) не вызывает переноса реплик.

## Вывести узел насовсем {#decommission}

1. Убедитесь, что оставшиеся узлы вместят реплики: при RF 3 на трёх узлах сначала добавьте четвёртый.
2. На карточке — **Вывести из кластера**. Предпросмотр покажет, сколько реплик и каких каналов переедет и как изменится нагрузка.
3. Подтвердите. Карточка покажет прогресс («перенесено N из M»), панель «Ребалансировка» — переезды. Отмена доделывает начатые переезды и возвращает узел в `Up`.
4. Когда карточка сообщит, что узел покинул кластер, остановите процесс. Каталог данных можно удалить. Перезапуск с тем же id подключит его как новый пустой узел.

Через REST:

```bash
curl -s -X POST -H "$AUTH" "$H/api/cluster/nodes/n3/decommission?dry_run=true"   # план, ничего не меняет
curl -s -X POST -H "$AUTH" $H/api/cluster/nodes/n3/decommission                  # запустить
curl -s -H "$AUTH" $H/api/cluster/nodes/n3/decommission                          # прогресс
```

## Узел умер насовсем {#dead}

1. Узел в статусе `Down`. Через `replace_after_secs` (по умолчанию 600 с) в режимах `repair`/`full` его реплики пересоздадутся на живых узлах сами; не хотите ждать — **Ребалансировать сейчас**.
2. Когда на узле не осталось реплик, на его карточке — **Забыть узел** (`DELETE /api/cluster/nodes/{id}`). Узел удаляется из Raft и реестра.

> [!WARNING]
> Кворум Raft: удалить голосующий узел можно, только если живы большинство и оставшихся, и текущих голосующих. При потере большинства метаданные становятся только для чтения, а failover невозможен. Не стирайте `data/raft/` у большинства узлов.

## Выровнять реплики вручную {#rebalance}

Панель «Ребалансировка» на экране «Узлы» → **Ребалансировать сейчас** → предпросмотр (какие разделы откуда куда переедут и прогноз нагрузки) → **Начать**. Переезд безопасен: новые реплики догоняют лидера и входят в ISR, только потом старые удаляются; ограничить нагрузку на сеть можно параметром «Ограничение догоняющей реплики». **Пауза** не начинает новые переезды, **Отменить** никогда не оставляет раздел с меньшим числом реплик.

Точечно переместить один раздел — клик по клетке матрицы → **Переназначить** (первая реплика — предпочтительный лидер).

## Ограничения {#limits}

- Одновременно выводится только один узел и не во время другой ребалансировки.
- Планировщик считает реплики, а не байты; rack/AZ-awareness нет.
- Публикации в разделы упавшего лидера стоят ~5–6 с, пока контроллер выбирает нового.

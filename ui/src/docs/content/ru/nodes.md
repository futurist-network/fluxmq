На одиночном брокере экран «Узлы» показывает одну карточку (CPU, память, диск, fsync p99, подключения) и пометку «Single-node mode». В кластере — всё, что нужно для эксплуатации: состав, репликацию и операции с узлами. Данные обновляются каждые 2 секунды.

## Как устроен кластер {#model}

- **Метаданные** (каналы, назначения разделов, токены, маршруты, список узлов) хранятся в Raft на всех узлах. Лидер Raft — **контроллер**: он раскладывает разделы по узлам и переключает их при сбоях.
- **Данные** реплицируются по разделам, как в Kafka: у раздела есть лидер и реплики, реплики забирают данные у лидера. Публикация подтверждается, когда сообщение есть у всех синхронных реплик (**ISR**). Получатели видят только реплицированное.
- Новым лидером становится только реплика из ISR. Если живых реплик ISR нет, раздел становится **недоступным** (offline), а не теряет данные.
- Обращаться можно к любому узлу: создание каналов идёт через контроллер, публикации пересылаются лидерам, чтение и операции с группами собираются с лидеров.

## Сводка {#summary}

| Показатель | Что значит | Норма |
|---|---|---|
| Работают | узлов не в статусе `Down` из всех | все |
| Контроллер | какой узел — лидер Raft, срок (term) Raft | есть |
| Фактор репликации | реплик у новых каналов (`--replication-factor`) | обычно 3 |
| Разделы | всего разделов | — |
| Недореплицированы | разделов, у которых в ISR меньше реплик, чем назначено | 0 (кроме перезапуска узла) |
| Недоступны | разделов без живого лидера | **всегда 0**, иначе публикации в них невозможны |
| Журнал Raft | зафиксирован ли журнал метаданных, эпоха | зафиксирован |

## Карточки узлов {#node-cards}

Статус: **Работает** (`Up`), **Недоступен** (`Down`), **Подключается** (`Joining` — догоняет лидеров перед входом в ISR), **Покидает кластер** (`Leaving` — после снятия лидерства), **Выводится** (`Decommissioning`). Цветом выделяется только не-«Работает». Бейджи: «контроллер», «голосующий» (voter) или learner.

В карточке: адреса клиентского протокола и HTTP, число лидерств и реплик, CPU, память, диск (жёлтый > 80 %, красный > 90 %), fsync p99 (предупреждение > 50 мс), подключения, время работы, версия. Действия (роль администратора):

- **Снять лидерство** (drain) — переносит лидерство разделов узла на другие реплики ISR и помечает узел `Leaving`. Узел продолжает реплицировать, его можно перезапустить без недоступных разделов; после перезапуска лидерства вернутся. Штатная остановка (`SIGTERM`) делает это автоматически.
- **Вывести из кластера** (decommission) — см. [ниже](#decommission).
- **Забыть узел** (forget) — для мёртвого узла, см. [ниже](#forget).

## Матрица лидеров разделов {#matrix}

Строки — каналы, клетки — разделы, цвет клетки — узел-лидер. **Жёлтая рамка** — недореплицирован, **штриховка** — недоступен, отдельная пометка — реплика переносится. Переключатель «Только проблемные» оставляет проблемные разделы. Подсказка у клетки: лидер, эпоха, ISR, отставание реплик.

Клик по клетке — **Переназначить**: выбрать набор реплик раздела; первая реплика — предпочтительный лидер. Новые реплики догоняют лидера и входят в ISR, только потом старые удаляются. Чтобы полностью перенести раздел, удобнее ребалансировка (ниже), чем ручное переназначение.

## Ребалансировка {#rebalancing}

Контроллер сам следит за размещением реплик:

- **Восстановление (repair)** — если узел лежит дольше `replace_after_secs` (по умолчанию 600 с), его реплики пересоздаются на живых узлах. Реплика убирается, только если есть куда её перенести, — число копий никогда не уменьшается.
- **Выравнивание (balance)** — если разница `max − min` реплик на живой узел больше порога (по умолчанию 1), минимальное число реплик переезжает с перегруженных узлов на свободные, затем выравниваются предпочтительные лидеры. Новый узел получает свою долю примерно через 10 с после `Up` плюс до 30 с до ближайшей проверки.

Как переезжает раздел: новые реплики добавляются и догоняют лидера (не входя в ISR) → когда все в ISR, фиксируется новый список, старые реплики удаляют свою копию → лидерство переходит на предпочтительную реплику. Подтверждённые сообщения не теряются; если новые реплики не попали в ISR за `move_timeout_secs`, переезд откатывается. План хранится в метаданных и продолжается после смены контроллера.

Панель **Ребалансировка** на экране «Узлы»:

- нагрузка по узлам (реплики, лидеры, объём) — сейчас и прогноз после плана, бейдж дисбаланса, число недореплицированных разделов;
- текущий или последний план — таблица переездов: раздел, реплики «было → станет», причина, состояние (`pending` — ждёт слота, `catching_up` — догоняет с отставанием и прогрессом, `finalizing`, `done`, `rolled_back` — старые реплики восстановлены, `cancelled`), время;
- **Ребалансировать сейчас** — сначала предпросмотр плана (ничего не меняет), затем запуск; работает и в режиме `off`;
- **Пауза / Продолжить / Отменить** — пауза не начинает новые переезды, текущие доходят до конца; отмена никогда не оставляет раздел с меньшим числом реплик;
- **Настройки** (хранятся в метаданных кластера):

| Параметр | По умолчанию | Смысл |
|---|---|---|
| Режим | `full` | `off` — только вручную, `repair` — только восстановление, `full` — восстановление и выравнивание |
| Макс. одновременных переездов | 2 | на весь кластер |
| Порог дисбаланса | 1 | допустимая разница `max − min` реплик на живой узел |
| Заменять реплики через | 600 с | через сколько `Down` пересоздавать реплики узла; 0 — никогда |
| Ограничение догоняющей реплики | 0 (без ограничения) | байт/с на реплику; синхронные реплики не ограничиваются |
| Тайм-аут переезда | 1800 с | после него переезд откатывается |

Флаг `--auto-rebalance` задаёт режим только при первом запуске кластера; дальше источник истины — эти настройки.

## Вывод узла {#decommission}

**Вывести из кластера** — убрать живой узел насовсем одной командой:

1. **Проверки** (предпросмотр показывает план и сколько реплик переедет). Отказ `409`, если идёт другая ребалансировка или вывод, оставшиеся узлы не вместят реплики (например, RF 3 на трёх узлах — сначала добавьте узел), у раздела нет живого лидера или удаление нарушит кворум Raft.
2. **Перенос реплик** — узел получает статус «Выводится», его лидерство переносится, запускается план ребалансировки только из переездов типа repair (виден в панели ребалансировки). Карточка показывает прогресс «перенесено N из M». **Отмена** доделывает начатые переезды, вывод завершается как отменённый, узел снова `Up`.
3. **Выход из состава Raft** — когда реплик не осталось.
4. **Удалён** — узел пропадает из списка, карточка сообщает, что процесс можно останавливать. Перезапуск с тем же id подключит его как **новый пустой узел**.

Одновременно выводится только один узел. Вывод контроллера тоже работает: он сначала переносит свои реплики, затем удаляет себя из Raft, оставшиеся узлы выбирают нового контроллера за 1–2 с.

## Забыть мёртвый узел {#forget}

**Забыть узел** — для машины, которая умерла насовсем, после того как её реплики уже восстановлены на других узлах (автоматически через `replace_after_secs` или ручной ребалансировкой). Доступно только для узла `Down` без реплик, иначе `409`. Если процесс вдруг вернётся с тем же id, его отклонят; перезапуск подключит его как новый узел.

> [!WARNING]
> Удалить голосующий узел можно, только если остаётся хотя бы один voter и живы большинство и оставшихся, и текущих voters. При трёх voters и одном упавшем вывести второй нельзя.

## Что происходит при падении узла {#failure}

| Время | Что происходит |
|---|---|
| 0 с | узел упал (`kill -9`, питание, сеть) |
| до 4 с | истекает его аренда — он сам перестаёт руководить разделами, даже если жив, но отрезан |
| ~6 с | контроллер помечает узел `Down`, выбирает новых лидеров из ISR, убирает узел из ISR; SDK получает `NotLeader`/`MetadataChanged` и повторяет запросы |
| узел вернулся | отрезает расходящийся хвост, догоняет, возвращается в ISR, через ~10 с после старта — `Up` и забирает свои предпочтительные лидерства |

Публикации в разделы упавшего лидера стоят ~5–6 с (при падении контроллера — до ~9 с). Подробно о добавлении и выводе узлов — [Добавить или убрать узел](/docs/howto-nodes).

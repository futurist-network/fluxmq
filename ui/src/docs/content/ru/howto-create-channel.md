## 1. Выберите режим {#mode}

| Вопрос | Ответ → режим |
|---|---|
| Нужно хранить события, перечитывать их и раздавать нескольким независимым потребителям? | `stream` (как топик Kafka) |
| Это задачи для пула воркеров, порядок не важен, каждая задача — один раз на группу? | `queue` (как очередь RabbitMQ) |
| Важен строгий порядок для каждого клиента / заказа / счёта, но разные ключи можно обрабатывать параллельно? | `keyed` |
| Срочные задачи должны обгонять ждущие (тревоги раньше рассылок, VIP раньше остальных)? | `priority` (как очередь с приоритетами RabbitMQ) |

Если сомневаетесь — берите `stream`: его можно перечитать, а несколько групп получат все сообщения в любом режиме.

Готовые сочетания режима и настроек под типовые задачи — в [Готовых связках](/docs/recipes#chooser).

## 2. Выберите число разделов {#partitions}

- `stream` и `keyed`: разделы — единица параллелизма внутри группы. Берите с запасом под будущее число экземпляров (по умолчанию 8). **Число разделов после создания не меняется.**
- `queue`: обычно хватает 1 — конкурирующие получатели и так делят работу.
- `priority`: разделы — это уровни приоритета, от 2 до 10 (по умолчанию 3). Получатели всегда берут самое срочное из ждущих; при непрерывном потоке срочных сообщений низшие уровни ждут (строгий приоритет).
- В `keyed` и при отправке с ключом сообщения одного ключа всегда в одном разделе (`crc32(key) % partitions`). Один очень «горячий» ключ ограничен скоростью одного раздела.

## 3. Хранение {#retention}

- Срок: сколько времени нужно иметь возможность перечитать или переиграть сообщения (по умолчанию 7 дней).
- Объём: страховка от переполнения диска (по умолчанию без ограничения). Старые сегменты удаляются первыми.
- В `queue` сообщение удаляется и после подтверждения всеми группами.

> [!WARNING]
> Если группа отстанет дольше срока хранения, непрочитанные ею сообщения будут удалены и **пропущены**. Ставьте срок с запасом на время простоя самого медленного получателя.

## 4. Повторы и DLQ {#retries}

| Параметр | По умолчанию | Как выбрать |
|---|---|---|
| Макс. число попыток | 5 | сколько раз имеет смысл пробовать, прежде чем звать человека |
| Задержки между попытками | `1s, 10s, 1m, 5m` | под характер сбоев: секунды — для сетевых сбоев, минуты — для перезапусков зависимостей |
| Тайм-аут подтверждения | 30 с | больше максимального времени обработки одного сообщения, иначе медленное сообщение будет доставлено повторно |
| DLQ | включена | выключайте, только если потерять неудачные сообщения не страшно |

Тайм-аут подтверждения, повторы и DLQ можно менять в любой момент на вкладке [Настройки канала](/docs/channel-detail#settings-tab).

## 5. Создайте канал {#create}

**В консоли**: «Каналы (топики)» → **Создать канал** → выбрать сценарий → имя, срок хранения, разделы → при необходимости **Дополнительно**. Подробно о полях — [Каналы](/docs/channels#create).

**Через REST** (роль администратора):

```bash
curl -s -X POST http://localhost:7421/api/channels \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' -d '{
    "name": "orders.events",
    "mode": "stream",
    "partitions": 8,
    "retention": {"max_age_secs": 604800, "max_bytes": null},
    "retry": {"max_attempts": 5, "backoff_ms": [1000, 10000, 60000, 300000], "ack_timeout_ms": 30000},
    "dlq_enabled": true,
    "ordering_key": "order_id"
  }'
```

Все поля, кроме `name` и `mode`, необязательны. Ответ `201` с конфигурацией канала; `409` — канал с таким именем уже есть; `400` — неверное имя или параметры.

**Из SDK** — идемпотентно, удобно при старте сервиса:

```rust
use fluxmq_client::{ChannelConfig, ChannelMode};

client.ensure_channel(ChannelConfig::new("orders.events", ChannelMode::Stream)).await?;
```

`ChannelConfig::new` берёт значения по умолчанию (8 разделов, 1 у `queue`, 7 дней, 5 попыток, DLQ включена); поля структуры можно поменять перед вызовом. Создание канала по клиентскому протоколу требует роль администратора.

## 6. Проверьте {#verify}

Откройте канал в консоли и опубликуйте тестовое сообщение:

```bash
curl -s -X POST http://localhost:7421/api/channels/orders.events/publish \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' -d '{
  "messages":[{"key":"8842","headers":{"flux-type":"OrderCreated"},
               "payload":{"encoding":"utf8","data":"{\"order_id\":8842}"}}]}'
```

Оно появится на вкладке «Сообщения» (режим «Последние»). Дальше — [подключите клиента](/docs/howto-connect-client).

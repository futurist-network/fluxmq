**Вебхук** — подписка, при которой брокер сам отправляет сообщения канала POST-запросами на ваш HTTP-адрес. Получателю не нужен SDK и постоянное соединение — достаточно HTTP-сервера, который отвечает `2xx`.

## Как это устроено {#how}

- Каждый вебхук — это группа получателей `$webhook:<имя>` на своём канале. Её отставание, повторы, история доставки и DLQ видны в консоли так же, как у обычных групп.
- В кластере каждый узел доставляет сообщения разделов, лидером которых он является.
- Фильтр — тот же [язык фильтров](/docs/ref-filter), что у маршрутов. Не подошедшие сообщения подтверждаются без запроса и считаются в «Пропущено фильтром».
- Выключение ставит доставку на паузу (группа и позиция сохраняются). Удаление останавливает доставку и удаляет группу; недоставленные сообщения остаются в DLQ.

## Список {#list}

| Колонка | Что значит |
|---|---|
| Имя | имя вебхука; рядом формат (конверт / сырое тело), размер пакета, пауза |
| Канал → адрес | канал и хост URL |
| Доставлено / Ошибки / Пропущено | счётчики по всему кластеру с момента старта процессов |
| p99 | задержка ответа вашего сервера |
| Последний статус | HTTP-код последней попытки; цветом — только ошибки: 5xx, 429, 408 — красным, прочие 4xx — жёлтым |
| В обработке | запросов в полёте сейчас |

Падающий вебхук подсвечен, рядом — ссылка на недоставленные сообщения его канала; **пауза** рядом со статусом значит, что доставку держит предохранитель (см. [Если получатель недоступен](#breaker)). Кнопка **Отправить тест** шлёт одну синтетическую доставку (`delivery_id` вида `test/…`). Бейдж в боковом меню — сколько вебхуков сейчас падают.

## Редактор {#webhook-editor}

Нужна роль администратора.

| Поле | Что задаёт |
|---|---|
| Имя | `[a-z0-9._-]`, становится группой `$webhook:<имя>`; после создания не меняется |
| Канал | после создания не меняется |
| URL | адрес доставки |
| Формат тела | **Конверт (JSON)** — метаданные и содержимое; **Сырое тело** — только байты сообщения, метаданные в заголовках `X-FluxMQ-*` (размер пакета всегда 1) |
| Секрет подписи | необязательный; с ним каждый запрос подписывается заголовком `X-FluxMQ-Signature` |
| Заголовки | ваши заголовки (например `Authorization`); их значения тоже секретны |
| Фильтр | условия, как в редакторе маршрутов (строки или текст) |
| Тайм-аут | 100–60 000 мс, по умолчанию 10 000; вместе с ожиданием пакета должен быть меньше тайм-аута подтверждения канала |
| Макс. в обработке | 1–64, по умолчанию 4; **1 = строгий порядок** в пределах раздела |
| Размер пакета | 1–500 сообщений в одном запросе (JSON-массив конвертов) |
| Ожидание пакета | 0–10 000 мс — сколько ждать, чтобы набрать пакет |
| Ответы 4xx | по умолчанию 4xx (кроме 408, 425, 429) не повторяются; можно включить повтор |
| Если получатель недоступен | приостанавливать доставку после N неудачных запросов подряд (1–1000); для вебхуков, созданных в консоли, включено, 5 — см. [ниже](#breaker) |
| Начать с | только новые / самое старое хранимое сообщение / с момента времени; только при создании |

Секреты после сохранения показываются как `••••••••` с кнопками «Заменить» / «Оставить сохранённый»; сервер их никогда не возвращает.

Справа — **Отправить тест**: статус, задержка и начало ответа. Для нового вебхука проверяется черновик, для сохранённого — то, что сейчас в форме, включая несохранённые правки; ничего не сохраняется. Ошибки короткие (`HTTP 503`, `timeout`, `connection refused`, `TLS error`, `DNS error`, `blocked by policy`), полный текст — во всплывающей подсказке. Там же — пример тела запроса и готовый код проверки подписи на Node.js и Python.

## Активность, последние запросы, перемотка {#activity}

Страница сохранённого вебхука начинается с:

- **Активность** — доставленные и неудачные сообщения по интервалам (10 с для 15 мин и 1 ч, 5 мин для 24 ч) и задержка ответа (средняя и максимальная), сумма по всем узлам.
- **Последние запросы** — по 100 последних на узел, новые сверху: время, сообщение (`delivery_id` первого, `+N в пакете`), попытка, результат («Доставлено», «Будет повтор», «В DLQ», а на паузе — проверки получателя), HTTP-код или короткая ошибка (полный текст во всплывающей подсказке), задержка и, в кластере, узел.
- **Перемотать позицию…** (роль оператора) справа — сброс позиции группы: доставить заново с самого старого хранимого сообщения или с момента времени либо пропустить всё до текущего. Работает и на ходу.

Активность и последние запросы хранятся в памяти каждого узла и начинаются заново после перезапуска, как и счётчики в списке.

## Если получатель недоступен {#breaker}

Без защиты, пока получатель лежит, каждое сообщение повторяется и, исчерпав попытки, уходит в DLQ — несколько минут простоя могут перенести в DLQ всю очередь. Настройка **Приостанавливать доставку после N неудачных запросов подряд** (предохранитель):

- Неудачей считаются тайм-ауты, ошибки соединения, `5xx`, `408`, `425` и `429`; любой другой ответ обнуляет счёт.
- После N неудач подряд вебхук перестаёт брать сообщения из канала. Они ждут там **и не тратят попытки**; в DLQ ничего не уходит. На странице — баннер, в списке — **пауза**, в боковом меню вебхук считается падающим.
- Получатель проверяется тестовой доставкой (`delivery_id` вида `probe/…`, заголовок `flux-test: true`): через 2 с, затем вдвое реже, до раза в 60 с. Любой ответ, кроме неудачи, — даже `4xx`, отвергающий тестовое тело, — возобновляет доставку с того места, где она остановилась.
- До паузы неудачные запросы потратили попытки своих сообщений (при полном отказе — не больше примерно N на сообщение). Держите N меньше максимума попыток канала, чтобы эти сообщения не попали в DLQ.
- Сообщения ждут в пределах хранения канала: если простой дольше, самые старые удалятся недоставленными. Об этом предупредят алерты отставания.
- В кластере у каждого узла свой предохранитель для разделов, где он лидер.

## Что получает ваш сервер {#request}

`POST <url>`, `Content-Type: application/json`, тело — конверт:

```json
{
  "delivery_id": "orders/1/0",
  "subscription": "orders-crm",
  "channel": "orders",
  "partition": 1,
  "offset": 0,
  "key": "order-1001",
  "headers": {},
  "timestamp_ms": 1791446775012,
  "attempt": 1,
  "payload": {"encoding": "utf8", "data": "{\"id\":1001,\"country\":\"MD\"}"}
}
```

- `delivery_id` (`канал/раздел/смещение`) одинаков у всех повторов одного сообщения — **дедуплицируйте по нему**.
- `payload.encoding` — `utf8` для текста или `base64` для двоичных данных.
- Заголовки запроса: `X-FluxMQ-Delivery-Id`, `X-FluxMQ-Attempt` (номер попытки с 1), ваши заголовки и `X-FluxMQ-Signature: t=<unix-время>,v1=<hex HMAC-SHA256(secret, "<t>.<тело>")>`, если задан секрет. Подпись проверяйте по **сырому** телу, сравнивайте в постоянное время и отклоняйте старые метки времени.

## Повторы и DLQ {#retries}

| Ответ сервера | Что делает брокер | Причина в DLQ |
|---|---|---|
| `2xx` | подтверждает | — |
| `408`, `425`, `429`, `5xx` | повтор по политике повторов канала | `HTTP <код>` |
| таймаут | повтор | `timeout` |
| соединение отклонено, DNS, TLS | повтор | `connection refused`, `DNS error`, `TLS error` |
| адрес запрещён политикой SSRF | сразу в DLQ, без повторов | `blocked by policy` |
| остальные `4xx` | сразу в DLQ (с «повторять 4xx» — повтор) | `HTTP <код>` |
| `3xx` | сразу в DLQ: редиректы не выполняются | `HTTP <код>` |

Заголовок `Retry-After` учитывается, но не дольше максимальной паузы канала. Когда попытки кончились, сообщение попадает в DLQ канала с группой `$webhook:<имя>`; оттуда его можно повторить.

## Безопасность (SSRF) {#ssrf}

Пока авторизация включена, вебхук не может обращаться к loopback-, приватным, link-local-, CGNAT- и multicast-адресам (`127.0.0.1`, `10.0.0.0/8`, `192.168.0.0/16`, `169.254.169.254`, `::1`…). Адрес проверяется при сохранении, при тесте и при каждой доставке (защита от DNS rebinding); редиректы и прокси не используются. В открытом режиме (без токенов) приватные адреса разрешены, чтобы тестировать на localhost. Явная настройка — флаг `--webhooks-allow-private` (см. [Флаги и переменные](/docs/ref-cli)).

## Порядок и производительность {#order}

- **Макс. в обработке = 1** — строгий порядок внутри раздела: пока сообщение ждёт повтора, следующие не обгоняют его (но на паузе вся подписка). Строгий порядок гарантирован при размере пакета 1.
- **Больше 1** — запросы идут параллельно, порядок не гарантирован, пропускная способность выше. Ориентиры на локальном получателе: ~25 тыс. сообщений/с при 1, ~65 тыс./с при 16–64, ~500 тыс./с при 4 и пакетах по 100.
- Нужен порядок по ключу, а не по разделу целиком, — используйте канал `keyed`.

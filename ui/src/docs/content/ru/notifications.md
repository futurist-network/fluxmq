FluxMQ сам сообщает о проблемах: оповещения (растёт отставание, нет получателей, растёт DLQ, упал узел…) и, по желанию, события брокера (канал удалён, получатель отключился…) уходят туда, где их увидит команда. Просмотр — роль наблюдателя; создание, изменение, удаление и тестовая отправка — администратор.

Модель простая: **канал уведомлений** (notifier) — *куда* слать; **правило** — *что* и *кому*.

## Каналы уведомлений {#notifiers}

| Тип | Что указать |
|---|---|
| Telegram | токен бота, ID чата, необязательный ID темы (для групп с темами); в форме есть подсказка «Как узнать ID чата» |
| Slack | URL входящего вебхука (`https://hooks.slack.com/…`): Apps → Incoming Webhooks → Add to channel |
| Discord | URL вебхука канала: настройки канала → Интеграция → Вебхуки → Новый вебхук → Копировать URL |
| Email (SMTP) | SMTP-сервер, порт, шифрование (STARTTLS — 587, TLS — 465, нет — только для локального relay), логин и пароль (необязательно), From, список получателей |
| PagerDuty | ключ интеграции Events API v2; открытое оповещение создаёт инцидент, закрытое — закрывает его (ключ дедупликации — id оповещения) |
| Webhook | URL, необязательный секрет подписи (`X-FluxMQ-Signature`, как у [вебхуков](/docs/webhooks#request)) и заголовки |

В списке: тип, имя и адресат, последняя доставка (отправлено/ошибка, время и короткая причина), переключатель «Включён» и **Отправить тест**. Выключенный канал ничего не отправляет — в истории такие сообщения отмечены «подавлено».

**Секреты** (токен бота, URL вебхуков Slack/Discord, пароль SMTP, ключ PagerDuty, секрет подписи, значения заголовков) сервер никогда не возвращает: поле показывается как `••••••••` с кнопкой «Заменить». В диалоге правки **Отправить тест** проверяет то, что сейчас в форме, включая несохранённые правки, и ничего не сохраняет. Канал, который используется в правиле, удалить нельзя (`409`) — сначала уберите его из правил.

## Правила {#rules}

| Поле | Что задаёт |
|---|---|
| Имя | как правило подписано в списке и истории |
| Отправлять в | один или несколько каналов уведомлений |
| Минимальная важность | «Внимание» (всё) или «Критично» — только для оповещений |
| Виды оповещений | пусто = любые; коды — в статье [Оповещения](/docs/alerts#kinds) |
| События брокера | пусто = **никаких** (события частые, включайте явно): `channel_deleted`, `dead_lettered`, `node_down`… |
| Маски каналов | `orders.*` и т. п.; пусто = все каналы и общекластерные оповещения; подсказка «подходит N каналов сейчас». Если маски заданы, оповещения без канала (например, `node_down`) правилу не подходят |
| Группировка (group wait) | нет / 10 с / 30 с / 1 мин / 5 мин — всё, что сработало за окно, приходит одним сообщением («3 issues need attention»); если оповещение открылось и закрылось внутри окна, сообщения не будет |
| Повтор, пока открыто | никогда / 1 / 4 / 12 / 24 ч — напоминание об ещё открытом оповещении |
| Восстановление | присылать ли «Resolved: …», когда оповещение закрылось |

По умолчанию: группировка 30 с, повтор раз в 4 часа, сообщение о восстановлении включено. Пустая страница подсказывает начать с правила «Критичное → дежурным».

## История доставки {#history}

Последние отправки (до 1000 на экране): время, состояние (**отправлено**, **ошибка**, **подавлено**), канал уведомлений и правило, текст, ошибка и число попыток; фильтр «С ошибкой». Неудачная отправка повторяется до 3 раз (через 2 и 10 с). Ошибки короткие — `connection refused`, `timeout`, `HTTP 503`, `TLS error`, `DNS error`, `SMTP 550`; полный текст — во всплывающей подсказке.

История хранится 7 дней в системном канале `$system.notifications` и переживает перезапуск и смену контроллера. В кластере отправляет **только контроллер** — дублей не будет.

> [!TIP]
> Запустите брокер с `--public-url https://mq.example.com`, и в каждом уведомлении будет ссылка на нужный экран консоли.

## Лента для внешних систем (pull API) {#pull-feed}

Всё то же самое — каждое изменение оповещений и каждое событие — пишется в системный канал `$system.events`. Внешняя система может забирать ленту сама, без входящего адреса:

```bash
# последние 20 записей (старые → новые)
curl -s "http://localhost:7421/api/events/feed?tail=20" -H "Authorization: Bearer $TOKEN"
# дальше — только новое: передайте next_cursor и ждите до 25 с (long-poll)
curl -s "http://localhost:7421/api/events/feed?after=<next_cursor>&wait_ms=25000" -H "Authorization: Bearer $TOKEN"
```

`after=latest` — только то, что появится после запроса; без `after` — с самой старой записи. `gap: true` в ответе значит, что часть записей уже удалена хранением. Для такого клиента достаточно токена наблюдателя с областью чтения `$system.events`. Внизу вкладки — живой пример ленты.

Пошагово, с Telegram — [Настроить оповещения и уведомления](/docs/howto-alerts).

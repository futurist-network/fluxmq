## Запуск и консоль {#startup}

| Симптом | Причина и решение |
|---|---|
| `Address already in use` | порт 7420 или 7421 занят (часто вторым экземпляром или `pnpm mock`). Найдите процесс: `lsof -i :7421`, или смените `--http-addr` / `--client-addr` |
| По адресу консоли — страница «UI is not built» | консоль не собрана: `cd ui && pnpm install && pnpm build`, проверьте `--ui-dir` |
| Баннер «Соединение потеряно» | брокер остановлен или недоступен; консоль переподключится сама |
| Ошибки записи, «restart the broker» | закончилось место на диске; освободите место и перезапустите — при старте брокер восстановит файлы |
| `cargo` ругается на версию | нужен Rust 1.88+: `rustup update stable` |

## Авторизация {#auth}

| Симптом | Причина и решение |
|---|---|
| Консоль просит токен, REST отвечает 401 | авторизация включена: введите токен в консоли или передайте `Authorization: Bearer …` |
| Клиент: `Unauthorized` при подключении | передайте токен (`auth_token`, `--token`, `FLUXMQ_TOKEN`) или настройте привязку сертификата |
| 403 `forbidden` / `Forbidden` в клиенте | токен верный, но роли или областей действия не хватает. Роль покажет `curl -s $H/api/auth/me -H "Authorization: Bearer $TOKEN"` |
| «Токен сеанса отозван или просрочен», WebSocket закрыт с кодом 4401 | токен отозвали или истёк срок; войдите с новым |
| Нельзя отозвать токен: `409 last_admin` | это последний токен администратора — сначала выпустите другой |

## Производительность {#performance}

| Симптом | Причина и решение |
|---|---|
| Медленная публикация на macOS, оповещения «Высокая задержка публикации» | так работает `F_FULLFSYNC` в режиме `group-commit` (7–10 мс на сброс). Для разработки — `--fsync os`; в продакшене — Linux с NVMe |
| «Получено» на Обзоре больше «Опубликовано» | норма: «Получено» — сумма подтверждений всех групп |
| Отставание растёт, оповещение «Медленный экземпляр» | откройте панель экземпляра на экране «Получатели»: CPU, время обработки, последняя ошибка. См. [Разобрать отставание](/docs/howto-investigate-lag) |
| Сообщения копятся в DLQ | откройте «Недоставленные», устраните причину, «Повторить все». См. [Разобрать DLQ](/docs/howto-handle-dlq) |
| Поиск сообщений пишет «достигнут предел просмотра» | индекса по содержимому нет, просматривается до 200 000 сообщений за запрос — сузьте время, раздел или ключ |

## Кластер {#cluster}

| Симптом | Причина и решение |
|---|---|
| 503 «partitions … are changing leaders; retry» | идёт смена лидера (failover, снятие лидерства, переназначение). Повторите через пару секунд; SDK делает это сам |
| Узел после штатной остановки показан как `Down` | так и должно быть: после запуска он станет `Up` примерно через 10 с |
| `Overloaded: not enough replicas` | в ISR раздела меньше узлов, чем `--min-isr`; верните упавшие узлы |
| Узел не стартует: «a cluster secret is required» | с `--peers` обязательны `--node-id` и `--cluster-secret` (одинаковый на всех узлах) |
| Вывод узла отклонён с `409` | идёт другая ребалансировка или вывод, не хватает узлов под фактор репликации, нет лидера раздела или нарушится кворум — причина в ответе |
| Клиенты не находят узлы в Docker | адреса `n1:7420` резолвятся только внутри сети compose — запускайте клиентов кластера в ней |

## TLS {#tls}

| Симптом | Причина и решение |
|---|---|
| Клиент: `this port requires TLS` | порт с TLS, а клиент подключается открытым текстом — используйте `tls://host:port` или `ClientOptions::tls` |
| HTTP-запрос: 400 «This port speaks HTTPS» | откройте консоль по `https://` |
| `TLS handshake with …` в клиенте | чужой CA или истёкший сертификат; проверьте `ca_file` и срок на вкладке [Безопасность](/docs/security) |
| Брокер не стартует с TLS-флагами | неполное сочетание (сертификат без ключа, `--tls-client-ca` без `--tls-cert`, cluster TLS без всех трёх файлов) или битый PEM — текст ошибки подскажет |
| Привязка сертификата «неактивна» | на клиентском порту нет mTLS — запустите брокер с `--tls-client-ca` |

## Вопросы {#faq}

**Теряются ли сообщения при падении брокера?** Подтверждённые — нет: в режиме по умолчанию подтверждение приходит только после fsync (и репликации на ISR в кластере). После сбоя брокер проверяет хвост последнего сегмента по CRC и отрезает недописанное — оно не было подтверждено. Смещения групп сохраняются раз в секунду, поэтому до ~1 с уже обработанных сообщений может прийти повторно.

**Почему пришёл дубликат?** Доставка at-least-once: повтор публикации после обрыва, сбой брокера, перемотка группы или повтор из DLQ могут доставить сообщение снова. Делайте обработчики идемпотентными.

**Можно ли изменить число разделов?** Нет, только при создании. Создайте новый канал и перенесите поток.

**Чем FluxMQ отличается от Kafka и RabbitMQ?** Один бинарник со встроенной консолью и оповещениями; режимы и потоков (как Kafka), и очередей (как RabbitMQ), и строгого порядка по ключу; подтверждение каждого сообщения, повторы и DLQ из коробки; fsync перед подтверждением по умолчанию.

**Есть ли SDK для других языков?** Пока только Rust. Остальные публикуют через REST, а получают через [вебхуки](/docs/webhooks).

**Где подробные логи?** `--log debug` или `RUST_LOG=info,fluxmq_core=debug,fluxmq_api=debug`.

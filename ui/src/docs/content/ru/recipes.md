Каждый рецепт — готовая карточка: задача, режим и почему именно он, точные настройки канала, что подключить после создания, как создать (консоль, REST, SDK), что мониторить и где обычно ошибаются. Значения в таблицах настроек — это ровно то, что принимает мастер **Создать канал** и `POST /api/channels`; их можно копировать как есть.

Общее для всех рецептов: публикация подтверждается **после fsync** (в кластере — после записи на все синхронные реплики), доставка — **at-least-once**. Сообщение может прийти повторно после сбоя, повтора публикации или перемотки, поэтому обработчики должны быть **идемпотентными** — например, по бизнес-ключу (`order_id`, `email_id`).

## Какой рецепт выбрать {#chooser}

| Задача | Рецепт | Режим |
|---|---|---|
| Обработать заказы / платежи строго по порядку внутри заказа или клиента | [Заказы со строгим порядком](#orders-keyed) | `keyed` |
| Отправка писем, генерация PDF, ресайз картинок пулом воркеров | [Фоновые задачи](#jobs-queue) | `queue` |
| Журнал событий / аудит, который перечитывают и читают несколько систем | [Журнал событий и аудит](#event-log) | `stream` |
| Одно событие нужно нескольким сервисам | [Fan-out на несколько сервисов](#fanout) | `stream` |
| Разложить сообщения по специализированным каналам по содержимому (страна, сумма, тип) | [Маршрутизация по содержимому](#content-routing) | `stream` + маршруты |
| Доставить события во внешний HTTP-сервис без SDK | [Push во внешний HTTP](#webhook-push) | `stream` + вебхук |
| Ненадёжная внешняя зависимость: повторять с растущей паузой, «ядовитые» сообщения — в сторону | [Отложенный повтор и «ядовитые» сообщения](#retry-poison) | `queue` |
| Метрики, клики, логи — сотни тысяч сообщений в секунду | [Сбор телеметрии](#telemetry-ingest) | `stream` + cumulative |

Как устроены режимы — в статье [Основные понятия](/docs/concepts#modes); как выбирать каждый параметр — в [Создать канал](/docs/howto-create-channel).

> [!NOTE]
> Число разделов, режим и ключ упорядочивания после создания не меняются. Хранение, повторы, тайм-аут подтверждения и DLQ можно поменять в любой момент на вкладке [Настройки](/docs/channel-detail#settings-tab) канала.

## 1. Заказы со строгим порядком {#orders-keyed}

**Задача.** Команды по заказу (`OrderCreated` → `OrderPaid` → `OrderShipped`) нужно обрабатывать строго по порядку внутри одного заказа, но разные заказы — параллельно, на нескольких экземплярах сервиса.

**Режим и почему.** `keyed`: следующее сообщение ключа не выдаётся, пока предыдущее не подтверждено или не ушло в DLQ; остальные ключи идут параллельно. В `stream` неудачное сообщение повторяется, не блокируя раздел, — следующие сообщения того же заказа могут его обогнать.

| Параметр | Значение |
|---|---|
| Режим | `keyed` |
| Разделы (партиции) | 16 |
| Срок хранения | 7 дней |
| Ограничение размера | без ограничений |
| Макс. число попыток доставки | 5 |
| Задержки между попытками | `1s, 5s, 30s, 2m` |
| Тайм-аут подтверждения (секунды) | 30 |
| Очередь недоставленных (DLQ) | включена |
| Ключ упорядочивания | `order_id` |

Паузы короче значений по умолчанию: пока сообщение ждёт повтора, весь его заказ стоит.

**Группы.** Одна группа на сервис (`order-processor`); экземпляров — сколько нужно, полезный максимум — 16 (число разделов).

**Как создать.** В консоли: «Каналы (топики)» → **Создать канал** → «Сохранять порядок по клиенту или заказу» → **Продолжить** → имя `orders.commands`, «Срок хранения» 7 дней, «Разделы (партиции)» 16, «Ключ упорядочивания» `order_id` → **Дополнительно**: попытки, задержки, тайм-аут → **Создать канал**.

```bash
curl -s -X POST http://localhost:7421/api/channels \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' -d '{
    "name": "orders.commands", "mode": "keyed", "partitions": 16,
    "retention": {"max_age_secs": 604800, "max_bytes": null},
    "retry": {"max_attempts": 5, "backoff_ms": [1000, 5000, 30000, 120000], "ack_timeout_ms": 30000},
    "dlq_enabled": true, "ordering_key": "order_id"
  }'
```

```rust
use fluxmq_client::{message, ChannelConfig, ChannelMode, SubscribeOptions};

let mut cfg = ChannelConfig::new("orders.commands", ChannelMode::Keyed);
cfg.partitions = 16;
cfg.retry.backoff_ms = vec![1_000, 5_000, 30_000, 120_000];
cfg.ordering_key = Some("order_id".into());
client.ensure_channel(cfg).await?;

// отправитель: ключ = номер заказа
client.producer("orders.commands")
    .send(message(r#"{"order_id":8842,"status":"paid"}"#).key("8842").event_type("OrderPaid"))
    .await?;

// получатель
let mut consumer = client.subscribe("orders.commands", "order-processor", SubscribeOptions::default()).await?;
```

**Что мониторить.** «Получатели» → карточка `order-processor`: «Отставание», «Ждут повтора», «Обработка p99». На вкладке «Хранилище» канала — перекос размеров разделов (горячий ключ). Оповещения `lag_growth`, `consumer_stalled`, `dlq_growth`.

**Подводные камни.**
- Публикуйте **каждое** сообщение с ключом — порядок существует только в пределах ключа.
- Один «горячий» ключ ограничен скоростью одного раздела, и одно зависшее сообщение тормозит весь свой ключ — смотрите [историю доставки](/docs/channel-detail#inspector).
- Когда сообщение уходит в DLQ, следующие сообщения ключа продолжают обрабатываться — порядок для этого заказа уже нарушен. Обработчик должен уметь это заметить (например, по статусу заказа в своей БД), а DLQ — разбираться быстро.
- `nack(reason, false)` для заведомо неисправимых данных: сразу в DLQ, ключ не ждёт всех попыток.

## 2. Фоновые задачи пулом воркеров {#jobs-queue}

**Задача.** Отправка писем (или PDF, ресайз картинок): много независимых задач, порядок не важен, каждую задачу берёт один воркер группы; временные сбои SMTP — повторять, неисправимые — в DLQ и потом переиграть.

**Режим и почему.** `queue`: конкурирующие получатели — следующую задачу берёт любой свободный экземпляр группы; подтверждённое всеми группами сообщение удаляется. Один медленный воркер не держит раздел, как в `stream`.

| Параметр | Значение |
|---|---|
| Режим | `queue` |
| Разделы (партиции) | 1 |
| Срок хранения | 24 часа |
| Ограничение размера | без ограничений |
| Макс. число попыток доставки | 8 |
| Задержки между попытками | `10s, 1m, 5m, 15m, 30m` |
| Тайм-аут подтверждения (секунды) | 60 |
| Очередь недоставленных (DLQ) | включена |

8 попыток с такими паузами растягиваются почти на 2 часа (10 с + 1 мин + 5 мин + 15 мин + 3 × 30 мин) — переживают перезапуск почтового сервера. Срок хранения — страховка на случай простоя воркеров: если группа не успеет за 24 часа, непрочитанное удалится; ставьте больше, если воркеры могут лежать дольше.

**Группы.** Одна группа `mailer`, N экземпляров. Масштабирование — просто запустить ещё экземпляров.

**Как создать.** В консоли: «Каналы (топики)» → **Создать канал** → «Распределять задачи между обработчиками» → **Продолжить** → имя `email.send`, «Срок хранения» 24 часа, «Разделы (партиции)» 1 → **Дополнительно** → **Создать канал**.

```bash
curl -s -X POST http://localhost:7421/api/channels \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' -d '{
    "name": "email.send", "mode": "queue", "partitions": 1,
    "retention": {"max_age_secs": 86400, "max_bytes": null},
    "retry": {"max_attempts": 8, "backoff_ms": [10000, 60000, 300000, 900000, 1800000], "ack_timeout_ms": 60000},
    "dlq_enabled": true
  }'
```

```rust
let mut consumer = client
    .subscribe("email.send", "mailer", SubscribeOptions::default().prefetch(16))
    .await?;
while let Some(d) = consumer.next().await {
    let d = d?;
    match send_email(d.payload()).await {
        Ok(()) => d.ack().await?,
        Err(e) if e.is_transient() => d.nack("SMTP unavailable", true).await?,  // повтор по политике канала
        Err(_) => d.nack("Invalid address", false).await?,                    // сразу в DLQ
    }
}
```

**Что мониторить.** Карточка группы `mailer`: «Отставание», «В обработке» (не упирается ли в prefetch), «Отказы (nack)». Экран «Недоставленные» — карточки причин. Оповещения `no_consumers`, `high_retry_rate`, `dlq_growth`. После исправления причины — **Повторить все (N)** на экране «Недоставленные».

**Подводные камни.**
- Тайм-аут подтверждения должен быть больше самой долгой обработки одной задачи, иначе медленная задача будет выдана второму воркеру — письмо уйдёт дважды. Дедуплицируйте по `email_id`.
- `prefetch` держите небольшим (8–32): задачи, выданные зависшему воркеру, вернутся только через тайм-аут подтверждения.
- Причины в `nack` пишите короткими и стабильными — по ним группируется DLQ.
- Вторая группа на том же канале получит **все** задачи заново (fan-out), а не поделит их с первой.

## 3. Журнал событий и аудит {#event-log}

**Задача.** Хранить доменные события или журнал аудита неделями, читать их несколькими независимыми системами (архив, аналитика, антифрод), уметь перечитать историю с нужного момента — например, после бага в обработчике.

**Режим и почему.** `stream`: хранимый лог, каждая группа читает всё в своём темпе, позицию можно перемотать к самому раннему сообщению или к моменту времени.

| Параметр | Значение |
|---|---|
| Режим | `stream` |
| Разделы (партиции) | 8 |
| Срок хранения | 30 дней |
| Ограничение размера | 100 ГБ |
| Макс. число попыток доставки | 5 |
| Задержки между попытками | `1s, 10s, 1m, 5m` |
| Тайм-аут подтверждения (секунды) | 30 |
| Очередь недоставленных (DLQ) | включена |

Ограничение размера — страховка диска: при превышении удаляются самые старые сегменты, даже если им меньше 30 дней. Для аудита, который нельзя терять, выберите «Бессрочно» и следите за диском (оповещение `storage_nearly_full`).

**Группы.** По группе на каждую систему: `audit-archive`, `analytics`, `fraud`. Новая группа начинает с `start`: `StartFrom::Earliest` — со всей истории, `StartFrom::TimestampMs(…)` — с момента.

**Как создать.** В консоли: «Каналы (топики)» → **Создать канал** → «Хранить события и переигрывать их позже» → **Продолжить** → имя `audit.events`, «Срок хранения» 30 дней, «Разделы (партиции)» 8 → **Дополнительно** → «Ограничение размера» 100 ГБ → **Создать канал**.

```bash
curl -s -X POST http://localhost:7421/api/channels \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' -d '{
    "name": "audit.events", "mode": "stream", "partitions": 8,
    "retention": {"max_age_secs": 2592000, "max_bytes": 107374182400},
    "retry": {"max_attempts": 5, "backoff_ms": [1000, 10000, 60000, 300000], "ack_timeout_ms": 30000},
    "dlq_enabled": true
  }'

# перечитать всё с 1 октября 2026 (00:00 UTC) группой analytics
curl -s -X POST http://localhost:7421/api/channels/audit.events/groups/analytics/reset \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"to":{"timestamp_ms":1790812800000}}'
```

```rust
use fluxmq_client::{StartFrom, SubscribeOptions};

// новая группа читает всю хранимую историю
let mut archive = client
    .subscribe("audit.events", "audit-archive", SubscribeOptions::default().start(StartFrom::Earliest))
    .await?;
```

В консоли перемотка — «Получатели» → карточка группы → **Сбросить смещения** → «С момента времени».

**Что мониторить.** Отставание каждой группы отдельно (на странице канала — максимум по группам). Вкладка «Хранилище»: «Самое старое сообщение» и полоса заполнения лимита. Метрика `fluxmq_group_retention_skipped_messages_total` — должна быть 0.

**Подводные камни.**
- `start` действует только для **новой** группы; позицию существующей меняют сбросом смещений.
- Отставшая дольше срока хранения группа **пропустит** удалённые сообщения. Срок — с запасом на простой самого медленного читателя.
- Сброс к прошлому заново доставит все сообщения — обработчики должны быть идемпотентными.
- Внутри группы параллельно работает не больше экземпляров, чем разделов.

## 4. Fan-out на несколько сервисов {#fanout}

**Задача.** Событие `UserRegistered` нужно CRM, сервису уведомлений и поисковому индексу; каждый обрабатывает его независимо, сбой одного не мешает другим.

**Режим и почему.** `stream` и **отдельная группа на каждый сервис**. Во всех режимах каждая группа получает все сообщения канала; у каждой группы свои смещения, повторы, отставание и записи в DLQ (повтор из DLQ возвращает сообщение только той группе, которая с ним не справилась).

| Параметр | Значение |
|---|---|
| Режим | `stream` |
| Разделы (партиции) | 8 |
| Срок хранения | 7 дней |
| Ограничение размера | без ограничений |
| Макс. число попыток доставки | 5 |
| Задержки между попытками | `1s, 10s, 1m, 5m` |
| Тайм-аут подтверждения (секунды) | 30 |
| Очередь недоставленных (DLQ) | включена |

**Группы или маршруты — что выбрать.**

| Нужно | Решение |
|---|---|
| Каждому сервису — все события, настройки канала общие | группы `crm`, `notifications`, `search-indexer` на одном канале |
| Сервису — только часть событий (по типу, стране, сумме) | группа читает всё и подтверждает лишнее, или [маршрут](#content-routing) копирует нужное в отдельный канал |
| Разные срок хранения, повторы, тайм-аут или режим (например, очередь для воркеров) | маршрут в отдельный канал со своими настройками |
| Внешнему сервису без SDK | [вебхук](#webhook-push) — это тоже отдельная группа `$webhook:<имя>` |

Маршрут — это лишняя копия на диске, зато у цели свои настройки и права. Если всё совпадает, достаточно групп.

**Как создать.** Канал — как в рецепте [Журнал событий](#event-log), но имя `user.events` и срок хранения 7 дней (или `ChannelConfig::new("user.events", ChannelMode::Stream)` — это и есть значения по умолчанию). Группы создавать не нужно: группа появляется при первой подписке.

```rust
// в CRM
let crm = client.subscribe("user.events", "crm", SubscribeOptions::default()).await?;
// в сервисе уведомлений — то же событие, своя позиция
let notify = client.subscribe("user.events", "notifications", SubscribeOptions::default()).await?;
```

**Что мониторить.** Вкладка «Получатели» канала: карточка на каждую группу. «Отставание» в списке каналов — максимум по группам, поэтому проблемную группу ищите в карточках. Оповещение `no_consumers` — сервис перестал читать.

**Подводные камни.**
- Новая группа по умолчанию начинает с `Latest`: события до её первой подписки она не увидит. Нужна история — `StartFrom::Earliest`.
- Два экземпляра одного сервиса с **разными** именами группы получат каждое событие оба — имя группы должно быть одинаковым у всех копий сервиса.
- В `queue` сообщение удаляется, только когда его подтвердили **все** группы: одна лежащая группа держит хранилище.

## 5. Маршрутизация по содержимому {#content-routing}

**Задача.** Из общего потока заказов отправлять заказы из Молдовы в канал `orders.md`, а крупные заказы (от 1000) — в очередь ручной проверки `orders.review`.

**Режим и почему.** Источник — `stream` (его читают и другие группы); маршрутизатор встроен в брокер и читает источник системной группой `$router`. Цели — каналы с режимом под своих получателей: `orders.md` — поток, `orders.review` — очередь для операторов.

Настройки источника `orders.events`:

| Параметр | Значение |
|---|---|
| Режим | `stream` |
| Разделы (партиции) | 8 |
| Срок хранения | 7 дней |
| Ограничение размера | без ограничений |
| Макс. число попыток доставки | 5 |
| Задержки между попытками | `1s, 10s, 1m, 5m` |
| Тайм-аут подтверждения (секунды) | 30 |
| Очередь недоставленных (DLQ) | включена |

Цели: `orders.md` — `stream`, 8 разделов, 7 дней; `orders.review` — `queue`, 1 раздел, 7 дней; повторы и DLQ — по умолчанию.

**Маршруты.**

| Маршрут | FROM | WHEN | THEN |
|---|---|---|---|
| Заказы MD | `orders.events` | `header.flux-type = OrderCreated AND country = MD` | `orders.md` |
| Крупные заказы | `orders.events` | `amount >= 1000` | `orders.review` |

Условия пишутся на [языке фильтров](/docs/ref-filter): `key`, `partition`, `header.<имя>`, пути в JSON (`shipping.country`), операторы `=`, `!=`, `>`, `>=`, `<`, `<=`, `in [..]`, `prefix`, `contains`, `exists`.

**Как создать.** Сначала создайте все три канала. Затем «Маршрутизация» → **Новый маршрут** → имя, FROM, условия WHEN (строками или в режиме «Текст»), каналы THEN → проверьте **Предпросмотр** («Совпало … из … проверенных») → **Создать маршрут**. Быстрый путь: на вкладке «Сообщения» источника подберите фильтр и нажмите **Создать маршрут по фильтру**.

```bash
H=http://localhost:7421; A="Authorization: Bearer $TOKEN"
# текст → условия (так делает редактор)
curl -s -X POST $H/api/filter/parse -H "$A" -H 'content-type: application/json' \
  -d '{"filter":"header.flux-type = OrderCreated AND country = MD"}'

# создать маршрут (роль администратора)
curl -s -X POST $H/api/routes -H "$A" -H 'content-type: application/json' -d '{
  "name": "Заказы MD", "source": "orders.events", "targets": ["orders.md"],
  "conditions": [
    {"field":{"kind":"header","name":"flux-type"},"op":"eq","value":"OrderCreated"},
    {"field":{"kind":"payload","name":"country"},"op":"eq","value":"MD"}]}'

# проверить условия на хранимых сообщениях за последний час
curl -s -X POST $H/api/routes/test -H "$A" -H 'content-type: application/json' -d '{
  "source": "orders.events", "window_ms": 3600000, "sample_limit": 5,
  "conditions": [{"field":{"kind":"payload","name":"amount"},"op":"gte","value":1000}]}'
```

Маршруты создаются через консоль или REST; в SDK отдельного API для них нет.

**Что мониторить.** Экран «Маршрутизация»: «Совпало», «Переслано», «Ошибки», «Последнее совпадение». Группа `$router` на экране «Получатели» — её отставание. В DLQ источника — группа `router` с причиной `route target unavailable: <канал>`.

**Подводные камни.**
- `OR` нет: для «или» заведите несколько маршрутов в одну цель — копия всё равно уйдёт один раз.
- Маршрут обрабатывает только сообщения, опубликованные **после** его создания; старые догоняют [переигрыванием](/docs/channel-detail#replay).
- Не удаляйте канал-цель при живом маршруте: сообщения пойдут в повторы, затем в DLQ источника.
- Условия по содержимому не срабатывают на не-JSON payload; тип события надёжнее брать из заголовка `flux-type`.
- Копия — новое сообщение в цели с теми же ключом, заголовками и содержимым плюс `flux-routed-from`, `flux-route-id`, `flux-route-path`.

## 6. Push во внешний HTTP (вебхук) {#webhook-push}

**Задача.** Доставлять события в CRM партнёра, который умеет только принимать HTTP POST: с подписью, повторами при `5xx`/таймаутах и DLQ.

**Режим и почему.** `stream` + вебхук. Вебхук — это группа получателей `$webhook:<имя>`: брокер сам отправляет сообщения на URL, а отставание, повторы и DLQ видны как у обычной группы. Если нужен строгий порядок по ключу (клиенту), а не по разделу целиком, берите канал `keyed`.

| Параметр | Значение |
|---|---|
| Режим | `stream` |
| Разделы (партиции) | 8 |
| Срок хранения | 3 дня |
| Ограничение размера | без ограничений |
| Макс. число попыток доставки | 10 |
| Задержки между попытками | `5s, 30s, 2m, 10m, 30m` |
| Тайм-аут подтверждения (секунды) | 30 |
| Очередь недоставленных (DLQ) | включена |

10 попыток покрывают около трёх часов недоступности получателя (5 с + 30 с + 2 мин + 10 мин + 6 × 30 мин). Срок хранения 3 дня — запас на долгий простой партнёра.

**Вебхук.** Имя `crm-sync`, «Формат тела» «Конверт (JSON)», «Секрет подписи», при необходимости «Заголовки» (`Authorization`), «Тайм-аут» 10 000 мс, «Макс. в обработке» 4 (или 1 — строгий порядок в разделе), «Размер пакета» 1, «Начать с» — «Только новые» или «Самое старое хранимое сообщение».

**Как создать.** Канал `crm.events` — через **Создать канал** («Хранить события и переигрывать их позже», «Срок хранения» 3 дня, в **Дополнительно** — попытки и задержки). Затем «Вебхуки» → **Создать вебхук** → поля выше → справа **Отправить тест** (статус и задержка ответа; ничего не сохраняется) → сохранить.

```bash
H=http://localhost:7421; A="Authorization: Bearer $TOKEN"
curl -s -X POST $H/api/channels -H "$A" -H 'content-type: application/json' -d '{
  "name": "crm.events", "mode": "stream", "partitions": 8,
  "retention": {"max_age_secs": 259200, "max_bytes": null},
  "retry": {"max_attempts": 10, "backoff_ms": [5000, 30000, 120000, 600000, 1800000], "ack_timeout_ms": 30000},
  "dlq_enabled": true
}'

# проверить черновик, ничего не сохраняя
curl -s -X POST $H/api/webhooks/test -H "$A" -H 'content-type: application/json' -d '{
  "name": "crm-sync", "channel": "crm.events", "url": "https://crm.example.com/hooks/fluxmq"}'

# создать (роль администратора)
curl -s -X POST $H/api/webhooks -H "$A" -H 'content-type: application/json' -d '{
  "name": "crm-sync", "channel": "crm.events", "url": "https://crm.example.com/hooks/fluxmq",
  "secret": "'"$CRM_WEBHOOK_SECRET"'", "headers": {"Authorization": "Bearer partner-token"},
  "format": "envelope", "timeout_ms": 10000, "max_in_flight": 4, "batch_max": 1,
  "start": "latest"
}'
```

Нужна только часть событий — добавьте `"filter"` (условия в том же JSON-формате, что у маршрутов) или задайте фильтр в редакторе; не подошедшие сообщения подтверждаются без запроса.

**Что мониторить.** Экран «Вебхуки»: «Доставлено / Ошибки / Пропущено», p99, «Последний статус»; бейдж в боковом меню — сколько вебхуков падают. Группа `$webhook:crm-sync` на экране «Получатели» — отставание. DLQ — причины `HTTP 503`, `timeout`, `connection refused`, `blocked by policy`.

**Подводные камни.**
- На стороне получателя дедуплицируйте по `delivery_id` (`канал/раздел/смещение`, одинаков у всех повторов) и проверяйте `X-FluxMQ-Signature` по **сырому** телу.
- «Тайм-аут» вебхука плюс «Ожидание пакета» должны быть меньше тайм-аута подтверждения канала — иначе вебхук не сохранится.
- Остальные `4xx` (кроме 408, 425, 429) и `3xx` сразу уходят в DLQ без повторов; редиректы не выполняются.
- При включённой авторизации приватные и loopback-адреса запрещены (защита от SSRF): для внутреннего адреса нужен флаг `--webhooks-allow-private`.
- «Макс. в обработке» больше 1 ускоряет доставку, но порядок не гарантирован.

## 7. Отложенный повтор и «ядовитые» сообщения {#retry-poison}

**Задача.** Синхронизация с внешним API, который бывает недоступен часами. Временные сбои — повторять с растущей паузой, не забивая API; сообщения, которые не обработаются никогда («ядовитые»), — сразу убрать в сторону, разобрать и при необходимости вернуть.

**Режим и почему.** `queue`: повторы одного сообщения не задерживают остальные, воркеры конкурируют. Пауза перед повтором — это политика повторов канала: брокер сам держит сообщение до следующей попытки.

:::diagram delivery

| Параметр | Значение |
|---|---|
| Режим | `queue` |
| Разделы (партиции) | 1 |
| Срок хранения | 3 дня |
| Ограничение размера | без ограничений |
| Макс. число попыток доставки | 6 |
| Задержки между попытками | `30s, 2m, 10m, 30m, 1h` |
| Тайм-аут подтверждения (секунды) | 60 |
| Очередь недоставленных (DLQ) | включена |

Шесть попыток растянуты примерно на 1 ч 43 мин. Последнее значение списка повторяется, поэтому при большем числе попыток паузы останутся часовыми.

**Группы.** Одна группа `partner-sync`. Обработчик различает виды ошибок:

```rust
let mut consumer = client.subscribe("partner.sync", "partner-sync", SubscribeOptions::default()).await?;
while let Some(d) = consumer.next().await {
    let d = d?;
    match push_to_partner(d.payload()).await {
        Ok(()) => d.ack().await?,
        Err(e) if e.is_transient() => d.nack("Partner API 503", true).await?,  // пауза по списку задержек
        Err(_) => d.nack("Invalid payload", false).await?,                      // «ядовитое» — сразу в DLQ
    }
}
```

`d.attempt()` — номер текущей попытки; по нему можно, например, писать в лог только последнюю неудачу.

**Как создать.** «Каналы (топики)» → **Создать канал** → «Распределять задачи между обработчиками» → имя `partner.sync`, «Срок хранения» 3 дня → **Дополнительно**: «Макс. число попыток доставки» 6, «Задержки между попытками» `30s, 2m, 10m, 30m, 1h`, «Тайм-аут подтверждения (секунды)» 60 → **Создать канал**.

```bash
curl -s -X POST http://localhost:7421/api/channels \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' -d '{
    "name": "partner.sync", "mode": "queue", "partitions": 1,
    "retention": {"max_age_secs": 259200, "max_bytes": null},
    "retry": {"max_attempts": 6, "backoff_ms": [30000, 120000, 600000, 1800000, 3600000], "ack_timeout_ms": 60000},
    "dlq_enabled": true
  }'
```

**Разбор DLQ.** «Недоставленные» → карточка причины → откройте пару сообщений (история доставки покажет все попытки и паузы) → устраните причину → **Повторить все (N)** (новый запас попыток, только для той же группы). Ненужное — **Экспорт NDJSON**, затем **Удалить**. Исправленное вручную сообщение можно опубликовать заново или **Переиграть…** из вкладки «Сообщения». Через REST:

```bash
H=http://localhost:7421; A="Authorization: Bearer $TOKEN"
curl -s -H "$A" "$H/api/dlq?channel=partner.sync&limit=20"
curl -s -H "$A" -X POST $H/api/dlq/retry -H 'content-type: application/json' \
  -d '{"reason":"Partner API 503","channel":"partner.sync"}'
```

**Что мониторить.** Карточка группы: «Ждут повтора» и «Отказы (nack)». Оповещения `high_retry_rate` и `dlq_growth`; событие `dead_lettered` — в [уведомления](/docs/howto-alerts). Подробно — [Разобрать DLQ](/docs/howto-handle-dlq).

**Подводные камни.**
- Пока причина не устранена, «Повторить все» лишь прогонит сообщения по всем попыткам заново и вернёт в DLQ.
- Тайм-аут подтверждения тоже тратит попытку: обработчик, который падает без `nack`, «съедает» попытки по 60 с.
- В `keyed` то же сообщение на паузе держит весь свой ключ — длинные паузы там опасны.
- С выключенной DLQ исчерпавшие попытки сообщения **отбрасываются**.

## 8. Сбор телеметрии на высокой скорости {#telemetry-ingest}

**Задача.** Принимать метрики устройств, клики или логи — сотни тысяч сообщений в секунду — и обрабатывать их потоково (агрегации, загрузка в хранилище аналитики).

**Режим и почему.** `stream`: максимальная скорость, разделы — единица параллелизма. Отправитель — `BatchingProducer` со сжатием, получатель — режим подтверждения `AckMode::Cumulative` (фиксация позиции в разделе вместо подтверждения каждого сообщения).

| Параметр | Значение |
|---|---|
| Режим | `stream` |
| Разделы (партиции) | 32 |
| Срок хранения | 24 часа |
| Ограничение размера | 100 ГБ |
| Макс. число попыток доставки | 3 |
| Задержки между попытками | `1s, 10s` |
| Тайм-аут подтверждения (секунды) | 30 |
| Очередь недоставленных (DLQ) | включена |

Повторы, тайм-аут и DLQ действуют только для групп в режиме `Individual`; cumulative-группы их не используют. 32 раздела — запас под 32 параллельных экземпляра в группе: число разделов потом не меняется.

**Как создать.** «Каналы (топики)» → **Создать канал** → «Хранить события и переигрывать их позже» → имя `telemetry.metrics`, «Срок хранения» 24 часа, «Разделы (партиции)» 32 → **Дополнительно**: «Ограничение размера» 100 ГБ, попытки 3, задержки `1s, 10s` → **Создать канал**.

```bash
curl -s -X POST http://localhost:7421/api/channels \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' -d '{
    "name": "telemetry.metrics", "mode": "stream", "partitions": 32,
    "retention": {"max_age_secs": 86400, "max_bytes": 107374182400},
    "retry": {"max_attempts": 3, "backoff_ms": [1000, 10000], "ack_timeout_ms": 30000},
    "dlq_enabled": true
  }'
```

```rust
use fluxmq_client::{message, BatchingOptions, Client, ClientOptions, Compression, SubscribeOptions};

// отправитель: пачки по разделам + lz4 (zstd — если важнее трафик и место)
let client = Client::connect(
    ClientOptions::new("127.0.0.1:7420", "ingest-1").compression(Compression::Lz4),
).await?;
let producer = client.batching_producer("telemetry.metrics", BatchingOptions::default());
let fut = producer.send(message(r#"{"device":"d-17","cpu":0.42}"#).key("d-17")).await?;
// fut завершится после записи на диск; ошибка — сообщение не сохранено

// получатель: cumulative — подтверждение фиксирует раздел до этого сообщения включительно
let mut consumer = client
    .subscribe("telemetry.metrics", "analytics", SubscribeOptions::default().prefetch(2000).cumulative())
    .await?;
while let Some(d) = consumer.next().await {
    let d = d?;
    aggregate(&d);
    d.ack().await?;
}
```

Подробности о `BatchingOptions` (`linger`, `max_batch`, `max_in_flight`, `ordered`) и сжатии — [Подключить клиента](/docs/howto-connect-client#batching).

**Что мониторить.** Список каналов: «Скорость (сообщ./с)» и «p99». Карточка группы `analytics`: «Отставание» и скорость подтверждений. Вкладка «Хранилище»: равномерность разделов и заполнение лимита. Оповещения `high_publish_latency`, `storage_nearly_full`, `lag_growth`.

**Подводные камни.**
- В cumulative `nack`, тайм-аут подтверждения и DLQ не работают (`nack` вернёт `BadRequest`); после сбоя всё после последней зафиксированной позиции придёт повторно. Подтверждайте сообщение, только когда обработаны все предыдущие в его разделе.
- Не ждите future каждого сообщения по очереди — так пропадает выигрыш от пачек; собирайте их в `FuturesUnordered`.
- Ключ (`device_id`) даёт порядок по устройству, но горячее устройство упирается в один раздел; без ключа сообщения раскладываются «липко» по запросам.
- Не включайте `--fsync os` ради скорости: это флаг всего брокера, и при сбое питания последние подтверждённые сообщения всех каналов могут потеряться. Скорость дают пачки и сжатие, а не ослабление fsync.
- Ограничение размера в 100 ГБ удалит старые сегменты раньше 24 часов, если поток больше ожидаемого, — отстающая группа их пропустит.

## Чего нет и чем заменить {#not-supported}

| Хочется | В FluxMQ | Что делать |
|---|---|---|
| Отложенная доставка «в момент X» | нет | паузы между попытками ([рецепт 7](#retry-poison)) или планировщик в своём сервисе |
| Request/response, `reply-to` | нет | два канала и свой заголовок корреляции (любые заголовки сохраняются) |
| Транзакции, exactly-once, outbox на брокере | нет | at-least-once + идемпотентные обработчики; outbox — в своей БД с публикацией после коммита |
| `OR` в условиях маршрутов и вебхуков | нет | несколько маршрутов в одну цель |
| Приоритеты сообщений | нет | отдельные каналы (например, маршрутом по полю) со своими группами |
| Изменить число разделов, режим, ключ | нельзя после создания | новый канал + маршрут или переигрывание |

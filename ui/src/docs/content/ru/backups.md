FluxMQ делает **консистентные инкрементальные бэкапы без остановки брокера**: в S3-совместимое хранилище (AWS S3, MinIO, Cloudflare R2, Backblaze B2…) или в каталог на диске. Восстановление — отдельной командой `fluxmq restore` в пустой каталог. Менять настройки и запускать бэкапы может только администратор; остальные видят состояние и историю.

## Что попадает в бэкап {#contents}

- **Сообщения** всех каналов — по каждому разделу до консистентной точки среза. Публикации во время бэкапа не блокируются.
- **Настройки каналов**, **смещения групп получателей**, **DLQ** — снимаются сразу после среза сообщений (поэтому после восстановления часть сообщений может прийти повторно, но ничего не теряется).
- **Метаданные**: маршруты, токены доступа (только хэши), каналы уведомлений, вебхуки. Настройки самих бэкапов (с ключами S3) в бэкап **не** попадают.

Бэкапы инкрементальные: закрытые сегменты неизменяемы и загружаются один раз, следующие бэкапы их переиспользуют. Активный сегмент каждого раздела загружается заново при каждом запуске, поэтому у маленьких каналов экономии почти нет.

## Состояние {#status}

Настроено ли и включено ли расписание; идущий бэкап с прогрессом (байты, сколько сегментов переиспользовано и загружено); последний успех (давность, размер, длительность), последняя ошибка, следующий запуск. Кнопка **Запустить** — бэкап сейчас (тот же запуск есть в палитре команд).

## Хранилище и расписание {#config}

| Поле | Что задаёт |
|---|---|
| Тип хранилища | S3-совместимое или файловая система |
| Шаблоны | AWS S3, MinIO, Cloudflare R2 — подставляют адрес, регион и адресацию |
| Адрес (endpoint), регион, бакет, префикс | для S3; пустой адрес = AWS; префикс — папка внутри бакета, по одной на кластер |
| Адресация | path-style (нужна MinIO и R2) или virtual-host |
| Access key id, Secret access key | ключи доступа; секрет после сохранения не показывается |
| Путь на хосте брокера | для файловой системы (удобно с NFS) |
| Каждые | 15 мин, раз в час, 6 ч, раз в сутки (через API — любой интервал от 300 с) |
| Хранить последние / и не старше | сколько бэкапов хранить и максимальный возраст в днях (0 — без ограничения); самый свежий не удаляется никогда |
| Включать сообщения | выключено — только метаданные, смещения и DLQ: быстро и мало места |

**Проверить подключение** записывает, читает и удаляет пробный объект — ничего не сохраняется.

## Шифрование {#encryption}

Если задан ключ, каждый объект шифруется на стороне брокера (AES-256-GCM) до отправки — владелец бакета видит только шифротекст. **Сгенерировать** создаёт случайный ключ (32 байта, base64) и показывает его один раз с кнопкой копирования. Сохранить нельзя, пока не отмечено «Я сохранил ключ шифрования в надёжном месте».

> [!WARNING]
> **Потеряли ключ — потеряли бэкап.** FluxMQ не хранит ключ нигде, кроме своих настроек. Сохраните его в менеджере секретов отдельно от брокера. Выключение шифрования удаляет сохранённый ключ, а старые зашифрованные бэкапы по-прежнему требуют его.

## История {#history}

Каждый бэкап: id, как запущен (по расписанию / вручную / из CLI), состояние, начало, длительность, размер и сколько загружено, полоса «экономия инкрементальности» (доля переиспользованных сегментов). **Восстановить…** открывает подробности: где снят бэкап, какие узлы загрузили данные разделов, состав (таблица каналов: разделы, сообщения до среза, размер, сегменты, группы, DLQ), шифрование, шаги и **готовую команду** `fluxmq restore` для этого бэкапа. Удаление бэкапа удаляет его манифест, а сегменты, на которые больше никто не ссылается, собираются автоматически.

## В кластере {#cluster}

Бэкапы выполняет **контроллер** (запрос к любому узлу проксируется ему), а данные каждого раздела загружает его лидер. Если во время бэкапа у раздела нет лидера, бэкап завершается ошибкой — повторите запуск. Восстановление всегда создаёт **одиночный узел**, из которого можно поднять новый кластер.

Пошагово, включая восстановление, — [Резервное копирование и восстановление](/docs/howto-backup-restore).

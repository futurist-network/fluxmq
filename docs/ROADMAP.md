# FluxMQ Roadmap

Источники: UI-концепт (Cluster → Channels → Messages → Consumers → Problems), концепт realtime observability pipeline, мокап дашборда `img.png`.

## 1. Принципы

- **Data plane и Observability plane разделены.** Брокер никогда не ждёт UI. В горячем пути — только atomic-счётчики и HDR-гистограммы; наружу — через bounded channel с `try_send` (drop при переполнении). Если телеметрия упала, брокер, продюсеры и консьюмеры продолжают работать.
- **UI получает агрегаты, а не сырой поток.** Обновления 4–10 раз/сек, один WebSocket на весь UI, подписки (subscribe/unsubscribe), full snapshot при подключении, затем дельты.
- **Четыре главных сигнала:** HEALTH / TRAFFIC / LAG / ERRORS. Подсвечивать только реально проблемное.
- **Cardinality под контролем:** метки только `channel`, `node`. Никаких `message_id`, `user_id`.
- **Contract-first:** UI разрабатывается параллельно с ядром на mock-сервере с тем же WS-контрактом.

## 2. Решения по стеку (MVP)

| Предложено в концепте | Решение для MVP | Позже |
|---|---|---|
| Protobuf поверх WS | JSON (при 4 Гц + дельтах выигрыш мизерный) | Protobuf, схема изначально совместима |
| Web Worker для декодирования | Батчинг через `requestAnimationFrame` + селекторы Zustand | Worker для live tail |
| ClickHouse для истории | Встроенные ring buffer + rollup'ы (1s → 1m → 30m) в собственном storage | Экспорт в Prometheus/OTel |
| Отдельный `fluxmq-ui-gateway` | Отдельный крейт в том же процессе, свой tokio runtime | Вынос в отдельный бинарник |
| Графики | Canvas (uPlot), downsampling до 500–2000 точек | WebGL для тяжёлых графиков |

## 3. Скрытые требования к ядру

Фичи UI, которые требуют поддержки в ядре и протоколе:

1. **Поиск по полям (`order_id = 8842`)** — индексация payload. MVP: поиск по key / offset / времени. Позже — индекс по явно указанным полям.
2. **DLQ grouping по причине** — `error_reason` в nack протокола.
3. **Retry timeline** — история попыток доставки на сообщение (время, ошибка, задержка).
4. **Метрики воркера (CPU, processing, last error)** — телеметрия из клиентского SDK.
5. **Producer и Trace ID в inspector** — headers в формате сообщения с первого дня.
6. **Routing preview «Matched last 24h»** — backtest правила по хранимым сообщениям.
7. **Replay / Discard / Retry all** — auth, RBAC и audit log (в концепте отсутствуют — главный пробел).

## 4. Замечания по мокапу (`img.png`)

- В мокапе есть режим **Fanout**, в тексте концепта — только Stream / Queue / Keyed. Набор режимов надо зафиксировать.
- «NAT3-compatible» — вероятно, NATS. Совместимость с NATS — отдельная крупная задача, на старте не берём.
- 6 KPI-карточек противоречат принципу «четыре вещи». 3D-кубы, приветствие и «Upgrade Plan» — декор; место наверху лучше отдать Alert Center.
- Стиль и палитра совпадают с концептом — берём как референс.

### Этап 13 — Производительность горячего пути — **сделано (v0.6)**
- [x] Retention без пауз: настраиваемый размер сегмента (по умолчанию 64 MiB), джиттер ролла,
  постепенное удаление с усечением по шагам; исправлена потеря данных при retention (удалялся
  новейший закрытый сегмент), пропуски видны в логе и в метрике.
- [x] Пул fsync-потоков вместо потока на каждый commit; sticky-партиционер для сообщений без ключа;
  конвейерный group commit за флагом (по умолчанию выключен).
- [x] SDK и доставка: адаптивный linger, меньше копий и задач, нулевое копирование payload,
  `stamp_producer`; исправлен расход coop-бюджета tokio в `PublishFuture` (при ~20 тыс.
  неподтверждённых сообщений пропускная способность падала в 4 раза).
- [x] Бенчмарк v0.6 (`bench/results/20261009-v0.6`, частичный набор): пропускная способность
  FluxMQ выросла в 1,7–2,5 раза при 1 KiB, p50 при 1k msg/s 1,96 мс, пауза retention при
  50k msg/s устранена (p99 0,6–1,2 с → 13–64 мс), CPU брокера при 10k msg/s −45 %.
- Осталось: голодание консьюмеров при перегрузке продюсерами (100 B, 4×4: 36k msg/s при 1,5M
  опубликованных); случайные хвосты 0,1–0,3 с при 50k msg/s; Kafka быстрее в 1,7–2,1 раза на
  одном узле; кластерное сравнение с Kafka/RabbitMQ и A/B конвейерного commit не измерены в v0.6.

### Этап 14 — Быстрый путь пачек, «лучше и надёжнее Kafka» — **сделано (v0.7)**

# FluxMQ — инструкция по запуску и работе

Версия 0.5: один узел или кластер из нескольких узлов с репликацией, автоматической
ребалансировкой и выводом узлов из кластера; пакетная доставка консьюмерам; TLS для клиентов,
HTTP и межузлового трафика, привязки клиентских сертификатов к ролям; отзыв токенов, который
обрывает живые сессии; уведомления (Telegram, Slack, Discord, email, PagerDuty, вебхук) с
историей, переживающей смену контроллера; HTTP push-вебхуки, бэкапы в S3 / на диск; Docker-образ
и сравнительные бенчмарки с Kafka и RabbitMQ. Документ для тех, кто запускает FluxMQ впервые,
разрабатывает на нём сервисы или эксплуатирует его.

## 1. Что такое FluxMQ

Брокер сообщений на Rust со встроенной веб-консолью. В одном бинарнике `fluxmq`:

- **хранилище** — append-only лог из сегментов на диске, с fsync и восстановлением после сбоя;
- **каналы** трёх режимов — Stream, Queue, Keyed (раздел 7);
- **consumer groups**, at-least-once доставка, повторы с backoff, **DLQ** с группировкой по причине;
- **телеметрия реального времени** — WebSocket, агрегаты 4 раза в секунду, а не сырой поток;
- **REST API** и **веб-консоль** на `http://localhost:7421`;
- **токены доступа и роли** viewer / operator / admin (раздел 11);
- **маршрутизация по содержимому** и поиск сообщений по полям payload (раздел 18);
- **кластер**: метаданные через Raft, репликация разделов, автоматический failover (раздел 19),
  автоматическая ребалансировка реплик (раздел 23), вывод узла из кластера (decommission и
  forget, раздел 19);
- **TLS** на клиентском порту (с mTLS), HTTPS для REST и консоли, взаимный TLS между узлами
  кластера, ротация сертификатов без перезапуска, привязки сертификатов к ролям (раздел 24);
- **метрики Prometheus** на `/metrics` (раздел 12);
- **Docker-образ** и `docker compose` с одиночным узлом, TLS-кластером, Kafka и RabbitMQ для
  сравнительных бенчмарков (раздел 25).

Дополнительно: Rust SDK (`fluxmq-client`), генератор демо-нагрузки `fluxmq-demo` и бенчмарк `fluxmq-bench`.

Устройство системы описано в [ARCHITECTURE.md](ARCHITECTURE.md), причины решений — в [ROADMAP.md](ROADMAP.md).

## 2. Требования

| Что | Версия | Проверка |
|---|---|---|
| Rust (через rustup) | 1.88+ | `rustc --version` |
| Node.js | 20+ | `node --version` |
| pnpm | 9+ | `pnpm --version` (установка: `npm i -g pnpm`) |
| ОС | macOS или Linux | |
| curl | любая | для проверок и примеров |

Node.js и pnpm нужны только для сборки веб-консоли. Брокер работает и без них, но тогда
вместо консоли по адресу `http://localhost:7421` откроется страница-подсказка.

Место на диске: сборка занимает около 3 ГБ (`target/`). Демо-нагрузка пишет десятки МБ в минуту.

## 3. Быстрый старт

Все команды выполняются из корня репозитория.

### Вариант А — одной командой (режим разработки)

```bash
scripts/dev.sh
```

Скрипт:

1. собирает брокер и демо (debug);
2. запускает брокер с данными в `./data-dev`;
3. ждёт готовности (`/api/health`);
4. запускает `fluxmq-demo` — живой сценарий с каналами, ошибками и лагом;
5. запускает dev-сервер UI (Vite) на `http://localhost:5173` с hot reload.

Откройте **http://localhost:5173**. `Ctrl-C` останавливает всё.

Переменные:

| Переменная | Что делает |
|---|---|
| `NO_DEMO=1` | не запускать демо-нагрузку |
| `NO_UI=1` | не запускать dev-сервер UI |
| `FLUXMQ_DATA_DIR=...` | другой каталог данных (по умолчанию `./data-dev`) |
| `FLUXMQ_ADMIN_TOKEN=...` | включить авторизацию (раздел 11) |

Чтобы начать с чистого листа: `rm -rf data-dev`.

### Вариант Б — как в продакшене (release, консоль раздаёт сам брокер)

```bash
# 1. Собрать веб-консоль -> ui/dist (она встраивается в бинарник брокера)
cd ui && pnpm install && pnpm build && cd ..

# 2. Собрать брокер, демо и бенчмарк
cargo build --release -p fluxmq-server -p fluxmq-client

# 3. Запустить брокер
./target/release/fluxmq --data-dir ./data
```

Брокер выведет адреса: клиенты подключаются на `0.0.0.0:7420`, HTTP работает на `0.0.0.0:7421`.

Во втором терминале, по желанию, демо-нагрузка:

```bash
./target/release/fluxmq-demo            # --speed 2 — вдвое больше трафика
```

Откройте **http://localhost:7421**.

### Вариант В — только UI на мок-сервере (без Rust)

Подходит для работы над интерфейсом:

```bash
cd ui
pnpm install
pnpm mock      # терминал 1: мок брокера на :7421 (REST + WebSocket)
pnpm dev       # терминал 2: UI на http://localhost:5173
```

Переменные мока: `MOCK_SCENARIO=empty` (пустой брокер) | `single` (один узел с демо-данными) |
`cluster` (3 узла; n3 падает через 12 с и возвращается), `MOCK_ROLE=viewer|operator|admin`
(включённая авторизация, запросы от имени этой роли), `MOCK_ADMIN_TOKEN=secret` (bootstrap-токен),
`MOCK_FAST=1` (ускоренная симуляция). Подробности — в `ui/README.md`.

### Проверка, что всё работает

```bash
curl -s http://localhost:7421/api/health
# {"status":"ok","version":"0.5.0","node_id":"...","uptime_secs":12}

curl -s http://localhost:7421/api/channels | head -c 300
```

## 4. Порты и адреса

| Порт | Протокол | Для чего |
|---|---|---|
| **7420** | TCP, бинарный протокол FluxMQ | продюсеры и консьюмеры (SDK, demo, bench) |
| **7421** | HTTP или HTTPS | REST `/api/*`, WebSocket `/ws`, веб-консоль `/` |
| 5173 | HTTP | только dev-сервер UI (Vite); проксирует `/api` и `/ws` на 7421 |

`wss://`. Кластерные порты (7422 Raft, 7423 репликация) — в разделе 19.

## 5. Настройка сервера

`./target/release/fluxmq --help` показывает все опции. Каждую можно задать флагом, переменной окружения
или ключом в TOML-файле `--config fluxmq.toml` (`FLUXMQ_CONFIG`); ключ — имя флага, пример — `deploy/fluxmq.toml`.
Приоритет: флаг > переменная окружения > файл > значение по умолчанию. Неизвестный ключ — ошибка.

| Флаг | Переменная | По умолчанию | Описание |
|---|---|---|---|
| `--data-dir` | `FLUXMQ_DATA_DIR` | `./data` | сообщения, offset'ы, DLQ, audit log |
| `--client-addr` | `FLUXMQ_CLIENT_ADDR` | `0.0.0.0:7420` | адрес клиентского протокола |
| `--http-addr` | `FLUXMQ_HTTP_ADDR` | `0.0.0.0:7421` | адрес REST, WebSocket и UI |
| `--cluster-name` | `FLUXMQ_CLUSTER_NAME` | `local` | имя кластера в UI |
| `--config` | `FLUXMQ_CONFIG` | — | TOML-файл с настройками |
| `--ui` | `FLUXMQ_UI` | `on` | веб-консоль; `off` — только API |
| `--ui-dir` | `FLUXMQ_UI_DIR` | — | раздавать консоль из каталога вместо встроенной |
| `--admin-token` | `FLUXMQ_ADMIN_TOKEN` | — | включает авторизацию (раздел 11) |
| `--admin-token-file` | `FLUXMQ_ADMIN_TOKEN_FILE` | — | то же, токен читается из файла (Docker/Kubernetes secrets) |
| `--fsync` | `FLUXMQ_FSYNC` | `group-commit` | `group-commit` или `os` (см. ниже) |
| `--segment-bytes` | `FLUXMQ_SEGMENT_BYTES` | `67108864` (64 MiB) | размер сегмента в байтах, от 1 MiB до 2 GiB; каждый раздел закрывает сегмент в пределах ±10 % от него (см. ниже) |
| `--commit-pipeline` | `FLUXMQ_COMMIT_PIPELINE` | `on` (с 0.9) | конвейерный group commit: следующие пакеты пишутся и fsync'аются, пока fsync'аются предыдущие; каждый раздел подтверждается по своему fsync (см. ниже) |
| `--commit-pipeline-depth` | `FLUXMQ_COMMIT_PIPELINE_DEPTH` | `1` | сколько пакетов одного раздела может fsync'аться одновременно (1–16) |
| `--fsync-threads` | `FLUXMQ_FSYNC_THREADS` | `0` (2 × CPU, от 4 до 32) | размер общего пула потоков fsync |
| `--log` | `FLUXMQ_LOG` / `RUST_LOG` | `info` | фильтр логов, например `info,fluxmq_core=debug` |
| `--node-id`, `--peers`, `--raft-addr`, `--replication-addr`, `--advertise-host`, `--replication-factor`, `--min-isr`, `--cluster-secret` | `FLUXMQ_…` | — | кластерный режим, см. раздел 19. Без `--peers` брокер — одиночный узел |
| `--auto-rebalance` | `FLUXMQ_AUTO_REBALANCE` | `full` | режим ребалансировки при первом запуске кластера, см. раздел 23 |
| `--tls-cert`, `--tls-key`, `--tls-client-ca`, `--http-tls*`, `--cluster-tls-*` | `FLUXMQ_TLS_…`, `FLUXMQ_HTTP_TLS…`, `FLUXMQ_CLUSTER_TLS_…` | — (без TLS) | TLS и mTLS, см. раздел 24 |

**Режимы долговечности (`--fsync`):**

- `group-commit` (по умолчанию) — публикация подтверждается только после fsync. Записи
  группируются в пакеты (до 2 мс), поэтому подтверждённое сообщение не теряется даже при
  отключении питания. Это режим для продакшена.
- `os` — подтверждение сразу после записи в ОС, сброс на диск делает ОС. Режим в несколько
  раз быстрее, но при сбое питания последние сообщения могут потеряться. Подходит для
  разработки и данных, которые можно потерять.

> На macOS fsync выполняется через `F_FULLFSYNC` и стоит около 7–10 мс на сброс (см. BENCHMARKS.md). Поэтому
> `group-commit` на Mac заметно медленнее, чем на Linux с NVMe.

**Конвейерный group commit (`--commit-pipeline`, с 0.6; с 0.9 включён по умолчанию).** Пока
fsync'и одних пакетов идут в общем пуле потоков, писатель канала принимает, пишет и отправляет на
fsync следующие. С 0.9 каждый раздел завершается отдельно: его записи становятся видны и
подтверждаются, как только закончился fsync *этого раздела* (медленный раздел не задерживает
остальные), а следующий пакет раздела уходит на fsync сразу после предыдущего. Гарантии не
меняются: запись подтверждается только после своего fsync, по каждому разделу строго по порядку;
при ошибке fsync откатываются все ещё не подтверждённые пакеты, их отправители получают ошибку.
`--commit-pipeline-depth N` разрешает N одновременных fsync'ов одного раздела (по умолчанию 1:
на macOS и, по всей видимости, на ext4 сбросы на устройство идут последовательно, и перекрытие
только добавляет fsync'и). `--commit-pipeline off` — поведение 0.8 (писатель ждёт fsync'и всего
пакета). Подробности — docs/design/v0.9-commit-path.md.

**Сегменты и retention.** Лог раздела состоит из сегментов по `--segment-bytes` (с 0.6 — 64 MiB
вместо 128 MiB; смена значения действует на новые сегменты, старые любого размера читаются как
прежде). Чтобы разделы канала не закрывали и не удаляли сегменты одновременно, размер каждого
сегмента детерминированно смещён на ±10 %. Retention удаляет только закрытые сегменты целиком и
работает раз в секунду порциями: за один проход — не больше `1 + (сколько пора удалить) / 8`
сегментов на канал (и не больше 16), по одному из самого «переполненного» раздела; сегмент,
который больше никто не читает, сначала укорачивается шагами по 16 MiB, потом удаляется. Так
удаление не тормозит fsync публикаций. Под очень большим потоком канал может кратковременно
превышать лимит на несколько сегментов.

Пример с переменными окружения:

```bash
FLUXMQ_DATA_DIR=/var/lib/fluxmq FLUXMQ_CLUSTER_NAME=prod-eu-1 \
FLUXMQ_ADMIN_TOKEN="$(openssl rand -hex 32)" ./target/release/fluxmq
```

## 6. Веб-консоль: экраны

**Язык интерфейса.** Консоль двуязычная — русский и английский. Язык меняется в
**Настройки → Общие → Язык** (или кнопкой `EN`/`RU` в верхней панели, или командой «Язык» в
палитре `⌘K`/`Ctrl+K`) и применяется сразу, без перезагрузки страницы. Выбор хранится в этом
браузере (`localStorage`, ключ `fluxmq.lang`) рядом с темой; при первом открытии язык берётся
из настроек браузера (`ru*` → русский, иначе английский). Переводятся надписи, подсказки,
сообщения об ошибках, форматы дат, чисел и размеров («5 минут назад», «1,2 тыс.», «4,2 КБ»).
Имена каналов, групп, метрик, ключи JSON, флаги CLI и примеры кода остаются как есть. В русском
интерфейсе каналы подписаны «Каналы (топики)»: режим `stream` ≈ топик Kafka, `queue` ≈ очередь
RabbitMQ, `keyed` — строгий порядок по ключу. Ниже экраны названы по английской версии.

Логика навигации повторяет то, как оператор ищет проблему:
**Кластер → Каналы → Сообщения → Консьюмеры → Проблемы**.

| Экран | Что там |
|---|---|
| **Dashboard** | общее здоровье кластера, полоса «N issues need attention», четыре главных сигнала (Traffic, Latency p99, Lag, Errors), графики трафика и задержек (5m/15m/1h/24h), таблица каналов (подсвечены только проблемные), лента событий |
| **Channels** | список каналов с поиском и фильтром по режиму; кнопка **Create channel**. Системные каналы брокера (имя начинается с `$`, например `$system.events`) помечены бейджем **system**: их можно читать, но нельзя менять и удалять (на вкладке Settings форма заблокирована, блока удаления нет) |
| **Channel → Overview** | скорость, p99, лаг, хранение, разделы |
| **Channel → Messages** | поле **Filter** на языке фильтров (`order_id = 8842 AND shipping.country = "DE"`, см. раздел 18): проверяется сервером на лету (`POST /api/filter/parse`), место ошибки подчёркивается по позиции из ответа сервера («Column 9: unexpected character '~'»), меню **Examples** подставляет примеры из полей реальных сообщений, в заголовке результатов — сколько сообщений просканировано (поиск без индекса); кнопка **Create route from filter**; поиск по key, разделу и offset, по времени (Latest / 15 min / 1 h / 24 h / custom); справа инспектор: JSON payload, метаданные (offset, partition, producer, trace), **Replay**, **Copy**, **retry timeline** по каждой группе; режим **Live tail** с паузой |
| **Channel → Consumers** | группы и их инстансы, медленный инстанс помечен с причиной (например «processing p99 3.6× group median»); **Inspect** показывает CPU, память, последнюю ошибку и разделы; **Reset offsets**; у группы без подключённых консьюмеров — **Delete group** (роль admin, с подтверждением) |
| **Channel → Routing** | маршруты, читающие этот канал, и блок «Routed here from» — маршруты, которые пишут в него |
| **Channel → Storage / Settings** | сегменты и offset'ы; изменение retention, retry и DLQ; удаление канала |
| **Consumers** | все группы всех каналов, сначала проблемные. Системная группа маршрутизатора `$router` подписана как «System · router» со ссылкой на маршруты. Группы HTTP-вебхуков `$webhook:<имя>` подписаны как «System · webhook» со ссылкой **View webhook**. В кластере у инстанса есть колонка **Node** (id инстанса имеет вид `n2/worker#7`). Те же действия **Reset offsets** и **Delete group**, что на вкладке канала |
| **Routing** | все маршруты: источник → цели, условие WHEN, счётчики matched / forwarded / failed с темпом в секунду, время последнего совпадения, переключатель Enabled. Редактор маршрута: FROM (источник; после создания не меняется), WHEN — строки «поле · оператор · значение» с автодополнением полей из последних 100 сообщений источника (`key`, `partition`, `header.<имя>`, пути в JSON вроде `shipping.country`; список операторов зависит от типа поля) или режим **Text** с тем же условием на языке фильтров (переключение: текст → строки через `POST /api/filter/parse`, строки → текст через `POST /api/filter/render`; под строками видна строка «As text: …»), THEN — каналы-цели (источник выбрать нельзя). Справа (на узком экране — под редактором) живой **Preview**: «Matched last 24h: 714 of 59.8K scanned», окно 1 h / 24 h / 7 d, примеры совпавших сообщений (клик открывает их в инспекторе), пометка, если упёрлись в лимит сканирования, и напоминание, что маршрут обрабатывает только новые сообщения. Под редактором — счётчики маршрута: Evaluated, Matched, Forwarded (**по каждой цели**), Failed, Last match |
| **Webhooks** (v0.3) | HTTP push: брокер сам POST'ит сообщения канала на ваш URL. Список: имя, канал → хост URL, Delivered / Failed / Skipped (отфильтровано) — счётчики по всему кластеру, p99 задержки, последний HTTP-статус (цветом выделяются только ошибки: 5xx/429/408 — красным, прочие 4xx — жёлтым), In flight, кнопка **Test**; падающий вебхук подсвечен, рядом ссылка на его dead letters. Бейдж в боковой панели — сколько вебхуков сейчас падают. Редактор: имя (`[a-z0-9._-]`, становится группой `$webhook:<имя>`, после создания не меняется), канал (не меняется), URL, формат **Envelope (JSON)** или **Raw body** (raw ⇒ batch = 1, поля батча блокируются), секрет подписи и заголовки — секреты: после сохранения показываются как «••••••••» с **Replace**/**Keep stored**; фильтр — тот же построитель WHEN, что в маршрутах (строки или текст на языке фильтров); Timeout (100–60000 мс и меньше ack timeout канала), Max in flight (1–64; 1 = строгий порядок), Batch size (1–500), Batch linger (0–10000 мс), «Retry 4xx too», Start from (новые / самые старые / с момента; только при создании). Справа: **Send test** (статус, задержка, начало ответа; для нового вебхука тестируется черновик через `POST /api/webhooks/test`; у сохранённого — его текущее состояние в редакторе, включая несохранённые правки: они уходят телом `POST /api/webhooks/{id}/test` в форме `UpdateWebhookRequest` и накладываются на сохранённую подписку, `********` = сохранённый секрет, ничего не сохраняется). Ошибки показываются коротко — `HTTP 503`, `timeout`, `connection refused`, `TLS error`, `DNS error`, `blocked by policy`; полный текст причины — во всплывающей подсказке, счётчики, ссылки на группу `$webhook:<имя>` и на DLQ канала, пример envelope (или массива при batch > 1) и копируемый код проверки подписи `X-FluxMQ-Signature` на Node и Python |
| **Dead Letters** | «почтовый ящик ошибок»: сообщения сгруппированы по причине (PostgreSQL timeout, HTTP 503, …); **Retry all / Retry selected / Discard / Export** |
| **Alerts** | открытые алерты: что случилось, возможная причина, кнопка **Inspect** |
| **Nodes** | один узел: карточка с CPU, памятью, диском, fsync p99 и соединениями и подсказка «Single-node mode». Кластер (раздел 19): сводка (узлы up — все, кто не `Down`, контроллер и терм Raft, фактор репликации, under-replicated и offline разделы, журнал Raft), карточки узлов (статус Up/Down/Joining/Leaving — цветом выделяется только не-Up, бейдж controller, voter/learner, адреса, число лидерств и реплик, **Drain leadership**), матрица «каналы × разделы», окрашенная по узлу-лидеру: жёлтая рамка — under-replicated, штриховка — offline, клик по разделу — **Reassign** (выбор реплик и предпочтительного лидера). Обновляется каждые 2 с |
| **Settings → General** | ваш токен доступа, тема (тёмная или светлая), **язык интерфейса** (русский / English), версия, адрес `/metrics` для Prometheus |
| **Settings → Access tokens** | кто вы (имя токена и роль, **Sign out**), список токенов (имя, роль, scopes, создан и кем, последнее использование, срок), **New token** (имя, роль, глобы каналов для publish/consume, срок 7/30/90 дней, год или без срока), секрет показывается **один раз** с кнопкой Copy, **Revoke** с подтверждением. В open mode кнопка называется **Create admin token**, а роль заблокирована на admin |
| **Settings → Notifications** (v0.3) | **Notifiers** — куда слать: Telegram (bot token, chat id, необязательный topic; встроенная подсказка «How to get the chat id» через `getUpdates`), Slack и Discord (webhook URL), Email (SMTP-хост, порт, STARTTLS/TLS/None, логин, пароль, From, список To), PagerDuty (routing key, инциденты открываются и закрываются по id алерта), Webhook (URL, секрет подписи, заголовки). В списке: иконка типа, имя и адресат, последняя доставка (Sent/Failed + время и ошибка), переключатель Enabled, **Send test** (тост с задержкой или ошибкой). Секреты сервер никогда не возвращает: поле показывается как «••••••••» с **Replace** (а у необязательных — удалить); при сохранении без замены уходит `********`, и сервер оставляет старое значение. В диалоге создания **Send test** проверяет черновик (`POST /api/notify/notifiers/test`), в диалоге правки — то, что сейчас в форме: несохранённые правки уходят телом `POST /api/notify/notifiers/{id}/test` (форма `UpdateNotifierRequest`, `********` = сохранённый секрет) и ничего не сохраняют. Ошибки везде короткие (`connection refused`, `timeout`, `HTTP 503`, `TLS error`, `DNS error`), полный текст — во всплывающей подсказке. **Rules** — что куда: имя, notifiers (несколько), минимальная серьёзность алертов (Warning/Critical — только для алертов), виды алертов и события брокера (чипсы; события по умолчанию выключены), глобы каналов с подсказкой «Matches N channels today», group wait (none/10 s/30 s/1 min/5 min), повтор открытых алертов (Never/1/4/12/24 h), сообщение о восстановлении; переключатель Enabled в списке. **Delivery history** — последние 1000 отправок: время, статус (sent/failed/suppressed), notifier и правило, текст, ошибка, число попыток; фильтр Failed. Пустая страница учит: «Get alerts in Telegram in 1 minute». Блок **External systems (pull API)**: что всё то же самое пишется в системный канал `$system.events`, пример `curl`, который один раз берёт последние записи (`?tail=20`), а дальше ждёт новые long-poll'ом (`/api/events/feed?after=<cursor>&wait_ms=25000`), совет завести viewer-токен с consume scope `$system.events`, и живой список последних элементов ленты (стартует с `?tail=6`, дальше — `after=<next_cursor>`) |
| **Settings → Backups** (v0.3) | **Status**: настроено ли и включено ли расписание, идущий бэкап с прогрессом (`progress_bytes / total_bytes`, сколько сегментов переиспользовано и загружено), последний успех (давность, размер, длительность), последняя ошибка, следующий запуск; кнопка **Run now**. **Target & schedule**: S3-совместимое хранилище (пресеты AWS S3 / MinIO / Cloudflare R2: endpoint, region, bucket, prefix, path-style, access key id, secret access key — секрет) или путь в файловой системе; **Test connection** (запись, чтение и удаление пробного объекта через `POST /api/backups/test-target`); интервал (15 min / hourly / 6 h / daily), сколько хранить (последние N и не старше D дней), включать ли сообщения; шифрование AES-256-GCM с кнопкой **Generate** (случайный ключ показывается один раз, с Copy) и красным предупреждением «Store this key safely — without it backups can't be restored» — без галочки «I have stored this key» сохранить нельзя; выключение шифрования удаляет сохранённый ключ. **History**: id, триггер (scheduled/manual/cli), статус, начало, длительность, размер и сколько загружено, полоса «incremental savings» (доля переиспользованных сегментов), **Restore…**, удаление с подтверждением. В кластере сверху пояснение: бэкапы выполняет контроллер, каждый раздел загружает его лидер, restore создаёт одиночный узел. **Restore**: где снят бэкап (узел-контроллер), «Partition data from» — узлы, загрузившие данные разделов, состав, шифрование, раскрывающаяся таблица каналов (разделы, сообщения до среза, размер, сегменты, группы, DLQ), шаги и готовая команда `fluxmq restore` для выбранного бэкапа (флаги цели, `--backup <id>`, `--data-dir`, ключи AWS и `FLUXMQ_BACKUP_ENCRYPTION_KEY` — через переменные окружения), плюс команда `fluxmq backup list` |

**Роли в консоли.** При старте консоль спрашивает `GET /api/auth/me`; имя токена и роль видны
внизу боковой панели. Кнопки, недоступные вашей роли, не прячутся, а становятся неактивными с
подсказкой «Requires operator or admin role» (viewer не может повторять DLQ, делать replay и
reset offsets; operator — менять каналы, маршруты, токены и кластер). Уведомления, вебхуки и
бэкапы (v0.3) все роли видят, а менять, тестировать и запускать их может только admin — для
остальных сверху страницы полоса «Read-only — … requires the admin role». Если сервер всё же ответит
403, появится сообщение «Your role (viewer) can't do this»; на 401 консоль попросит токен.

Пока токенов нет (open mode), сверху висит предупреждение «Auth disabled — anyone can administer
this broker». Кнопка **Create admin token** создаёт первый токен: роль только admin (сервер
отвечает 400 на любую другую), имена `admin` / `anonymous` зарезервированы. Сервер сразу
переходит в enforced и отвечает `"adopt": true` — по этому признаку консоль сохраняет новый
токен в браузере, чтобы вы не потеряли доступ. Секрет всё равно скопируйте — он показывается
один раз.

В шапке под именем кластера — «N/M nodes up» (`nodes_up` из телеметрии: узлы, которые не
`Down`; узел в `Leaving` после drain тоже считается up) и общее здоровье цветом точки и
словом (Healthy / Warning / Critical). В кластере добавляется «· N under-replicated» или
«· N offline», а при неполной телеметрии — «partial data».

**Горячие клавиши:**

- `⌘K` (Mac) или `Ctrl+K` — палитра команд: «Open orders channel», «Search messages in…», «Open DLQ», «Create channel», «Create route», «Go to Routing», «Create access token», «Create webhook», «Add Telegram notifier», «Run backup now» (запускает бэкап и открывает Settings → Backups), «Go to Webhooks / Notifications / Backups»… Если набрать условие (`total > 500`), палитра предложит «Search messages in orders.events where total > 500» для каждого канала, начиная с открытого.
- `↑↓` или `j/k` — навигация по списку сообщений.

**LIVE / PAUSED** (вверху справа) замораживает картинку, чтобы спокойно разобрать данные.
Сбор данных в это время не останавливается.

При потере связи сверху появляется баннер с обратным отсчётом до переподключения.
Подписки восстанавливаются автоматически.

## 7. Каналы и режимы

| Режим | Для чего | Как распределяются сообщения в группе | Хранение |
|---|---|---|---|
| **Stream** | «хранить события и перечитывать их позже» | разделы распределяются между инстансами группы | по retention, перечитывание с любого offset'а |
| **Queue** | «раздать задачи воркерам» | конкурирующие консьюмеры: следующую задачу берёт любой свободный | сообщение считается обработанным после ack всеми группами |
| **Keyed** | «сохранить порядок по клиенту или заказу» | строгий порядок по ключу: следующее сообщение ключа K не выдаётся, пока предыдущее не подтверждено | по retention |

Во всех режимах **каждая consumer group получает все сообщения** (fan-out). Доставка at-least-once,
поэтому обработчики должны быть идемпотентными.

Раздел выбирается так: `crc32(key) % partitions` (у одного ключа всегда один раздел).
Сообщения **без ключа** с 0.6 распределяются «липко» (sticky): все бесключевые сообщения одного
запроса publish (до ~1 MiB, дальше — следующий раздел) попадают в один раздел, а следующий
запрос — в следующий раздел по кругу. Нагрузка выравнивается по разделам со временем, а не
сообщение за сообщением; зато запрос стоит один fsync, а не по одному на каждый раздел.
Порядок сообщений без ключа никогда не гарантировался; внутри одного запроса они теперь лежат
подряд в одном разделе.

**Как создать канал:**

- **В UI** — кнопка *Create channel*. Мастер спросит «What do you need?» и сам подскажет режим.
  Тонкие настройки спрятаны в *Advanced*.
- **Через REST** — раздел 9.
- **Через SDK** — `client.ensure_channel(ChannelConfig::new("orders", ChannelMode::Stream))`.

Правила для имени: 1–128 символов `[a-zA-Z0-9._-]`, не начинается с `.` и не заканчивается
на `.consumers` или `.tail`.

**Параметры по умолчанию:**

| Параметр | Значение |
|---|---|
| разделы | 8 для stream и keyed, 1 для queue |
| retention | 7 дней |
| повторы | 5 попыток, backoff 1 с → 10 с → 60 с → 300 с |
| ack timeout | 30 с |
| DLQ | включена |

### Готовые связки

Для типовых задач есть готовые рецепты «режим + точные настройки канала + группы, маршруты,
вебхуки» с командами для консоли, REST и SDK: заказы со строгим порядком (`keyed`), фоновые
задачи пулом воркеров (`queue`, повторы, DLQ), журнал событий и аудит (`stream`, перемотка),
fan-out на несколько сервисов, маршрутизация по содержимому, push во внешний HTTP, отложенный
повтор и «ядовитые» сообщения, сбор телеметрии (пачки, сжатие, cumulative). Они лежат во
встроенной документации консоли: **Документация → Готовые связки (рецепты)** (`/docs/recipes`),
исходник — [ui/src/docs/content/ru/recipes.md](../ui/src/docs/content/ru/recipes.md).

## 8. Отправка и чтение сообщений (Rust SDK)

Подключите SDK в `Cargo.toml` своего сервиса. Пока он подключается по пути, в crates.io не опубликован:

```toml
[dependencies]
fluxmq-client = { path = "../FluxMQ/crates/fluxmq-client" }
fluxmq-proto  = { path = "../FluxMQ/crates/fluxmq-proto" }
tokio = { version = "1", features = ["full"] }
```

### Продюсер

```rust
use fluxmq_client::{message, Client, ClientOptions};
use fluxmq_proto::{ChannelConfig, ChannelMode};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let mut opts = ClientOptions::new("127.0.0.1:7420", "order-api-1");
    opts.auth_token = std::env::var("FLUXMQ_TOKEN").ok();   // если включена авторизация
    let client = Client::connect(opts).await?;

    client.ensure_channel(ChannelConfig::new("orders", ChannelMode::Stream)).await?;

    let producer = client.producer("orders");
    let id = producer
        .send(
            message(r#"{"order_id":8842,"amount":129.9,"currency":"EUR"}"#)
                .key("8842")                     // порядок и раздел по ключу
                .event_type("OrderCreated")      // заголовок flux-type, виден в UI
                .content_type("application/json")
                .new_trace_id(),                 // flux-trace-id
        )
        .await?;
    println!("partition {} offset {}", id.partition, id.offset);
    Ok(())
}
```

Для высокой нагрузки есть `client.batching_producer("orders", BatchingOptions::default())`. Он сам собирает сообщения в
пакеты и возвращает future на каждое сообщение. Linger адаптивный: если по партиции ничего
не в полёте, сообщение уходит сразу; ждать попутчиков пакет может, только пока предыдущий
запрос этой партиции не подтверждён. Заголовок `flux-producer` (имя клиента)
ставится автоматически, поэтому в инспекторе UI видно, кто отправил сообщение. Отключается
`ClientOptions::stamp_producer(false)`: минус один заголовок на сообщение в сети, на диске и
в каждой доставке.

Изменение в 0.6: можно держать в ожидании сколько угодно future от `send` (например, тысячи в
одном `FuturesUnordered`), стоимость на сообщение от этого не растёт (O(1)). В 0.5 future
расходовали кооперативный бюджет задачи tokio, и при ~20 тыс. неподтверждённых сообщений
пропускная способность падала в 4 раза.

SDK 0.7 работает с брокерами 0.4–0.7. Он предлагает протокол v4; если брокер его отвергает,
SDK сразу переходит на версию, которую брокер назвал в отказе (v3 для 0.6, v2 для 0.4/0.5;
если версия не названа, SDK спускается на одну ступень), запоминает её для адреса на 5 минут
и пишет об этом в лог один раз. После обновления брокера на месте следующее переподключение
снова получит v4. API одинаковый на всех версиях.

### Консьюмер

```rust
use fluxmq_client::{Client, ClientOptions, StartFrom, SubscribeOptions};

let client = Client::connect(ClientOptions::new("127.0.0.1:7420", "billing-worker-1")).await?;
let mut consumer = client
    .subscribe("orders", "billing",
        SubscribeOptions::default().prefetch(32).start(StartFrom::Earliest))
    .await?;

while let Some(delivery) = consumer.next().await {
    let delivery = delivery?;
    match handle(delivery.payload()).await {
        Ok(()) => delivery.ack().await?,
        // Причина видна в DLQ-инбоксе и группирует ошибки. Пишите коротко и стабильно.
        Err(e) if e.is_transient() => delivery.nack("PostgreSQL timeout", true).await?,  // повторить
        Err(_) => delivery.nack("Invalid schema", false).await?,                        // сразу в DLQ
    }
}
```

- `prefetch` — сколько неподтверждённых сообщений может одновременно находиться у инстанса.
- `start` действует только для **новой** группы: `Earliest`, `Latest` (по умолчанию) или `TimestampMs(..)`.
- Подтверждения копятся и уходят пачкой (одним кадром `Ack`): когда набралось `ack_batch`
  штук (по умолчанию 64, но не больше половины `prefetch` — иначе брокер остался бы без
  «кредита» и перестал присылать сообщения) или через `ack_linger` после первого
  неотправленного ack (по умолчанию `ClientOptions::ack_linger` = 1 мс). Настройка:
  `SubscribeOptions::default().ack_batch(128).ack_linger(Duration::from_millis(2))`;
  `ack_linger(Duration::ZERO)` — отправлять каждый ack сразу. Накопленные ack отправляются
  и при `unsubscribe()`, при удалении (drop) консьюмера и при `client.close()`. `nack`
  всегда уходит сразу.
- С брокером v0.5 SDK говорит по протоколу v3: брокер присылает готовые к доставке сообщения
  пачками (`DeliverBatch`), не дожидаясь, пока пачка наполнится, — задержка не растёт.
  Для кода приложения ничего не меняется: `consumer.next()` по-прежнему отдаёт по одному сообщению.
- SDK сам каждые 2 с отправляет статистику: время обработки, CPU, память, последнюю ошибку.
  Её показывают экран Consumers и Inspect.

### Быстрый путь (брокер 0.7+, протокол v4): пачки, сжатие и режимы подтверждения

**Пачки записей.** `BatchingProducer` складывает сообщения каждой партиции в один буфер, пока
пачка ждёт (adaptive linger), и отправляет её одним `PublishBatch`. Брокер дописывает пачку в
лог как есть и не разбирает отдельные сообщения. Надёжность та же: ответ приходит после fsync
(group commit) и, в кластере, после репликации на ISR. Партиция всегда указывается явно, как
только SDK знает число партиций (из метаданных, в том числе на одном узле). Сообщения с ключом
идут в партицию своего ключа (`crc32(key) % partitions`). Сообщения без ключа «прилипают» к
одной партиции, пока её пачка не уйдёт, затем переходят на следующую. Так пачки крупнее, чем
при раздаче по кругу, а нагрузка со временем распределяется так же. Консьюмер получает
сохранённые пачки целиком (`DeliverRecords`) и разбирает их лениво: payload — срез принятого
кадра, без копирования. Код приложения не меняется: `consumer.next()` отдаёт по одному
`Delivery`.

**Сжатие** — на уровне клиента, для каждой пачки:

```rust
use fluxmq_client::{ClientOptions, Compression};
let opts = ClientOptions::new("127.0.0.1:7420", "ingest-1").compression(Compression::Lz4);
```

| Вариант | Когда выбирать | Цена |
|---|---|---|
| `None` (по умолчанию) | маленькие или уже сжатые/зашифрованные payload, минимальная задержка | — |
| `Lz4` | JSON, логи, текст; сеть или диск — узкое место | немного CPU продюсера, распаковка у консьюмера очень дешёвая |
| `Zstd` (уровень 1) | максимум экономии трафика и места (репликация, долгая retention) | больше CPU, чем у lz4, у обеих сторон |

Продюсер сжимает пачку один раз. Брокер хранит, реплицирует и отдаёт её сжатой, а распаковывает
только для функций, которым нужно содержимое: фильтров, инспектора сообщений, поиска. Если
пачка от сжатия не уменьшилась, она уходит несжатой. С брокерами до 0.7 настройка
игнорируется.

**Режимы подтверждения** (`SubscribeOptions::ack_mode`):

- `AckMode::Individual` (по умолчанию) — каждое сообщение подтверждается отдельно (`ack`
  или `nack`). Работают повторная доставка, ack timeout, nack с повтором и DLQ. Подряд
  идущие подтверждения SDK отправляет диапазонами (`AckRanges`), поэтому подтверждение целой
  пачки занимает несколько байт.
- `AckMode::Cumulative` (только stream-каналы) — консьюмер фиксирует позицию в каждой
  партиции. `delivery.ack()` фиксирует всё до этого сообщения включительно в его партиции,
  `consumer.commit().await` — всё, что консьюмер уже получил, и ждёт подтверждения брокера.
  Фиксации копятся и уходят так же, как ack (`ack_batch` / `ack_linger`). Это самый дешёвый
  режим, но `nack`, ack timeout и DLQ в нём не работают: `nack` возвращает `BadRequest`.
  После падения или ребаланса доставка продолжается с последней зафиксированной позиции.
  Это по-прежнему at-least-once, но все сообщения после неё придут повторно. Подтверждайте
  сообщение только после того, как обработаны все предыдущие в той же партиции.

```rust
let mut consumer = client
    .subscribe("clicks", "analytics",
        SubscribeOptions::default().prefetch(2000).cumulative())
    .await?;
while let Some(d) = consumer.next().await {
    let d = d?;
    process(&d).await?;
    d.ack().await?;            // фиксирует партицию до d включительно
}
```

С брокером до 0.7 cumulative-режим эмулируется обычными подтверждениями: семантика и API те
же, но без экономии.

Остальные опции консьюмера: `raw_records(false)` — получать сообщения по одному, как в 0.6
(нужно редко); `prefetch_bytes(n)` — дополнительно ограничить объём неподтверждённого в байтах;
`verify_crc(false)` — не проверять CRC-32C пачек (по умолчанию проверка включена). Проверка
аппаратная, и её цена в замерах в пределах шума. При несовпадении CRC SDK разрывает
соединение и переподключается, а брокер доставляет пачку заново.

Готовые примеры:

```bash
cargo run -p fluxmq-client --example producer -- 127.0.0.1:7420 10
cargo run -p fluxmq-client --example consumer -- 127.0.0.1:7420
```

### Переподключение и кластер

Клиент сам восстанавливает соединения. Перезапуск брокера, обрыв сети или смена лидера
раздела в кластере не требуют кода в приложении.

**Адреса (seeds).** Укажите один или несколько адресов брокеров. Клиент подключается к первому
доступному, загружает метаданные кластера (узлы и лидеры разделов) и затем сам открывает
соединения с нужными узлами. Одиночный брокер без поддержки кластера отвечает на `Metadata`
ошибкой `BadRequest`. Тогда клиент работает как в v0.1: всё идёт через одно соединение,
раздел выбирает брокер.

```rust
use std::time::Duration;
use fluxmq_client::{Client, ClientOptions, ConnectionState, ReconnectPolicy};

let opts = ClientOptions::with_seeds(
        ["10.0.0.1:7420", "10.0.0.2:7420", "10.0.0.3:7420"],
        "order-api-1",
    )
    // Экспоненциальная задержка 100 мс → 5 с с разбросом ±20 %, попытки без ограничения
    .reconnect(
        ReconnectPolicy::default()
            .backoff(Duration::from_millis(100), Duration::from_secs(5))
            .jitter(0.2)
            .max_attempts(None)              // Some(n) — сдаться после n неудачных попыток
            .retry_initial_connect(true),    // ждать брокер и при первом подключении
    )
    .publish_timeout(Duration::from_secs(30))           // общий срок publish с повторами
    .metadata_refresh_interval(Duration::from_secs(30)); // плюс обновление по событиям
let client = Client::connect(opts).await?;

// Состояние соединения: Connecting → Connected ⇄ Reconnecting → Closed
let mut state = client.state();
tokio::spawn(async move {
    while state.changed().await.is_ok() {
        let s: ConnectionState = *state.borrow();
        tracing::info!("fluxmq: {s:?}");
    }
});
println!("переподключений: {}", client.reconnects());
```

Адрес можно задать и строкой через запятую: `ClientOptions::new("n1:7420,n2:7420", "svc")`.
`ReconnectPolicy::disabled()` выключает переподключение (поведение v0.1): первый же обрыв
закрывает клиент.

**Как ведёт себя publish.**

- Раздел вычисляется на клиенте той же функцией, что и в брокере: `crc32(key) % partitions`,
  а без ключа по кругу (round-robin). Сообщение уходит прямо лидеру раздела
  (`partition: Some(p)`), пакет делится по разделам.
- Обрыв соединения, таймаут запроса, `NotLeader` и `Overloaded` (в том числе «not enough
  replicas») повторяются, пока не истечёт `publish_timeout`. Между попытками клиент обновляет
  метаданные. `BadRequest`, `Forbidden` и `Unauthorized` не повторяются никогда.
- **Повтор может создать дубликат.** Брокер мог успеть сохранить пакет, а ответ потерялся
  вместе с соединением. Доставка в FluxMQ работает по принципу at-least-once, поэтому
  обработчики должны быть идемпотентными, например по бизнес-ключу.
- В `BatchingProducer` пакеты собираются по разделам. С `BatchingOptions { ordered: true, .. }`
  у каждого раздела в полёте не больше одного пакета. Так порядок сообщений с одним ключом
  сохраняется и при повторах.

**Как ведёт себя консьюмер.**

- В кластере консьюмер подписывается на каждом узле, который лидирует хотя бы в одном разделе
  канала, и сливает доставки в один поток. `ack`/`nack` уходят на тот узел, который прислал
  сообщение (`delivery.node_id()`).
- После переподключения или `MetadataChanged` подписка восстанавливается сама: та же группа,
  `start` для существующей группы игнорируется. Сообщения из буфера старой подписки
  отбрасываются, брокер доставит их заново. `ack` для них ничего не делает и пишет запись в
  debug-лог.
- Поток возвращает `Err` и завершается только при неисправимых ошибках: `Forbidden`, канал
  удалён (`NotFound`), клиент закрыт или исчерпал попытки переподключения.

Проверить это вживую можно примером `resilience`. Он публикует нумерованные сообщения и
в конце проверяет, что ни одно подтверждённое сообщение не потерялось. Пока он работает,
убивайте и перезапускайте брокер:

```bash
cargo run -p fluxmq-client --example resilience -- 127.0.0.1:7420 60
# в другом терминале: kill -9 <pid брокера>, затем запустить его с тем же --data-dir
```

`fluxmq-demo` и `fluxmq-bench` принимают `--seeds n1:7420,n2:7420` (или `FLUXMQ_SEEDS`)
и продолжают работу при перезапуске брокера. Бенчмарк выводит число переподключений.

## 9. REST API: примеры curl

Полный список маршрутов — в [ARCHITECTURE.md → HTTP routes](ARCHITECTURE.md#http-routes-fluxmq-api).
Если включена авторизация, добавляйте `-H "Authorization: Bearer $TOKEN"`.

```bash
H=http://localhost:7421

# Создать канал
curl -s -X POST $H/api/channels -H 'content-type: application/json' \
  -d '{"name":"orders","mode":"stream","partitions":8}'

# Опубликовать сообщение (payload: utf8-текст или base64)
curl -s -X POST $H/api/channels/orders/publish -H 'content-type: application/json' -d '{
  "messages":[{"key":"8842","headers":{"flux-type":"OrderCreated"},
               "payload":{"encoding":"utf8","data":"{\"order_id\":8842}"}}]}'

# Найти сообщения по ключу (самые новые)
curl -s "$H/api/channels/orders/messages?key=8842&limit=20&newest_first=true"

# Одно сообщение и история его доставок (retry timeline): раздел/offset — из ответа publish,
# например {"ids":[{"partition":5,"offset":0}]} (ключ 8842 всегда попадает в раздел 5 из 8)
curl -s $H/api/channels/orders/messages/5/0

# Сводка DLQ по причинам и повтор всех сообщений одной причины
curl -s $H/api/dlq/summary
curl -s -X POST $H/api/dlq/retry -H 'content-type: application/json' \
  -d '{"reason":"PostgreSQL timeout"}'

# Выгрузить DLQ в NDJSON
curl -s "$H/api/dlq/export?channel=orders" > dlq.ndjson

# Перемотать группу на начало (группа должна существовать, иначе 404;
# "to": "earliest" | "latest" | {"timestamp_ms": 1791380000000}; ответ 204)
curl -s -X POST $H/api/channels/orders/groups/billing/reset \
  -H 'content-type: application/json' -d '{"to":"earliest"}'

# Удалить группу без консьюмеров (роль admin; 204). 409 — если к группе подключены
# консьюмеры или это `$router` канала, у которого есть маршруты; 404 — группы нет
curl -s -X DELETE $H/api/channels/orders/groups/billing

# История метрики для графика
curl -s "$H/api/history?metric=ingress_rate&range=15m"

# Открытые алерты и журнал действий
curl -s $H/api/alerts
curl -s "$H/api/audit?limit=20"
```

Ошибки всегда приходят как JSON `{"error": "...", "message": "..."}`. У синтаксических ошибок
языка фильтров (раздел 18) есть ещё поле `position` — смещение ошибки в байтах:

```bash
curl -s -X POST $H/api/filter/parse -H 'content-type: application/json' -d '{"filter":"country ~ MD"}'
# {"error":"bad_request","message":"filter syntax error at 8: unexpected character '~'","position":8}
```

### Живая подписка из браузера: WebSocket и SSE (v0.10)

Браузер, мобильное приложение или устройство могут читать канал в реальном времени прямо с HTTP-порта
брокера, без SDK и без своего бэкенда. Подписка только читает: consumer group не создаётся, ничего не
коммитится, другие консьюмеры ничего не замечают. Видно ровно то, что увидел бы обычный консьюмер
(подтверждённые, надёжно записанные сообщения).

```js
// SSE: проще всего, браузер сам переподключается и продолжает с места обрыва (Last-Event-ID)
const es = new EventSource('/api/channels/orders/events?from=latest&key=user_42&access_token=' + token);
es.addEventListener('messages', (e) => {
  for (const m of JSON.parse(e.data).messages) console.log(m.offset, m.payload);
});

// WebSocket: несколько подписок в одном соединении; токен — во втором подпротоколе
const ws = new WebSocket(`wss://${location.host}/api/channels/orders/live?from=earliest`,
                         ['fluxmq.live.v1', 'fluxmq.token.' + token]);
ws.onmessage = (e) => {
  const ev = JSON.parse(e.data);           // hello | messages | gap | reset | progress | error
  if (ev.type === 'messages') localStorage.cursor = ev.cursor;  // для продолжения: ?cursor=...
};
ws.onopen = () => ws.send(JSON.stringify({ op: 'subscribe', id: 'big', channel: 'orders',
                                           filter: 'amount >= 100' }));
```

- Откуда читать: `from=latest` (по умолчанию), `earliest`, `time:<unix ms>`, `offsets:0=10,1=20`; `cursor=` из
  последнего события продолжает без потерь и без повторов.
- Фильтры на сервере: `key=a,b`, `header.type=order.created`, `filter=<язык фильтров>`.
- Токены для браузера: роль `subscriber` — может только подписываться на каналы из `scopes.subscribe`, никаких
  других прав. Выдавайте короткоживущие токены (`ttl_secs`) со своего бэкенда:
  `{"name":"web-user-42","role":"subscriber","ttl_secs":3600,"scopes":{"subscribe":["notifications.user42"]}}`.
- Чужие сайты по умолчанию не пустят (проверка `Origin`); разрешить: `--live-allowed-origins https://app.example.com`.
- Лимиты и настройки: флаги `--live-*` (`fluxmq --help`), метрики `fluxmq_live_*` в `/metrics`.

## 10. Повторы и Dead Letters

Путь сообщения:

```text
publish → доставка (attempt 1) ── ack ──────────────────────────► готово
                 │
                 ├─ nack(retry=true) или нет ack за ack_timeout
                 ▼
          ждём backoff[attempt-1] → attempt 2 → … → attempt = max_attempts
                 │                                        │
                 └─ nack(retry=false) ────────────────────┴──► DLQ (reason = последняя причина)
```

**Работа с DLQ в консоли (Dead Letters):**

1. Сообщения сгруппированы по причине. Кликните на причину, например *PostgreSQL timeout*.
2. Откроется список сообщений. По каждому видны канал, группа, ключ, время и попытки,
   по клику — инспектор и retry timeline.
3. Доступные действия:
   - **Retry all N** / **Retry selected** — вернуть сообщения исходной группе с новым бюджетом попыток;
   - **Discard** — удалить;
   - **Export** — скачать NDJSON.

Удобный порядок разбора: сначала устранить причину (например, поднять PostgreSQL),
затем нажать *Retry all*.

## 11. Безопасность

По умолчанию авторизация **выключена** (режим разработки, CORS открыт). Для любого окружения,
доступного по сети, задайте токен:

```bash
./target/release/fluxmq --admin-token "$(openssl rand -hex 32)"
# или FLUXMQ_ADMIN_TOKEN=...
```

С токеном:

- **REST** требует заголовок `Authorization: Bearer <token>`. Без токена доступен только `/api/health`.
- **WebSocket** принимает токен в заголовке или параметром `?token=` (консоль делает это сама).
- **Клиенты SDK** передают токен через `opts.auth_token`. Demo и bench берут его из `--token`
  или переменной `FLUXMQ_TOKEN`.
- **Веб-консоль** при первом ответе 401 попросит токен и сохранит его в браузере
  (поменять можно в *Settings*).
- Все изменяющие действия (создание и удаление каналов, retry/discard в DLQ, replay, reset)
  пишутся в **audit log**: `GET /api/audit` и файл `<data-dir>/audit.log`.

> Не открывайте порты 7420 и 7421 в интернет без токена и TLS — встроенного (раздел 24) или
> TLS-прокси (nginx, Caddy) перед ними.

**Шифрование и mTLS** (с 0.4, раздел 24): `--tls-cert`/`--tls-key` включают TLS на
клиентском порту и HTTPS на 7421, `--tls-client-ca` требует от клиентов сертификат (mTLS),
`--cluster-tls-*` шифрует трафик между узлами. Сам по себе mTLS — это проверка «кто
подключился», а не права: роль и scope задаёт токен. С 0.5 можно выдать права и самому
сертификату — **привязкой сертификата** (CN → роль и scopes, раздел 24); тогда клиенту токен
не нужен. Токен и TLS дополняют друг друга.

### Токены доступа (роли)

Кроме bootstrap-токена `--admin-token` можно выпускать именные **токены доступа** с ролью:

| Роль | Что разрешено |
|---|---|
| `viewer` | всё чтение: REST GET, WebSocket-телеметрия, просмотр сообщений |
| `operator` | + retry/discard/выгрузка DLQ, replay, сброс оффсетов, публикация через REST; в протоколе — публикация и чтение любых каналов |
| `admin` | + создание/изменение/удаление каналов, удаление consumer group, маршруты, токены, операции кластера |

Для сервисов есть **scopes** — маски каналов (`*` — любые символы, `?` — один символ), по
которым токен с ролью `viewer` может публиковать (`publish`) и читать (`consume`) через
клиентский протокол.

```bash
# Выпустить токен (нужна роль admin). Секрет показывается ОДИН раз — сохраните его.
curl -s -X POST localhost:7421/api/auth/tokens \
  -H "Authorization: Bearer $ADMIN" -H 'Content-Type: application/json' \
  -d '{"name":"orders-svc","role":"viewer",
       "scopes":{"publish":["orders.*"],"consume":["orders.eu"]},
       "ttl_secs":2592000}'
# {"token":"fmq_k3x9...._9f2c...","info":{"id":"k3x9....","name":"orders-svc",...}}

# Кто я (роль, режим open/enforced)
curl -s localhost:7421/api/auth/me -H "Authorization: Bearer $TOKEN"

# Список токенов (без секретов) и отзыв
curl -s localhost:7421/api/auth/tokens -H "Authorization: Bearer $ADMIN"
curl -s -X DELETE localhost:7421/api/auth/tokens/<id> -H "Authorization: Bearer $ADMIN"
```

Что важно знать:

- Брокер хранит только SHA-256 секрета (`<data-dir>/meta.json`, в кластере — реплицируется);
  потерянный токен восстановить нельзя — выпустите новый и отзовите старый.
- Если `--admin-token` не задан, первый выпущенный токен **включает авторизацию** (без токена
  больше ничего не доступно, CORS закрывается). Поэтому первый токен **обязан** иметь роль
  `admin` — на любую другую сервер отвечает 400. В его ответе `"adopt": true` (консоль
  сохраняет такой токен у себя). Отозвать последний токен без `--admin-token` нельзя (400) —
  брокер снова стал бы открытым.
- Имена `admin` и `anonymous` (в любом регистре) зарезервированы.
- Все `GET` доступны роли viewer, кроме двух: выгрузка DLQ `GET /api/dlq/export` (operator —
  это массовая выгрузка payload), список токенов `GET /api/auth/tokens` и список привязок
  сертификатов `GET /api/auth/cert-bindings` (admin). Удаление consumer group — admin.
- Ответ `401` — токена нет, он неверный или истёк; `403` (`"error":"forbidden"`) — токен
  верный, но роли/scopes не хватает. В клиентском протоколе это ошибка `Forbidden`,
  соединение при этом не рвётся.
- **Отзыв и истечение срока закрывают живые сессии** (с 0.5). Каждое соединение клиентского
  протокола и каждая WebSocket-сессия помнят токен, с которым вошли. Когда токен отзывают
  (`DELETE /api/auth/tokens/<id>`) или у него истекает `ttl_secs`, брокер не позже чем через
  1 секунду закрывает их: клиент протокола получает `Goodbye` с причиной `token revoked` или
  `token expired` (SDK показывает `broker goodbye: token revoked`), WebSocket закрывается с
  кодом **4401** и той же причиной. Это работает во всём кластере: токены хранятся в
  реплицируемых метаданных, и каждый узел следит за ними сам — отзыв через `n1` обрывает
  сессии на `n2`. Повторное подключение с этим токеном получает `Unauthorized`. Сессии
  bootstrap-токена `--admin-token` и открытого режима (без токенов) это не затрагивает.
  REST-запросы проверяются при каждом запросе, как и раньше.
- **Последний администратор.** Если `--admin-token` не задан, отозвать последний действующий
  (не истёкший) токен с ролью `admin`, пока есть другие токены, нельзя: ответ
  `409 {"error":"last_admin", ...}`. Сначала выпустите другой admin-токен. Истёкшие
  admin-токены не считаются. Отзыв самого последнего токена по-прежнему отклоняется с 400.
  Защита работает и при одновременном отзыве двух последних админов через разные узлы
  кластера: один из запросов получит 409.
- В audit log действие записывается от имени `имя#id` токена (bootstrap-токен — `admin`,
  привязка сертификата — `cert:<cn>`).

## 12. Мониторинг и алерты

Консоль показывает четыре главных сигнала: **HEALTH / TRAFFIC / LAG / ERRORS**.
Цветом выделяется только то, что действительно требует внимания.

**Здоровье группы:**

- **Critical**:
  - есть лаг, но нет ни одного консьюмера;
  - лаг вырос больше чем в 10 раз и превысил 10k за 5 минут;
  - 30 секунд нет ни одного ack при наличии работы.
- **Warning**:
  - лаг больше 1k и растёт уже 60 секунд;
  - доля nack больше 5%;
  - DLQ росла за последние 5 минут.

**Алерты** открываются после трёх подряд неудачных проверок (раз в секунду) и закрываются
после десяти чистых. Это защищает от мигания. Виды алертов:

| Алерт | Когда открывается |
|---|---|
| рост лага | лаг группы быстро растёт |
| консьюмер завис | группа перестала подтверждать сообщения |
| нет консьюмеров | у группы с лагом нет инстансов |
| рост DLQ | в DLQ прибавляются сообщения |
| много повторов | высокая доля повторов |
| медленный инстанс | ack-rate инстанса меньше 50% медианы группы или его p99 больше чем втрое выше группового |
| мало места на диске | диск заполнен больше чем на 80% (warning) или 90% (critical) |
| высокая задержка публикации | p99 публикации больше 100 мс |

В кластере добавляются алерты **узел недоступен** (critical), **недореплицированные разделы**
(warning) и **офлайн-разделы** (critical, у раздела нет лидера); смена контроллера и
падение/возврат узла попадают в ленту событий. Все ссылки ведут на экран `/nodes`.

Для внешнего мониторинга:

- `GET /api/health` — liveness/readiness;
- `GET /api/alerts` — открытые алерты (JSON);
- `GET /api/history?metric=...&range=5m|15m|1h|24h|7d` — метрики;
- `GET /metrics` — метрики в формате Prometheus (text 0.0.4).

### Prometheus

`/metrics` есть на каждом узле и отдаёт **только метрики этого узла**: в кластере
перечислите в scrape-конфиге все узлы, а суммируйте уже в PromQL. Если включены токены,
нужен токен с любой ролью, хватит `viewer` (передаётся как Bearer).

```yaml
# prometheus.yml
scrape_configs:
  - job_name: fluxmq
    scrape_interval: 15s
    metrics_path: /metrics
    authorization:            # только если включены токены
      type: Bearer
      credentials_file: /etc/prometheus/fluxmq.token
    static_configs:
      - targets: ["fluxmq-1:7421", "fluxmq-2:7421", "fluxmq-3:7421"]
```

Полезные запросы:

```promql
# Публикаций в секунду по каналам (сумма по узлам)
sum by (channel) (rate(fluxmq_channel_published_messages_total[1m]))
# Лаг группы
sum by (channel, group) (fluxmq_group_lag_messages)
# p99 задержки публикации
histogram_quantile(0.99, sum by (le, channel) (rate(fluxmq_channel_publish_latency_seconds_bucket[5m])))
# Узлы, которые видят проблемы кластера
max(fluxmq_cluster_offline_partitions) > 0
```

Маршрутизатор отдаёт суммы по всем маршрутам узла: `fluxmq_router_routes`,
`fluxmq_router_evaluated_total`, `…_matched_total`, `…_forwarded_total`, `…_failed_total`.

Метки только `channel`, `group`, `node` (и `severity` у `fluxmq_alerts_open`) — число рядов
не растёт с числом консьюмеров. Задержки — гистограммы в секундах (корзины от 100 мкс до
60 с); `_sum` приблизительный (HDR-гистограмма не хранит точную сумму). Метрики
`fluxmq_cluster_*` (контроллер, недореплицированные/офлайн-разделы, Raft term) появляются
только в кластерном режиме. Полный список — в `docs/ARCHITECTURE.md`, раздел «Monitoring».

Консоль в кластере показывает **сводные** цифры: узел, к которому подключён браузер, раз в
секунду забирает компактную статистику остальных узлов (`/internal/v1/node-stats`, защищено
`--cluster-secret`) и суммирует её. Если узел не отвечает 3,5 с, он помечается как
недоступный, а цифры — как неполные (`partial`).

```bash
cargo build --release -p fluxmq-server -p fluxmq-client
```

дочитали всё.

## 14. Данные, остановка, восстановление

**Каталог данных** (`--data-dir`):

```text
data/
  node_id                    стабильный id узла
  channels/<канал>/
    channel.json             конфигурация канала
    offsets.json             offset'ы consumer groups (checkpoint раз в секунду)
    p0/, p1/, …              разделы: сегменты 000…000.log и sparse-индексы 000…000.idx
    …                        DLQ канала (появляется с первым dead letter)
  trash/                     удалённые каналы до фоновой очистки
  audit.log                  журнал действий (NDJSON)
```

**Остановка:** `Ctrl-C` или `SIGTERM`. Брокер останавливается корректно:

1. в кластере — передаёт лидерство разделов другим узлам и выходит из ISR (раздел 19), чтобы
   публикации на остальных узлах не ждали таймаута;
2. перестаёт принимать соединения;
3. отправляет клиентам `Goodbye`;
4. дописывает и fsync'ает данные;
5. сохраняет offset'ы.

Не используйте `kill -9` без необходимости.

**После сбоя** (питание, `kill -9`) брокер при старте сам проверяет хвост последнего сегмента
по CRC и отрезает недописанное. Offset'ы групп сохраняются раз в секунду, поэтому после аварии
часть уже подтверждённых сообщений (до 1 с) может прийти повторно. Это нормально для at-least-once.

**Резервная копия:** остановите брокер и скопируйте каталог данных целиком — или настройте
онлайн-бэкапы в S3 / на диск без остановки (раздел 22).

**Сброс всех данных:** остановите брокер и выполните `rm -rf data` (или `data-dev`).

## 15. Решение проблем

| Симптом | Причина и решение |
|---|---|
| `Address already in use` | порт 7420 или 7421 занят другим процессом (часто вторым экземпляром или `pnpm mock`). Найти его: `lsof -i :7421`. Либо смените адрес через `--http-addr` / `--client-addr` |
| По `http://localhost:7421` страница «UI is not built» | консоль не собрана: `cd ui && pnpm install && pnpm build`, затем проверьте `--ui-dir` |
| UI просит токен или REST отвечает 401 | брокер запущен с `--admin-token`: введите токен в консоли или передайте `Authorization: Bearer …` |
| Клиент: `Unauthorized` при подключении | передайте токен (`opts.auth_token`, `--token`, `FLUXMQ_TOKEN`) |
| Публикация медленная на macOS, висят алерты «High publish latency» / «Disk latency» | так работает `F_FULLFSYNC` в `group-commit`: каждый канал сбрасывает весь диск, и при нескольких каналах эти сбросы стоят в очереди друг за другом (p99 до 100 мс). Для разработки используйте `--fsync os`. Общий сброс на все каналы запланирован |
| «Consumed» на дашборде больше «Published» | это нормально: consumed — сумма ack по всем группам, при двух группах на канал каждое сообщение подтверждается дважды |
| Ошибки записи, «restart the broker» | закончилось место на диске. Освободите место и перезапустите брокер: при старте он восстановит файлы |
| Консоль показывает «Connection lost» | брокер остановлен или недоступен. Консоль переподключится сама |
| Лаг растёт, есть алерт «slow instance» | откройте *Consumers → Inspect* у подсвеченного инстанса: CPU, время обработки, последняя ошибка |
| Сообщения копятся в DLQ | откройте *Dead Letters*, посмотрите причину, устраните её и нажмите *Retry all* |
| `dev.sh: pnpm not found` | `npm i -g pnpm` или запускайте с `NO_UI=1` |
| `cargo` ругается на версию | нужен Rust 1.88+: `rustup update stable` |
| 403 `forbidden` в REST или `Forbidden` в клиенте | токен верный, но роли не хватает (раздел 11). `curl -s $H/api/auth/me -H "Authorization: Bearer $TOKEN"` покажет роль |
| Кластер: 503 «partitions … are changing leaders; retry» | идёт смена лидера (failover, drain, reassign). Повторите через пару секунд; SDK делает это сам |
| Кластер: узел после штатной остановки показан как `Down` | так и должно быть: при SIGTERM узел сообщает контроллеру, что уходит. После запуска он станет `Up` через ~10 с |
| Кластер: `Overloaded: not enough replicas` | в ISR раздела меньше узлов, чем `--min-isr`. Верните упавшие узлы |
| Кластер: узел не стартует, «a cluster secret is required» | с `--peers` обязательны `--node-id` и `--cluster-secret` (одинаковый на всех узлах) |

Подробные логи: `--log debug` или `RUST_LOG=info,fluxmq_core=debug,fluxmq_api=debug`.

## 17. Ограничения версии 0.7 и обновление

### Обновление до 0.7

- **Rolling upgrade 0.6 → 0.7 поддерживается**: по одному узлу (остановить или даже `kill -9`,
  заменить бинарник, запустить с тем же `--data-dir`), дождаться `Up` и
  `under_replicated_partitions = 0`, затем следующий. Каталог данных 0.6 открывается без
  преобразования; старые записи читаются, новые пишутся пачками, в одном сегменте могут быть оба
  формата.
- **Пока в кластере есть хоть один узел 0.6**, лидер раздела пишет публикации в старом формате
  (те же offset'ы и подтверждения): узел 0.6 не умеет читать пачки. Пачки включаются сами, когда
  последний узел раздела зарегистрировался как 0.7. Лидер никогда не отправляет пачку реплике,
  которая не объявила их поддержку: она получает только старый префикс, а брокер пишет громкую
  ошибку и считает отказы (`refused_old_follower_fetches`) — без порчи данных.
- **Пока лидеры ещё на 0.6**, у их разделов возможны две ошибки ISR 0.6 (в 0.7 исправлены, см.
  ниже): ISR может «мигать» (реплика то входит, то выходит), а вернувшаяся реплика может
  остаться вне ISR в метаданных, хотя данные она догнала (раздел висит недореплицированным).
  Данные при этом не теряются: подтверждения по-прежнему требуют `--min-isr` реплик. Если
  после перезапуска узла раздел, которым руководит узел 0.6, остаётся недореплицированным
  дольше ~30 с при `ISR ≥ min-isr`, продолжайте обновление: перезапуск (обновление) этого
  лидера снимает проблему. После обновления последнего узла ISR сходится сам.
- Проверено: три настоящих процесса 0.6 → 0.7 под нагрузкой (SDK `publish_batch`, lz4), каждый
  узел убит `kill -9` и запущен на новом бинарнике, затем ещё три `kill -9` лидера: 0
  потерянных подтверждённых сообщений, ни одной пачки на диске, пока в кластере был узел 0.6.
- **Откат на 0.6 после того, как записаны пачки, не поддерживается.** Пачки появляются, как
  только последний узел раздела работает на 0.7 (или одиночный брокер 0.7 принял первую
  публикацию). Если откат может понадобиться — сделайте бэкап (раздел 22) до обновления
  последнего узла. Узел 0.6, снова добавленный в раздел с пачками, не повредит данные: лидер
  откажет ему с ошибкой, но реплицировать этот раздел он не сможет.

**Совместимость SDK и брокера** (версия протокола договаривается в `Hello`):

| SDK \ брокер | 0.4 (v2) | 0.5 (v3) | 0.6 (v3) | 0.7 (v4) |
|---|---|---|---|---|
| SDK 0.4 (протокол v2) | да | да | да | да |
| SDK 0.5 / 0.6 (v3) | **нет** (`unsupported protocol version 3`) | да | да | да |
| SDK 0.7 (v4) | да, v2 | да, v3 | да, v3 | да, v4: пачки, сжатие, cumulative |

SDK 0.7 сам переходит на версию, которую назвал брокер, поэтому клиентов 0.7 можно обновлять в
любом порядке относительно брокеров; выигрыш (`PublishBatch`, `DeliverRecords`, сжатие,
cumulative-подтверждения) появляется, когда брокер — 0.7. Старые клиенты (v2/v3) работают с
брокером 0.7 без изменений: брокер сам переводит пачки в `Deliver`/`DeliverBatch`.

### Ограничения версии 0.7

- **Откат на 0.6** после записи пачек — не поддерживается (см. выше).
- **Режим `AckMode::Cumulative`** — только для stream-каналов; `nack`, ack timeout и DLQ в нём
  не работают (`BadRequest`). После падения консьюмера сообщения после последней фиксации
  придут повторно.
- **Точный рестарт** (с 0.7 брокер сохраняет подтверждённые диапазоны выше committed offset, до
  1024 диапазонов на партицию) работает на одном узле. В кластере реплицируется только
  committed offset: после смены лидера сообщения, подтверждённые «выше» него, могут прийти
  повторно один раз (at-least-once сохраняется).
- **Время сообщения — одно на пачку**: все сообщения одной пачки получают время её записи;
  поиск по времени и retention по возрасту работают с точностью до пачки.
- **Пачку нельзя разделить**: сегмент может превысить свой размер на одну пачку (не больше
  16 MiB), а сообщение больше 16 MiB (только через REST) пишется старым форматом.
- **Сжатые пачки** брокер распаковывает только для функций, которым нужно содержимое: фильтры
  маршрутов, инспектор сообщений, поиск, queue/keyed-каналы и консьюмеры v2/v3. Для них сжатие
  стоит CPU брокера.
- **Память**: кэш последних пачек — `--partition-cache-bytes` (по умолчанию 16 MiB) **на
  партицию**: 8 партиций = 128 MiB плюс разобранные сообщения для консьюмеров v2/v3.
  Неподтверждённые «сырые» доставки держат буфер своей пачки, пока не подтверждено ≥ 7/8
  её сообщений (затем остаток копируется). `prefetch_bytes` ограничивает размер кадра, а не
  объём неподтверждённого.
- **Без `sendfile`**: сырые кадры кодируются с одной копией в буфер записи; на 1 KiB+ это
  заметная часть CPU брокера.
- **Один поток записи на канал** (не на партицию): по замерам он упирается только выше ~4 млн
  сообщений/с по 100 B, что выше потолка fsync и 2 CPU брокера.
- **Поток доставки** (`--delivery-threads`, по умолчанию 2) — один на процесс.
- **Исправлено в 0.7** (касается и кластеров 0.6): потерянный отчёт об изменении ISR больше не
  «залипает» — лидер повторяет его каждые 2 с, пока контроллер не зафиксирует ISR (раньше
  вернувшаяся реплика могла навсегда остаться вне ISR в метаданных); реплика, исключённая
  зафиксированным ISR, возвращается в него не раньше чем через 1 с, а отчёты об ISR
  записываются только в последней версии (раньше ISR мог «мигать» десятки секунд, ~20 записей
  метаданных в секунду).
- **Исправлено до выпуска бенчмарка 0.7** (найдено проверкой id в бенчмарке): когда retention
  по размеру догоняла отстающую группу, чтение «вдогонку» могло выбросить уже прочитанный с
  диска буфер следующей порции, и группа перескакивала через **ещё хранящиеся,
  недоставленные** сообщения — без предупреждения и без счётчика. Теперь буфер чтения
  вдогонку никогда не теряется, а любой пропуск недоставленных сообщений (удалены retention
  или нечитаемый участок лога) виден в предупреждении и в
  `fluxmq_group_retention_skipped_messages_total`. Курсор группы не проходит мимо хранящегося
  недоставленного сообщения. Касается и одиночного узла, и лидеров в кластере.

### Ограничения, оставшиеся с 0.5

- **Поиск по payload без индекса**: фильтр просматривает до 200 000 сообщений за запрос
  (раздел 18). В фильтрах нет `OR`.
- **Маршрут не обрабатывает историю** — только сообщения, опубликованные после его создания;
  старые сообщения перегоняются через *Replay*. Счётчики маршрутов — с момента старта узла и
  у каждого узла свои.
- **Пакетная доставка** (с 0.5): брокер отдаёт клиентам протокола v3 до 256 сообщений / 1 MiB
  одним кадром `DeliverBatch`, но только в пределах свободного prefetch: с маленьким prefetch
  (по умолчанию в SDK — 64) выигрыш меньше. Клиенты протокола v2 получают по одному `Deliver`,
  как раньше.
- История попыток доставки (retry timeline) хранится в памяти, последние 100k сообщений на канал;
  в кластере — только на узле, который доставлял.
- **Отзыв и истечение токена** (с 0.5) закрывают живые соединения и WebSocket-сессии в течение
  ~1 с на всех узлах, но REST-запрос, начатый до отзыва, доработает. Привязки сертификатов
  работают только на клиентском порту с mTLS; CRL и OCSP не проверяются (раздел 24).
- **Кластер** (раздел 19):
  - обнаружение упавшего узла занимает ~6 с (`node_timeout`): публикации в разделы, которыми он
    руководил, стоят ~5–6 с (при падении контроллера — до ~9 с);
  - остановка контроллера (даже штатная) стоит выборов Raft (1–3 с);
  - перезапущенный узел помечается `Up` через ~10 с после старта (данные он догоняет раньше);
  - audit log у каждого узла свой; `/metrics` — метрики только этого узла;
  - на macOS все узлы на одном диске делят `F_FULLFSYNC`: задержка подтверждения с репликацией
    ~60–80 мс (см. BENCHMARKS.md).
- **Ребалансировка** (раздел 23): планировщик считает реплики, а не байты; нет rack/AZ-awareness
  и unclean election; новый узел получает реплики не сразу, а после ~10 с стабильной работы и
  ближайшей проверки (раз в 30 с).
- **Вывод узла** (раздел 19, с 0.5): одновременно выводится только один узел; во время вывода
  нельзя запустить другую ребалансировку (и наоборот); вывод контроллера стоит одних выборов
  Raft (1–2 с). События `node_decommission_started` / `node_decommissioned` /
  `node_decommission_failed` / `node_forgotten` каждый узел выводит из реплицируемого
  состояния раз в секунду, поэтому очень короткий промежуточный шаг может не дать отдельного
  события (итоговое событие приходит всегда).
- **Метаданные без кворума**: запись метаданных на контроллере, потерявшем кворум Raft,
  через несколько секунд (не больше ~15 с) завершается ответом 503 (результат неизвестен: запись может
  примениться позже, если кворум вернётся), а не зависает.
- **TLS** (раздел 24): файлы CA перечитываются только при перезапуске; CRL и OCSP не
  проверяются; один сертификат на поверхность (без SNI); cluster TLS включается и выключается
  только перезапуском всех узлов; событие `tls_reload_failed` попадает в ленту только с
  контроллера (алерт `tls_reload_failed` виден и уведомляется с любого узла).
- **Обновление с 0.3**: узел 0.4+ удаляет локальные копии разделов, репликой которых он больше
  не является (раздел 19, «Обновление с 0.3»). **С 0.4 на 0.5** обновление по одному узлу,
  формат данных не меняется; клиенты SDK 0.4 (протокол v2) продолжают работать с брокером 0.5.
  Обратное неверно: SDK 0.5 (протокол v3) не понижает версию и брокером 0.4 отклоняется
  (`unsupported protocol version 3 (broker speaks 2)`) — **сначала обновите все брокеры, потом
  клиентов**.
- **Удаление сегментов по retention под нагрузкой** (исправлено в 0.6): в 0.5 сегмент по
  умолчанию был 128 MiB, и все разделы удаляли по сегменту почти одновременно; в Docker на
  macOS это давало одну паузу подтверждений ~0,5–1 с при 50 000 сообщений/с. С 0.6 сегменты
  меньше (64 MiB), их размер смещён по разделам на ±10 %, а retention удаляет порциями (см.
  «Сегменты и retention» в разделе о запуске).
- **Docker** (раздел 25): адреса узлов кластера в метаданных (`n1:7420` …) резолвятся только
  внутри сети compose; бенчмарки в Docker Desktop на macOS измеряют виртуальную машину, а не
  «железо» (диск и сеть VM).
- **Бэкапы** (раздел 22):
  - инкрементальность — только для закрытых сегментов: активный сегмент каждого раздела
    загружается заново при каждом запуске, поэтому у небольших и малонагруженных каналов
    экономии почти нет (в живой проверке второй бэкап переиспользовал 2 сегмента из 25);
  - в кластере срезы разных лидеров снимаются в немного разные моменты: каждый раздел
    консистентен сам по себе, но не «одномоментен» с разделами других узлов;
  - если во время бэкапа у раздела нет лидера (идёт перенос лидерства или переезд раздела,
    узел недоступен), бэкап завершается ошибкой — повторите запуск;
  - прогресс разделов других узлов появляется только когда каждый из них закончит свою часть;
  - restore всегда создаёт одиночный узел;
  - манифест не шифруется (имена и настройки каналов, диапазоны offset'ов — без сообщений);
  - два писателя (два брокера/кластера или брокер и `fluxmq backup run`) не должны делить один
    префикс хранилища;
  - DLQ канала хранится одним JSON-объектом — большой DLQ раздувает бэкап.
- **Уведомления** (раздел 20): история отправок хранится 7 дней в реплицируемом канале
  `$system.notifications` (переживает перезапуск и смену контроллера), API отдаёт не больше
  10 000 последних записей; отправка, начатая контроллером в момент его падения, может не
  попасть в историю. Telegram и PagerDuty проверены автотестами на имитации API и запросами с
  выдуманными ключами, но не с настоящими ключами.
- **Лента `$system.events`** хранится 7 дней. В кластере `GET /api/events/feed` можно
  запрашивать у любого узла: узел без реплики канала проксирует запрос лидеру раздела
  (long-poll сохраняется). Пока у раздела нет лидера (failover, ~6 с), узел отвечает из своей
  копии, а узел без копии — пустой страницей с тем же курсором.
- **Вебхуки** (раздел 21): счётчики `GET /api/webhooks/stats` — с момента старта процесса
  (в кластере сумма по узлам).

## 18. Маршрутизация

**Маршрут** — правило «сообщения канала S, подходящие под условия, копировать в каналы T…».
Например: заказы из Молдовы на сумму от 100 — в `orders.md` и в `audit`.

Как это работает:

- Маршрутизатор встроен в брокер и читает канал-источник как обычная группа потребителей
  с системным именем **`$router`**. Публикацию он не замедляет, а его лаг и здоровье видны
  на вкладке *Consumers*, как у любой группы.
- Каждое сообщение проверяется всеми включёнными маршрутами источника. Копия уходит в каждый
  целевой канал один раз, даже если совпало несколько маршрутов. Ключ, заголовки и payload
  сохраняются, к ним добавляются заголовки:
  - `flux-routed-from` — откуда сделана копия (`канал/партиция/offset`);
  - `flux-route-id` — какой маршрут её сделал;
  - `flux-route-path` — через какие каналы прошло сообщение (`orders,orders.md`).
- **Защита от циклов**: в канал, который уже есть в `flux-route-path`, копия не отправляется.
  Цепочка не длиннее 8 пересылок. Маршруты A→B и B→A безопасны.
- **Ошибки**: если целевой канал недоступен (например, удалён), сообщение повторяется по
  retry-политике канала-источника. Когда попытки кончаются, оно попадает в DLQ источника с
  группой `$router` и причиной `route target unavailable: <канал>`. После исправления нажмите
  *Retry* в Dead Letters.
- Новый маршрут обрабатывает сообщения, опубликованные **после** его создания. Backtest в
  Preview только показывает, что подошло бы из истории, но ничего не пересылает. Старые
  сообщения можно перегнать через *Replay*.
- **Выключенный** маршрут — это пауза: группа `$router` остаётся со своим offset'ом, после
  включения маршрутизатор продолжит с места остановки. Когда удалён **последний** маршрут
  источника, группа `$router` удаляется автоматически (в журнале действий — `group.delete`
  от `system`).
- Счётчики: `evaluated` и `matched` считают сообщения, `forwarded` и `failed` — копии **по
  каждой цели** (совпадение маршрута с тремя целями добавляет 1 к `matched` и 3 к `forwarded`).
- Маршруты хранятся в `<data-dir>/meta.json` (в кластере реплицируются) и применяются без
  перезапуска.

### Язык фильтров

Один и тот же язык используется в маршрутах (текстовый режим редактора WHEN/THEN) и в поиске
сообщений. Условия объединяются через `AND`, `OR` не поддерживается: для «или» заведите
несколько маршрутов.

| Поле | Что это |
|---|---|
| `key` | ключ сообщения |
| `partition` | номер партиции |
| `header.<имя>` | заголовок, например `header.flux-type` |
| `a.b.0.c` | путь в JSON payload; числа — индексы массивов |
| `payload.<путь>` | явный путь в payload. **Обязателен** для полей с именами `key` и `partition`: без префикса это ключ и раздел сообщения, а `payload.key` — поле `key` в JSON |

Операторы: `=`, `!=`, `>`, `>=`, `<`, `<=`, `in [..]`, `not in [..]`, `prefix`, `contains`,
`exists`, `not exists`. Ключевые слова можно писать в любом регистре.

Примеры:

```text
order_id = 8842
type = "order.created" AND country = "MD" AND amount >= 100
country in [MD, RO] AND header.flux-type prefix payment.
customer.tier != gold AND items.0.sku = "A-1"
tags contains vip
header.x-trace-id exists
key prefix "user-" AND partition = 3
created_at >= "2026-10-01"
```

Правила сравнения:

- числа сравниваются как числа, строки — лексикографически;
- число равно строке с этим числом: `order_id = 8842` найдёт и `8842`, и `"8842"`;
- строки без пробелов можно не брать в кавычки (`country = MD`);
- отсутствующее поле не подходит ни под какой оператор, кроме `!=`, `not in` и `not exists`;
- условия по payload никогда не срабатывают, если payload — не JSON;
- `contains` ищет подстроку в строке или элемент в массиве.

Ошибки синтаксиса возвращаются с позицией (в байтах): `filter syntax error at 8: unexpected character '~'`.

### Через консоль

*Routing* (глобальная страница или вкладка *Routing* канала) → **New route** (или **Create route
from filter** на вкладке *Messages*). Задайте источник, условия (строками или текстом) и цели.
В панели **Preview** справа (на узком экране — под редактором) видно, сколько сообщений за
последний час / 24 часа / 7 дней подошло бы под маршрут, и примеры (backtest, до 200 000
последних сообщений). Под редактором — счётчики маршрута: проверено, совпало, переслано (по
целям), ошибок, время последнего совпадения.

Пример на демо-данных (`fluxmq-demo`): создайте канал `orders.md`, затем маршрут из
`orders.events` с условием `type = "OrderCreated" AND country = "MD"` и целью `orders.md`.
Preview сразу покажет сотни совпадений за 24 часа, через несколько секунд вырастут
счётчики, а у сообщений в `orders.md` появятся заголовки `flux-route-id`,
`flux-route-path: orders.events,orders.md` и `flux-routed-from: orders.events/<раздел>/<offset>`.

### Через REST

```bash
# Разобрать фильтр (то, что делает редактор)
curl -s -X POST localhost:7421/api/filter/parse -H 'Content-Type: application/json' \
  -d '{"filter":"country = MD AND amount >= 100"}'
# {"conditions":[...],"rendered":"country = \"MD\" AND amount >= 100"}

# Обратно: условия → текст (то, что делает редактор при переключении в Text)
curl -s -X POST localhost:7421/api/filter/render -H 'Content-Type: application/json' \
  -d '{"conditions":[{"field":{"kind":"payload","name":"country"},"op":"eq","value":"MD"}]}'
# {"rendered":"country = \"MD\""}

# Создать маршрут (роль admin); conditions — из ответа выше
curl -s -X POST localhost:7421/api/routes -H 'Content-Type: application/json' -d '{
  "name": "MD orders", "source": "orders", "targets": ["orders.md", "audit"],
  "conditions": [
    {"field":{"kind":"payload","name":"country"},"op":"eq","value":"MD"},
    {"field":{"kind":"payload","name":"amount"},"op":"gte","value":100}]}'

# Проверить условия на сохранённых сообщениях за последний час
curl -s -X POST localhost:7421/api/routes/test -H 'Content-Type: application/json' \
  -d '{"source":"orders","conditions":[...],"window_ms":3600000,"sample_limit":5}'

curl -s localhost:7421/api/routes                 # список
curl -s localhost:7421/api/routes/stats           # счётчики
curl -s -X PATCH localhost:7421/api/routes/<id> -H 'Content-Type: application/json' \
  -d '{"enabled":false}'                          # выключить
curl -s -X DELETE localhost:7421/api/routes/<id>  # удалить
```

### Поиск сообщений по содержимому

Параметр `filter` в `GET /api/channels/{name}/messages` (и строка поиска на вкладке *Messages*):

```bash
curl -s -G localhost:7421/api/channels/orders/messages \
  --data-urlencode 'filter=order_id = 8842' --data-urlencode 'newest_first=true'
```

Работают и обычные параметры (`key`, `partition`, `offset`, `since_ms`/`until_ms`, `limit`).
Индекса по payload нет: брокер просматривает сообщения, пока не наберёт `limit` совпадений, но
не больше 200 000 за запрос. В ответе `scanned` — сколько просмотрено, `has_more: true` —
просмотр остановился раньше конца диапазона (сузьте время или продолжите с `until_ms`).
Ориентир по скорости: около 2 млн сообщений в секунду, то есть 200 000 — примерно 0,1 с.

## 19. Кластер

Без флага `--peers` брокер работает одиночным узлом (как в v0.1). С `--peers` несколько процессов
образуют кластер:

- **метаданные** (каналы, назначения разделов, токены, маршруты, список узлов) хранятся в
  Raft-группе (openraft) на всех узлах; лидер Raft — **контроллер**: он раскладывает разделы по
  узлам и переключает их при сбоях;
- **данные** реплицируются по разделам, как в Kafka: у каждого раздела есть лидер и реплики,
  реплики забирают данные у лидера. Публикация подтверждается, когда сообщение есть у всего
  ISR (in-sync replicas, `acks=all`), поэтому подтверждённое сообщение не теряется при падении
  узла. Консьюмеры видят только реплицированное (ниже high watermark);
- новым лидером становится только реплика из ISR; если живых реплик ISR нет, раздел уходит
  в offline, а не теряет данные.

Подробное описание модели и внутренних эндпоинтов — в [CLUSTER.md](CLUSTER.md).

### Локальный кластер из трёх узлов

Из корня репозитория, после сборки (`cd ui && pnpm install && pnpm build && cd ..` и
`cargo build --release -p fluxmq-server -p fluxmq-client`). По терминалу на узел:

```bash
export FLUXMQ_CLUSTER_SECRET=dev-secret
PEERS=n1@127.0.0.1:17422,n2@127.0.0.1:17432,n3@127.0.0.1:17442

./target/release/fluxmq --node-id n1 --peers $PEERS --data-dir ./data/n1 \
  --client-addr 127.0.0.1:17420 --http-addr 127.0.0.1:17421 \
  --raft-addr 127.0.0.1:17422 --replication-addr 127.0.0.1:17423

./target/release/fluxmq --node-id n2 --peers $PEERS --data-dir ./data/n2 \
  --client-addr 127.0.0.1:17430 --http-addr 127.0.0.1:17431 \
  --raft-addr 127.0.0.1:17432 --replication-addr 127.0.0.1:17433

./target/release/fluxmq --node-id n3 --peers $PEERS --data-dir ./data/n3 \
  --client-addr 127.0.0.1:17440 --http-addr 127.0.0.1:17441 \
  --raft-addr 127.0.0.1:17442 --replication-addr 127.0.0.1:17443
```

Порты сдвинуты относительно стандартных (7420–7423), чтобы кластер не мешал одиночному брокеру
или мок-серверу. Узлы можно запускать в любом порядке; кластер инициализирует узел с наименьшим
id (`n1`), как только наберётся большинство.

Проверка:

```bash
curl -s 127.0.0.1:17421/api/cluster/metadata | jq '.controller, [.nodes[] | {id, status, is_voter}]'
curl -s -X POST 127.0.0.1:17431/api/channels -H 'content-type: application/json' \
  -d '{"name":"orders","mode":"stream","partitions":6}'
curl -s 127.0.0.1:17441/api/cluster/metadata | jq -c '.channels.orders[] | {partition, leader, replicas, isr}'
curl -s -X POST 127.0.0.1:17441/api/channels/orders/publish -H 'content-type: application/json' \
  -d '{"messages":[{"key":"a","payload":{"encoding":"utf8","data":"hello"}}]}'
curl -s 127.0.0.1:17421/api/cluster/status | jq -c '.raft, .under_replicated_partitions, .offline_partitions'
```

Демо-нагрузка и консоль:

```bash
./target/release/fluxmq-demo --seeds 127.0.0.1:17420,127.0.0.1:17430,127.0.0.1:17440
open http://127.0.0.1:17421/nodes      # консоль отдаёт любой узел
```

Обращаться можно к любому узлу: создание и удаление каналов идут через контроллер, публикации
пересылаются лидерам разделов, чтение сообщений и DLQ, replay и операции с группами
собираются с лидеров. Канал, созданный через один узел, сразу можно использовать через любой
другой.

Остановить всё: `Ctrl-C` в каждом терминале. Удалить данные: `rm -rf data`.

### Флаги кластера

| Флаг | Переменная | По умолчанию | Описание |
|---|---|---|---|
| `--node-id` | `FLUXMQ_NODE_ID` | — (обязателен с `--peers`) | постоянный id узла |
| `--peers` | `FLUXMQ_PEERS` | — | начальные участники `id@raft_host:port,…`, одинаковый список на всех начальных узлах (может включать сам узел) |
| `--raft-addr` | `FLUXMQ_RAFT_ADDR` | `0.0.0.0:7422` | Raft и внутренние RPC (HTTP+JSON) |
| `--replication-addr` | `FLUXMQ_REPLICATION_ADDR` | `0.0.0.0:7423` | репликация разделов |
| `--advertise-host` | `FLUXMQ_ADVERTISE_HOST` | IP из адреса прослушивания, для `0.0.0.0` — `127.0.0.1` | адрес, по которому узел видят другие узлы и клиенты. **Обязательно задайте на нескольких машинах** |
| `--replication-factor` | `FLUXMQ_REPLICATION_FACTOR` | `3` | число реплик новых каналов (не больше числа живых узлов на момент создания) |
| `--min-isr` | `FLUXMQ_MIN_ISR` | `1` | минимум реплик в ISR для приёма публикации, иначе ошибка `Overloaded` («not enough replicas») |
| `--cluster-secret` | `FLUXMQ_CLUSTER_SECRET` | — (обязателен с `--peers`) | общий секрет межузлового трафика, одинаковый на всех узлах |
| `--auto-rebalance` | `FLUXMQ_AUTO_REBALANCE` | `full` | режим автоматической ребалансировки при первом запуске кластера: `off`, `repair`, `full` (раздел 23) |

Новый узел добавляется так: запустите его с новым `--node-id`, тем же секретом и `--peers`,
перечисляющим существующие узлы (без него самого). Контроллер добавит его в Raft сначала
learner'ом, потом voter'ом (до 5 voters). Новые каналы будут использовать новый узел, а
существующие реплики переедут на него автоматически (раздел 23, «Ребалансировка»; вручную —
через *Reassign*).

### Что происходит при падении узла

| Время | Что происходит |
|---|---|
| 0 с | узел упал (`kill -9`, сбой питания, обрыв сети) |
| до 4 с | его аренда (lease) у контроллера истекает — он сам перестаёт руководить разделами, даже если жив, но отрезан |
| ~6 с | контроллер помечает узел `Down`, выбирает новых лидеров из ISR (epoch + 1) и убирает узел из всех ISR. Публикации идут дальше; SDK получает `MetadataChanged` / `NotLeader`, обновляет метаданные и повторяет запросы |
| узел вернулся | он отрезает расходящийся хвост лога, догоняет лидеров как реплика, возвращается в ISR, помечается `Up` (~10 с после старта процесса) и забирает обратно свои предпочтительные лидерства |

Измерено локально (3 процесса, release, демо-нагрузка): после `kill -9` лидера самая длинная пауза
между подтверждениями публикаций — 4,5–5,7 с; failover — 5,6 с; пример `resilience`
(30 260 подтверждённых публикаций) — **0 потерянных**, 17 повторных доставок. Штатная остановка
(`SIGTERM`) почти незаметна: пауза 0,9 с (контроллер — 1,3 с), потому что узел сначала отдаёт
лидерство и выходит из ISR. Если упал контроллер, Raft выбирает нового за 1–3 с, а failover
начинается после короткого периода ожидания — пауза до ~9 с.

Проверить самому — пример `resilience` против кластера, пока вы убиваете и перезапускаете узлы:

```bash
cargo run --release -p fluxmq-client --example resilience -- \
  127.0.0.1:17420,127.0.0.1:17430,127.0.0.1:17440 120
# в другом терминале: kill -9 <pid узла>, через 15 с запустить его той же командой
```

В конце пример печатает `acked but missing 0` и `OK: no acknowledged publish was lost`.

### Обслуживание: drain и reassign

- **Drain** (Nodes → карточка узла → *Drain leadership*, или
  `curl -X POST 127.0.0.1:17421/api/cluster/nodes/n3/drain`, роль admin) переносит лидерство
  разделов с узла на другие реплики ISR и помечает узел `Leaving`. Узел продолжает
  реплицировать, его можно перезапустить без недоступных разделов; после перезапуска он снова
  `Up`, а лидерства вернутся. Штатная остановка (`SIGTERM`) делает drain автоматически.
- **Reassign** (Nodes → клик по квадрату раздела в матрице) меняет набор реплик раздела;
  первая реплика — предпочтительный лидер:

  ```bash
  curl -s -X POST 127.0.0.1:17421/api/cluster/partitions/reassign -H 'content-type: application/json' \
    -d '{"channel":"orders","partition":0,"replicas":["n2","n1","n3"]}'
  ```

  Чтобы полностью перенести раздел, сначала добавьте новые реплики, дождитесь их в ISR
  (`GET /api/cluster/status`), затем уберите старые.
- **Здоровье**: `GET /api/cluster/status` (терм и лидер Raft, under-replicated и offline
  разделы, HW/LEO/ISR и отставание реплик по разделам), экран *Nodes*, алерты «узел
  недоступен», «недореплицированные разделы», «офлайн-разделы», метрики `fluxmq_cluster_*`.

### Вывод узла из кластера: decommission и forget (с 0.5)

**Вывести живой узел насовсем** — одна команда (роль admin, любой узел; выполняет контроллер):

```bash
curl -s -X POST -H "$AUTH" 127.0.0.1:17421/api/cluster/nodes/n3/decommission
# {"node":"n3","state":"moving_replicas","replicas_remaining":8,"started_at_ms":…,
#  "finished_at_ms":null,"error":null}

# Прогресс (роль viewer, любой узел)
curl -s -H "$AUTH" 127.0.0.1:17421/api/cluster/nodes/n3/decommission
# {"node":"n3","state":"removed","replicas_remaining":0,…,"finished_at_ms":…}
```

Что происходит:

1. **Проверки.** Отказ — `409 conflict` с причиной, ничего не меняется: идёт ребалансировка
   (отмените её или дождитесь); уже выводится другой узел; оставшиеся `Up`-узлы не вмещают
   реплики раздела (например, RF 3 на трёх узлах — сначала добавьте узел); у раздела нет
   живого лидера; удаление нарушит кворум Raft (см. ниже). Неизвестный узел — 404. Повторный
   `POST` во время вывода просто возвращает текущий статус.
2. **`moving_replicas`.** Узел получает статус `Decommissioning`, его лидерство переносится
   на другие реплики, и запускается план ребалансировки только из переездов типа `repair`
   (причина `decommission n3`, виден в `GET /api/cluster/rebalance` и на экране
   ребалансировки). Работает в любом режиме, в том числе `off`. Выводимый узел никогда не
   получает новых реплик, а все его реплики переезжают — в любом плане. Переезд идёт обычным
   протоколом (добавить → догнать → переключить), устойчивость не падает. Если после плана
   реплики остались (откаты), запускается следующий (до 5); если 120 с нечего двигать —
   `failed`. **Отмена** — `POST /api/cluster/rebalance/cancel` во время `moving_replicas`:
   начатые переезды доделываются, вывод завершается `failed` с ошибкой `cancelled`. После
   любой ошибки узел остаётся в кластере со статусом `Up` (уже переехавшие реплики остаются на
   новых местах), `POST` можно повторить.
3. **`leaving_membership`.** Реплик 0 — узел удаляется из состава Raft (`change_membership`:
   и voter, и learner удаляются полностью). Если кворум сейчас небезопасен, вывод ждёт, а
   причина видна в `error`.
4. **`removed`.** Запись `cluster/nodes/<id>` удаляется, узел пропадает из списка. Процесс
   можно останавливать: его heartbeat'ы отклоняются, он сам останавливает Raft и репликацию и
   оставляет в каталоге данных метку `cluster-removed`.

В ответе есть `initial_replicas` — сколько реплик было на узле в начале (для прогресса).
Запись о выводе читается ещё 24 часа после окончания; список текущих и недавних —
`GET /api/cluster/decommissions` (роль viewer). Посмотреть план, ничего не меняя:
`POST …/decommission?dry_run=true` — те же проверки (те же 409/404) и `RebalanceStatus` с
планируемыми переездами. Начало и конец вывода пишутся в журнал действий как
`node.decommission`, а в ленту событий (консоль, `$system.events`, уведомления) попадают
`node_decommission_started`, `node_decommissioned` или `node_decommission_failed` (с причиной в
заголовке); забытый узел даёт `node_forgotten`.

**Перезапуск выведенного узла** с тем же id и тем же `--data-dir` подключает его как **новый
пустой узел**: по метке он стирает старое Raft-состояние, контроллер добавляет его learner'ом,
затем voter'ом. В режиме `full` ребалансировка затем
отдаст ему реплики.

**Вывод контроллера** работает так же. В openraft 0.9 нет передачи лидерства, поэтому
контроллер сначала, оставаясь контроллером, переносит свои реплики и лидерство разделов, а
затем сам удаляет себя из состава Raft. openraft держит его лидером, пока это изменение не
зафиксировано, и затем снимает с него лидерство; оставшиеся voters выбирают нового
контроллера за 1–2 с, и тот завершает удаление записи узла. Разделы при этом не страдают
(выводимый узел ничем не руководит), команды контроллеру сами повторяются через выборы.

**Забыть мёртвый узел** (машина умерла, реплики уже восстановлены на других узлах —
автоматически через `replace_after_secs` в режимах `repair`/`full` или ручной
ребалансировкой):

```bash
curl -s -X DELETE -H "$AUTH" 127.0.0.1:17421/api/cluster/nodes/n3
# {"node":"n3","state":"removed","replicas_remaining":0,…}
```

Только для узла в статусе `Down` без реплик; иначе 409 (живой узел — выводите через
decommission; реплики сначала должны переехать), неизвестный — 404. Если тот же процесс
вдруг вернётся, его отклонят; перезапуск подключит его как новый узел.

**Безопасность кворума** (обе операции): удалить learner можно всегда. Удаление voter'а
разрешено, только если остаётся хотя бы один voter и живы большинство и оставшихся, и
текущих voters. Например, при трёх voters и одном упавшем вывести второй нельзя.

На одиночном узле все три запроса отвечают `400 unsupported_single_node`.

### Ограничения кластера

- Межузловой трафик шифруется только с cluster TLS (раздел 24); без него он защищён лишь общим
  секретом — тогда держите порты Raft и репликации в приватной сети.
- Узел выводится из кластера одной командой (decommission, мёртвый — forget, см. выше), но
  только по одному и не во время другой ребалансировки.
- Нет rack/AZ-awareness и unclean election (раздел без живого ISR ждёт возвращения реплики).
- Остановка контроллера стоит выборов Raft; обнаружение падения узла — ~6 с.
- Потеряно большинство voters → метаданные только для чтения, failover невозможен.
- Не стирайте Raft-состояние (`data/raft/`) у большинства узлов.
- Бэкап кластера выполняет контроллер, восстановление всегда даёт одиночный узел (раздел 22).

### Обновление с 0.3

Обновляйте узлы по одному (остановить, заменить бинарник, запустить с тем же `--data-dir` и
теми же флагами), дожидаясь, пока узел снова станет `Up` и его реплики вернутся в ISR.
Формат данных и метаданных не меняется, отката данных не нужно.

Что меняется в поведении — **в любом режиме, включая `--auto-rebalance off`**:

- **Узел удаляет локальные копии разделов, репликой которых он не является** по текущему
  назначению в метаданных кластера. В 0.3 такие копии оставались после *Reassign* (раздел
  переехал, а старые файлы лежали на диске). Каталог канала исчезает с узла, на котором не
  осталось ни одного его раздела; канал по-прежнему виден в списках и REST, а каталог
  появится снова, если узел опять станет репликой.
- Удаление выполняется только после того, как узел догнал метаданные контроллера, только
  для разделов, которых нет в списке реплик назначения, и только если назначение не старее
  локальной копии (epoch). Роль «нет роли» (лидер неизвестен, раздел offline, узел отрезан)
  **никогда** не удаляет данные. Разделы, репликой которых узел является, не трогаются.
- Первый узел 0.4, ставший контроллером, записывает настройки ребалансировки
  (`cluster/rebalance/config`) из `--auto-rebalance` (по умолчанию `full`). Если вы не хотите,
  чтобы реплики начали переезжать сразу после обновления, запускайте узлы с
  `--auto-rebalance off` и включите режим позже через API или консоль.

Если копии старых разделов нужны (например, для расследования), скопируйте каталоги
`data/channels/<канал>/p<N>` до запуска 0.4.

Проверено: кластер 0.3.0 из трёх узлов (RF 2, канал на 6 разделов, 3 400 сообщений, два
раздела перенесены через *Reassign* — у прежних реплик остались старые копии) обновлён по
одному узлу до 0.4 с `--auto-rebalance off` под нагрузкой примера `resilience`. В смешанном
режиме (контроллер 0.4, реплики 0.3) недореплицированных разделов не было. Удалены только две
старые копии и пустые заготовки разделов, которых узел никогда не держал; разделы, которые узел
реплицирует, не изменились ни на байт. Все 3 400 сообщений читаются с любого узла с одинаковой
контрольной суммой, из 92 770 подтверждённых за время обновления публикаций не потеряна ни одна.

## 20. Уведомления

FluxMQ сам сообщает о проблемах: алерты (растёт лаг, нет потребителей, DLQ растёт, узел упал…)
и, по желанию, события брокера (канал удалён, потребитель отключился…) уходят в Telegram,
Slack, Discord, на почту, в PagerDuty или на ваш HTTP-адрес.

Модель простая:

- **получатель** (notifier) — куда слать: бот Telegram, вебхук Slack, SMTP-сервер и т.д.;
- **правило** (rule) — что слать и кому: минимальная важность, типы алертов, типы событий,
  маски каналов (`orders.*`) и список получателей.

Как работает доставка:

- **Группировка.** Первый подходящий алерт открывает окно `group_wait_secs` (по умолчанию
  30 с); всё, что сработало за это время, приходит одним сообщением («3 issues need
  attention»). Если алерт открылся и закрылся внутри окна, сообщения не будет.
- **Повтор.** Пока алерт открыт, напоминание приходит каждые `repeat_interval_secs` (по
  умолчанию 4 часа, `0` — не напоминать).
- **Восстановление.** Когда алерт закрылся, приходит сообщение «Resolved: …»
  (`send_resolved`, по умолчанию включено).
- **Повторы отправки.** Неудачная отправка повторяется до 3 раз (через 2 и 10 с). Результат
  каждой отправки виден в истории: `GET /api/notify/history` (по умолчанию
  последние 1000, `?limit=` до 10 000).
- **Кластер.** Отправляет только контроллер, поэтому дублей нет. История (с 0.5) хранится в
  реплицируемом системном канале `$system.notifications` (1 раздел, 7 дней; API отдаёт до
  10 000 последних записей) и переживает смену контроллера и полный перезапуск кластера.
  Пишет в канал только контроллер; тестовая отправка через другой узел передаётся
  контроллеру. `GET /api/notify/history` работает на любом узле: запрос проксируется лидеру
  раздела канала, как лента событий.
- **Короткие ошибки.** В `error` (история, результат теста) — короткая причина:
  `connection refused`, `timeout`, `HTTP 503`, `TLS error`, `DNS error`, `SMTP 550`…;
  полный текст (цепочка причин или начало ответа сервера) — в `error_detail`. Секретов там нет.
- **Ссылки.** Если запустить брокер с `--public-url https://mq.example.com`
  (`FLUXMQ_PUBLIC_URL`), в сообщениях будет ссылка на нужный экран консоли.

Секреты (токен бота, адреса вебхуков Slack/Discord, пароль SMTP, ключ PagerDuty, секрет
подписи, значения всех пользовательских заголовков) API никогда не возвращает — вместо них
`********`. При изменении `********` оставляет сохранённое значение, `""` удаляет его, любое
другое значение заменяет. В журнал аудита и в логи секреты не попадают.

Права: просмотр — роль viewer, создание, изменение, удаление и тестовая отправка — admin. В
примерах ниже брокер запущен с `--admin-token adm-demo`:

```bash
FLUX=http://127.0.0.1:7421
AUTH='Authorization: Bearer adm-demo'
J='Content-Type: application/json'
```

### Telegram: пошагово

1. **Создайте бота.** Откройте в Telegram [@BotFather](https://t.me/BotFather), отправьте
   `/newbot`, задайте имя и username (должен оканчиваться на `bot`). BotFather пришлёт токен
   вида `7123456789:AAH…` — это `bot_token`. Храните его как пароль.

2. **Добавьте бота в чат.** Личный чат: просто напишите боту `/start`. Группа: добавьте бота в
   участники и отправьте в группе `/start@имя_бота` (в группах бот по умолчанию видит только
   команды). Канал: добавьте бота администратором с правом публикации и опубликуйте любой пост.

3. **Узнайте `chat_id`.** Запросите последние обновления бота:

   ```bash
   curl -s "https://api.telegram.org/bot<ТОКЕН>/getUpdates"
   ```

   В ответе найдите `"chat":{"id":…}`: у личного чата это положительное число, у групп —
   отрицательное, у супергрупп и каналов — вида `-1001234567890`. Публичный канал можно указать
   и как `@имя_канала`. Если в группе включены темы (форум), номер темы — поле
   `message_thread_id` в том же ответе; его можно передать как `thread_id`. Если `result` пустой,
   отправьте в чат ещё одно сообщение и повторите запрос (для бота не должен быть настроен
   webhook, иначе `getUpdates` не работает).

4. **Создайте получателя:**

   ```bash
   curl -s -X POST $FLUX/api/notify/notifiers -H "$AUTH" -H "$J" -d '{
     "name": "Дежурные (Telegram)",
     "kind": {"type": "telegram", "bot_token": "7123456789:AAH…", "chat_id": "-1001234567890", "thread_id": null}
   }'
   # {"id":"g8ql9g2ab7","name":"Дежурные (Telegram)","enabled":true,
   #  "kind":{"type":"telegram","bot_token":"********","chat_id":"-1001234567890","thread_id":null},…}
   ```

5. **Отправьте тестовое сообщение** (в консоли — кнопка «Send test»):

   ```bash
   curl -s -X POST $FLUX/api/notify/notifiers/g8ql9g2ab7/test -H "$AUTH"
   # при верных токене и chat_id: {"ok":true,"latency_ms":184,"error":null}
   # с неверным токеном:          {"ok":false,"latency_ms":2096,"error":"HTTP 401",
   #                               "error_detail":"Telegram 401: Unauthorized"}
   ```

   При ошибке `ok` будет `false`, в `error` — код (`HTTP 401`), а в `error_detail` — ответ
   Telegram, например `"Telegram 401: Unauthorized"` (неверный токен),
   `"Telegram 400: Bad Request: chat not found"` (неверный `chat_id` или бот не добавлен в чат),
   `"Telegram 403: Forbidden: bot was blocked by the user"`.

6. **Создайте правило** — например, всё критичное, группировка 30 с, напоминание раз в 4 часа:

   ```bash
   curl -s -X POST $FLUX/api/notify/rules -H "$AUTH" -H "$J" -d '{
     "name": "Критичное — в Telegram",
     "notifier_ids": ["g8ql9g2ab7"],
     "match": {"min_severity": "critical"},
     "group_wait_secs": 30,
     "repeat_interval_secs": 14400,
     "send_resolved": true
   }'
   ```

Так выглядит сообщение об алерте:

```text
🔴 CRITICAL · Email queue is growing rapidly
Lag increased from 1.2k → 18k in 6 min
Possible reason: Consumers processing slower than producers.
Channel: email · Group: workers · Open for: 6m
Open in console

FluxMQ · prod · console
```

Сменить чат, не вводя токен заново, — отправьте `********` вместо токена:

```bash
curl -s -X PATCH $FLUX/api/notify/notifiers/g8ql9g2ab7 -H "$AUTH" -H "$J" \
  -d '{"kind":{"type":"telegram","bot_token":"********","chat_id":"-1009876543210","thread_id":15}}'
```

### Правила

```json
{
  "name": "Заказы: всё важное",
  "enabled": true,
  "notifier_ids": ["g8ql9g2ab7", "m7z7u5d7rp"],
  "match": {
    "min_severity": "warning",
    "alert_kinds": ["lag_growth", "consumer_stalled", "no_consumers", "dlq_growth"],
    "event_kinds": ["channel_deleted", "dead_lettered"],
    "channels": ["orders", "orders.*"]
  },
  "group_wait_secs": 30,
  "repeat_interval_secs": 14400,
  "send_resolved": true
}
```

- `min_severity` — `warning` (всё) или `critical` (только критичное). Относится только к
  алертам.
- `alert_kinds` — пусто = любые. Типы: `lag_growth`, `consumer_stalled`, `no_consumers`,
  `dlq_growth`, `high_retry_rate`, `slow_instance`, `storage_nearly_full`,
  `high_publish_latency`, `node_down`, `under_replicated_partitions`, `offline_partitions`.
- `event_kinds` — события брокера; пусто = **никаких** (события частые, включайте явно):
  `channel_created`, `channel_deleted`, `channel_updated`, `consumer_connected`,
  `consumer_disconnected`, `dead_lettered`, `dlq_retried`, `dlq_discarded`,
  `messages_replayed`, `controller_changed`, `node_down`, `node_up`.
- `channels` — маски каналов: `*` — любая последовательность символов (включая точки), `?` —
  один символ. Пусто = любые каналы. Если маски заданы, алерты без канала (например,
  `node_down`) правилу не подходят.

Пример правила только для событий — сообщать на вебхук об удалении каналов `orders*`:

```bash
curl -s -X POST $FLUX/api/notify/rules -H "$AUTH" -H "$J" -d '{
  "name": "Удаление каналов",
  "notifier_ids": ["uxhfsqi4d1"],
  "match": {"min_severity": "warning", "event_kinds": ["channel_deleted"], "channels": ["orders*"]},
  "group_wait_secs": 5
}'
```

Изменить или отключить правило — `PATCH /api/notify/rules/{id}` (например,
`{"enabled": false}`), удалить — `DELETE`. Получателя, которого использует правило, удалить
нельзя (`409` со списком правил) — сначала уберите его из правил. Отключённый получатель
(`"enabled": false`) ничего не отправляет; в истории такие сообщения отмечены `suppressed`.


`status`: `firing` (алерты в `alerts`), `resolved`, `event` (события в `events`) или `test`.
`id` уникален для каждой отправки — используйте его для дедупликации (повтор после сбоя
приходит с тем же `id`).

Подпись: `X-FluxMQ-Signature: t=<unix-время>,v1=<hex HMAC-SHA256(secret, "<t>.<тело>")>` —
та же схема, что у HTTP-вебхуков (примеры на Node.js и Go — в разделе 21,
«Проверка подписи»). Минимальный приёмник на Python (только стандартная библиотека):

```python
import hashlib, hmac, os, time
from http.server import BaseHTTPRequestHandler, HTTPServer

SECRET = os.environ["FLUXMQ_WEBHOOK_SECRET"].encode()

def verify(header: str, raw: bytes) -> bool:
    parts = dict(p.strip().split("=", 1) for p in header.split(",") if "=" in p)
    t = int(parts.get("t", "0"))
    if abs(time.time() - t) > 300:          # защита от повторов
        return False
    expected = hmac.new(SECRET, f"{t}.".encode() + raw, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, parts.get("v1", ""))

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        raw = self.rfile.read(int(self.headers.get("Content-Length", 0)))
        if not verify(self.headers.get("X-FluxMQ-Signature", ""), raw):
            self.send_response(401); self.end_headers(); return
        print(raw.decode())                 # разбирайте JSON только после проверки
        self.send_response(204); self.end_headers()

HTTPServer(("127.0.0.1", int(os.environ.get("PORT", "8099"))), Handler).serve_forever()
```

### История и тесты

```bash
curl -s -H "$AUTH" "$FLUX/api/notify/history?limit=3"
# [{"id":"gfznwqk01b","ts":1791447236769,"rule_id":"w693rb01je","notifier_id":"uxhfsqi4d1",
#   "status":"sent","summary":"event: Channel deleted orders.tmp","attempts":1,"error":null,
#   "error_detail":null},
#  {"id":"5fpi02e0ms",…,"rule_id":null,"notifier_id":"oiuvd78f4q","status":"failed",
#   "summary":"test message","attempts":1,"error":"HTTP 400",
#   "error_detail":"HTTP 400: Invalid routing key"}, …]
```

`status`: `sent`, `failed` (после всех попыток; короткая причина в `error`, подробности в
`error_detail`) или `suppressed` (получатель отключён). Тестовые отправки записываются с
`rule_id: null`. Сгруппированные отправки выглядят как `firing: 7 alerts`,
`resolved: 7 alerts`, `event: 6 events`. История хранится в канале `$system.notifications`
(7 дней) и не теряется при перезапуске или смене контроллера; канал виден в консоли только
для чтения, как любой системный. Тестовая отправка попадает в историю до ответа на запрос.

### Лента событий для внешних систем (pull)

Если принимать входящие запросы неудобно, забирайте события сами. Каждое открытие и закрытие
алерта и каждое событие брокера записывается в системный канал `$system.events` (1 раздел,
хранение 7 дней). Канал создаётся при старте, виден в консоли, но изменить, удалить или
опубликовать в него нельзя (`403`); читать его можно как любой канал — через SDK, HTTP-вебхук
или так:

```bash
# Всё, что сохранилось (с самого старого)
curl -s -H "$AUTH" "$FLUX/api/events/feed?limit=100"
# {"items":[{"cursor":"1","ts":1791447231765,"kind":"event","alert":null,
#   "event":{"id":3,"kind":"channel_created","title":"Channel created","subject":"orders.tmp",…},
#   "node":"n-ab4fce038c96"}, …],"next_cursor":"2","gap":false}

# Последние N записей (старые → новые) — чтобы показать «что было недавно»
curl -s -H "$AUTH" "$FLUX/api/events/feed?tail=3"
# {"items":[{"cursor":"28","kind":"alert_opened",…},{"cursor":"29",…},{"cursor":"30",…}],
#  "next_cursor":"30","gap":false}

# Дальше — только новое: передайте next_cursor и ждите до 25 с (long-poll)
curl -s -H "$AUTH" "$FLUX/api/events/feed?after=30&wait_ms=25000"
# возвращается, как только появилась запись (в проверке — через 2.4 с после создания канала):
# {"items":[{"cursor":"31","kind":"event","event":{"kind":"channel_created","subject":"feed.probe",…},…}],
#  "next_cursor":"31","gap":false}

# Только то, что появится после запроса
curl -s -H "$AUTH" "$FLUX/api/events/feed?after=latest"

# tail и after вместе нельзя; tail вне 1–1000 — тоже 400
curl -s -H "$AUTH" "$FLUX/api/events/feed?after=1&tail=5"
# {"error":"bad_request","message":"tail and after are mutually exclusive"}
```

- `kind`: `alert_opened`, `alert_resolved` (алерт в `alert`) или `event` (в `event`).
- `cursor` — позиция записи (offset в `$system.events`); в ответах ленты он заполнен всегда,
  передавайте `next_cursor` как `after` в следующем запросе. В самом канале записи хранятся с
  `"cursor": ""` (offset неизвестен до записи) — если читаете `$system.events` через SDK или
  HTTP-вебхук, курсор — это offset сообщения.
- `tail=N` (1–1000, нельзя вместе с `after`) — N самых свежих записей, от старых к новым; с
  `wait_ms` и пустой лентой ждёт, как `latest`. Удобно для первого показа, дальше — `after`.
- `wait_ms` (до 30000): если новых записей нет, запрос ждёт и возвращается сразу, как только
  они появятся.
- `gap: true` — часть записей после вашего `after` уже удалена по сроку хранения (вы долго не
  забирали ленту).
- Доступ: любой действующий токен, в том числе клиентский токен только с правом чтения.

### Как проверено

Все команды этого раздела выполнены на локальном брокере (release-сборка 0.3.0, трафик от
`fluxmq-demo`). Получатели webhook (с секретом и заголовком `Authorization`), Slack и Discord
указывали на локальный тестовый HTTP-приёмник, email — на локальный SMTP-приёмник (aiosmtpd);
подпись `X-FluxMQ-Signature` проверялась приёмником. Правило «warning и выше + событие
`channel_created`, group wait 10 с, send resolved» дало сгруппированные сообщения
(`event: 6 events`, `firing: 3 alerts`). Остановка `fluxmq-demo` (все консьюмеры отключились)
открыла алерты `no_consumers` — каждому получателю пришло одно сообщение `firing: 7 alerts`;
после повторного запуска демо пришло `resolved: 7 alerts`. Проверка правки без сохранения
(`/test` с телом) вернула короткую ошибку `connection refused` с подробностями в
`error_detail`, а сохранённый получатель не изменился. В кластере из трёх узлов событие
создания канала отправлено ровно один раз (контроллером), история видна с другого узла.
Настоящие Telegram и PagerDuty без действующих ключей проверить
нельзя: запросы с выдуманными ключами дошли до `api.telegram.org` и `events.pagerduty.com` и
получили ожидаемые ответы `Telegram 401: Unauthorized` и `HTTP 400: Invalid routing key`
(проверено в 0.3.0-разработке до перехода на короткие ошибки: теперь это `error: "HTTP 401"` /
`"HTTP 400"` с этим текстом в `error_detail`).
Формат запросов к Telegram и PagerDuty проверяется автотестами на имитации API
(`cargo test -p fluxmq-notify`).

## 21. HTTP-вебхуки (push)

Вебхук — это подписка, при которой брокер сам отправляет сообщения канала POST-запросами на
ваш HTTP-адрес. Потребителю не нужен SDK и постоянное TCP-соединение: достаточно HTTP-сервера,
который отвечает `2xx`.

Как это устроено:

- Каждый вебхук — это consumer group `$webhook:<name>` на своём канале. Лаг, ретраи, таймлайн
  попыток и DLQ видны в консоли так же, как у обычных групп.
- Определения хранятся в метаданных (`webhooks/<id>`) и сразу применяются на всех узлах. В
  кластере каждый узел доставляет сообщения разделов, лидером которых он является.
- `start` (`earliest` / `latest` / `{"timestamp_ms": …}`) действует только при создании
  группы. По умолчанию `latest` — только новые сообщения.
- Фильтр — тот же язык, что у маршрутизации (см. раздел 18). Сообщения, которые
  не подходят, подтверждаются без запроса и считаются в `skipped_by_filter`.
- Отключение (`"enabled": false`) ставит доставку на паузу: группа и её позиция сохраняются.
  Удаление останавливает доставку и удаляет группу.

### Создание и проверка (curl)

Чтение (`GET`) доступно роли viewer. Создание, изменение, удаление и тестовая отправка — роль
admin; в enforced-режиме добавьте `-H "Authorization: Bearer $TOKEN"`.

```bash
FLUX=http://127.0.0.1:7421

# Канал для примера
curl -s -X POST $FLUX/api/channels -H 'Content-Type: application/json' \
  -d '{"name":"orders","mode":"stream","partitions":4}'

# Проверить адрес до сохранения: одна синтетическая доставка, ничего не сохраняется
curl -s -X POST $FLUX/api/webhooks/test -H 'Content-Type: application/json' \
  -d '{"name":"orders-crm","channel":"orders","url":"http://127.0.0.1:8080/hooks/fluxmq","secret":"whsec_demo"}'
# {"ok":true,"status":204,"latency_ms":17,"response_snippet":null,"error":null,"error_detail":null}

# Создать вебхук: только заказы из Молдовы, строгий порядок, с начала канала
curl -s -X POST $FLUX/api/webhooks -H 'Content-Type: application/json' -d '{
    "name": "orders-crm",
    "channel": "orders",
    "url": "http://127.0.0.1:8080/hooks/fluxmq",
    "secret": "whsec_demo",
    "headers": {"Authorization": "Bearer crm-token"},
    "filter": [{"field": {"kind": "payload", "name": "country"}, "op": "eq", "value": "MD"}],
    "max_in_flight": 1,
    "start": "earliest"
  }'
# {"id":"5xptcxwhwo","name":"orders-crm",…,"headers":{"Authorization":"********"},"secret":"********",…}

# Опубликовать сообщения
curl -s -X POST $FLUX/api/channels/orders/publish -H 'Content-Type: application/json' -d '{"messages":[
  {"key":"order-1001","payload":{"encoding":"utf8","data":"{\"id\":1001,\"country\":\"MD\",\"amount\":250}"}},
  {"key":"order-1002","payload":{"encoding":"utf8","data":"{\"id\":1002,\"country\":\"RO\",\"amount\":90}"}}]}'

# Статистика (в кластере — сумма по всем узлам)
curl -s $FLUX/api/webhooks/stats
# [{"id":"5xptcxwhwo","delivered":1,"failed":0,"skipped_by_filter":1,"in_flight":0,
#   "last_status":204,"last_error":null,"last_error_detail":null,
#   "last_delivery_ms":1791446775074,"latency_p50_ms":2.688,"latency_p99_ms":2.688}]

# Отправить тестовую доставку существующему вебхуку (сохранённая конфигурация)
curl -s -X POST $FLUX/api/webhooks/5xptcxwhwo/test

# Проверить ПРАВКУ, не сохраняя её: тело — как у PATCH (UpdateWebhookRequest), накладывается
# на сохранённую подписку; "********" = сохранённый секрет / значение заголовка
curl -s -X POST $FLUX/api/webhooks/5xptcxwhwo/test -H 'Content-Type: application/json' \
  -d '{"secret":"********","headers":{"Authorization":"********","X-Env":"staging"}}'

# Поставить на паузу / удалить (группа $webhook:orders-crm удаляется вместе с вебхуком)
curl -s -X PATCH $FLUX/api/webhooks/5xptcxwhwo -H 'Content-Type: application/json' -d '{"enabled": false}'
curl -s -X DELETE $FLUX/api/webhooks/5xptcxwhwo
```

Остальные параметры: `timeout_ms` (100–60000, по умолчанию 10000), `max_in_flight` (1–64, по
умолчанию 4), `batch_max` (1–500, по умолчанию 1), `batch_linger_ms` (0–10000),
`retry_on_4xx` (по умолчанию `false`), `format` (`envelope` или `raw`). Нужно, чтобы
`timeout_ms + batch_linger_ms` был меньше `ack_timeout_ms` канала (по умолчанию 30 с), иначе
брокер отклонит настройку. `name`, `channel` и `start` после создания не меняются.

Секреты (`secret` и значения всех заголовков) API никогда не возвращает — вместо них
`********`. В `PATCH` значение `********` оставляет сохранённый секрет, `""` удаляет его,
любое другое значение заменяет. Поле `headers` в `PATCH` заменяет весь набор заголовков.

В консоли: раздел **Webhooks** в боковом меню (список со статистикой, редактор с конструктором
фильтра, *Send test*, ссылки на группу `$webhook:*` и её DLQ).

### Формат запроса

`POST <url>`, `Content-Type: application/json`, тело — конверт:

```json
{
  "delivery_id": "orders/1/0",
  "subscription": "orders-crm",
  "channel": "orders",
  "partition": 1,
  "offset": 0,
  "key": "order-1001",
  "headers": {},
  "timestamp_ms": 1791446775012,
  "attempt": 1,
  "payload": {"encoding": "utf8", "data": "{\"id\":1001,\"country\":\"MD\",\"amount\":250}"}
}
```

- `payload.encoding` — `utf8` для текста или `base64` для бинарных данных.
- `delivery_id` (`{channel}/{partition}/{offset}`) одинаков у всех повторов одного сообщения.
  Доставка «как минимум один раз», поэтому дедуплицируйте по нему.
- При `batch_max > 1` тело — JSON-массив конвертов, заголовок `X-FluxMQ-Batch-Size` — их
  число.
- При `"format": "raw"` тело — сами байты сообщения. Метаданные идут в заголовках
  `X-FluxMQ-Channel`, `-Partition`, `-Offset`, `-Key`, `-Timestamp` и
  `X-FluxMQ-Header-<имя>`. Режим `raw` нельзя сочетать с батчами.

Заголовки каждого запроса:

- `X-FluxMQ-Delivery-Id`;
- `X-FluxMQ-Attempt` — номер попытки, начиная с 1;
- ваши заголовки из `headers`;
- `X-FluxMQ-Signature: t=<unix-время>,v1=<hex HMAC-SHA256(secret, "<t>.<тело>")>`, если задан
  `secret`.

### Проверка подписи

Подпись считается по **сырому** телу запроса: не разбирайте и не пересериализуйте JSON до
проверки. Сравнивайте в постоянное время и отклоняйте старые метки времени (защита от
повторов). Все три примера проверены на живом брокере. Секрет передаётся через переменную
окружения `FLUXMQ_WEBHOOK_SECRET`, порт — через `PORT`.

Node.js (18+, без зависимостей):

```js
// Node.js 18+: npm-free receiver with signature verification.
const http = require("node:http");
const crypto = require("node:crypto");

const SECRET = process.env.FLUXMQ_WEBHOOK_SECRET;
const TOLERANCE_SECS = 300;

function verify(header, rawBody) {
  const parts = Object.fromEntries(
    (header || "").split(",").map((p) => p.trim().split("=", 2)),
  );
  const t = Number(parts.t);
  if (!t || !parts.v1) return false;
  if (Math.abs(Date.now() / 1000 - t) > TOLERANCE_SECS) return false;
  const expected = crypto
    .createHmac("sha256", SECRET)
    .update(`${t}.`)
    .update(rawBody)
    .digest();
  const got = Buffer.from(parts.v1, "hex");
  return got.length === expected.length && crypto.timingSafeEqual(got, expected);
}

http
  .createServer((req, res) => {
    const chunks = [];
    req.on("data", (c) => chunks.push(c));
    req.on("end", () => {
      const raw = Buffer.concat(chunks);
      if (!verify(req.headers["x-fluxmq-signature"], raw)) {
        res.writeHead(401).end("bad signature");
        return;
      }
      const msg = JSON.parse(raw);
      // Dedupe on delivery_id: retries of the same message reuse it.
      console.log("node ok", msg.delivery_id, "attempt", msg.attempt);
      res.writeHead(204).end();
    });
  })
  .listen(Number(process.env.PORT || 8080));
```

Python 3 (только стандартная библиотека):

```python
# Python 3 standard library only.
import hashlib, hmac, json, os, time
from http.server import BaseHTTPRequestHandler, HTTPServer

SECRET = os.environ["FLUXMQ_WEBHOOK_SECRET"].encode()
TOLERANCE_SECS = 300

def verify(header: str, raw: bytes) -> bool:
    try:
        parts = dict(p.strip().split("=", 1) for p in header.split(","))
        t = int(parts["t"])
    except (KeyError, ValueError):
        return False
    if abs(time.time() - t) > TOLERANCE_SECS:
        return False
    expected = hmac.new(SECRET, f"{t}.".encode() + raw, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, parts.get("v1", ""))

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        raw = self.rfile.read(int(self.headers.get("Content-Length", 0)))
        if not verify(self.headers.get("X-FluxMQ-Signature", ""), raw):
            self.send_response(401); self.end_headers(); return
        msg = json.loads(raw)
        print("python ok", msg["delivery_id"], "attempt", msg["attempt"], flush=True)
        self.send_response(204); self.end_headers()

HTTPServer(("0.0.0.0", int(os.environ.get("PORT", 8080))), Handler).serve_forever()
```

Go (только стандартная библиотека):

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"encoding/json"
	"fmt"
	"io"
	"math"
	"net/http"
	"os"
	"strconv"
	"strings"
	"time"
)

var secret = []byte(os.Getenv("FLUXMQ_WEBHOOK_SECRET"))

const toleranceSecs = 300

func verify(header string, raw []byte) bool {
	var t int64
	var sig []byte
	for _, p := range strings.Split(header, ",") {
		k, v, _ := strings.Cut(strings.TrimSpace(p), "=")
		switch k {
		case "t":
			t, _ = strconv.ParseInt(v, 10, 64)
		case "v1":
			sig, _ = hex.DecodeString(v)
		}
	}
	if t == 0 || sig == nil || math.Abs(float64(time.Now().Unix()-t)) > toleranceSecs {
		return false
	}
	mac := hmac.New(sha256.New, secret)
	fmt.Fprintf(mac, "%d.", t)
	mac.Write(raw)
	return hmac.Equal(sig, mac.Sum(nil))
}

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		raw, _ := io.ReadAll(r.Body)
		if !verify(r.Header.Get("X-FluxMQ-Signature"), raw) {
			http.Error(w, "bad signature", http.StatusUnauthorized)
			return
		}
		var msg struct {
			DeliveryID string `json:"delivery_id"`
			Attempt    int    `json:"attempt"`
		}
		_ = json.Unmarshal(raw, &msg)
		fmt.Println("go ok", msg.DeliveryID, "attempt", msg.Attempt)
		w.WriteHeader(http.StatusNoContent)
	})
	port := os.Getenv("PORT")
	if port == "" {
		port = "8080"
	}
	http.ListenAndServe(":"+port, nil)
}
```

### Повторы и DLQ

| Ответ получателя | Что делает брокер | Причина в DLQ |
|---|---|---|
| `2xx` | подтверждает (ack) | — |
| `408`, `425`, `429`, `5xx` | повтор по политике канала (`retry.backoff_ms`, `max_attempts`) | `HTTP <код>` |
| таймаут (`timeout_ms`) | повтор | `timeout` |
| соединение отклонено | повтор | `connection refused` |
| прочие ошибки соединения, DNS, TLS | повтор | `connection failed`, `DNS error`, `TLS error` |
| адрес запрещён политикой SSRF в момент доставки | сразу в DLQ, **без повторов** (одна попытка) | `blocked by policy` |
| остальные `4xx` | сразу в DLQ, без повторов (с `retry_on_4xx: true` — повтор) | `HTTP <код>` |
| `3xx` | сразу в DLQ: редиректы не выполняются | `HTTP <код>` |

- `Retry-After` в ответе (секунды или HTTP-дата) учитывается, но не дольше максимального
  `backoff_ms` канала. Брокер держит сообщение примерно `min(Retry-After, max backoff) −
  очередной backoff`, затем возвращает его в очередь повторов.
- Когда попытки исчерпаны, сообщение попадает в DLQ канала с группой `$webhook:<name>`. В
  инбоксе DLQ причины группируются (`HTTP 503`, `timeout`, …), оттуда же сообщения можно
  повторить.
- В `GET /api/webhooks/stats`: `last_status` — HTTP-код **последней** попытки (`null`, если она
  не получила ответа), `last_error` — короткая причина последней неудачи (те же классы, что в
  DLQ), `last_error_detail` — полный текст (цепочка ошибок или начало ответа). Так выглядел
  получатель, отвечавший `503` (3 попытки на сообщение, затем DLQ с причиной `HTTP 503`):

  ```text
  {"id":"stwz6quztz","delivered":3,"failed":6,…,"last_status":503,"last_error":"HTTP 503",
   "last_error_detail":"HTTP 503: upstream down",…}
  ```

### Порядок доставки

- `max_in_flight: 1` — строгий порядок внутри раздела. Если запрос не удался, брокер ничего не
  отправляет, пока не подойдёт время повтора этого сообщения, и следующие сообщения раздела не
  обгоняют его. Но пока идёт backoff, на паузе вся подписка, включая другие разделы. Строгий
  порядок гарантирован при `batch_max: 1`; с батчами порядок при ошибках не гарантирован.
- `max_in_flight > 1` — запросы идут параллельно, порядок не гарантирован, пропускная
  способность выше. Ориентиры на локальном получателе (release, см. BENCHMARKS.md): ~25 тыс. сообщений/с при
  `max_in_flight: 1`, ~65–68 тыс./с при 16–64, ~500 тыс./с при `max_in_flight: 4` и
  `batch_max: 100`.
- Если нужен порядок по ключу, а не по разделу целиком, используйте канал `keyed`.

### Безопасность (SSRF)

По умолчанию вебхук не может обращаться к loopback-, приватным, link-local, CGNAT- и
multicast-адресам (`127.0.0.1`, `10.0.0.0/8`, `192.168.0.0/16`, `169.254.169.254`, `::1`, …).
Брокер проверяет адрес при сохранении и тесте (резолвит имя хоста) и ещё раз при каждом
запросе (защита от DNS rebinding). Редиректы и прокси не используются.

- В open-режиме (без токенов, dev) приватные адреса разрешены, чтобы можно было тестировать на
  localhost.
- Когда авторизация включена (`--admin-token` или есть токены), приватные адреса запрещены:

  ```text
  {"error":"bad_request","message":"url resolves to a private/loopback/link-local address (::1); start the broker with --webhooks-allow-private to allow it"}
  ```

  Уже сохранённый вебхук на такой адрес (например, созданный в open-режиме) при доставке не
  повторяется: сообщение сразу уходит в DLQ с причиной `blocked by policy`, а статистика и
  тестовая отправка показывают:

  ```text
  {"id":"stwz6quztz",…,"last_status":null,"last_error":"blocked by policy",
   "last_error_detail":"blocked address 127.0.0.1 (private targets are not allowed)",…}
  {"ok":false,"status":null,"latency_ms":0,"response_snippet":null,"error":"blocked by policy",
   "error_detail":"blocked address 127.0.0.1 (private targets are not allowed)"}
  ```

- Явная настройка: `--webhooks-allow-private` (или `--webhooks-allow-private=false`),
  переменная `FLUXMQ_WEBHOOKS_ALLOW_PRIVATE=true|false`.

## 22. Бэкапы и восстановление

FluxMQ умеет делать **консистентные инкрементальные бэкапы** без остановки брокера: в
S3-совместимое хранилище (AWS S3, MinIO, Cloudflare R2, Backblaze B2) или в каталог на диске.
Восстановление — отдельной командой в пустой каталог данных.

### Что попадает в бэкап

- **Сообщения** всех каналов: по каждому разделу — данные до консистентной точки среза
  (`end` в манифесте). Публикации во время бэкапа не блокируются и в бэкап не попадают.
- **Конфигурации каналов**, **offset'ы consumer groups**, **DLQ** — снимаются сразу после среза
  сообщений. Поэтому после восстановления часть сообщений может прийти повторно (at-least-once),
  но ничего не теряется.
- **Метаданные**: маршруты, токены доступа (только хэши), нотификаторы, вебхуки. Настройки самих
  бэкапов (`backup/*`, там ключи S3) в бэкап **не** попадают.

Бэкапы инкрементальные: закрытые сегменты неизменяемы и загружаются один раз, следующие бэкапы
их переиспользуют (в истории — колонка «reused»). Активный (ещё дописываемый) сегмент каждого
раздела загружается заново при каждом запуске, поэтому пока каналы малы и все их сегменты
активные, экономии почти нет (в проверке на ~40 МБ данных второй бэкап переиспользовал 2
сегмента из 25). Ненужные объекты удаляются автоматически после ротации.

### Настройка в консоли

**Settings → Backups**: цель (S3 или каталог), кнопка **Test connection** (запишет, прочитает и
удалит пробный объект), расписание, ротация, шифрование, **Run now** с прогрессом, история и
готовая команда восстановления. Менять настройки и запускать бэкапы может только admin;
viewer видит статус и историю, секреты всегда показываются как `********`.

### Настройка через REST

Каталог на диске (удобно для проверки и для NFS):

```bash
curl -X PUT http://localhost:7421/api/backups/config \
  -H 'Content-Type: application/json' -H "Authorization: Bearer $ADMIN" \
  -d '{"enabled": true,
       "target": {"type": "filesystem", "path": "/var/backups/fluxmq"},
       "interval_secs": 3600, "keep_last": 24, "keep_days": 7,
       "include_messages": true, "encryption_key": null}'
```

**AWS S3:**

```json
"target": {"type": "s3", "endpoint": null, "region": "eu-central-1",
           "bucket": "my-fluxmq-backups", "prefix": "prod",
           "access_key_id": "AKIA…", "secret_access_key": "…", "path_style": false}
```

**MinIO** (path-style обязателен):

```json
"target": {"type": "s3", "endpoint": "http://minio.local:9000", "region": "us-east-1",
           "bucket": "fluxmq", "prefix": "", "access_key_id": "minioadmin",
           "secret_access_key": "minioadmin", "path_style": true}
```

**Cloudflare R2** (регион `auto`, endpoint с id аккаунта):

```json
"target": {"type": "s3", "endpoint": "https://<account_id>.r2.cloudflarestorage.com",
           "region": "auto", "bucket": "fluxmq", "prefix": "prod",
           "access_key_id": "<R2 access key>", "secret_access_key": "<R2 secret>",
           "path_style": true}
```

Бакет нужно создать заранее; ключу достаточно прав на чтение, запись, удаление и листинг в
нём. Проверить доступ до сохранения:

```bash
curl -X POST http://localhost:7421/api/backups/test-target \
  -H 'Content-Type: application/json' -H "Authorization: Bearer $ADMIN" \
  -d '{"type": "filesystem", "path": "/var/backups/fluxmq"}'
# {"ok":true,"latency_ms":34,"error":null,"error_detail":null}
```

При ошибке `error` — короткая причина, `error_detail` — полный ответ хранилища. Примеры из
проверки на S3-эмуляторе:

```text
{"ok":false,"latency_ms":8,"error":"bucket not found","error_detail":"write failed: Object at location probe/….txt not found: … <Code>NoSuchBucket</Code> …"}
{"ok":false,…,"error":"connection failed","error_detail":"write failed: Generic S3 error: Error performing PUT http://127.0.0.1:15001/… after 10 retries … HTTP error: error sending request"}
```

Другие короткие причины: `access denied`, `invalid credentials`, `permission denied`
(каталог), `timeout`, `TLS error`, `DNS error`.

Секреты (`secret_access_key`, `encryption_key`) в ответах всегда `********`. При обновлении
настроек `********` означает «оставить сохранённое значение», пустая строка `""` — «удалить».

### Расписание и ротация

| Поле | Смысл |
|---|---|
| `enabled` | включает запуск по расписанию (ручной запуск работает всегда) |
| `interval_secs` | период, не меньше 300 с; отсчитывается от начала предыдущего бэкапа |
| `keep_last` | сколько последних бэкапов хранить (≥ 1) |
| `keep_days` | дополнительно удалять бэкапы старше N дней (0 — без ограничения по возрасту) |
| `include_messages` | `false` — только метаданные, offset'ы и DLQ (быстро и мало места) |

Самый свежий бэкап не удаляется никогда. Первый плановый бэкап после старта — через минуту
(или по расписанию, если в хранилище уже есть недавний бэкап). Запуск вручную и статус:

```bash
curl -X POST -H "Authorization: Bearer $ADMIN" http://localhost:7421/api/backups/run
curl -H "Authorization: Bearer $TOKEN" http://localhost:7421/api/backups/status   # прогресс: progress_bytes / total_bytes
curl -H "Authorization: Bearer $TOKEN" http://localhost:7421/api/backups          # история
```

Успешные, неудачные и удалённые ротацией бэкапы записываются в журнал действий (Audit).

Что внутри конкретного бэкапа (`latest` — самый свежий) — `BackupManifest`: `info` (как в
истории), `node_id` (кто записал манифест; в кластере — контроллер), `cluster_name`,
`fluxmq_version`, `include_messages`, `encryption` (отпечаток ключа или `null`), `nodes` (узлы,
загрузившие данные разделов) и сводка по каналам. Ключи объектов и CRC наружу не отдаются.

```bash
curl -H "Authorization: Bearer $TOKEN" http://localhost:7421/api/backups/latest
# {"info":{"id":"20261008T091952Z-775eee","status":"succeeded",…,"messages":119964,
#   "segments_uploaded":23,"segments_reused":2,…},
#  "node_id":"n-d150aea0ac54","cluster_name":"local","fluxmq_version":"0.3.0",
#  "include_messages":true,"encryption":null,"nodes":["n-d150aea0ac54"],
#  "channels":[{"name":"$system.events","mode":"stream","partitions":1,"messages":104,
#    "bytes":39076,"segments":1,"groups":0,"dlq_entries":0},
#   {"name":"email","mode":"queue","partitions":1,"messages":20018,"bytes":4274403,
#    "segments":1,"groups":1,"dlq_entries":0}, …]}
```

### Шифрование

Если задан `encryption_key`, каждый объект шифруется на стороне брокера (AES-256-GCM) до
отправки в хранилище; владелец бакета видит только шифротекст. Ключ — 32 случайных байта в
base64:

```bash
openssl rand -base64 32
```

> **Внимание: потеряли ключ — потеряли бэкап.** Восстановить зашифрованный бэкап без ключа
> невозможно, FluxMQ не хранит ключ нигде, кроме своих настроек. Сохраните ключ в менеджере
> секретов отдельно от брокера. После смены ключа старые бэкапы восстанавливаются только старым
> ключом (в манифесте хранится отпечаток ключа, и при неверном ключе restore сразу сообщает об
> этом).

   ```text
   encryption: wrong encryption key for backup '20261008T092120Z-0082ea' (key fingerprint 60de5ba7f818ef2c, backup needs a1293b09c57b433a)
   ```

   В непустой каталог restore писать откажется. Каждый сегмент
   проверяется (длина, CRC объекта, CRC каждой записи); если что-то не так, restore
   останавливается — удалите каталог и повторите.

3. Запустите брокер на восстановленном каталоге:

   ```bash
   fluxmq --data-dir /var/lib/fluxmq-restored
   ```

   Consumer groups продолжат с сохранённых offset'ов, DLQ, маршруты, токены, получатели
   уведомлений, вебхуки и настройки каналов на месте (в проверке: тот же admin-токен работал,
   9 каналов, 73 записи DLQ с теми же причинами, группы с небольшим лагом — повторная доставка
   хвоста, at-least-once). Настройки бэкапов не восстанавливаются — задайте их заново.

Бэкап остановленного брокера без консоли (например, перед переездом):

```bash
fluxmq backup run --data-dir /var/lib/fluxmq --fs-path /mnt/backup   # брокер должен быть остановлен!
```

Флаги цели у всех команд одинаковые; у `backup run` есть ещё `--encryption-key` и
`--no-messages`. Ротация при этом не выполняется (её делает брокер после своих бэкапов).

### Кластер

В версии 0.3 бэкап кластера поддерживается:

- Расписание и `POST /api/backups/run` выполняются на **контроллере**; запрос к любому другому
  узлу проксируется на контроллер (так же `GET /api/backups/status` — прогресс виден с любого
  узла).
- Контроллер просит каждый узел (`POST /internal/v1/backup/partial`, общий секрет кластера)
  срезать и загрузить разделы, лидером которых тот сейчас является. Узлы берут настройки
  бэкапа из общих метаданных и отказываются, если их копия ещё не совпадает с контроллерской.
- Контроллер проверяет, что каждый раздел каждого канала покрыт (раздел, у которого во время
  бэкапа не было лидера, — ошибка, повторите запуск), записывает offset'ы групп, DLQ,
  метаданные и манифест: `node_id` — контроллер, `nodes` — узлы, загрузившие данные.
- Если в кластере есть узел версии ниже 0.3.0, запуск отклоняется:
  HTTP 400 `{"error":"unsupported_in_cluster","message":"this cluster can't run backups: …"}`.
- Restore всегда создаёт **одиночный узел** (ключи `cluster/*` отбрасываются) — из него можно
  поднять новый кластер.

Проверено на кластере из трёх узлов (порты из CLUSTER.md, S3-эмулятор): канал `orders` из 6
разделов с лидерами на n1, n2 и n3, бэкап запущен через n3, манифест записал n1 с
`"nodes":["n1","n2","n3"]`; `fluxmq restore` в пустой каталог и запуск одиночного узла — все 30
сообщений на месте, вебхук и группа восстановлены.

### Ограничения

- Активные сегменты загружаются заново при каждом запуске (см. выше); в кластере срезы разных
  лидеров снимаются в немного разные моменты, а прогресс чужих разделов появляется по мере
  завершения каждого узла.
- Не направляйте два брокера (или брокер и `fluxmq backup run`) в один и тот же префикс
  хранилища: сборка мусора одного может удалить объекты, которые другой ещё не записал в манифест.
- Манифест (`manifests/<id>.json`) не шифруется — в нём имена и настройки каналов и диапазоны
  offset'ов, но не сообщения.
- DLQ канала хранится в бэкапе одним JSON-объектом (полезные нагрузки — массивами байтов), так
  что очень большой DLQ раздувает бэкап.
- Без ключей доступа (`access_key_id` пустой) клиент S3 пытается получить временные ключи из
  метаданных инстанса AWS — это работает только на EC2/ECS с IAM-ролью.

## 23. Ребалансировка

С версии 0.4 контроллер кластера сам следит за размещением реплик: восстанавливает фактор
репликации после потери узла и выравнивает нагрузку, когда в кластер добавили узел. Одиночного
узла это не касается.

### Что делает ребалансировка

- **Восстановление (repair).** Если узел лежит (`Down`) дольше `replace_after_secs` (по умолчанию
  600 с), его реплики переезжают на живые узлы — фактор репликации восстанавливается. Канал,
  созданный, когда живых узлов было меньше, чем `--replication-factor` (RF был урезан), дорастает
  до нужного RF, как только узлов хватает. Реплика с мёртвого узла убирается только если есть,
  куда её перенести, — число копий никогда не уменьшается.
- **Выравнивание (balance).** Если разница между самым загруженным и самым свободным живым узлом
  (`max − min` реплик) больше `imbalance_threshold` (по умолчанию 1), планировщик переносит
  минимально возможное число реплик с перегруженных узлов на свободные. Затем так же
  выравниваются **предпочтительные лидеры** (первая реплика раздела) — это только порядок реплик,
  данные не копируются; лидерство переходит на предпочтительную реплику обычным выбором лидера.
  Новый узел получает свою долю примерно через `node_timeout + 4 с` (≈10 с) после того, как стал
  `Up`, плюс до 30 с до ближайшей проверки.

Целевыми никогда не становятся узлы `Down`, `Leaving` (drain) и только что поднявшиеся.
Разделы без живого лидера не трогаются (копировать неоткуда). Две реплики одного раздела на
одном узле невозможны.

### Как переезжает раздел

1. К списку реплик добавляются новые (`replicas = старые ∪ новые`), лидер и epoch не меняются.
   Новые реплики догоняют лидера, но **не входят в ISR**, пока не догонят, — публикации их не
   ждут.
2. Когда все новые реплики в ISR, фиксируется итоговый список (epoch + 1). Удалённые реплики
   выходят из ISR и удаляют свою локальную копию. Если лидер был среди удалённых, лидером
   становится живая реплика из ISR.
3. Лидерство переходит на предпочтительную реплику (первую в списке).

Каждый шаг — обычная запись назначения с проверкой ревизии (CAS), клиенты и репликация
отрабатывают его так же, как failover: SDK получает `MetadataChanged`/`NotLeader` и повторяет
запрос. Подтверждённые сообщения не теряются. Одновременно переезжает не больше
`max_concurrent_moves` разделов; если новые реплики не попали в ISR за `move_timeout_secs`,
переезд откатывается к старому списку. План хранится в метаданных
(`cluster/rebalance/plan`), поэтому новый контроллер после failover продолжает его с того же
места.

Автоматические проверки идут не чаще раза в 30 с и не запускаются, пока выполняется план.

### Режимы и настройки

Режим при первом запуске кластера задаёт флаг `--auto-rebalance off|repair|full`
(`FLUXMQ_AUTO_REBALANCE`, по умолчанию `full`). Дальше источник истины — настройки в
метаданных, их меняют через API или консоль; флаг на уже настроенном кластере ничего не меняет.

| Режим | Что происходит само |
|---|---|
| `off` | ничего (как в 0.3); ручной запуск работает |
| `repair` | только восстановление RF |
| `full` | восстановление + выравнивание реплик и лидеров |

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `mode` | `full` | режим (см. выше) |
| `max_concurrent_moves` | 2 | сколько разделов переезжает одновременно на весь кластер |
| `imbalance_threshold` | 1 | допустимая разница `max − min` реплик на живой узел |
| `replace_after_secs` | 600 | через сколько секунд `Down` заменять реплики узла; `0` — никогда |
| `throttle_bytes_per_sec` | 0 | ограничение скорости догоняющей реплики (байт/с на реплику; 0 — без ограничения); реплики в ISR не ограничиваются |
| `move_timeout_secs` | 1800 | после этого переезд откатывается |

`replace_after_secs` намеренно большой: короткий перезапуск или обслуживание узла не должны
вызывать копирование всех его данных.

### Консоль

**Nodes → Rebalancing**: нагрузка по узлам (реплики, лидеры, объём), бейдж дисбаланса, число
недореплицированных разделов, текущий план (таблица переездов с состоянием и отставанием
догоняющих реплик) и причина запуска, прогноз нагрузки после плана, кнопки **Rebalance now**
(сначала предпросмотр, потом подтверждение), **Pause / Resume / Cancel** и форма настроек.
Изменять может только admin.

### REST API

```bash
# Состояние: настройки, нагрузка, дисбаланс, текущий/последний план (роль viewer)
curl -s 127.0.0.1:17421/api/cluster/rebalance | jq '{state, imbalance, under_replicated, trigger, load}'

# Настройки (admin) — передаётся объект целиком
curl -s -X PUT 127.0.0.1:17421/api/cluster/rebalance/config -H 'content-type: application/json' \
  -d '{"mode":"full","max_concurrent_moves":2,"imbalance_threshold":1,
       "replace_after_secs":600,"throttle_bytes_per_sec":0,"move_timeout_secs":1800}'

# Предпросмотр плана — ничего не меняет (admin); channels пустой = все каналы
curl -s -X POST 127.0.0.1:17421/api/cluster/rebalance -H 'content-type: application/json' \
  -d '{"dry_run":true,"channels":["orders"]}' | jq '.moves[] | {channel, partition, from_replicas, to_replicas}, .projected_load'

# Запустить сейчас (работает и в режиме off; порог дисбаланса не учитывается)
curl -s -X POST 127.0.0.1:17421/api/cluster/rebalance -H 'content-type: application/json' -d '{}'

# Пауза (новые переезды не начинаются, текущие доходят до конца), продолжение, отмена
curl -s -X POST 127.0.0.1:17421/api/cluster/rebalance/pause
curl -s -X POST 127.0.0.1:17421/api/cluster/rebalance/resume
curl -s -X POST 127.0.0.1:17421/api/cluster/rebalance/cancel
```

Запросы можно слать на любой узел — они выполняются контроллером. `state`: `idle`, `running`,
`paused`, `cancelling` (ждёт окончания текущих переездов; отмена никогда не оставляет раздел с
меньшим числом реплик, чем было). Состояния переезда: `pending`, `catching_up` (с `lag` и
`initial_lag` — прогресс = 1 − lag / initial_lag), `finalizing`, `done`, `rolled_back` (с
текстом ошибки), `cancelled` (не начатый переезд отменённого плана). Запуск, пока план
выполняется, на паузе или отменяется, — 409 `conflict` (предпросмотр можно всегда);
неизвестный канал в `channels` — 404. `load` перечисляет все зарегистрированные узлы со
статусом (у `Down`/`Leaving` видны оставшиеся на них реплики), дисбаланс считается только по
узлам `Up`. Каждая команда отвечает итоговым `RebalanceStatus`.
На одиночном узле `GET` возвращает `mode: off`, `state: idle`, а изменения — 400
`unsupported_single_node`.

### События

В ленту событий (и `$system.events`, и уведомления) попадают `rebalance_started` (субъект —
причина: `node n4 joined`, `node n2 down 605s`, `imbalance 3 > threshold 1`, `manual`),
`replica_repair_started` (узел, чьи реплики заменяются), `partition_moved` (субъект
`канал/раздел`, заголовок вида `n1,n2 → n2,n4`), `rebalance_completed` (заголовок «completed»
или «cancelled» с числом выполненных и откаченных переездов) и `rebalance_failed` (были
откаты). План вывода узла (раздел 19) даёт те же события с причиной `decommission <id>`, а сам
вывод — события `node_decommission_started`, `node_decommissioned`, `node_decommission_failed`
и `node_forgotten` (субъект — id узла). Все эти события каждый узел выводит из реплицируемого
состояния, поэтому лента одинакова на любом узле.

### Ограничения

- Планировщик считает реплики, а не байты: объём хранилища используется только чтобы выбрать
  между одинаково загруженными узлами. Нет rack/AZ-awareness.
- Пока идёт вывод узла (раздел 19), его план нельзя заменить другим: `POST
  /api/cluster/rebalance` отвечает 409; отмена плана вывода (`…/rebalance/cancel`) завершает
  вывод как `failed` (`cancelled`), узел снова `Up`.
- После неудачного (с откатами) плана автоматические проверки делают паузу на 10 интервалов
  (5 минут), чтобы не повторять один и тот же переезд по кругу. С 0.5 пауза не касается
  восстановления (`repair`) упавшего узла: его реплики заменяются и во время паузы.

## 24. TLS

С версии 0.4 брокер умеет шифровать все три вида трафика. Их настраивают независимо:

| Поверхность | Порт | Что защищает |
|---|---|---|
| `client` | 7420 | бинарный протокол SDK; по желанию — клиентские сертификаты (mTLS) |
| `http` | 7421 | REST, WebSocket, веб-консоль (HTTPS) |
| `cluster` | 7422, 7423, внутренний HTTP | Raft, репликацию и `/internal/*` между узлами — всегда взаимный TLS |

Используется rustls (провайдер aws-lc-rs), TLS 1.2 и 1.3. **Без TLS-флагов всё работает как
раньше** — открытым текстом. Открытый текст и TLS на одном порту не смешиваются: TLS-порт
отвергает клиента без TLS (и считает это неудачным рукопожатием).

### Сертификаты для разработки: `gen-dev`

```bash
./target/release/fluxmq tls gen-dev --out ./certs --nodes n1,n2,n3 --hosts localhost,127.0.0.1
```

| Файл | Для чего |
|---|---|
| `ca.pem` / `ca-key.pem` | учебный CA: `--tls-client-ca`, `--cluster-tls-ca`, `--tls-ca` у клиентов |
| `server.pem` / `server-key.pem` | клиентский и HTTP-порт (`--tls-cert/--tls-key`), SAN = `--hosts` |
| `client.pem` / `client-key.pem` | клиентский сертификат для mTLS (CN `client`) |
| `node-<id>.pem` / `node-<id>-key.pem` | сертификат узла кластера (CN = id узла, SAN = `--hosts`) |

Ключи пишутся с правами `0600`; существующие файлы не перезаписываются без `--force`.

- `--valid-days N` — срок действия выпускаемых сертификатов (по умолчанию 397 дней; сам CA —
  10 лет). Например, `--valid-days 5` даёт сертификат, на котором сразу срабатывает алерт
  `tls_cert_expiring`.
- `--reuse-ca` — выпустить сертификаты от уже лежащих в `--out` `ca.pem` / `ca-key.pem`, не
  создавая новый CA (файлы CA не меняются). Так удобно проверять ротацию: перевыпустить
  сертификат узла тем же CA (`--reuse-ca --force --nodes n2`) и отправить узлу `SIGHUP`.

> `gen-dev` — только для разработки: ключ CA лежит рядом с сертификатами. В продакшене
> выпускайте сертификаты своим CA (или публичным — для HTTP-порта) и передавайте брокеру PEM-файлы.

### Флаги

| Флаг | Переменная | Смысл |
|---|---|---|
| `--tls-cert`, `--tls-key` | `FLUXMQ_TLS_CERT`, `FLUXMQ_TLS_KEY` | PEM-цепочка и ключ: TLS на клиентском порту и (по умолчанию) на HTTP |
| `--tls-client-ca` | `FLUXMQ_TLS_CLIENT_CA` | CA клиентских сертификатов: включает mTLS на клиентском порту |
| `--http-tls-cert`, `--http-tls-key` | `FLUXMQ_HTTP_TLS_CERT`, `FLUXMQ_HTTP_TLS_KEY` | отдельный сертификат для HTTP-порта |
| `--http-tls on\|off` | `FLUXMQ_HTTP_TLS` | `off` оставляет HTTP открытым (например, за TLS-прокси); по умолчанию HTTPS, если есть сертификат |
| `--cluster-tls-cert`, `--cluster-tls-key`, `--cluster-tls-ca` | `FLUXMQ_CLUSTER_TLS_CERT`, `_KEY`, `_CA` | взаимный TLS между узлами; нужны все три, только с `--peers` |

Неполные или противоречивые сочетания (сертификат без ключа, `--tls-client-ca` без
`--tls-cert`, `--http-tls on` без сертификата) брокер отвергает при старте с понятной ошибкой.
Нечитаемый или битый PEM — тоже ошибка старта, а не тихий откат на открытый текст.

### Одиночный узел: TLS и mTLS

```bash
./target/release/fluxmq --data-dir ./data \
  --tls-cert ./certs/server.pem --tls-key ./certs/server-key.pem \
  --tls-client-ca ./certs/ca.pem
```

В баннере при старте видно `clients: tls://…`, `http: https://…` и строку `tls:` с субъектами
сертификатов. Проверка:

```bash
curl --cacert ./certs/ca.pem https://localhost:7421/api/health
openssl s_client -connect localhost:7420 -CAfile ./certs/ca.pem \
  -cert ./certs/client.pem -key ./certs/client-key.pem </dev/null | head -20
```

**mTLS.** С `--tls-client-ca` клиент обязан предъявить сертификат, подписанный этим CA; без него
или с чужим сертификатом соединение рвётся на рукопожатии. CN сертификата показывается рядом с
адресом подключения — в консоли (Consumers → instance) и в логах: `127.0.0.1:52144 (tls:orders-svc)`.
Сам CN — только подсказка: права задаёт токен в `Hello` или, с 0.5, привязка сертификата
(ниже).

### Привязки сертификатов (с 0.5)

Привязка сопоставляет CN проверенного клиентского сертификата с ролью и scopes, как у
токена. Клиент с таким сертификатом подключается **без токена**:

- если в `Hello` есть `auth_token`, решает токен (даже если у CN есть привязка; неверный токен
  не «спасается» сертификатом);
- если токена нет, а у CN сертификата есть привязка — клиент получает её роль и scopes;
- если нет ни токена, ни привязки — `Unauthorized`.

Привязки работают только на клиентском порту и только с `--tls-client-ca` (тогда CN проверен
CA). Без mTLS они хранятся, но ни на что не влияют: `GET` показывает
`"client_mtls_enabled": false`. HTTP (REST, WebSocket, консоль) по-прежнему требует токен.
Управление — только роль admin:

```bash
# Сервис с сертификатом CN=billing-svc может писать в billing.* и читать billing.events
curl -s --cacert ./certs/ca.pem -X POST https://localhost:7421/api/auth/cert-bindings \
  -H "Authorization: Bearer $ADMIN" -H 'Content-Type: application/json' \
  -d '{"cn":"billing-svc","role":"viewer",
       "scopes":{"publish":["billing.*"],"consume":["billing.events"]}}'

# Список: привязки, last_used_ms и признак client_mtls_enabled
curl -s --cacert ./certs/ca.pem https://localhost:7421/api/auth/cert-bindings \
  -H "Authorization: Bearer $ADMIN"
# {"bindings":[{"cn":"billing-svc","role":"viewer","scopes":{...},
#   "created_at_ms":...,"created_by":"admin","last_used_ms":null}],
#  "client_mtls_enabled":true}

# Удаление: открытые сессии с этим сертификатом закрываются в течение 1 с
curl -s --cacert ./certs/ca.pem -X DELETE \
  https://localhost:7421/api/auth/cert-bindings/billing-svc -H "Authorization: Bearer $ADMIN"
```

Сертификат для такого сервиса выпускается тем же CA, что передан в `--tls-client-ca`. Для
разработки подойдёт `client.pem` из `gen-dev` (его CN — `client`). В SDK достаточно
`TlsOptions::identity_files(...)` без `auth_token`.

Что важно знать:

- CN сравнивается точно (с учётом регистра). Пустой CN, CN с `/` или управляющими символами
  и CN длиннее 256 байт отклоняются (400). Вторая привязка того же CN — `409 conflict`
  (чтобы поменять роль, удалите привязку и создайте заново).
- Удаление привязки закрывает живые соединения с этим сертификатом на всех узлах: `Goodbye`
  с причиной `certificate binding revoked`. Сессии, вошедшие по токену, не затрагиваются.
- В audit log и логах такой клиент виден как `cert:<cn>`. `last_used_ms` обновляется не чаще
  раза в минуту.
- Привязки не включают авторизацию сами по себе: режим open/enforced по-прежнему зависит
  только от токенов. В открытом режиме все клиенты — анонимный admin.
- Сертификат проверяется только при подключении: CRL и OCSP не поддерживаются, поэтому
  скомпрометированный сертификат отзывайте удалением его привязки.

**Клиент без TLS на TLS-порту** получает понятную ошибку, а не зависание:
`server: ProtocolViolation: this port requires TLS: connect with a tls:// address or
ClientOptions::tls`. HTTP-запрос на HTTPS-порт получает `400` с текстом «This port speaks
HTTPS». Оба случая увеличивают `handshake_failures_total`.

### HTTP-порт и веб-консоль по HTTPS

По умолчанию HTTP-порт использует тот же сертификат, что и клиентский. Отдельный сертификат
(например, публичный для консоли и внутренний CA для клиентов):

```bash
./target/release/fluxmq --tls-cert ./certs/server.pem --tls-key ./certs/server-key.pem \
  --http-tls-cert /etc/fluxmq/console.pem --http-tls-key /etc/fluxmq/console.key
```

Консоль открывается по `https://<host>:7421/`, WebSocket телеметрии идёт по `wss://` через тот
же порт. Если перед брокером стоит TLS-прокси (nginx, Caddy), оставьте HTTP открытым:
`--http-tls off`.

### SDK (Rust)

```rust
use fluxmq_client::{Client, ClientOptions, TlsOptions};

let tls = TlsOptions::new()
    .ca_file("certs/ca.pem")                                   // CA брокера
    .identity_files("certs/client.pem", "certs/client-key.pem");  // для mTLS
let client = Client::connect(
    ClientOptions::with_seeds(["tls://n1:7420", "tls://n2:7420"], "order-api-1").tls(tls),
)
.await?;
```

- Адреса: `host:port` (открытый текст, если `tls` не задан) и `tls://host:port`. Адрес
  `tls://…` без `TlsOptions` означает TLS с системным хранилищем сертификатов (подходит для
  публичного CA).
- TLS действует для **всех** соединений клиента: сидов, переподключений и узлов кластера,
  которые клиент узнаёт из метаданных (там адреса без схемы).
- Имя для проверки сертификата — хост из адреса; заменить: `.server_name("mq.internal")`.
  `.use_system_roots(true)` добавляет системные корни к своему CA. `.ca_pem(bytes)` /
  `.identity_pem(cert, key)` — те же данные из памяти.
- `.danger_accept_invalid_certs(true)` отключает проверку сертификата — **только для отладки**.
- Ошибки: неверный путь или PEM — `ClientError::Protocol("TLS configuration: …")` сразу при
  `connect`; чужой CA или истёкший сертификат — `ClientError::Io("TLS handshake with …")`.

`fluxmq-bench` и `fluxmq-demo` принимают `--tls-ca`, `--tls-cert`, `--tls-key`
(переменные `FLUXMQ_CLIENT_TLS_CA/CERT/KEY`) и адреса `tls://`:

```bash
./target/release/fluxmq-bench --addr tls://127.0.0.1:7420 --tls-ca ./certs/ca.pem \
  --tls-cert ./certs/client.pem --tls-key ./certs/client-key.pem
```

### Ротация сертификатов без перезапуска

Брокер перечитывает PEM-файлы сертификатов и ключей:

- **раз в 30 секунд**, если изменились время модификации, размер или inode файла;
- **сразу по `SIGHUP`**: `kill -HUP $(pgrep -x fluxmq)`.

Новые рукопожатия используют новый сертификат, **уже открытые соединения не рвутся**.
Заменяйте файлы атомарно (записать во временный файл и `mv`) — так делают certbot, cert-manager
и большинство deploy-скриптов. Порядок замены сертификата и ключа не важен: если в момент
проверки пара не сходится, перезагрузка считается неудачной и повторится, когда изменится
второй файл.

**Неудачная перезагрузка** (битый PEM, ключ не от этого сертификата) **оставляет прежний
сертификат**: брокер продолжает работать, в `GET /api/tls` появляется `last_error`, в ленте
событий — `tls_reload_failed`, открывается алерт `tls_reload_failed`. Следующая удачная
перезагрузка очищает ошибку.

Файлы CA (`--tls-client-ca`, `--cluster-tls-ca`) читаются только при старте: смену CA делайте
перезапуском узлов по одному (на время перехода положите в файл CA оба сертификата — старый и
новый).

### Кластер: TLS между узлами

```bash
export FLUXMQ_CLUSTER_SECRET=dev-secret
PEERS=n1@127.0.0.1:17422,n2@127.0.0.1:17432,n3@127.0.0.1:17442
TLS="--tls-cert ./certs/server.pem --tls-key ./certs/server-key.pem --tls-client-ca ./certs/ca.pem --cluster-tls-ca ./certs/ca.pem"

./target/release/fluxmq --node-id n1 --peers $PEERS --data-dir ./data/n1 \
  --client-addr 127.0.0.1:17420 --http-addr 127.0.0.1:17421 \
  --raft-addr 127.0.0.1:17422 --replication-addr 127.0.0.1:17423 \
  --cluster-tls-cert ./certs/node-n1.pem --cluster-tls-key ./certs/node-n1-key.pem $TLS
# n2 и n3 так же, с node-n2.* / node-n3.* и своими портами (см. раздел 19)
```

- Каждый узел предъявляет свой сертификат и проверяет сертификат собеседника по
  `--cluster-tls-ca` — и при входящих, и при исходящих соединениях (Raft, репликация, внутренний
  HTTP). Имена в сертификате (SAN) не сверяются: узлы обращаются друг к другу по объявленным
  адресам, часто по IP. CN должен совпадать с id узла — иначе в логе предупреждение.
- `--cluster-secret` по-прежнему обязателен: сертификат не заменяет секрет, а дополняет его.
- **Все узлы должны быть настроены одинаково.** Узел без cluster TLS не подключится к
  TLS-кластеру, и наоборот. Включение или выключение cluster TLS — перезапуск всех узлов с
  новыми флагами (данные не затрагиваются).
- HTTPS на HTTP-порту в кластере требует cluster TLS (узлы вызывают `/internal/*` друг друга
  через этот порт); без него брокер не стартует и подскажет, что делать. Сертификат HTTP-порта
  должен быть выпущен кластерным CA или публичным CA.
- Можно включить только cluster TLS, оставив клиентский и HTTP-порты открытыми: узлы всё равно
  будут ходить на HTTP-порт друг друга по взаимному TLS (порт распознаёт TLS-рукопожатие), а
  браузер и curl — по HTTP. `/internal/*` без сертификата узла отвечает `401` в любом режиме.

### Мониторинг TLS

`GET /api/tls` (роль viewer и выше) — что включено и когда истекают сертификаты:

```bash
curl -s --cacert ./certs/ca.pem https://localhost:7421/api/tls | jq '.client'
# {"enabled":true,"mutual":true,
#  "certificate":{"subject":"O=FluxMQ development, CN=fluxmq-server","issuer":"…",
#                 "sans":["localhost","127.0.0.1"],"not_before_ms":…,"not_after_ms":…,
#                 "sha256_fingerprint":"9c1f…"},
#  "loaded_at_ms":…,"last_error":null,"handshake_failures_total":2}
```

Карточка TLS в консоли — *Settings → Security*.

Prometheus (только когда TLS настроен):

| Метрика | Тип | Смысл |
|---|---|---|
| `fluxmq_tls_handshake_failures_total{surface}` | counter | неудачные рукопожатия: открытый текст на TLS-порту, нет или чужой клиентский сертификат, несовпадение протокола, таймаут |
| `fluxmq_tls_cert_expiry_seconds{surface}` | gauge | секунд до истечения сертификата (отрицательное — уже истёк) |

Счётчик неудачных рукопожатий — повод посмотреть, а не обязательно атака: в него попадают и
браузеры, которые не доверяют CA (Chromium с сертификатами `gen-dev` обрывает несколько
соединений на каждую загрузку страницы с `CertificateUnknown`), и запросы соседних узлов,
не дождавшиеся рукопожатия, пока узел только стартует. Постоянный рост без таких причин — уже
сигнал (открытый текст на TLS-порту, чужой клиентский сертификат).

```promql
min by (node, surface) (fluxmq_tls_cert_expiry_seconds) < 14 * 86400
rate(fluxmq_tls_handshake_failures_total[5m]) > 0
```

Алерты (приходят в уведомления, как остальные). Каждый узел считает их для своих
сертификатов и передаёт остальным вместе со статистикой узла (раз в секунду), поэтому в
кластере алерт `tls_cert_expiring:n2/cluster` виден в консоли любого узла, а уведомление о нём
рассылает контроллер — один раз, даже если сертификат истекает только на n2:

| Алерт | Когда |
|---|---|
| `tls_cert_expiring` | до истечения меньше 14 дней (warning), меньше 3 дней или уже истёк (critical) |
| `tls_reload_failed` | последняя перезагрузка сертификата не удалась (прежний ещё работает) |

### Ограничения TLS в версии 0.5

- Событие `tls_reload_failed` попадает в ленту `$system.events` только с контроллера; с
  других узлов о неудачной перезагрузке сообщает алерт `tls_reload_failed` (он уведомляется).
- Файлы CA перечитываются только при перезапуске; CRL и OCSP не проверяются.
- Один сертификат на поверхность (без выбора по SNI).
- Смешанного режима для cluster TLS нет: включение и выключение — перезапуск всех узлов.
- Привязки сертификатов действуют только на клиентском порту; REST, WebSocket и консоль
  по-прежнему требуют токен.

## 25. Docker

С версии 0.5 FluxMQ собирается в Docker-образ, а `deploy/docker-compose.yml` поднимает одиночный
узел, TLS-кластер из трёх узлов, демо-нагрузку, а также Kafka и RabbitMQ для сравнительных
бенчмарков. Подробности на английском — в [deploy/README.md](../deploy/README.md) и
[bench/README.md](../bench/README.md).

### Образ

```bash
deploy/build.sh                 # рабочее дерево -> fluxmq:dev
deploy/build.sh --ref HEAD      # последний коммит (git archive + упаковка из рабочего дерева)
```

- Многоступенчатая сборка: UI через pnpm, Rust release с кешем BuildKit (реестр cargo и
  `target`), итоговый образ на Debian slim, около 150 МБ.
- Внутри: `fluxmq` (брокер, `tls gen-dev`, `backup`, `restore`), `fluxmq-bench`, `fluxmq-demo`;
  консоль встроена в `fluxmq` (`FLUXMQ_UI=off` выключает её).
- Пользователь `fluxmq` (uid 10001), том данных `/var/lib/fluxmq`, порты 7420–7423,
  healthcheck — `/api/health` (HTTPS или HTTP).
- Повторная сборка с тёплым кешем — около 2 минут; первая (все зависимости) — 6–10 минут.

```bash
docker run --rm -p 127.0.0.1:37420:7420 -p 127.0.0.1:37421:7421 \
  -v fluxmq-data:/var/lib/fluxmq fluxmq:dev
```

### Профили compose

```bash
dc() { docker compose -f deploy/docker-compose.yml "$@"; }   # bash and zsh
dc --profile single up -d                      # один узел: http://localhost:37421
dc --profile cluster up -d                     # 3 узла, полный TLS: https://localhost:37431
dc --profile single --profile demo up -d       # демо-нагрузка (или --profile cluster --profile demo)
dc --profile kafka up -d                       # Kafka 1 узел (KRaft); kafka-cluster — 3 узла
dc --profile rabbitmq up -d                    # RabbitMQ 1 узел; rabbitmq-cluster — 3 узла, quorum
dc --profile '*' down -v                       # остановить всё и удалить данные
```

| Профиль | Что поднимает |
|---|---|
| `single` | один брокер; `FLUXMQ_SINGLE_TLS=on` включает TLS и HTTPS |
| `cluster` | init-контейнер `certs` (`fluxmq tls gen-dev --nodes n1,n2,n3 --hosts n1,n2,n3,fluxmq,localhost,127.0.0.1` в том `certs` + случайный секрет кластера), затем `n1`–`n3`: RF=3, `--min-isr 2`, TLS клиентского порта, HTTPS, mTLS между узлами |
| `demo` | `fluxmq-demo`; сам выбирает кластер, если он запущен, иначе одиночный узел |
| `kafka`, `kafka-cluster` | официальный `apache/kafka` в режиме KRaft; кластер — RF=3, `min.insync.replicas=2` |
| `rabbitmq`, `rabbitmq-cluster` | официальный `rabbitmq`; кластер из трёх узлов, quorum-очереди, Erlang cookie генерируется в том |
| `bench` | клиенты бенчмарка (запускает `bench/run.sh`) |

- Порты на хосте — в диапазоне 3xxxx, только на 127.0.0.1, переопределяются переменными
  (`FLUXMQ_HTTP_PORT`, `N1_HTTP_PORT`, `KAFKA_PORT`, …; таблица в `deploy/README.md`).
- Кластер без TLS: `FLUXMQ_CLUSTER_TLS=off`. Обязательный mTLS для клиентов:
  `FLUXMQ_CLIENT_MTLS=on` (демо и бенчмарк сами предъявят `client.pem` из тома).
- Сертификаты `gen-dev` и секрет кластера живут только в томе `certs`; в файлах репозитория
  секретов нет. Проверить HTTPS:
  `dc --profile cluster cp n1:/certs/ca.pem ./ca.pem && curl --cacert ca.pem https://localhost:37431/api/health`.
- Метаданные кластера публикуют адреса `n1:7420` и т. д., которые резолвятся только внутри сети
  compose, поэтому SDK-клиентов кластера запускайте в этой сети (как `demo` и `bench`).
- Лимиты: каждый контейнер брокера (FluxMQ, Kafka, RabbitMQ) получает одинаковые
  `BROKER_CPUS`/`BROKER_MEM` (по умолчанию 2 CPU и 2 ГБ), клиенты — `BENCH_CPUS`/`BENCH_MEM`.

### Сравнительные бенчмарки

```bash
bench/run.sh --smoke                                       # всё по несколько секунд (~10 мин)
bench/run.sh                                               # полный прогон (~1,5 ч; с --repeat 3 — ~2,5 ч)
bench/run.sh --systems fluxmq,kafka --scenarios saturation  # подмножество
open bench/report/index.html
```

- Системы: FluxMQ 1 узел и 3 узла RF=3 (без TLS и с TLS), Kafka 1 и 3 узла (`acks=all`),
  RabbitMQ 1 узел (classic, publisher confirms) и 3 узла (quorum-очереди).
- Сценарии: `saturation` (максимальная пропускная способность, 1 KiB и 100 B, 1×1 и 4×4
  клиентов; `--repeat 3` — три повтора, в отчёте медиана и разброс), `latency` (open loop
  1k/10k/50k сообщений/с, p50/p99/p99.9; недостижимые скорости пропускаются с пояснением),
  `idle` (CPU и память в покое), `batching` (v0.4 против текущей версии через `fluxmq-bench`,
  три чередующихся раунда, включая режим drain — чистую скорость чтения). CPU и память под нагрузкой берутся из `docker stats` во время
  saturation.
- Все системы гоняет один harness (`bench/harness`, Rust: SDK FluxMQ, librdkafka, lapin) с
  одинаковой методикой: метка времени в payload, один процесс для продюсеров и консьюмеров,
  HDR-гистограммы, open loop от запланированного времени отправки.
- Сырые JSON — в `bench/results/<время>/` вместе с окружением (CPU/RAM хоста, ресурсы VM
  Docker, версии образов, git sha); отчёт — один HTML-файл `bench/report/index.html`.
- Клиенту одиночных систем даётся 4 CPU (`--bench-cpus 4`), клиенту кластеров — 2 (3×2 CPU
  брокеров + 2 = 8 CPU VM), одинаково для всех систем внутри одного сравнения; лимиты
  записываются в каждый JSON (см. `bench/README.md`).
- Ограничения: Docker VM на macOS, один ноутбук, три «узла» на одном диске, разные гарантии
  надёжности у систем. Отчёт перечисляет их рядом с цифрами.

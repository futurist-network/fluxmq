# v0.8 — 3-node latency and replication throughput

Scope: `fluxmq-replication` and `fluxmq-core::replica`. Goals: 3-node p99 end-to-end ≤ 20 ms at 50k msg/s (and no worse at 1k/10k), 3-node 1 KiB 1×1 saturation at least Kafka's default, and no regression anywhere else. Durability does not change: a publish is acked only after the leader's fsync **and** after every ISR member has fsynced the batch.

**Status.** One structural fix shipped: follower fetch-ahead with durable-progress reports (§2). Per-component metrics show replication overhead down by about 60 % (§3.2), and paired runs show it better at every rate (§3.3). **The headline targets are not met here, and this machine can't show whether they are reachable** (§1.1). The host disk is about 97 % full. After about 15 s of sustained synced writes, fsync latency climbs from 1–2 ms to 4–130 ms, with stalls of several seconds. Every system that fsyncs then shows p99 in the hundreds of milliseconds or seconds, whatever its code. Saturation throughput in this session is 130–147k msg/s for both baseline and candidate. The published v0.7 figure was 239k.

## 1. Root cause

### 1.1 The 61 → 131 ms "regression" is mostly measurement noise

v0.6 (6e4897e) and v0.7 (cac69af) images, same harness (`fluxmq-harness` at 4533c6c; it falls back to `Publish` for v0.6), interleaved, 50k msg/s, `--repeat 1`:

| run | p50 | p99 |
|---|---|---|
| v0.6 #1 | 33 ms | 2949 ms |
| v0.7 #1 | 647 ms | 2181 ms |
| v0.6 #2 | 670 ms | 3553 ms |
| v0.7 #2 | 354 ms | 4829 ms |

While the disk was still calm (the first ~15 s of each run), the broker `/metrics` scraped every 5 s showed the same picture for both versions: about 1450–1550 fsyncs/s per node at 1.8 ms mean, and a local publish → durable time of about 5 ms. Then both degraded the same way: fsync mean 7–25 ms, p99 ≥ 100–250 ms. The 61 ms (v0.6) and 131 ms (v0.7) figures come from two runs on different days, and in this session the run-to-run spread is 10–20×. v0.7's overlap of leader and follower fsyncs (followers read the unsynced tail) is not the cause. The fsync count and per-fsync cost are the same with it.

Environment evidence:
- Host free disk was 8–13 GB of 460 GB throughout, and macOS `CacheDelete` ran at 100 % CPU.
- Idle fsync micro-benchmark in a broker container (`dd … conv=fdatasync`, 64 KiB appends): 0.9–1.3 ms for one file, 2.0–2.6 ms for 8 files in parallel, 2.4–3 ms for one `syncfs`. The device itself is fine when idle.
- Under 3 × 50 MB/s of synced writes, the same device degrades within about 15 s in every run, on every image.

### 1.2 The structural cost: a serial follower cycle

A temporary diagnostics build (log2 histograms, logged every 5 s, not committed) measured the ack path at 50k msg/s on v0.7:

- **HW advances are follower-bound.** 764 of 765 HW advances came from a follower's fetch report. Only 1 came from the leader's own fsync completing.
- **The follower cycle.** For each partition the follower did fetch → append → wait for its own fsync → fetch again. Measured times: fetch round trip 1.1 ms; append 13.3 ms mean, of which about 5 ms was waiting in the writer queue behind an fsync already in progress; append → durable inside the writer 8.3 ms.
- **The ack wait.** Time from local durable on the leader to the ISR ack: 24.7 ms mean, against a local publish → durable time of 15.9 ms. Data the leader wrote while a follower was busy with its previous chunk waited for that whole cycle (about ½ cycle), then a fetch, then a full follower append. That matches the measured ack wait.

Across all diagnostic runs, the median per 5-s period of (ack wait ÷ local publish → durable) was **1.26–1.49** (4 runs). Replication cost more than the leader's own group commit.

## 2. Change: follower fetch-ahead and durable-progress reports

A follower no longer waits for a chunk to be durable before it fetches the next one. The fetch position and the durable end are now reported separately.

**Follower (`fetcher.rs`)**
- Against a leader that declares the `durable-progress` capability, the fetch loop:
  1. hands each verified chunk to the writer with `ReplicaHandle::append_async`, which returns once the chunk is queued;
  2. fetches again right away, from the end of what it queued;
  3. tracks the queued chunks with an `AppendTicket` each, in FIFO order.
- Fetch-ahead is bounded at 16 chunks or max(2 × `fetch_max_bytes`, 1 MiB) per partition.
- Each fetch carries a `FetchExt { durable_offset }` in its frame payload. `fetch_offset` now means only where to read from.
- When queued chunks become durable while a fetch is parked in the leader's long-poll, the follower sends `Request::Progress { durable_offset }`. It sends one report for all the chunks completed at that point.
- Only `log_end_offset` is ever reported, and it is published only after the follower's fsync.
- On any error, truncation, reset or boundary anomaly, the loop first drains every queued chunk, so the log end is settled before it restarts. The anomaly handling itself is shared with the serial loop (`verified`, `boundary_mismatch`).
- Against a leader without the capability (v0.7), the follower uses the unchanged serial loop, where `fetch_offset` is the durable end.

**Leader (`server.rs`, `replica.rs`)**
- `FetchRequest::durable_offset` is new. Only it counts for the HW and for ISR admission (`durable ≥ HW`). The fetch position still measures fetch lag.
- `record_progress` is new.
- A follower's reports (from a `Fetch` and from a `Progress`) are applied inline in the connection's read loop, in the order the follower sent them. A durable end can drop after a truncation, and ordered application keeps the leader's view equal to the follower's latest report. Only the long-poll and the read of a fetch run in their own task.

**Liveness: durability lag.** A follower whose fsyncs stall keeps fetching ahead (up to the bound) and would look "caught up". Three changes keep it from holding the HW:
- `Progress::durable_caught_up` and `durable_mark` record when the follower's durable end last reached the leader's written end.
- ISR eviction uses the older of fetch lag and durability lag against `replica_lag_max`.
- A candidate (a follower outside the ISR that holds the HW back so it can catch up) loses that role once its durable end has been stale for longer than `replica_lag_max`.

Without these three changes, a follower with a stuck disk would block acks until its fsync returned. Regression test: `follower_with_stalled_fsyncs_leaves_the_isr`.

**Wire compatibility.** The protocol version stays 1.
- `Request::Progress` and `Response::Progress` are appended enum variants, so v0.7's variant indexes are unchanged.
- `FetchExt` rides in the fetch frame payload. A v0.7 leader would ignore it.
- `durable-progress` is declared in `HelloOk`, and a follower sends neither `Progress` nor `FetchExt` to a leader that didn't declare it.

Each mixed pair works as follows:
- **v0.8 follower, v0.7 leader:** the follower uses the serial loop.
- **v0.7 follower, v0.8 leader:** with no payload, the leader takes `durable_offset = fetch_offset`, which is what v0.7 meant.

**Files**
- `crates/fluxmq-replication/src/`: `fetcher.rs`, `server.rs`, `client.rs` (`call_with`, `notify`), `protocol.rs`.
- `crates/fluxmq-core/src/`: `replica.rs` (`durable_offset`, `record_progress`, `append_async`/`AppendTicket`, durability lag), `lib.rs` (export).
- `crates/fluxmq-core/tests/replica_storage.rs`: new field.
- Tests: `crates/fluxmq-replication/tests/fetch_ahead.rs` (new).
- `bench/runner.py`: new A/B-only system `fluxmq-cluster-pipeline`.

## 3. Results

### 3.1 Setup

- Docker Desktop: brokers with 2 CPUs / 2 GiB each, harness and settings as in v0.7 (§ v0.7.md), group commit.
- Baseline: `fluxmq:v07-base` (cac69af).
- Candidate: `fluxmq:v08-repl-f`, which is cac69af plus only this change (built from a `git archive` of cac69af with the patch applied, so the other agents' in-progress work is not included).
- Runs were interleaved and took the shared bench lock. All result directories are in a local working directory (`repl/res/*`).

### 3.2 Component metrics

Median over 5-s periods. These ratios hold up much better under the environment's drift than end-to-end p99 does.

| build | runs | ack wait ÷ local publish→durable |
|---|---|---|
| v0.7 | 4 | 1.26 / 1.49 / 1.41 / 1.29 |
| fetch-ahead | 2 | 0.56 / 0.55 |

With fetch-ahead, 99 % of HW advances now come from `Progress` reports, and the ack wait median at 50k is 5.5–8.2 ms. **The leader's own group commit is now the larger share of publish latency.** Its local publish → durable time is 10–15 ms at 50k in this environment, about 1.5–2 × the commit's fsync time.

|---|---|---|---|---|---|---|
| A1 | – | – | 7.0 / 18.6 | 8.4 / 22.8 | 23.4 / 349 | 23.0 / 342 |

The candidate has the better p50 in 9 of 10 pairs and the better p99 in 8 of 10. At 1k and 10k it is better in every pair: p50 −8 % to −60 %, p99 −18 % to −63 %. At 50k the p99 in both builds is set by disk stalls.

**The 20 ms p99 target at 50k is not reachable on this host.** Even in its calm phase, fsync p99 sits in the 10–25 ms bucket and local commit p99 in the 25–50 ms bucket. Re-measure on a host with free disk space.

### 3.4 Saturation, 1 KiB 1×1

| build | runs | consumed msg/s |
|---|---|---|
| baseline | 2 | 144k / 139k |
| candidate | 2 | 134k / 147k |
| candidate + pipeline | 2 | 142k / 137k |

All are device-bound: fsync mean 17–22 ms at about 50–80 fsyncs/s per node. Throughput is window-bound, 20000 / ack latency (publish p50 120–135 ms), so it follows the device. There is no difference beyond the noise. The goal (≥ Kafka's 253k, measured on a healthy disk) can't be judged here.

### 3.5 Durability

Crash test with `bench/crash/crash.py --systems fluxmq-cluster --iterations 2`, candidate image: kill -9 and power cut, each against the leader and against all 3 nodes, 8 runs. **771,160 messages acked, 0 lost**, recovery in 0.3 s.

### 3.6 Changes tried and rejected

- **fsync pool floor 16 threads instead of 4.** On 2-CPU brokers a commit touching 8 partitions ran its fsyncs in two waves. Raising the floor gave 30–60 % more fsyncs/s on the shared device and a higher per-fsync mean (3.6 vs 2–3 ms), with no gain in local commit latency. Reverted.
- **Commit pipeline on for clusters** (`fluxmq-cluster-pipeline`, existing `FLUXMQ_COMMIT_PIPELINE`). Better than off in some pairs (10k: 11 vs 21 ms, 14 vs 129 ms), worse or equal in others (F1: 14.6 vs 6.8 ms at 10k; F2 equal). It stays off, as in v0.7.

## 4. Tests

- **New, `fluxmq-replication/tests/fetch_ahead.rs`:**
  - `ack_waits_for_the_follower_fsync_not_its_fetch`: the follower's fsync is held 250 ms and then fails. The publish must not be acked and the HW must not pass the batch before the follower refetches it and makes it durable.
  - `lone_publish_is_acked_without_waiting_for_the_long_poll`: `fetch_max_wait` set to 4 s; acks must arrive in < 2 s. This fails with progress reports disabled.
  - `follower_with_stalled_fsyncs_leaves_the_isr`: a 6-s fsync stall while the follower keeps fetching. The follower must leave the ISR and acks with `min_isr = 1` must resume. This fails without the durability-lag rules.
- **New, `protocol.rs`:** `v08_additions_keep_the_v07_wire_compatible`, covering variant indexes, `FetchExt` round trip and capabilities.
- **Passing:**
  - `cargo fmt --check`.
  - `cargo clippy --workspace --all-targets -D warnings`.
  - `cargo test -p fluxmq-replication -p fluxmq-cluster -p fluxmq-core`.
  - `fluxmq-server` tests `cluster`, `cluster_batch`, `cluster_auth`, `cluster_tls`, `decommission`, `rebalance`.
- **Bug found while testing (fixed before the final image):** a completed `AppendTicket` was polled again when draining after an append error. That is a oneshot double-poll panic.
- **Not run:** `rolling_upgrade_bin` (v0.7 → v0.8 with real binaries). It needs a local release build of cac69af, and the host disk was below the 10 GB floor. Compatibility is covered at the protocol level and by the serial-loop fallback.

## 5. Next steps

1. **Re-measure on a healthy disk** (≥ 50 GB free, nothing else running), with the full latency matrix at `--repeat 3` and 1 KiB 1×1 saturation. Every end-to-end number in this document is environment-bound.
2. **Local commit is now the dominant cost.** The writer thread blocks on each commit's fsyncs, and a publish waits for the commit in flight plus its own (about 1.5–2 × the fsync time). Candidates, in the fsync path that single-node mode shares:
   - per-partition completion inside a commit (publish each partition's mark when its own chain finishes);
   - a commit pipeline deeper than one batch.
3. **Export the ack-wait histogram** (`leader_ack_wait`) as a Prometheus metric. It isolates replication cost from disk cost, which end-to-end numbers on a shared device can't.

## 6. Results — final (set `bench/results/20261010-v0.8`)

Re-measured from HEAD `95107b0` on the same laptop with 34–43 GB free disk. FluxMQ fsync means stayed at 10–14 ms on 3
nodes under saturation and 2–6 ms in the latency runs, with no multi-second stalls. Brokers had 2 CPUs / 2 GiB each.
The client got **4 CPUs** (v0.7: 2) for every system, group commit. The report is `bench/report/index.html`.

| 3 nodes RF=3 | v0.7 set | v0.7 image, same host | **v0.8** | Kafka default |
|---|---:|---:|---:|---:|
| 1 KiB 1×1, consumed msg/s | 217k | – | **278k** (2 runs: 267k–288k) | 253k (v0.7 set) |
| 1 KiB 4×4 | 207k | 251k | **273k** (255k–290k) | 251k (same day, 4 client CPUs) |
| 100 B 1×1 / 4×4 | 622k / 328k | – | **586k / 1.09M** | 617k / client-bound (v0.7) |
| p50 / p99 at 1k | 2.7 / 7.5 ms | 4.2 / 40 ms | **2.9 / 6.7 ms** | 2.8 / 8.3 ms (v0.7) |
| p50 / p99 at 10k | 7.6 / 19 ms | 8.6 / 59 ms | **6.7 / 15 ms** | 2.4 / 94 ms |
| p50 / p99 at 50k | 14 / 131 ms | 17 / 86, 15 / 136, 45 / 366 ms | **17 / 84, 16 / 142, 39 / 203 ms** | 2.6 / 81 ms |

- **Goal "1 KiB 1×1 ≥ Kafka's default": met** (278k vs 253k). At 4×4, 1.09× Kafka measured the same day with the same
  client CPUs. Against the v0.7 set the gain is +28–32 %, but the broker's own share is +8 % (same-host A/B at 4 client
  CPUs: 251k → 273k). The rest comes from the larger client.
- **Goal "p99 ≤ 20 ms at 50k": not met.** Three runs gave 84 / 142 / 203 ms, and the v0.7 image in alternating runs gave
  86 / 136 / 366 ms: no regression and no gain at 50k. The p99 follows the fsync mean of the three brokers on one SSD
  (2.0 ms → 136 ms, 3.2 → 142, 5.3–5.6 → 203–366). That points at the leader's local commit (§5, item 2), which
  fetch-ahead does not address. At 1k / 10k the p99 is better than v0.7 and than Kafka's default at 10k. The p50 stays
  above Kafka's default, which acks from the page cache.
- **Durability:** 4 crashes in this set (kill -9 and power cut, leader and all 3 nodes): 372,101 acked, 0 lost. Leader
  failover with a live consumer: 300,991 acked, 0 lost, acks resumed after 5.6 s (v0.7: 5.9 s), 0 client errors. With
  §3.5's 8 runs that makes 12 cluster crashes on this code with 0 lost.

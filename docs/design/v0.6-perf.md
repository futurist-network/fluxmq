# FluxMQ v0.6 design: hot-path performance

Source: a read-only audit made during the v0.5 full benchmark (`bench/results/20261009-full`), cross-checked with that run's numbers.

Baseline, single node with 2 CPUs and 2 GB:
- saturation: ~150–160k msg/s at 1 KiB, ~200k at 100 B;
- p50 latency 3.6–5 ms at 1k and 10k msg/s;
- p99 ~0.8–1 s at 50k msg/s.

Publish p50 ≈ e2e p50, so the time is spent in publish→durable.

**Rule:** durability, ordering and at-least-once semantics never weaken silently. A trade-off is only allowed behind an explicit option, and the default stays group-commit fsync.

## Work items, by expected gain

1. **Retention / segment-roll stall, the cause of the ~1 s p99:**
   - Today: every partition rolls together, a 128 MiB default segment, and one retention tick unlinks ~1 GiB while acks wait on fdatasync.
   - Fix:
     - configurable `segment_bytes` with a lower default (16–64 MiB);
     - jitter each partition's roll size by ±10%;
     - delete at most one segment per channel per tick, with optional `ftruncate` in steps first;
     - the roll's sync and dir-fsync never block the in-progress batch.
   - Code: `core/config.rs:39`, `core/broker.rs:324-334, 1184-1209`, `storage/log.rs:384-412, 1037-1066`.
2. **A new OS thread per fsync per commit:**
   - Today: `std::thread::scope` spawns up to 8 threads on every commit (`core/channel.rs:917-941`).
   - Fix: a long-lived fsync thread pool.
3. **Keyless publish scatters each batch over every partition,** so up to 8 fdatasyncs per commit.
   - Fix: a sticky partitioner. Keyless messages from one request, or up to N KiB, go to one partition, rotating per request.
   - Code: `core/channel.rs:315-351`, `client/client.rs:422-439`.
   - Keyless ordering was never guaranteed; document the change.
4. **Double-buffered group commit:** append and write batch N+1 while batch N is fdatasynced. Visibility and acks stay strictly in order, each after its own fsync.
   - Code: `core/channel.rs:945-1094`.
   - `fail_all` and `rollback` must handle more than one uncommitted batch.
5. **Adaptive SDK linger:** send immediately when the worker has nothing in flight; linger only while requests are outstanding.
   - Code: `client/producer.rs:337-363`.
6. **Per-message overhead:**
   - `flux-producer` header stamping: stamp once per connection on the server, or make it optional (`client/producer.rs:143-149`);
   - deep clones and allocations under the group mutex: deliveries should hold `Arc<Message>`, consumer names `Arc<str>`, and the duplicate attempts bookkeeping goes (`core/group.rs:1061-1118`);
   - over-broad wake-ups: per-subscription notify instead of `notify_waiters` on every ack or commit;
   - payload copies in wire encode and decode (`proto/wire.rs:212`, `client/conn.rs:84-106, 421`);
   - FramedWrite backpressure boundary (`server/net/connection.rs`);
   - the dup per sync (`storage/log.rs:1108`);
   - client task hops (`client/producer.rs:255-395`);
   - the cluster publish clone (`cluster/publish.rs:62`);
   - make the recent-message cache size configurable (`storage/log.rs:40-41`).

## Results — client/delivery

Items 5 and 6 (SDK, wire, delivery overhead) plus the SDK protocol fallback.

### What changed

- **Adaptive linger** (`client/producer.rs`). A partition worker with nothing in flight sends at once. It lingers (up to `BatchingOptions::linger`) only while a batch of its partition is outstanding, and a lingering batch leaves as soon as the last in-flight batch completes. Before an idle send the worker yields to the scheduler up to 3 times while new messages keep arriving. Without that, a closed-loop producer alternated 1-message and N-message batches, which doubled broker CPU per message in the first measurement. `linger = 0` still never waits. `ordered` keeps at most one batch per partition in flight.
- **Fewer task hops** (`client/producer.rs`):
  - no dispatcher task: `send` routes straight into the partition worker's queue, with `try_send` under the map lock and no sender clone;
  - no `tokio::spawn` per batch: in-flight batches are a `FuturesUnordered` driven by the worker;
  - one linger timer per worker, re-armed per batch, instead of a new timer per loop iteration.

  `queue_capacity` is now per partition queue.
- **`flux-producer` stamping is optional**: `ClientOptions::stamp_producer` / `.stamp_producer(bool)`, default `true`, so the UI and consumers keep working. The server cannot attribute a producer per connection without a wire or storage-format change, so this is opt-out. The harness turns it off (`nostamp` rows below); the bench report must say so, since Kafka and RabbitMQ clients send no header either.
- **Client encode without copies** (`client/conn.rs`):
  - the publish body is encoded once into a pre-sized buffer (`encoded_size_hint`), so the buffer never grows and re-copies;
  - the frame head (length + `req_id`) is kept apart from the shared body, with no per-attempt frame copy;
  - the writer task replaces `FramedWrite<BytesCodec>`, which copied everything again: small frames are staged, bodies over 8 KiB go out by vectored write.
- **Zero-copy payload decode on both sides**, wire format unchanged:
  - the server decodes `Publish` and the client decodes `Deliver`/`DeliverBatch` through borrowing mirror structs (same fields, same order), and payloads are `Bytes::slice_ref` of the frame;
  - all other frames use the reference decoder;
  - tests check byte-identical results against `wire::encode_frame`/`decode_body`.
- **Deliveries share the stored message** (`core/group.rs`, `server/net/codec.rs`):
  - `Group::poll_batch` returns `SharedDelivery { message: Arc<Message> }`, and the server writer encodes `Outbound::Deliveries` straight from it, byte-identical to `Deliver`/`DeliverBatch`;
  - there is no deep clone (key, headers, payload) per delivery;
  - `Subscription::next()` still returns the wire `Delivery`.
- **Group bookkeeping**:
  - attempts are kept as `{consumer: Arc<str>, …}`, with no allocation for the usual single attempt and no `String` per delivery; `DeliveryAttempt`s are built only when a message is dead-lettered;
  - first-attempt delivery latencies are recorded once per batch, outside the group lock (one histogram lock per batch, not per message);
  - `now_ms()` is read once per batch.
- **Targeted wake-ups**:
  - each subscription has its own `Notify`, and an ack wakes only the subscriptions whose prefetch credit it freed;
  - the group-wide `notify_waiters` stays for real broadcast events: a keyed ack unblocking a deferred key, nack, timeout, commit, rebalance, fetch.
  - `channel.rs::notify_groups` is unchanged (storage-owned). A per-partition commit wake-up is the next step.
- **Server writer**:
  - `FramedWrite` backpressure boundary raised from 128 KiB to 2 × `MAX_DELIVER_BATCH_BYTES`, so batches coalesce into one write;
  - `feed` arms the `write_timeout` timer only when the socket is actually full, instead of once per frame.
- **Cluster publish** (`cluster/publish.rs`): when this node already leads the partition (`Broker::leads_partition`), the messages are moved, not cloned. The clone-and-retry settle loop stays for the not-yet-leader case.
- **Payload unpinning**: a zero-copy payload pins its publish frame. Messages parked for long (retry backoff, DLQ) get their own copy (`Pending::detach`, cold path only).
- **SDK protocol fallback**: when a broker refuses `Hello` v3 with "unsupported protocol version" (v0.4 brokers), the SDK reconnects with v2 (no `DeliverBatch`). It caches the version per address and logs it once at info.

### Risks

- **Pinned frames.** Zero-copy payloads keep their frame buffer alive while any message of it is referenced: the recent-message cache (≤ 4 MiB of payload per partition), in-flight deliveries, keyed `deferred`. Retry/DLQ copies bound the long-lived cases. The worst case is a small multiple of the cache size per partition.
- **Adaptive linger changes batch shapes.** Batches are smaller at low load, which saves latency and costs requests. The 3-yield coalescing fixed the closed-loop ping-pong, but an open-loop producer that trickles messages exactly one per RTT will send one request per message. That was already the case with `linger = 0`.
- **Cluster publish.** If leadership is lost between `leads_partition` and the append, the client gets `NotLeader` right away (nothing was appended) and re-routes, instead of the node waiting up to 1.5 s.
- **Protocol fallback.** The fallback is cached per address and never upgraded within a client's lifetime: after a broker upgrade, clients stay on v2 until they restart.

## Results — storage (items 1–4)

### What changed

1. **Segments and retention** (`core/config.rs`, `storage/log.rs`, `core/broker.rs`):
   - `--segment-bytes` / `FLUXMQ_SEGMENT_BYTES`, in bytes, 1 MiB..=2 GiB. The default drops from 128 MiB to **64 MiB**: per-unlink work halves, and the file count stays modest at 16 segments, so 16 read descriptors, per GiB per partition. 16 MiB, Kafka's bench value, would mean 64 descriptors per GiB per partition and 4× more rolls for a default install. Deployments that want it set the flag, as the bench does.
   - A per-channel override is not implemented. `ChannelConfig` lives in `fluxmq-proto`, which the client agent owns; it would need a wire/API field and a live writer reconfiguration. The server-wide flag is the only knob.
   - Roll jitter: each segment rolls at `segment_bytes × (0.9..=1.1)`. The factor is a deterministic `splitmix64` of the channel and partition directory names and the segment base offset (`LogConfig::roll_size`), so it is reproducible across restarts and independent of the data-dir path. It varies per segment, so partitions written at the same rate drift apart instead of colliding again. `BrokerConfig::segment_jitter` turns it off; tests use that.
   - Paced retention: the background pass now runs every 1 s, not 5 s. Per channel it removes at most `min(1 + due/8, 16)` segments, where `due` is the number of eligible segments. It takes them one at a time from the partition with the most due. `Broker::enforce_retention` (explicit, used by tests and admin) stays unpaced.
   - A removed segment that nothing else references (`Arc::try_unwrap` succeeds, so no reader, backup pin or writer handle) is truncated from the end in 16 MiB steps with a 2 ms pause, then unlinked. Referenced segments are only unlinked, so readers keep the full file. Shrinking is best-effort.
   - Roll: the sealed segment's data is still `fdatasync`ed synchronously before the new file is created. That keeps the "no durable segment after a torn one" ordering, so recovery never sees an offset gap. The new directory entry's fsync and the sealed index's fsync are deferred into the next commit's sync ops, where they run in parallel with the other fsyncs. v0.5 ran three serial full syncs inline on the append path per roll; v0.6 runs one. Records in the new segment are still only acked after both have run.
   - Recovery needed no change for mixed segment sizes: segments are self-describing and the indexes are positional. A test covers 64 KiB → 1 KiB → 2 KiB → 1 MiB layouts, including reads, time seek, replication and retention.
   - **Retention data-loss fix** (found by the reliability agent). The per-partition size rule was `total > budget`, which right after a roll deleted the only closed segment and kept far less than the budget. Groups whose cursor was inside that segment then skipped unconsumed messages: the 250 "not drained" messages in the v0.5 cluster-TLS run. The rule is now Kafka's: delete a segment only if what remains still holds the budget (`total - seg >= budget`). `tests/retention_loss.rs` is the regression test; it failed on HEAD with "53 of 70 published messages never delivered". `replica_storage::partition_log_starting_at_a_nonzero_offset` needed `max_bytes` 6000 → 3000, because it relied on the old under-retention.
   - Skipping by retention is no longer silent. When a group cursor is below the log start, `group.rs` `take_next` logs a `warn` with channel, partition and the skipped range, and counts the skipped messages. The count is exposed as `GroupStats::retention_skipped_total` and the Prometheus counter `fluxmq_group_retention_skipped_messages_total{channel,group}`. The counter is node-local and not carried in cluster snapshots.
2. **fsync pool** (`core/fsync_pool.rs`, new): one bounded pool per broker, in `Shared::fsync_pool`.
   - Threads start lazily up to `--fsync-threads` / `FLUXMQ_FSYNC_THREADS`; the default 0 means 2 × CPUs, clamped to 4..=32. They exit when the broker drops.
   - A commit becomes a list of `SyncOp`s, grouped into chains by `chains_for`. Elsewhere each `fdatasync` is its own chain. On Apple there is one chain of plain `fsync(2)` calls ending in a single `F_FULLFSYNC` barrier.
   - Fast path: a single chain without pipelining (one dirty file, and every commit on Apple) runs inline on the writer thread with no hand-off.
   - `PartitionWriter.file` is now an `Arc<File>` shared with sync jobs, which also removes the `try_clone` dup per sync (item 6).
3. **Sticky partitioner** (`core/channel.rs` `StickyPartitioner`, reused by `cluster/publish.rs` for partition-less publishes on a cluster node):
   - Keyless messages of one request go to one partition, round-robin per request. A request moves on to the next partition after about 1 MiB.
   - Keyed messages are unchanged: `crc32(key) % n`.
   - GUIDE.ru.md documents that keyless distribution is balanced over time, not per message.
   - The SDK's client-side routing in cluster mode (`client/client.rs` `partition_of`) is still per message. That is the client agent's file; it needs the same per-request rule.
4. **Pipelined group commit** (`core/channel.rs` `WriterState`, `storage/log.rs` `CommitMark`):
   - `PartitionWriter::prepare_commit` writes out and takes a mark: the state to publish plus the fsync ops it needs. `publish_mark` publishes marks in order, and `rollback` discards everything after the last published mark, however many marks are outstanding.
   - The writer keeps at most one batch in flight on the pool while it appends the next. That batch is published and acked only after its own fsync, so acks and visibility stay strictly in order.
   - On failure, everything unpublished (the in-flight batch and the current one) is rolled back and failed. An append or write error in the current batch first lets the in-flight batch finish, so a rollback never truncates data whose fsync is still running.
   - Barriers (truncate, purge, release, close) drain first. Replication `on_leo` uses the mark's end offset, not the writer's.
   - **Default off** (`--commit-pipeline` / `FLUXMQ_COMMIT_PIPELINE`), see the measurements below. When on, a batch is pipelined only under concurrent load, meaning commands are queued behind it or it holds at least 4 requests; a lone request is fsynced inline.

Tests added:
- storage unit tests: `pipelined_marks_publish_in_order`, `rollback_discards_every_unpublished_mark`, `crash_recovery_with_pipelined_commit` (torn record, lost new segment, empty new segment), `mixed_segment_sizes_recover_and_replicate`, `roll_jitter_is_deterministic_and_bounded`, `paced_removal_and_stepwise_shrink`;
- `fsync_pool` unit tests (bounded reuse, errors, waker, shutdown);
- `tests/storage_pipeline.rs`:
  - sticky distribution and the byte bound;
  - concurrent publish with pipeline on, off and with OS-buffered fsync, checking that acked offsets are exactly `0..n` and survive a restart;
  - abrupt stop with pipelining;
  - paced retention bounds and convergence;
  - fsync pool shared and bounded;
  - retention-skip counter;
- `tests/retention_loss.rs`;
- `--segment-bytes`, `--fsync-threads` and `--commit-pipeline` CLI parsing.

### Measurements

**Environment.**
- Hardware and storage: local macOS, 8 CPUs, APFS, with `F_FULLFSYNC` at ~7–10 ms per flush.
- Binaries: release builds of `a8a9d03` ("before") and of `a8a9d03` plus only this work ("after", built in a separate worktree so the client and `group.rs` changes of other agents are excluded).
- Client: the same `fluxmq-bench` binary (`a8a9d03`) for both.
- Channel: 8 partitions, 1 GiB channel retention (128 MiB per partition, the stall case).
- Saturation: closed loop, 8 in flight × 100 msgs per producer, 15 s.
- Latency: open loop, 4p4c, batch 1 at 1k msg/s and batch 10 at 10k and 50k msg/s, 20–45 s.
- Order: runs interleaved before/after, 5 repeats, medians.
- **Load average was 15–50 throughout** (other agents building and benchmarking). Single runs vary 2–3× (for example, before sat-1k-4x4 ran 105k–233k msg/s), and every lat-50000 configuration shows random 0.5–2 s stalls at arbitrary times, including in "before". The stalls fall at random seconds. The retention start in this scenario is at t ≈ 20 s, and the stalls do not cluster there.

**The v0.5 stall does not reproduce on APFS.** A direct microtest unlinked 8 × 64 MiB files, with and without stepwise truncation, while another thread ran back-to-back `F_FULLFSYNC`. The concurrent fsync max stayed within its baseline range (13–39 ms with unlinks vs 17–41 ms baseline). The mechanism is the ext4 journal (the Docker VM in the bench). **Item 1 must be confirmed in the Docker bench:** `lat-50000` with `--retention-mb 128` before and after, looking for the t ≈ 24 s dip disappearing.

**Pipelined commit.**
- Measured in-process: `Broker::publish` directly, no network, 8 partitions, 1 KiB, 3 interleaved repeats.
  - 32 publishers × 100 msgs, keyless: on 333k / 360k / 351k msg/s vs off 326k / 321k / 337k (+5 %).
  - 16 publishers × 1 msg: on 857 / 853 / 1755 msg/s with p50 18.9 / 18.8 / 9.0 ms, vs off 1369 / 1337 / 2474 msg/s with p50 10.1 / 10.5 / 5.1 ms: 35–40 % fewer msg/s, about 2× p50.
- Why: with closed-loop publishers and an expensive fsync, pipelining splits them into two cohorts. Cohort A's batch is in flight while B's accumulates, and B is submitted the moment A completes, just before A's publishers' next requests arrive. Each message then waits about two fsyncs and the device does more fsyncs per message. Without pipelining the cohorts merge into one batch.
- Pipelining pays only when appending and writing a batch costs CPU time comparable to the fsync (fast NVMe, large batches). That could not be shown here, so it is **off by default**, correct and tested, behind `FLUXMQ_COMMIT_PIPELINE=on`. Worth one Linux Docker A/B run.

**fsync pool.** On Apple every commit is a single chain and runs inline, before and after, so there is nothing to measure locally. On Linux it replaces up to 8 thread spawns per commit with pooled threads. Confirm in Docker with `lat-10000 --partitions 1` broker CPU, the experiment in the confirmation list.

**Sticky partitioner.** Keyless with sticky routing vs keyed spread over all partitions (the v0.5 keyless shape), in-process, 32 × 100 with pipelining off:
- sticky: 275k / 278k / 121k msg/s;
- spread: 321k / 246k / 75k msg/s.

Noise dominates here too. On Apple a commit costs one device barrier however many files are dirty, so the expected gain is on Linux, where each dirty partition is its own `fdatasync`.

### Risks
- Paced retention can let a channel exceed its byte budget by a few segments under sustained ingest above about 64 MiB/s per channel. `due/8` catch-up bounds this. Explicit `enforce_retention` is unpaced.
- Stepwise truncation helping on ext4 is an inference from the measured stall, not measured: it could not be reproduced on macOS. It touches only unreferenced segments.
- The `total - seg >= budget` rule keeps up to one segment more than before, so disk usage per partition is at most budget + one segment. With the new 64 MiB default that is ≤ budget + ~70 MiB.
- When enabled, pipelined commit changes batch shapes. Semantics are unchanged, and the rollback paths are covered by unit and integration tests, but failure injection at the fsync level is only tested at the storage layer, not through the writer thread.

### Findings

- **Retention stall (item 1): fixed on ext4.** See the table above. It is fixed even with the v0.5 segment layout (segment = cap), so the paced, stepwise deletion is what fixed it. Smaller segments do not lower the tail further on this disk.
- **fsync pool + sticky partitioner (items 2, 3): about 45 % less broker CPU** at 10k msg/s with 8 partitions (v0.5 1.21–1.27 cores, v0.6 0.63–0.74, 3 interleaved runs). With 1 partition there is no change (0.51 both).
- **Pipelined commit (item 4): not measured in Docker.** No evidence for changing the default, so it stays off.
- **SDK coop bug (found by this run, fixed).** `PublishFuture` wrapped a tokio oneshot. A caller with about 20k sends outstanding in one `FuturesUnordered` got `Pending` for completed sends once the task's coop budget ran out, and the cost per message grew with the window. FluxMQ 1 KiB 1×1 by window: 2000 → 215k msg/s, 10000 → 105k, 20000 → 50k. The v0.5 SDK had it too (42k at 20000). Fix: `futures::channel::oneshot`, plus the regression test `completed_sends_are_ready_without_coop_budget`. After the fix: 389k msg/s published at window 20000.
- **New weakness: consumers starve under producer overload.** With the larger window the producers are no longer throttled. At 100 B 4×4, FluxMQ publishes 1.4–1.5M msg/s while its consumers get only 29–43k msg/s (1 node) or 11–14k (3 nodes). Kafka in the same situation consumes 374k. Most of the backlog stays stored, and the rest is removed by the size cap. The id audit and the retention-skip counter show **no loss**.
  - Candidate fixes for v0.7: fair scheduling of fetch against append in the partition writer, producer backpressure (`Overloaded`) when a group's lag exceeds a bound, and reads from segments without the publish path's locks.

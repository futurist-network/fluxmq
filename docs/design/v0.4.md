# FluxMQ v0.4 design: TLS and automatic rebalancing

The contracts live in code. `fluxmq_proto::tls` covers surfaces, flags, reload and the SDK; the rebalancing contract is the v0.4 block at the end of `fluxmq_proto::cluster`; the new `EventKind`s are in `fluxmq_proto::telemetry`; `api::ERROR_UNSUPPORTED_SINGLE_NODE` is the new error code. Read their docs first. This file covers placement, ownership and acceptance criteria.

## 1. TLS: new crate `fluxmq-tls` plus the transports

**The `fluxmq-tls` crate** is shared and owned by the TLS engineer:
- `ServerTls` and `ClientTls` builders from PEM paths, using rustls with the aws-lc-rs provider (the same provider reqwest and lettre already pull in, so there is one crypto stack).
- A reloadable `ResolvesServerCert` and client-cert resolver. Certificates are reloaded on an mtime watch every 30 s and on SIGHUP. A failed reload keeps the old certificate and records the error.
- `CertificateInfo` extraction (x509-parser), handshake-failure counters, a `TlsStatus` snapshot, and dev certificate generation (rcgen).

**Transports:**
- **Client port:** `tokio-rustls` acceptor in `fluxmq-server/src/net/listener.rs`. The connection code becomes generic over `AsyncRead + AsyncWrite`. The mTLS principal hint shows in connection info.
- **HTTP port:** axum served over TLS (hyper-util + tokio-rustls, no extra framework). `--http-tls off` keeps it plaintext.
- **Cluster:**
  - Raft transport, replication TCP (both directions) and internal HTTP (the reqwest client with an identity and a custom root, and the server side on the HTTP or internal listener) all use mutual TLS against the cluster CA.
  - The peer certificate must chain to the cluster CA. Node-id pinning is optional: CN = node id, warn on mismatch.
- **SDK:** `TlsOptions { ca_pem: Option<PathBuf | Vec<u8>>, use_system_roots, client_cert, client_key, server_name, danger_accept_invalid_certs }`; `tls://` addresses; works across reconnects and all cluster nodes. `fluxmq-bench` and `fluxmq-demo` get `--tls-ca` / `--tls-cert` / `--tls-key`.

**Elsewhere:**
- **API:** `GET /api/tls` (viewer) returns `TlsStatus`. Telemetry alerts: `tls_cert_expiring` (warning at 14 days, critical at 3 days or expired) and `tls_reload_failed`, which arrive in notifications automatically. Prometheus: `fluxmq_tls_handshake_failures_total{surface}` and `fluxmq_tls_cert_expiry_seconds{surface}`.
- **CLI:** `fluxmq tls gen-dev …` per the proto docs.

**Performance gate:** release `fluxmq-bench` publish+consume over TLS stays within 15% of plaintext throughput at 1 KiB messages. Record it in BENCHMARKS.

## 2. Rebalancing: `fluxmq-cluster` controller

**Planner** (`assign.rs` or a new `rebalance.rs`):
- Pure functions over (assignments, view, config, per-node storage) that return `Vec<PartitionMove>`.
- Sticky, minimal moves; never two replicas of one partition on one node. Replica counts per live node are balanced first, then preferred leaders (replica 0).
- Deterministic (stable ordering) and heavily unit- and property-tested: invariants hold, it converges, and planning again after applying the plan gives an empty plan.

**Executor:**
- A controller task drives moves through `MoveState` with at most `max_concurrent_moves` at a time, using assignment writes with preconditions (the same conflict-retry pattern as the drain fix).
- It persists the plan at `cluster/rebalance/plan` and resumes it on controller failover. A move times out after `move_timeout_secs` and is rolled back.
- Pause, resume and cancel are supported. It reports progress (lag of new replicas from `ReplicationManager` / `PartitionReplicationStatus`).

**Triggers:**
- A node joined and has been stable for `rebalance_stable`.
- A node has been Down longer than `replace_after_secs`.
- RF was capped and nodes are now available.
- The imbalance exceeds the threshold. Re-evaluate at most every 30 s.

No triggers fire while a plan is running. Leaving or Draining nodes are never targets.

**Also owned here:**
- REST in `api/routes/cluster.rs`, the permission table entries, and events.
- On a single node, `GET` returns mode off and mutations return 400 `unsupported_single_node`.

**Config:** `--auto-rebalance off|repair|full` (`FLUXMQ_AUTO_REBALANCE`) sets the initial mode when `cluster/rebalance/config` is absent. After that, the API is the source of truth.

## 3. Replication and storage support: `fluxmq-replication` + `fluxmq-core`

- **Bootstrapping a new replica:**
  - A follower whose local partition is empty, or below the leader's low offset (retention), starts at the leader's `low_offset`, so core needs a log that starts at a non-zero base offset.
  - It also receives a snapshot of group committed offsets and DLQ state before tailing state records, so a later failover to this replica resumes consumption correctly (at-least-once).
- **A removed replica** stops following and deletes its local partition data. The channel directory goes away once no partitions remain locally.
- **Throttle:** per-follower catch-up rate limit (`throttle_bytes_per_sec`, set via `ReplicationManager` for partitions in `CatchingUp`). It never throttles in-sync followers.
- **Property test:** under concurrent publish and consume, moving every partition of a channel to a disjoint replica set loses no acked messages and keeps group offsets, including a kill -9 of the old leader in the middle of a move.

## 4. UI

**Nodes page, Rebalancing panel:**
- Load bars per node (replicas, leaders, storage), the imbalance badge and the under-replicated count.
- The current plan as a table of moves with state chips and catch-up lag progress, and the trigger.
- Buttons: Rebalance now (dry-run preview → confirm → execute), Pause / Resume / Cancel.
- A config form (mode, concurrency, threshold, replace-after, throttle, timeout).
- Projected load after the plan.
- A single node shows an explanatory empty state.

**Security:**
- A TLS card shows client / http / cluster: enabled, mTLS, certificate subject / SANs / expiry countdown, last reload error and handshake failures.
- Expiry warnings feed the existing alerts UI.

**Rules:** role-aware (admin for mutations), mock server support, Playwright screenshots.

| Engineer | Owns | Shared-file edits |

| Replication/storage | new-replica bootstrap, group/DLQ snapshot, removed-replica cleanup, throttle, the move property test (`fluxmq-replication`, `fluxmq-core`) | the transport setup lines belong to TLS; coordinate |
| UI | `ui/` | none |

Shared files: small, additive, localized edits, re-read immediately before editing. `fluxmq-proto` is architect-owned (additive changes only if essential, and report them). v0.3 behaviour must not change when TLS is not configured, and on a single node.

## 6. Acceptance criteria

**TLS:**
- A 3-node cluster with full TLS (`gen-dev` certificates) runs end to end: publish and consume over `tls://`, mTLS clients, the UI over https, and the failover test passing with TLS on.
- A plaintext client against a TLS port gets a clean failure, and the handshake failure is counted.
- Certificate rotation without restart is shown live.

**Rebalancing:**
- Starting 3 nodes with 6-partition RF=2 channels, adding n4 rebalances replicas to within the threshold automatically, with no publish errors beyond retries.
- Killing n2 for longer than `replace_after_secs` (set short in the test) restores RF on the remaining nodes.
- Controller failover in the middle of a plan resumes it.
- No acked message is lost in any of these cases.

## 7. Integration decisions

Made while integrating the four v0.4 work streams and verifying them live (full-TLS 3→4-node
cluster with `gen-dev` certificates, release build). No `fluxmq-proto` change was needed:
every fix below is additive behind existing contracts.

**Bugs found live and fixed at the root:**

| # | Symptom | Root cause | Fix |
|---|---|---|---|
| 1 | In any cluster with cluster TLS every node reported every peer as `node_down` ("has not answered since this node started (HTTP 400)"); the HTTPS port counted ~2 failed handshakes per second; cluster-wide telemetry was local-only | `ClusterSource` pulled `/internal/v1/node-stats` with its own plain `reqwest` client over `http://` (TLS HTTP port → 400; plaintext HTTP + cluster TLS → 401, `/internal/*` needs a cluster-verified connection) | pulls go through `Cluster::internal_http()` (scheme, node certificate, secret); new `InternalHttp::get_bytes`. `InternalHttp::delete` also hard-coded `http://` (group-delete fan-out under TLS) — now uses the client scheme. Regression asserts in both `cluster_tls` tests (no `node_down`, zero HTTPS handshake failures) |
| 2 | `GET /api/cluster/status` showed an empty ISR and a stale LEO for partitions with a catching-up replica; the rebalance plan showed a frozen catch-up lag (25000 for a replica that was 9k behind) | every node lists the partitions it *follows* too (`leader` = the node it follows, no follower lag); both the status endpoint (since v0.2) and the rebalancer's lag refresh keyed rows by partition only, so a follower row could win | keep only rows a node reports as leader of (`row.leader == reporting node`); leaderless rows (offline partitions) stay. Test `cluster_status_rows_come_from_partition_leaders` |
| 3 | `GET /api/events/feed` on a node without a replica of `$system.events` returned an empty feed | the feed reads the node-local replica | the node proxies the validated request to the partition leader's `/internal/v1/events/feed` (below). Test `events_feed_is_served_by_every_node` |
| 4 | a TLS certificate expiring on a non-controller node never notified | TLS alerts are node-local, only the controller notifies | peer alerts ride in the node-stats snapshot (below) |

**Events feed on any node.** Proxy to the leader rather than fan-out: the feed is one
partition, cursors are offsets (identical on every replica), so the leader alone answers
exactly what a single node would, with long-poll intact (proxy timeout = `wait_ms` + 10 s).
Validation stays on the receiving node (same 400s everywhere). With no leader (failover) the
node answers from its own copy — empty with the cursor preserved when it has none — instead of
failing a poll loop; graceful shutdown re-asks the leader with `wait_ms=0` so the cursor stays
the leader's. The internal handler never proxies again (no loops across a leadership change).

**Peer node-local alerts.** The node-stats snapshot every node already pulls from each peer
every second carries the peer's alert-source output as an optional postcard trailer
(`Vec<Alert>`): `SNAPSHOT_FORMAT` stays 1, older decoders ignore trailing bytes, a missing
trailer decodes as no alerts — so mixed 0.3/0.4 clusters keep working. `ClusterInfo` collects
the live peers' alerts and `cluster_candidates` adds them, so every node shows
`tls_cert_expiring:n4/cluster` and the controller notifies it once through the normal
hysteresis/rules path. A down peer's alerts drop out (its `node_down` covers it). The
`TlsReloadFailed` *event* stays node-local (the feed only gets the controller's events); the
`tls_reload_failed` alert covers it. Verified live: a 5-day certificate on n4 (controller n2)
showed on all four nodes and produced exactly one webhook notification; a broken PEM produced
one `firing` and, after the fix, one `resolved`.

**Cleanup of non-replica copies in every mode.** Kept as implemented (it is the only way a
moved replica frees its disk), guarded as before (caught-up metadata, absent from `replicas`,
epoch not older than the local copy, never on a `None` role). Documented as a behaviour change
in GUIDE §19 and CLUSTER *Upgrading from 0.3*, with the advice to start upgraded nodes with
`--auto-rebalance off` until the whole cluster runs 0.4. Verified live on a rejoining node
(136 MB of copies it no longer replicated removed, nothing else) and on a v0.3 data
directory (see the report / CLUSTER).

**Tooling (additive).** `fluxmq tls gen-dev --valid-days N --reuse-ca` (short-lived and
re-issued certificates from the existing CA — expiry alerts and rotation can be shown without
`openssl`); `GenDevOptions: Default`. The `resilience` example takes comma-separated seeds,
`FLUXMQ_CLIENT_TLS_*` and `RESILIENCE_PARTITIONS`, so the zero-loss check runs against a TLS
cluster.

**Kept as designed, documented.** Catch-up `lag` / `initial_lag` are live values attached
while a move is `catching_up` and are not persisted after `done`. `handshake_failures_total`
also counts browsers that don't trust the CA (Chromium aborts with `CertificateUnknown`
before proceeding; ~9 per page load against `gen-dev` certificates) and peers' short-timeout
requests abandoned mid-handshake while a node is busy starting — it is a "look here" counter,
not an attack counter. Formatting and clippy were already clean at integration; the version is
0.4.0 (workspace and UI).

# v0.10 — live subscription gateway (WebSocket + SSE)

Scope: `fluxmq-core` (`live.rs`: a read-only, HW-bounded reader plus a commit notification), `fluxmq-auth` /
`fluxmq-proto::auth` (role `subscriber`, scope `subscribe`), `fluxmq-api` (`live/`: endpoints, shared fan-out,
limits, metrics), `fluxmq-server` (flags). Step 1 is **read-only**: a live subscription has no consumer-group
state, commits nothing, and never changes what other consumers see.

**Status.** Implemented: `fluxmq-api/src/live/{feed,sub,ws,sse,handler}.rs` on top of the core reader, flags
`--live-*` in `fluxmq-server`, metrics in `/metrics`, tests `crates/fluxmq-server/tests/live.rs` (WS earliest → live →
resume by cursor without loss or duplicates, filters, several subscriptions per connection, reset, channel deletion
4404, SSE ids and `Last-Event-ID`, the `subscriber` role, origin check, per-channel limit, revocation 4401, 200
subscribers on one shared feed) and the load run `tests/live_load.rs` (§9). `leader_http` in `unavailable` events is
`null` for now (the leader's node id is given).

Goal: browsers, mobile apps and devices read a channel's messages in real time over the broker's existing HTTP
listener, resume after a reconnect without losing anything that is stored, and see exactly the data a normal
consumer may see (durable, ≤ HW). Thousands of subscribers on one channel must not multiply disk reads.

## 1. API

| Endpoint | Transport | Notes |
|---|---|---|
| `GET /api/channels/{name}/live` | WebSocket upgrade | several subscriptions per connection (`subscribe` / `unsubscribe` ops) |
| `GET /api/channels/{name}/events` | SSE (`text/event-stream`) | one subscription; `id:` = cursor; honours `Last-Event-ID` |

Both live under `/api/channels/{name}/…` next to `messages`, `publish`, `replay`. They are **not** behind the REST RBAC
middleware: the handler authenticates itself (the token may arrive in places the middleware does not read, §4) and
authorizes `Subscribe(channel)`.

### 1.1 Query parameters (both endpoints; the WS `subscribe` op takes the same fields as JSON)

| Parameter | Meaning |
|---|---|
| `from` | `latest` (default), `earliest`, `time:<unix ms>`, `offsets:<p>=<off>,<p>=<off>` (unlisted partitions start at `latest`) |
| `cursor` | resume position (opaque, §2). Wins over `from`. For SSE the `Last-Event-ID` header wins over both. |
| `partitions` | `0,2,5` — restrict to these partitions (default: all) |
| `key` | exact key match; repeat or comma-separate for a small set (≤ 64): `key=user_42` |
| `header.<name>` | header equality, e.g. `header.type=order.created` (all given headers must match) |
| `filter` | the routing filter language (`ref-filter`), e.g. `amount >= 100 AND country in [MD, RO]` |
| `access_token` | **SSE only** — the token for `EventSource`, which cannot set headers (§4) |

`key`, `header.*` and `filter` are ANDed. Filtering is server-side (`fluxmq_router::filter::matches`, the same evaluator as
message search, routes and webhooks); filtered-out messages still advance the cursor.

### 1.2 Events

Every event is one JSON object with a `type`; the same JSON is the WS text frame and the SSE `data:` line (SSE also sets
`event: <type>`). `sub` names the subscription (`"0"` for the one opened by the URL; client-chosen for WS `subscribe`).

| `type` | Fields | When |
|---|---|---|
| `hello` | `sub, channel, partitions, cursor, limits{…}` | subscription started; `cursor` = start position |
| `messages` | `sub, cursor, messages: [envelope…]` | one or more messages; `cursor` = position after them |
| `gap` | `sub, cursor, partition, from, to, lost` | `[from, to)` was removed by retention before it could be delivered |
| `reset` | `sub, cursor, partition, requested, actual` | a resume offset beyond the log end (restored/rewound node): continuing at `actual` |
| `progress` | `sub, cursor` | filtered-out messages advanced the position (at most every 2 s) |
| `unavailable` | `sub, partitions: [{partition, leader, leader_http}]` | cluster: this node holds no replica / role for a partition (§6) |
| `error` | `sub?, code, message` | bad WS command, subscribe refused (forbidden, limit) |
| `end` | `reason` | SSE only, last event before the server closes (`slow`, `shutdown`, `revoked`, `deleted`, `limit`) |

Envelope:

```json
{"partition":0,"offset":42,"key":"user_42","headers":{"type":"x"},"timestamp":1760000000000,
 "encoding":"utf8","payload":"{\"a\":1}","size":7}
```

`encoding` is `utf8` (payload as text) or `base64`. Payloads above `--live-max-payload-bytes` (default 64 KiB) are
**truncated** (`"truncated": true`, `size` = original size; UTF-8 cut on a character boundary) rather than skipped: the
client learns the message exists and can fetch it in full over REST if it may. Skipping would be a silent hole.

Batching: one `messages` event carries up to `--live-max-batch` (256) messages / about 256 KiB, so a busy channel costs one
frame per committed batch, not per message.

### 1.3 WebSocket commands (client → server, JSON text)

```json
{"op":"subscribe","id":"orders","channel":"orders","from":"earliest","key":["k1"],"filter":"…","cursor":"…"}
{"op":"unsubscribe","id":"orders"}
```

`id` ≤ 64 chars, unique per connection. At most `--live-max-subscriptions` (16) per connection.

### 1.4 Errors and close codes

Before the upgrade / stream start: `400` bad parameters or cursor, `401` no/invalid token, `403` not allowed
(`forbidden`, or `origin_not_allowed`), `404` channel, `429` per-token or per-channel connection limit, `503` node
connection limit or channel not served by this node.

WS close codes after the upgrade: `4008` slow client, `4401` token revoked/expired (as `/ws`), `4404` channel deleted,
`4429` limit, `1001` server shutdown, `1008` idle timeout.

## 2. Cursor

`c1.` + base64url (no padding) of: `crc32(channel name)` (4 bytes LE) followed by `(varint partition, varint next
offset)` pairs, one per partition of the subscription. Opaque for clients; versioned (`c1.`) so it can change. The
channel CRC rejects a cursor of another channel (400). A cursor names the **next** offset to deliver per partition, so
resuming with the cursor of the last received event delivers exactly what came after it; a client that crashed between
receiving and processing an event resumes from an older cursor and sees that event again (at-least-once at the
boundary, never a hole).

Every event that moves the position carries the cursor; SSE sets `id: <cursor>` on them, so the browser's automatic
reconnect sends it back in `Last-Event-ID`.

Resume rules per partition: `next < log start` → `gap` event `[next, log start)` with the count, then continue at the
log start (the client is told, never silently skipped). `next > log end` → `reset` event, continue at the end.

## 3. Reading and fan-out

### 3.1 Core (`fluxmq_core::live`)

- `Channel::live` — a `tokio::sync::watch` generation bumped wherever consumers are woken (`notify_groups`: commits, HW
  advance, role change) plus on follower HW adoption and channel close. Costs one relaxed atomic load per commit when
  nobody is subscribed (`receiver_count() == 0`).
- `Broker::live_reader(channel) -> LiveReader`: `visible_end(p)` (`None` = not served here), `low(p)`, `read(p, from,
  max_records, max_bytes)` bounded by `visible_end` (served from the partition's recent-entry cache, else positional
  reads), `offset_for_time(p, ts)`, `changed()`.
- Visibility: single node → committed end (`high`); replicated → `min(HW, high)` on the leader **and on followers**
  (followers adopt the leader's HW capped by their own durable LEO; data below it is on every electable replica and is
  never truncated by KIP-101 reconciliation). Offline partitions are not served.

### 3.2 Shared feed (`fluxmq_api::live::feed`)

One **pump** task per channel with ≥ 1 live subscriber (refcounted, stops when the last leaves): a per-partition
frontier initialized at `visible_end`; on every `changed()` it reads `[frontier, visible_end)` in bounded chunks (1024
records / 1 MiB) and broadcasts `Arc<Batch>` on a `tokio::sync::broadcast` ring of `--live-fanout-buffer` (1024)
batches. A batch carries its messages (`Arc<Message>`, shared with the log cache), its position after, and lazily built
(once, shared by all receivers) envelope JSON and complete WS/SSE frames for the common "unfiltered, all partitions,
at the tail" subscriber. 5 000 tail subscribers therefore cost one read and one serialization per batch; per-subscriber
work is a refcount clone and a socket write.

### 3.3 Subscription task

Each subscription keeps its own per-partition `next`. It subscribes to the broadcast **first**, then catches up from
storage up to `visible_end` in bounded chunks (round-robin across partitions), then consumes batches:

- `batch.next <= next[p]` → already delivered, skip;
- `batch.from <= next[p]` → deliver the suffix;
- `batch.from > next[p]` (a hole: joined late, or the ring overran it — `Lagged`) → read the hole from storage, then the batch.

So a subscriber that falls behind degrades into a private storage reader and rejoins the shared fan-out by itself; no
explicit hand-off protocol, no window where data can be skipped. Memory per subscriber is bounded by the outbound queue.

## 4. Security

- **Role `subscriber`** (new, below `viewer`; roles stay cumulative `subscriber ⊂ viewer ⊂ operator ⊂ admin`): may
  only open live subscriptions on channels matching its `subscribe` scope. It cannot call any REST route (`Read` now
  requires `viewer`), cannot use `/ws`, cannot publish or consume over the client protocol (no `publish`/`consume`
  scopes allowed on such tokens), cannot be bound to a certificate. Existing roles are unchanged.
- **Scope `subscribe`** (new `ClientScopes.subscribe`, same glob syntax as `publish`/`consume`: `notifications.*`,
  `user-feed`). `Subscribe(channel)` is allowed for `viewer`+ (they may already read every message over REST) or when the
  channel matches `scopes.subscribe`. A `subscriber` token without patterns is rejected at creation. Persisted like
  other tokens (`auth/tokens/<id>`, field omitted when empty, so existing records are byte-identical); revocation and
  expiry close live connections within 1 s (`session_watch`), as for `/ws`.
- **Token transport.** `Authorization: Bearer` everywhere (servers, mobile, devices). Browsers:
  - WS: `Sec-WebSocket-Protocol: fluxmq.live.v1, fluxmq.token.<token>` — the server answers with `fluxmq.live.v1`
    only (the token is never echoed). Not logged by proxies like URLs are.
  - SSE: `?access_token=<token>` — `EventSource` cannot set headers. Query strings end up in proxy/access logs and
    browser history: use short-lived `subscriber` tokens (`ttl_secs`), scoped to the channels the page needs, minted
    by your backend per user session. The broker's own request spans carry the path only. Query tokens are **not**
    accepted on the WS endpoint (the subprotocol works in every browser).
- **Origin allow-list** (`--live-allowed-origins`, comma-separated exact origins or `*`). A request with an `Origin`
  header must be same-origin (`Origin` host:port = `Host`) or listed; otherwise `403 origin_not_allowed`. Requests
  without `Origin` (non-browser clients) pass. This blocks cross-site WebSocket hijacking with a victim's ambient
  credentials. Applies in open mode too (stricter than REST's permissive dev CORS, deliberately: a live stream is the
  easiest exfiltration channel). Allowed cross-origin SSE responses carry `Access-Control-Allow-Origin: <origin>`.
- Open mode (no tokens): everyone is the anonymous admin, as elsewhere; all limits still apply.

## 5. Limits and backpressure

| Flag / env | Default | Effect |
|---|---|---|
| `--live-max-connections` / `FLUXMQ_LIVE_MAX_CONNECTIONS` | 10 000 | per node; over → `503` |
| `--live-max-connections-per-token` / `…_PER_TOKEN` | 1 000 | per token id (bootstrap admin / anonymous exempt); over → `429` |
| `--live-max-connections-per-channel` / `…_PER_CHANNEL` | 10 000 | per channel; over → `429` (WS `subscribe` → `error`) |
| `--live-max-subscriptions` | 16 | per WS connection |
| `--live-max-msgs-per-sec` | 10 000 | per connection, token bucket; 0 = off |
| `--live-max-bytes-per-sec` | 16 MiB | per connection, token bucket; 0 = off |
| `--live-max-payload-bytes` | 65 536 | larger payloads are truncated (§1.2) |
| `--live-max-batch` | 256 | messages per event |
| `--live-send-buffer` | 64 | outbound frames queued per connection |
| `--live-send-timeout` | 10 s | a socket write that does not complete in time → `slow` close |
| `--live-heartbeat` | 15 s | WS ping / SSE comment |
| `--live-idle-timeout` | 60 s | WS: nothing (not even a pong) received for this long → close |
| `--live-fanout-buffer` | 1 024 | batches in a channel's broadcast ring |
| `--live-allowed-origins` | empty | see §4 |

Rate limits **throttle** (the subscription simply falls behind and catches up from storage) instead of disconnecting.
A client whose socket stops draining blocks its writer; after `--live-send-timeout` it is closed with `slow` (WS 4008;
SSE: `end` event when it still fits, then the stream ends). Memory per connection is bounded by `--live-send-buffer`
frames (each ≤ ~256 KiB + one envelope); the shared ring is bounded by `--live-fanout-buffer` batches per channel. The
client resumes by cursor; nothing is lost.

## 6. Cluster

Any node holding a replica (leader or follower) serves the partition, bounded by its local HW (§3.1). With the default
RF=3 on ≤ 3 nodes every node serves every partition. Partitions this node holds no replica of (or that are offline
here) produce one `unavailable` event naming the leader and its HTTP address; their cursor positions are carried
unchanged, so a client may open a second subscription on that node (`partitions=`) without losing anything; the
subscription re-checks every second and starts serving if a replica moves here. A channel with no replica on this node
at all → `503`.

Follower latency = leader HW propagation (one fetch round trip, a few ms with fetch-ahead). Rejected alternatives:
leader-only serving (every client would need a connection per leader — unusable for browsers); proxying remote
partitions over `/internal/*` (a second data path with its own backpressure and failure modes; can be added later
without changing the API).

## 7. Observability

`/metrics`: `fluxmq_live_connections{endpoint}` (gauge), `fluxmq_live_subscriptions{state="catchup|live"}`,
`fluxmq_live_feeds` (pumps), `fluxmq_live_messages_sent_total{endpoint}`, `fluxmq_live_bytes_sent_total{endpoint}`,
`fluxmq_live_slow_disconnects_total{endpoint}`, `fluxmq_live_rejections_total{reason}`, `fluxmq_live_gaps_total`.
Telemetry documents are unchanged in this step (console screen later).

## 8. Alternatives rejected

- **A hidden consumer group per subscriber**: durable state per browser tab, group sprawl, commits on the write path.
- **The telemetry tail** (`Broker::tail`): sampled and rate-limited by design, not a data feed.
- **Per-subscriber storage readers only**: N× reads and N× serialization of the same bytes at the tail.
- **Disconnect on broadcast lag**: needless reconnect storms on bursts; falling back to storage reads keeps memory bounded
  without dropping the client.
- **Skipping oversized messages**: a silent hole; truncation is explicit.
- **Token in the WS URL**: leaks into logs; the subprotocol carries it without a URL.

## 9. Measurements

`crates/fluxmq-server/tests/live_load.rs` (ignored; release build). Broker and all clients run in **one process** on a
4-CPU WSL2 VM, and every client parses the JSON of every message. This measures correctness under load and the
whole box's capacity, not the gateway alone.

2026-10-12, `LIVE_SUBS=2000 LIVE_RATE=2000 LIVE_SECS=10` (4 partitions, ~170 B events):

| | |
|---|---|
| subscribers / messages | 2 000 WS tail subscribers, 20 000 messages → **40 000 000 deliveries, 2 000 / 2 000 complete**, 0 slow disconnects, 0 gaps |
| shared feed | `fluxmq_live_feeds` = 1 (one read and one envelope encoding per batch for all 2 000) |
| fan-out rate | 0.64 M deliveries/s, CPU-bound: the producer reached its 2 000 msg/s target only on average over 62 s instead of 10 s, because the clients' JSON parsing shares the 4 CPUs |
| latency publish → receipt | p50 136 ms, p99 233 ms, p99.9 344 ms (CPU saturation; sampled on 40 subscribers) |
| memory | 22 MB → 577 MB RSS with 2 000 idle subscribers (broker **and** client sockets/buffers in one process: ≈ 280 KB per pair) |

Next: run the clients from another machine/process to measure the gateway alone and the per-connection broker memory.

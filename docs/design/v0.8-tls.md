# v0.8 — TLS cost: in-place record layer

Status: implemented in the working tree (not committed). Code: `crates/fluxmq-tls/src/fast/`
(record layer, handshake hand-over, async halves, TLS 1.2 path, tests),
`crates/fluxmq-tls/src/stream.rs` (implementation selection), wiring in the client listener
(`fluxmq-server::tls`, `net::listener`), the SDK connector (`fluxmq-client::conn`) and
replication (`fluxmq-replication::transport`). Bench: Kafka TLS rows (`bench/runner.py`,
`deploy/docker-compose.yml`, harness `--kafka-tls-ca`).

**Docker A/B: not run.** The Docker build/bench commands were refused by the session's
permission policy (twice, with the final-bench flag present, the bench lock free and no
containers running). Everything below the Docker line is therefore measured natively on the
bench host (M1 Pro, macOS) — micro-benchmarks, a native broker + harness run, a latency
ping-pong — and the Docker A/B is a ready script (`work/tls2/ab.sh` +
`summarize.py`, section 7). The target (≤ 15 % at 1 KiB, ≤ 10 % at 100 B) is **not yet
demonstrated**.

## 1. Root cause (confirmed in the rustls 0.23.45 / tokio 1.53 sources)

Per received TLS record, the classic path (tokio-rustls → rustls buffered API):

1. `recv` into rustls' deframer buffer, at most ~4 KiB per call (`DeframerVecBuffer`
   read-size), so ~4 syscalls per 16 KiB record;
2. AEAD decrypts in place in that buffer (`conn.rs`, `process_more_input` → record layer);
3. **copy 1**: `CommonState::take_received_plaintext` → `received_plaintext.append(bytes.into_vec())`
   (`common_state.rs:483`), a fresh `Vec` per record;
4. **copy 2**: `Reader::read` copies that `Vec` into the caller's buffer (`conn.rs`), i.e. the
   `FramedRead` buffer.

Per sent record: `OutboundChunks::copy_to_vec` into a fresh record `Vec`, seal in place,
`writev` — one copy (needed: the AEAD seals in place).

On top, `tokio::io::split` over one `TlsStream` puts both directions behind one
`std::sync::Mutex` (`tokio-1.53.2/src/io/split.rs:59`), held while rustls decrypts or
encrypts: the read task (main runtime) and the write task (delivery runtime on the broker,
the ack writer in the SDK) block each other's OS threads.

**The unbuffered API does not help** (the previous note's claim, confirmed and extended):
`ReadTraffic::next_record` pops the same `received_plaintext` `Vec` ("TODO … requires
in-place decryption", `conn/unbuffered.rs:348`) — copy 1 remains, and the caller copies out
of the borrowed `Vec`; `WriteTraffic::encrypt` → `write_fragments` encrypts into a record
`Vec` and then `copy_from_slice`s it into the caller's buffer (`common_state.rs:625-652`) —
**two** copies on send instead of one.

What the published v0.8 numbers show (`bench/results/20261010-v0.8`, 1 node, 1 KiB 1×1):
plaintext consumed 468–510k msg/s at 112 % broker CPU (of 200 %); TLS published 421k but
consumed only **214k**, broker 169 %, harness 202 % (of 400 %). The consumer is the limiter,
and it is window-bound: with prefetch 2000 and 214k msg/s the delivery→ack round trip is
~9 ms (plaintext ~4 ms). Every bit of per-round-trip latency (lock waits, 4 KiB reads,
copies) cuts consumed throughput directly; once consumers lag past the recent cache they
read from disk, which costs more broker CPU per message (broker CPU per GB moved: 1.1 ms/MB
plaintext, 2.6 ms/MB with TLS — far more than AES, ~0.12–0.14 ms/MB per direction on this
CPU). At 100 B the cost is per message, not per byte: TLS was +4 % (730k vs 702k).

## 2. Design

**Handshake by rustls, records by rustls' AEAD objects, in our buffers.**

1. The handshake runs on rustls' unbuffered connection (`fast/handshake.rs`): same configs,
   verifiers (mTLS, CRLs), SNI, ALPN, versions, suites as before. Only a *finished*
   handshake counts (a TLS 1.3 server may already write after its Finished, before the
   client certificate is verified: `WriteTraffic` while `is_handshaking()` keeps reading).
   On a handshake error the alert rustls queued is sent (the peer still sees e.g.
   `received fatal alert: BadCertificate`).
2. TLS 1.3 sessions are handed over with `dangerous_into_kernel_connection`: rustls returns
   the traffic secrets with their current sequence numbers plus a `KernelConnection` that
   derives every later KeyUpdate secret and stores session tickets. From the secrets we build
   rustls' own `MessageEncrypter` / `MessageDecrypter` (`Tls13CipherSuite::aead_alg`) — the
   AEAD and the nonce construction (`iv XOR seq`) stay in rustls/aws-lc.
3. **Receive** (`fast/io.rs`, `KernelRead`): `recv` up to 64 KiB into the connection's buffer,
   decrypt each complete record **in place** (`MessageDecrypter::decrypt` on
   `InboundOpaqueMessage` borrowing our buffer), copy the plaintext **once** into the
   caller's buffer. No per-record allocation. 4 KiB → up to 64 KiB per `recv`.
4. **Send** (`record.rs`, `RecordWriter::seal_app`): records of ≤ 16 KiB are sealed straight
   from the caller's `IoSlice`s (`OutboundChunks::new(&slices)`) — the one copy the in-place
   AEAD needs — and queued for `writev` (≤ 64 records per call, 256 KiB queue limit for
   backpressure). The server's zero-copy `FrameWriter` (envelope `Bytes` as iovecs) feeds it
   directly.
5. **Independent halves**: read half and write half own their socket half
   (`TcpStream::into_split`) and their crypto state; they share only an `Arc` with the
   `KernelConnection` (locked on key updates and tickets — rare), a "peer asked for a key
   update" flag and a "failed" flag. No lock is held across encryption, decryption or I/O.
6. **TLS 1.2** sessions (rare: every FluxMQ client and node negotiates 1.3) stay on rustls'
   own record layer (`fast/locked.rs`): the unbuffered connection behind a mutex held only
   while rustls runs, never during socket I/O. Reason: rustls seals AES-GCM with aws-lc's
   `TlsRecordSealingKey`, which treats the first nonce a key object sees as sequence 0 and
   then enforces strictly increasing sequences — a TLS 1.2 hand-over happens at write
   sequence 1 and TLS 1.2 has no KeyUpdate to start a fresh key at 0. (Found by the tests:
   the first version failed after three records.)
7. The same monotonicity rule applies to TLS 1.3: a server hands over at write sequence 2
   (after rustls' two NewSessionTickets). Its first record from the fresh encrypter is
   therefore a KeyUpdate (valid at the key object's first nonce), after which every key
   starts at 0, exactly as in rustls. Clients hand over at 0 and do not rotate.
8. Receive buffer: 21 KiB at first (one record + 4 KiB, ≈ rustls' deframer buffer), grows to
   80 KiB once a `recv` fills it; idle connections stay small.

**Selection**: `FLUXMQ_TLS_IMPL=fast` (default) | `classic` (tokio-rustls behind
`tokio::io::split`, the v0.7 path) — read once per process by the broker (client port,
replication) and by the SDK. Both implementations interoperate in every combination (same
TLS on the wire). The cluster Raft RPC and the HTTPS port keep tokio-rustls (low volume).

**Cipher preference** (`fluxmq_tls::prefer_aes128`): TLS 1.3 AES-128-GCM moved ahead of
AES-256-GCM in the provider order. Same suite set, same versions, TLS 1.2 order untouched
(`suite_set_unchanged_aes128_first` test). The server keeps following the client's order
(`ignore_client_order` stays false), so FluxMQ clients and nodes negotiate AES-128 and
third-party clients get what they prefer. AES-128-GCM is ~15 % cheaper per byte here
(8.3 vs 6.9 GB/s seal, aws-lc ARMv8) and has twice rustls' per-key confidentiality limit
(2^24 vs 2^23 records).

## 3. Security analysis

What stays in rustls / aws-lc: handshake, certificate and CRL verification, client
authentication policy, SNI, ALPN, version and suite negotiation, the key schedule, every
KeyUpdate secret, session tickets, AEAD, nonce derivation. The handshake code path is
rustls' (the unbuffered API is rustls' supported sans-I/O interface).

What FluxMQ code does in kernel mode (`fast/record.rs`, ~500 lines, each rule mirroring
rustls' record layer):

| concern | rule (rustls reference) |
|---|---|
| sequence numbers | one `u64` per direction, starts at rustls' value, +1 per record, 0 after a key update; refuse at `SEQ_SOFT_LIMIT` (`record_layer.rs`) |
| confidentiality limit | KeyUpdate when the write sequence reaches `min(suite limit, SEQ_SOFT_LIMIT)` (`pre_encrypt_action`, `maybe_refresh_traffic_keys`) |
| KeyUpdate received | `update_rx_secret`, new decrypter at 0; must end its record (`KeyEpochWithPendingFragment`); value 0/1 only; `update_requested` → our next record is a KeyUpdate (RFC 8446 4.6.3); ≤ 32 between application records (`TemperCounters`) |
| NewSessionTicket | client: `KernelConnection::handle_new_session_ticket`; server: unexpected message |
| other post-handshake handshake types | fatal (`InappropriateHandshakeMessage`); messages ≤ 64 KiB; no interleaving with other types |
| record header | known content type, `0x03xx` version, body ≤ 2^14 + 256, non-empty; TLS 1.3 outer type must be application_data (no plaintext alerts / CCS after the handshake) |
| plaintext | ≤ 2^14 after unpadding (`into_tls13_unpadded_message` checks inner type/padding) |
| alerts | close_notify → EOF; warnings fatal except user_canceled (TLS 1.3 rule), ≤ 4; fatal → error |
| truncation | EOF without close_notify → `UnexpectedEof` error (at a record boundary or mid-record), never a clean end |
| failure | any record error marks the connection failed; the write half refuses further writes |

Defence in depth: aws-lc's `TlsRecordSealingKey` rejects any non-increasing nonce for
AES-GCM, so a sequence bug fails closed instead of reusing a nonce; a receive-side sequence
bug fails AEAD authentication. Interop tests against rustls' buffered implementation
(both roles) would expose any off-by-one immediately.

Deviation from the brief: it asked for no FluxMQ-owned sequence numbers. rustls 0.23 has no
API that decrypts application data in place *and* keeps the counter internal (section 1);
the kernel API (built for kTLS, which keeps exactly these counters in the kernel) is the
supported way. The counter logic is three lines per direction; nonces remain rustls'.

Differences from the classic path: in kernel mode a fatal record error closes the
connection without sending a fatal alert (the peer sees EOF / a reset; handshake alerts are
still sent). `enable_secret_extraction = true` is set on FluxMQ's configs: it only allows
in-process extraction through the API, nothing changes on the wire. 0-RTT stays disabled
(early data is refused). TLS 1.2 behaviour (including renegotiation refusal) is rustls'
own. Memory per connection: 21 KiB idle / 80 KiB busy receive buffer plus ≤ 256 KiB queued
ciphertext (classic: rustls' ~18 KiB deframer buffer plus a 64 KiB send limit).

### Tests (`crates/fluxmq-tls/src/fast/tests.rs`, all against both implementations)

* `roundtrip_all_impl_pairs_tcp` — fast↔fast, fast↔classic, classic↔fast, classic↔classic
  over TCP, 3 MiB / 2 MiB both ways at once, random write and read sizes.
* `random_splits_through_duplex_pipe` — property test: 24 seeds, random sizes (1 B … 600 KB),
  plain and vectored writes, random read buffers, through 977 B … 64 KiB pipes (partial
  records on every read, write backpressure); byte-identical, clean close.
* `every_suite_and_tls12` — every TLS 1.3 suite and three TLS 1.2 suites, negotiated suite
  and version asserted, data both ways.
* `key_updates_at_confidentiality_limit` — suites with limit 5: ≥ 10 key updates each way,
  fast initiating and applying the classic peer's.
* `key_update_requested_mid_stream` — fast sends KeyUpdate(update_requested) mid-stream;
  classic and fast peers answer, data intact before and after.
* `tls12_limit_closes` — TLS 1.2 at the limit: writes fail, peer sees a clean close_notify.
* `truncation_is_an_error` — EOF without close_notify at a record boundary and mid-record
  → `UnexpectedEof`, data before the cut delivered; close_notify → clean EOF; write after
  shutdown refused.
* `tampering_is_detected` — one flipped ciphertext bit → `InvalidData` (decrypt error), only
  authentic bytes before it, write half refuses afterwards.
* `hostile_stream_never_yields_forged_data` — 40 seeds of corrupted / inserted / dropped
  bytes at random offsets: never a panic or hang, never forged data, always an error.
* `untrusted_server_certificate_is_rejected`, `mtls_required_and_verified` (no certificate,
  foreign CA → refused; valid → CN visible), `revoked_client_certificate_is_rejected` (CRL),
  `alpn_and_version_policy_unchanged` (ALPN both sides; TLS 1.2-only client vs TLS 1.3-only
  server refused on every path), `large_and_tiny_frames` (8 × 1 MiB writes + 10 000 1-byte
  writes), `impl_selection`, `suite_set_unchanged_aes128_first`.
* Integration: `fluxmq-server` `tls`, `revocation` (classic tokio-rustls client ↔ fast
  server), `cluster_tls` (fast replication), `v4_e2e`; `fluxmq-client`, `fluxmq-replication`
  — all pass with the default (fast) and with `FLUXMQ_TLS_IMPL=classic`.

## 4. Measurements (native, M1 Pro / macOS — not the Docker VM)

Micro-benchmark (`work/tls2/micro`): one-way bulk over loopback TCP with 64-byte acks,
both ends in one process on one tokio thread (CPU-bound, no wake-up noise), CPU ms per GB:

| | 1 MiB writes | 16 KiB writes + flush | 1 KiB writes + flush |
|---|---|---|---|
| plaintext | 99–110 | — | — |
| classic, AES-256 (v0.8 default) | 574–586 | — | — |
| classic, AES-128 | 520–543 | 564 | 2 876 |
| **fast, AES-128** | **446–474** | 573 | 2 673 |

TLS overhead over plaintext at 1 MiB: classic/AES-256 ≈ 475 ms/GB → fast/AES-128 ≈ 350
(**−27 %**); AES itself is ~240–290 of it. Natively a hot `memcpy` runs at ~77 GB/s, so
the removed copies matter little here; in the Linux VM the previous profile measured each
copy at ~60 % of the AES cost per byte (glibc `memcpy` 33 % of TLS CPU), so the saving
there should be larger — unmeasured.

Native broker + harness (`work/tls2/nat.sh`: release `fluxmq` + `mq-harness`,
1 KiB 1×1, 15 s, unconstrained CPUs; throughput is bound by macOS `F_FULLFSYNC` here —
plaintext itself ranged 430–569k — so only CPU is meaningful), CPU seconds per run:

| | broker | harness | consumed |
|---|---|---|---|
| plaintext | 9.0–12.4 | 15.6–20.6 | 430–569k |
| classic | 17.0–18.0 | 23.0–24.9 | 488–543k |
| fast | 12.8–15.0 | 18.9–22.9 | 496–516k |

TLS CPU over plaintext: broker ≈ +8 s classic → +5 s fast (**−37 %**), harness ≈ +8 s →
+6 s (**−25 %**).

Latency: 1 KiB TLS ping-pong (20 000 round trips): p50 23.8 → 22.3 µs, p99 52–56 →
49–56 µs; 64 KiB: p50 91.9 → 76.1 µs, p99 140 → 119 µs. Native broker latency scenario
(4×4, 1k and 10k msg/s): p99 within macOS fsync noise for both (16–25 ms typical; two
outliers on the fast path, 34 and 63 ms, not reproduced in 6 further runs).

## 5. Kafka with TLS (rows added, not yet run)

`kafka-single-tls` / `kafka-cluster-tls` (`bench/runner.py`, alias `tls` = plain and TLS rows
of FluxMQ and Kafka): `KAFKA_TLS=on` adds a `TLS://:9095` listener (security protocol SSL)
to the Kafka services, serving the stack's `gen-dev` server certificate (the certs init
service now also issues SANs `kafka,kafka1..3` and writes `kafka-keystore.pem` = key +
chain, PEM key store, no client auth); the 3-node row also replicates over it
(`KAFKA_INTER_BROKER_LISTENER=TLS`, like FluxMQ's full-TLS cluster; the KRaft controller
listener stays plaintext). The harness gets `--kafka-tls-ca /certs/ca.pem`
(`security.protocol=ssl`, `ssl.ca.location`, hostname verification on). Default flush
policy, compared with the `fluxmq-*-tls` rows as "TLS cost within each system". The
listener is named `TLS`, not `SSL`, so the apache/kafka image's configure script does not
switch to its JKS/credential-file mode; whether the image accepts the PEM settings as
plain `KAFKA_SSL_*` properties is **untested** (no Docker). Certificates are generated at
runtime into the `certs` volume; nothing is committed.

  Baseline to beat (published v0.8): 1 KiB 1×1 −56 %, 100 B 1×1 +4 %, 3 nodes 1 KiB 4×4
  −16 %.
* If consumers still lag under TLS after this change, the next lever is the receive copy
  (decrypting into the caller's buffer needs one `recv` per record so records land
  contiguously) and consumer-side scheduling in the SDK; kTLS (no userspace copies at all)
  remains unavailable on the bench kernel (`CONFIG_TLS` off).

## 7. Results — Docker A/B (2026-10-10)

Bench VM (Docker Desktop, 2 broker CPUs, harness 4 CPUs), images `fluxmq:v08p1` (95107b0,
tokio-rustls, AES-256 first) vs the working tree (fast record layer, AES-128 first). Consumed
msg/s, median of 2; TLS overhead is against plaintext of the same image.

| Config | v08p1 TLS (overhead) | fast TLS (overhead) |
|---|---|---|
| 1 node, 1 KiB 1×1 | 199k (−63 %) | **438k (−17 %)** |
| 1 node, 1 KiB 4×4 | 513k (−14 %) | **541k (−7 %)** |
| 1 node, 100 B 1×1 | 758k (−1 %) | 749k (−1 %) |
| 1 node, 100 B 4×4 | 638k (−22 %) | **702k (−10 %)** |
| 3 nodes, 1 KiB 4×4 | 238k (−16 %) | **267k (−3 %)** |

Plaintext rows are unchanged between the images (no regression).

Kafka with TLS, same host (harness rdkafka with OpenSSL): 1 node 1 KiB 1×1 291k msg/s (plaintext
480k, −39 %), 4×4 197k consumed (plaintext 624k, −68 %, consumers lag). FluxMQ with TLS is
1.5× / 2.7× Kafka with TLS at 1 KiB 1×1 / 4×4.

Latency (3 nodes, TLS on clients and replication): early runs showed 0.3–1.3 s p99 outliers on
the fast path. A dedicated investigation (16 same-image runs crossing broker/harness
implementations, cgroup CPU sampling, an in-process 3-node TLS cluster on Linux) found the
outliers in every combination — classic, the baseline image and Kafka too (Kafka cluster TLS
max 350 ms) — and tied them to virtual-disk fsync stalls plus the 100 ms fetch long-poll, not
to the record layer. On Linux, group commit: fast p99/max 8–12 / 36–52 ms vs classic 11–14 /
194–200 ms. Interleaved Docker reruns, median p99: 1k msg/s fast 9.7 / classic 8.0 / baseline
6.7 ms; 10k msg/s 27.3 / 21.6 / 53.7 ms — inseparable at this noise level. Regression test for
the "sealed but not sent / missed waker" class: `lock_step_request_response_never_stalls`.

Decision: fast is the default in v0.8.0; `FLUXMQ_TLS_IMPL=classic` stays as a fallback for one
release. Target "≤ 15 % at 1 KiB" is met at 4×4 and on 3 nodes and missed by 2 points at 1 KiB 1×1.

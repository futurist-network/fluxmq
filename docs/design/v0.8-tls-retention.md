# v0.8 — TLS cost and retention at saturation

Status: implemented in the working tree (not committed). Owner areas: `crates/fluxmq-tls`, the TLS
acceptor/connector wiring (client port, SDK connector, cluster/replication connector), paced
retention in `crates/fluxmq-core/src/broker.rs`.

## 1. Retention at saturation

### Problem (v0.7)

The background pass ran once a second and removed at most `min(16, 1 + due/8)` segments per
channel. With 16 MiB segments that is ≤ 256 MB/s per channel; at 500–830 MB/s ingest the
partitions grew past their byte budget without bound for as long as the ingest lasted.

### Design

* **Pass interval 50 ms** (`RETENTION_TICK`, was 1 s). A pass with nothing due only counts
  segments under read locks; channels without any limit (no age, no size, not a queue with
  groups) are skipped before any lock beyond the config read.
* **A pass removes every due segment** (was ≤ 16 per channel), one at a time, always from the
  partition (of any channel) with the most due, re-evaluating the predicate against the
  partition as it is at that moment.
* **Spread in time, not capped in count** (the v0.5 lesson: back-to-back deletion of large
  segments stalled group-commit fsyncs 0.5–1 s). Between two removals the pass sleeps
  `RETENTION_TICK / due`, at least `RETENTION_MIN_GAP` = 5 ms; each unreferenced segment is
  still truncated in 16 MiB steps with 2 ms pauses before the unlink. So deletions follow the
  ingest rate evenly instead of arriving in bursts, and the deletion rate is capped at
  ~200 segments/s (3 GiB/s at 16 MiB segments — far above any ingest we sustain).
* A pass stops after 1 s (`RETENTION_PASS_BUDGET`); the next one starts a tick later with fresh
  counts.
* Unchanged: Kafka's rule (a segment goes for size only if the remainder still covers the
  budget), age and queue-consumed rules, pins (backup cuts), never the active segment, the
  unpaced `Broker::enforce_retention`, and the at-least-once handling of lagging groups
  (`fluxmq_group_retention_skipped_messages_total`; `tests/retention_overtake.rs` passes).

### Bound

A segment is removed within about two ticks (≈ 100 ms) of becoming due. Per partition the size
is therefore below `budget + 1 segment` (Kafka's rule; the active segment counts toward the
total) plus the segments rolled since the last pass — at most one at up to ~10 rolls/s per
partition (160 MB/s per partition at 16 MiB segments). Overshoot bound: **≤ 2 segments per
partition**.

### Tests

* `storage_pipeline.rs::paced_retention_keeps_up_with_sustained_ingest` (new): 16 partitions,
  32 KiB segments, budget 4 segments per partition, producers paced at 32 segment rolls/s on
  one channel (2× v0.7's fixed pace) for 6 s while sampling every partition's size every 5 ms;
  asserts every sample ≤ budget + 2 segments and convergence below budget + 1 segment after
  ingest stops. On the v0.7 code the same test fails (partitions reach ~11 segments over).
* `storage_pipeline.rs::paced_retention_spreads_deletions` (updated): a pass removes everything
  due, but never back to back (≥ 5 ms apart); repeated passes reach the unpaced end state.
* `retention_overtake.rs`, `retention_loss.rs`, `persistence.rs` and the rest of `fluxmq-core`
  pass unchanged.

### Docker check (1 node, 1 KiB 1×1 saturation, 16 MiB segments, cap 64 MiB × 8 partitions = 512 MiB)

Data directory size (`du`, sampled ~every 1.5 s during the run):

| build | ingest | max data dir | over the cap | after the run |
|---|---|---|---|---|
| v0.7 (`fluxmq:v07-base`) | 531 MB/s | **4 666 MiB** | +4 154 MiB (≈ 32 segments / partition) | drains at ~16 segments/s, settles at 577 MiB ~45 s after ingest stops |
| v0.8 (`fluxmq:v08-tls`) | 585 MB/s | **628 MiB** | +116 MiB (≈ 0.9 segment / partition) | 578 MiB |

## 2. TLS cost

> Superseded by [v0.8-tls.md](v0.8-tls.md) (in-place record layer, independent halves,
> AES-128 preference). The analysis below is the first pass that led to it.

**Outcome (first pass): target not met; no TLS code change shipped.** Every transport/config lever I could
pull at the stream layer measured between −7 % and +15 % CPU per GB in the Linux VM, so I left
the TLS path unchanged rather than ship noise or a regression. Below are the root cause, the
measurements and what would actually close the gap.

### Where the cost goes

`perf` on the broker and harness (Docker, 1 node, TLS, 1 KiB 1×1, `fluxmq:prof` image):

* Broker: TLS takes ~27 % of samples. AES-GCM encrypt 9.2 % and decrypt 3.3 %, rustls
  `OutboundChunks::copy_to_vec` (plaintext copied into each outgoing record) 8.2 %,
  `take_received_plaintext` (each decrypted record copied into a new `Vec`) 3.0 %,
  `TlsStream::poll_read` copying that `Vec` into the `FramedRead` buffer 3.3 %, plus 4 KiB `recv`
  calls.
* Harness consumer `reader_task`: `take_received_plaintext` 11 % (9.6 % memcpy), the
  `poll_read` copy 9.5 %, decrypt 8.9 %, `recv` 8.2 %.

Micro-benchmark (`tokio-rustls` over loopback TCP, 1 MiB frames one way with acks back, same
crate versions; 2-CPU Linux container on the bench host vs native macOS on the same M1):

| | plain | TLS (rustls 0.23.45, aws-lc-rs, TLS 1.3 AES-256-GCM) |
|---|---|---|
| macOS native, CPU ms per GB (both ends) | 290–340 | 650–810 |
| Linux container, CPU ms per GB | 194–243 | 1 227–1 459 |

`perf` of the Linux run: glibc `memcpy` 33 % (rustls `copy_to_vec` 10.6 %, the `poll_read` copy
10.2 %, `take_received_plaintext` 8.6 %), AES-GCM 33.5 % (enc 16.7, dec 16.9), kernel copies
7.6 %. In this VM each userspace copy of a byte costs about 60 % of encrypting it.

**Root cause.** The rustls buffered API (which `tokio-rustls` wraps) copies every byte twice
on receive (decrypted record → `received_plaintext` `Vec` → caller) and once on send
(plaintext → a freshly allocated record `Vec`). rustls 0.23's unbuffered API still pops
`received_plaintext` `Vec`s ("TODO … in-place decryption"), so switching APIs does not remove
the receive copies. In v0.7 the plaintext path itself got cheaper and in the v0.8 working tree
(zero-copy outbound frames, by the hot-path work) much cheaper, so the TLS share grows: the
fixed per-byte TLS cost (~1 ms per MB per direction in this VM) lands on the 2-CPU broker,
which spends it mostly decrypting ~0.5 GB/s of publishes; producers (deep pipelines) win the
CPU and the consumers (prefetch-window bound) lose it. That is why *consumed* drops so much
more than *published*. The flush-per-frame / small-record / buffer-size hypotheses do not hold:
frames are written as whole 16 KiB records, 64 KiB per `writev`.

### Experiments (all rejected)

| change | Linux micro (CPU per GB vs stock TLS) | verdict |
|---|---|---|
| `ReadBuffered`: 64 KiB read-ahead under rustls (one `recv` instead of 4 KiB ones) | **+14 %** (1 434 vs 1 258; 1 452 vs 1 270) — the extra ciphertext copy costs more than the saved syscalls | rejected (also in the `v08-tls` Docker image below) |
| Custom split: socket I/O outside the session lock (replacing `tokio::io::split`'s mutex) | +14 % to +87 % (extra ciphertext copy into the write buffer; worst with frequent acks) | rejected |
| `set_buffer_limit(256 KiB)` (fewer, larger `writev`) | −4 % (noise level) | not shipped |
| `set_buffer_limit(1 MiB)` | +12 % | rejected |
| Prefer TLS 1.3 AES-128-GCM over AES-256-GCM | −7 % | not shipped: would change the negotiated cipher (policy) for a small gain |
| rustls crypto provider ring vs aws-lc-rs | not pursued: aws-lc-rs already runs the ARMv8 AES-GCM kernels (`aes_gcm_enc_kernel`); the binary must keep one crypto stack | — |

Code of the two rejected stream wrappers is kept out of the tree.

### Docker A/B (1 node, saturation, 2 repeats, cap 256 MiB/partition; consumed msg/s, median)

The candidate image `fluxmq:v08-tls` was built from the working tree (includes the other v0.8
agents' in-progress changes and the rejected `ReadBuffered`), so the meaningful number is the
TLS overhead *within* each image. The host was heavily loaded by parallel work during these
runs (e.g. v0.7 plain 100 B 4×4 measured 180k vs 620k in the published set), so treat absolute
numbers as indicative only.

| config | v0.7 plain | v0.7 TLS | v0.8-wt plain | v0.8-wt TLS | TLS overhead v0.8-wt |
|---|---|---|---|---|---|
| 1 KiB 1×1 | 243k | 49k (1 run) | 519k | 223k | −57 % |
| 1 KiB 4×4 | 251k | 34k | 455k | 159k | −65 % |
| 100 B 1×1 | 541k | 390k | 778k | 610k | −22 % |
| 100 B 4×4 | 180k | 107k | 190k | 173k | −9 % |

### What would reach ≤ 15 %

1. **kTLS on Linux** (rustls `kernel` API: extract the traffic secrets after the handshake,
   `setsockopt(TCP_ULP, "tls")`; the kernel decrypts straight into the read buffer and
   encrypts the `writev`/`sendfile` source, no userspace copies; zero-copy sends stay
   possible). Same ciphers and certificates, same handshake (rustls), so the security policy
   is unchanged; needs handling of post-handshake messages (NewSessionTicket, KeyUpdate)
   through `KernelConnection` and a fallback when the module is missing. **The Docker Desktop
   kernel of the bench host has `CONFIG_TLS` disabled**, so it cannot be measured there; most
   production distribution kernels ship the `tls` module.
2. Without kTLS: an in-place record layer on rustls' `kernel` API (decrypt in our read buffer,
   one copy to the caller; encrypt into a reused buffer). Estimated −20 % TLS CPU at most;
   security-sensitive (nonces, sequence numbers, KeyUpdate, confidentiality limits) for a
   modest gain — not attempted.
3. Consumer-side flow: the TLS loss lands on consumers because the broker gives the CPU to
   producers; consumer-paced admission (v0.7 item 9) would turn part of the producer surplus
   into consumption.

## 3. Results — final (set `bench/results/20261010-v0.8`)

HEAD `95107b0`, same laptop, 34–43 GB free disk, cap 512 MiB × 8 partitions = 4 GiB per broker, 16 MiB segments. The
data directory was sampled with `du` every ~2 s during every saturation, overload and catch-up run
(`samples-summary.json` in the set).

**Retention: met.** 21 of 21 FluxMQ saturation and overload runs stayed within cap + 2 segments per partition
(bound 4,352 MiB). The peak was 4,232 MiB, with up to 32 GiB written in one run (1-node 1 KiB overload) and 14 GiB per
node on 3 nodes. Kafka, at its own retention pace, reached 9.3 GiB (1 node, 1 KiB 1×1). 0 true missing messages: every
id not delivered was a counted retention skip.

**TLS: not met** (no TLS code change, as described above):

| | v0.7 set: TLS vs plain | v0.8: TLS vs plain |
|---|---:|---:|
| 1 node, 1 KiB 1×1 | 122k vs 231k (−47 %) | 214k vs 489k (**−56 %**) |
| 1 node, 100 B 1×1 | 360k vs 427k (−16 %) | 730k vs 702k (**+4 %**) |
| 3 nodes, 1 KiB 4×4 | 111k vs 207k (−47 %) | 228k vs 273k (**−16 %**) |

TLS is faster in absolute terms everywhere (+76 % to +106 %). Its relative cost grew on one node at 1 KiB because the
plaintext path got 2× cheaper. Broker CPU with TLS was 1.75 cores (of 2) at 214k, and 0.85 cores plaintext at 511k. The
1-node TLS run publishes 421k but consumes only 214k: the CPU goes to the producers. The fix remains kTLS (§2) plus
consumer-paced admission.

# FluxMQ v0.3 design — notifications, HTTP push webhooks, backups

Contracts live in `fluxmq-proto::{notify, webhooks, backup}` — read their module docs first; they
define semantics, payloads, signatures and REST bodies. This file covers placement, routes and
ownership.

## 1. Notifications — new crate `fluxmq-notify`

* Input: telemetry alert transitions + broker events. Add to `fluxmq-telemetry` a public
  `TelemetryHub::notifications() -> broadcast::Receiver<TelemetrySignal>` where
  `TelemetrySignal = AlertOpened(Alert) | AlertResolved(Alert) | Event(Event)` emitted by the
  existing alert engine / events feed (additive; one computation, any number of listeners).
* `NotifyService::start(meta, telemetry, cluster, config)`: loads notifiers/rules from meta
  (`notify/notifiers/<id>`, `notify/rules/<id>`, watch for changes), dispatches only when this node
  is the controller (single node: always; re-check on `cluster.watch_epoch()`), grouping window,
  repeat interval, resolved messages, retries with backoff, history ring (1000).
* Senders: Telegram (Bot API, HTML), Slack (Block Kit), Discord (embeds), Email (SMTP via
  `lettre`, rustls), PagerDuty Events v2 (trigger/resolve, dedup_key = alert id), generic
  webhook (HMAC-SHA256 signature). HTTP via `reqwest` with **rustls** (`rustls-tls` feature).
  Messages are concise, emoji-light, include severity, title, detail, possible reason, channel/
  group, and a console link when `--public-url` is set.
* REST (`fluxmq-api/src/routes/notify.rs`):
  `GET/POST /api/notify/notifiers`, `GET/PATCH/DELETE /api/notify/notifiers/{id}`,
  `POST /api/notify/notifiers/{id}/test`, `GET/POST /api/notify/rules`,
  `GET/PATCH/DELETE /api/notify/rules/{id}`, `GET /api/notify/history`.
  Permissions: GET = Read (secrets redacted), mutations + test = Admin.
* Server flag: `--public-url` (`FLUXMQ_PUBLIC_URL`) for console links.

## 2. HTTP push webhooks — new crate `fluxmq-webhooks`

* Pattern = the router (`fluxmq-router`): meta-stored definitions (`webhooks/<id>`), hot reload,
  per-subscription worker = consumer group `$webhook:<name>` on the channel; in a cluster only
  partitions led locally are served (the subscription already scopes this); filter reuses
  `fluxmq_router::filter::matches_in`.
* Delivery per the contract (status mapping, Retry-After, signature, batching, in-flight limit,
  raw/envelope formats), latency histogram + counters for stats, graceful shutdown (finish or
  nack in-flight). Delete subscription → stop worker → delete group (`Broker::delete_group` /
  cluster group fan-out, like `$router`).
* SSRF guard: reject URLs resolving to loopback/link-local/private ranges unless
  `--webhooks-allow-private` (default off in enforced-auth mode, on in open/dev mode).
* REST (`routes/webhooks.rs`): `GET/POST /api/webhooks`, `GET/PATCH/DELETE /api/webhooks/{id}`,
  `POST /api/webhooks/{id}/test`, `GET /api/webhooks/stats`. GET = Read, mutations/test = Admin.

## 3. Backups — new crate `fluxmq-backup`

* Storage via the `object_store` crate (S3 incl. custom endpoint/path-style for MinIO/R2/B2,
  local filesystem; in-memory for tests).
* Core support needed (additive, `fluxmq-core`): a consistent **backup cut** per partition —
  list sealed segment files + active segment path and committed length, captured atomically;
  group offsets and DLQ export; and an offline **restore writer** (lay down segments/offsets/DLQ
  into an empty data dir, then `Broker::open` recovers normally).
* `BackupService`: config in meta `backup/config`, scheduler (controller-only in a cluster),
  manual run, incremental upload (skip objects already present by name+crc), manifest,
  retention + GC, optional AES-256-GCM encryption, progress in `BackupOverview`, history from
  manifests.
* CLI subcommands in the `fluxmq` binary: `fluxmq backup list --target …`,
  `fluxmq restore --target … --backup <id|latest> --data-dir <empty>` (target via flags/env:
  `--s3-endpoint --s3-region --s3-bucket --s3-prefix --s3-path-style`, credentials from
  `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, or `--fs-path`).
* REST (`routes/backups.rs`): `GET/PUT /api/backups/config`, `GET /api/backups/status`,
  `POST /api/backups/run`, `GET /api/backups`, `GET /api/backups/{id}`,
  `DELETE /api/backups/{id}`. GET = Read (secrets redacted), others = Admin.
* Cluster v0.3: each partition is uploaded by its leader through `/internal/v1/backup/*`; the
  controller coordinates and writes the manifest. Restore → single node.

## 4. UI

Settings → **Notifications** (notifiers with per-type forms + Send test, rules with matcher
builder, delivery history), sidebar **Webhooks** (list with stats, editor with filter builder
reused from routing, Send test, links to the `$webhook:*` group / DLQ), Settings → **Backups**
(target form with Test connection, schedule/retention/encryption, Run now with progress, history
table, restore instructions with the exact CLI command). Role-aware (admin for mutations).

Shared files: small, additive, localized edits; re-read immediately before editing. proto is
architect-owned (additive changes if essential, report them). Single-node v0.2 behaviour must not
change when nothing is configured.

## 6. Contract clarifications (round 2, before implementation)

* Uniform secret rule everywhere (notifiers, webhooks, backup target): reads return `REDACTED`;
  updates: `REDACTED` keeps, `""` removes, other values replace. Every custom header value is a
  secret. The generic webhook notifier `url` is not.
* PagerDuty tag is `"pagerduty"`.
* Test-before-save: `POST /api/notify/notifiers/test` (CreateNotifierRequest body),
  `POST /api/webhooks/test` (CreateWebhookRequest body), `POST /api/backups/test-target`
  (BackupTarget body) — all Admin, no persistence.
* Pull feed for external systems (owner: notifications engineer): system channel
  `$system.events` + `GET /api/events/feed?after=&limit=&wait_ms=` (long-poll), contract in
  `fluxmq_proto::notify::{FeedItem, FeedPage, SYSTEM_EVENTS_CHANNEL}`. In a cluster only the
  controller appends (exactly one copy per signal); the channel is replicated like any other.
  System channels (`$…`) are read-only in the console and can't be deleted via API.
* Webhooks: validation ranges/name rules in the module docs; 3xx = non-retryable; immutable
  `name`/`channel`/`start`; stats summed cluster-wide; Retry-After implemented by holding the
  delivery for `min(Retry-After, max backoff) − next backoff` before the nack (core has no
  per-nack delay), capped below `ack_timeout_ms`.
* Backups: `GET /api/backups/config` → `null` when unset; `BackupInfo.progress_bytes`;
  restore takes `--encryption-key` / `FLUXMQ_BACKUP_ENCRYPTION_KEY`; the meta snapshot excludes
  `backup/*` (secrets) and restore drops `cluster/*` keys.
* HTTP client: `reqwest` 0.13, `default-features = false`, `features = ["rustls", "json"]`
  everywhere (one TLS stack). New dependencies must be fetched from crates.io (network is
  available).

## 7. Integration decisions (v0.3.0)

* `GET /api/backups/{id}` returns `fluxmq_proto::backup::BackupManifest` (info, encryption
  fingerprint, nodes, per-channel summary); the stored manifest format is unchanged (new fields
  `groups`, `dlq_entries`, `nodes` are `serde(default)`).
* Feed: `tail=N` (1–1000, exclusive with `after`); responses always carry real cursors; stored
  payloads keep `cursor: ""` (SDK consumers use the message offset).
* `ApiError.error = "unsupported_in_cluster"` (`fluxmq_proto::api::ERROR_UNSUPPORTED_IN_CLUSTER`)
  for cluster-refused operations — now: backups when a node is older than 0.3.0.
* `POST /api/notify/notifiers/{id}/test` and `POST /api/webhooks/{id}/test` accept an optional
  update-request draft (empty body = stored item), merged with the update secret rule, never
  persisted.
* Short errors (`fluxmq_proto::api::short_error`) + additive `error_detail` /
  `last_error_detail`; webhook `last_status` = status of the last attempt (`null` when it got no
  response).
* Webhooks: SSRF block at delivery time → dead-letter at once, reason `blocked by policy`.
* Notifications history in a cluster: proxied to the controller (`/internal/v1/notify/history`).
* Cluster backups implemented (`fluxmq_backup::cluster`, `/internal/v1/backup/{partial,run,status}`).
* Graceful leave: drain retries CAS conflicts; the leaving node waits for local demotion before
  it stops replicating (root cause of the "publishes stalled 5.1 s" flake: a skipped or
  not-yet-demoted partition accepted forwarded publishes it could never ack — senders hung for
  the 5 s internal forward timeout).

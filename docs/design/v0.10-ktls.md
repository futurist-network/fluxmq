# v0.10 — kernel TLS (kTLS) on Linux

Scope: `fluxmq-tls` (`fast/ktls.rs`, `fast/handshake.rs`, `fast/io.rs`, `fast/record.rs`, `stream.rs`). The client
listener, the SDK connector and replication use it through `stream::{accept, connect}` unchanged. Goal from v0.8
§"not done": TLS costs ≤ 15 % of plaintext throughput at 1 KiB (v0.8: −56 % on one node), and a TLS socket that can
carry `sendfile` later.

**Status.** Implemented and tested against the live kernel (WSL2 6.18, `tls` module loaded). Results: §5.

## 1. Why the v0.8 record layer is not enough

v0.8 removed rustls' extra copies and the shared lock, but every byte still crosses userspace twice per direction:
the AEAD seals into a record buffer, and `writev` copies the record into the socket (receive: `recv` copies
ciphertext out, the AEAD opens it in place, the caller gets one more copy). With kTLS the kernel encrypts while it
copies from the caller's buffer into the socket (and decrypts while it copies out), so each direction makes one pass
over the data, and the bytes the broker serves never need to be in userspace at all (the future `sendfile` path).

## 2. Design

**Hand-over.** The handshake is unchanged (rustls' unbuffered API, `docs/design/v0.8-tls.md` §2). After it, a TLS 1.3
session on a real `TcpStream` (the `RawTcp` trait: `OwnedReadHalf` / `OwnedWriteHalf` expose their socket, test pipes
do not) goes through these steps:

1. Copy the key material of both directions out of rustls' `ExtractedSecrets` (`KeyMaterial`, wiped on drop).
2. **Receive boundary.** The kernel must start at a record boundary, but the bytes read during the handshake may
   already hold application records, and the last one may be incomplete. They are opened in userspace with the v0.8
   `RecordReader`. Their plaintext goes to the front of the read half, and the missing tail of an incomplete record is
   read exactly (`read_exact` of the bytes the header announces). If one of them was a KeyUpdate (the receive key
   changed and rustls only holds the newest one inside its decrypter) or a close_notify, the connection stays on the
   userspace layer.
3. `setsockopt(TCP_ULP, "tls")`, `TLS_TX` (send key, rustls' send sequence), `TLS_RX` (receive key, the sequence after
   step 2), `TLS_RX_EXPECT_NO_PAD` (a hint; FluxMQ peers never pad).
   - **ULP or `TLS_TX` refused:** the socket is still plain TCP, the connection continues on the v0.8 record layer.
     `ENOENT` / `ENOPROTOOPT` / `EOPNOTSUPP` (no module, no `CONFIG_TLS`) also turn kTLS off for the process.
   - **`TLS_RX` refused after `TLS_TX`:** the send direction already belongs to the kernel, so the connection fails.
     It is logged as a warning; not seen in practice.
   - A cipher the kernel lacks fails at `TLS_TX` and falls back. Example: WSL's kernel has no
     `CONFIG_CRYPTO_CHACHA20POLY1305`. AES-GCM is in every kTLS kernel, and FluxMQ prefers AES-128-GCM (v0.8).
4. A server hands over at send sequence 2 (after its NewSessionTickets). The kernel takes any starting sequence, so
   the v0.8 "KeyUpdate before the first record" (an aws-lc nonce rule) is not needed here.

**Read half** (`KtlsRead`). `recvmsg` with room for a `TLS_GET_RECORD_TYPE` control message:

- With ≥ 16 KiB of room, the kernel decrypts straight into the caller's buffer. Smaller reads go through a 16 KiB
  stash, so one record always fits.
- Application data is returned as is. EOF (0 bytes) without close_notify is `UnexpectedEof`, as in v0.8.
- Other records (alerts, KeyUpdate, NewSessionTicket) go through `record::Control`. These are the same rules the
  userspace layer applies, extracted from `RecordReader`: alert levels and limits, no interleaving, KeyUpdate at a
  record end, at most 32 between data records, client-only tickets.
- A KeyUpdate from the peer gives the kernel the next receive key (`update_rx_secret`, `TLS_RX` again; Linux 6.14+
  re-keys, older kernels refuse and the connection fails). Until then the kernel holds further records back
  (`EKEYEXPIRED`).
- Kernel errors `EBADMSG` (authentication), `EMSGSIZE`, `EINVAL`, `EIO` map to `InvalidData` and mark the connection
  failed, so the write half refuses further writes, as in v0.8.

**Write half** (`KtlsWrite`). `writev` of plaintext (the server's zero-copy `FrameWriter` iovecs go straight to the
kernel). Records are counted conservatively: a call of `n` bytes ends at most `n / 2^14 + 1` records.

- Before the count can reach the suite's confidentiality limit, a KeyUpdate goes out as a handshake record
  (`sendmsg` + `TLS_SET_RECORD_TYPE`). The next send key then goes to the kernel (`update_tx_secret`, `TLS_TX`).
- A single call is capped so it cannot cross the limit (found by the limit-5 test: one 600 KB `writev` sealed 37
  records under one key).
- A KeyUpdate the peer requested is answered the same way.
- `shutdown` sends close_notify as an alert record, then `SHUT_WR`.

**Selection.** `FLUXMQ_TLS_IMPL`:

| value | meaning |
|---|---|
| `fast` | default (alias `userspace`). The v0.8/v0.9 userspace record layer |
| `ktls` | opt-in (alias `kernel`). kTLS when the kernel takes the keys, else the same as `fast` |
| `classic` | tokio-rustls |

Until the A/B (§5) `fast` meant kTLS and the userspace layer was `userspace`. kTLS lost the A/B, so the default is
the v0.8/v0.9 layer again and kTLS is opt-in. Bench systems `fluxmq-{single,cluster}-tls-ktls` (alias `ktls`) run
kTLS for A/B.
`SessionInfo::kernel_tls`, `TlsReadHalf::is_kernel_tls` and `TlsWriteHalf::is_kernel_tls` report which path a
connection took.

## 3. Security analysis

Unchanged from v0.8: the handshake, certificate and CRL checks, the key schedule, every KeyUpdate secret and session
tickets stay in rustls. The AEAD and nonces move from aws-lc to the kernel's crypto API (AES-GCM via AES-NI here).

What the kernel enforces itself:

- per-direction sequence numbers;
- the TLS 1.3 record header;
- the maximum record size;
- the inner content type and padding;
- authentication: a forged record is `EBADMSG` and nothing of it is returned.

What FluxMQ code still owns:

- **Starting sequence numbers.** Taken from rustls.
- **The confidentiality limit.** An upper-bound record count and a per-call cap. Undercounting is impossible: every
  record holds ≥ 1 byte of one call, and a call adds at most one partial record at its start.
- **Post-handshake records.** The shared `Control` rules (§2).

Key material is copied once into a struct that is wiped on drop, and into a `setsockopt` argument that is wiped after
the call.

Behaviour differences from v0.8:

- A fatal record error closes the connection without sending a fatal alert. v0.8 did the same.
- After a peer's KeyUpdate the kernel delays further records until the new key is installed. That happens in the
  same `poll_read`.

## 4. Tests

- **Existing TLS suite** (`crates/fluxmq-tls/src/fast/tests.rs`): it runs over TCP with `ktls` and over pipes
  (userspace). `roundtrip_all_impl_pairs_tcp` adds `fast` to every pairing (8 pairs).
  `key_update_requested_mid_stream` runs against kTLS on both roles.
- **New:**
  - `ktls_every_suite_every_peer`: 3 TLS 1.3 suites × 8 implementation pairs over TCP. AES suites must be on kTLS,
    ChaCha20 may fall back.
  - `ktls_key_updates_at_confidentiality_limit`: limit 5, 1 MiB each way. ≥ 10 kernel send re-keys; the peer's
    re-keys are applied by the kernel. Fast, classic and userspace peers.
  - `ktls_tampering_is_detected`: one bit flipped by a TCP relay. `InvalidData`, only authentic bytes, writes refused
    afterwards.
  - `ktls_truncation_and_clean_close`: EOF at a record boundary and mid-record is an error; close_notify from fast and
    classic peers is a clean EOF; a write after shutdown is refused.
  - `ktls_handover_with_buffered_records_and_small_reads`: a classic client writes 1 B to 300 KB right behind its
    Finished. The server opens the buffered records in userspace, completes the partial one, hands over, and reads
    in 777-byte calls (stash path), then echoes back.
- The kTLS tests detect a host without kTLS and print `skipping` instead of failing (macOS, or no module).
- **Integration:** `fluxmq-server` `tls`, `revocation`, `cluster_tls`, `v4_e2e`, plus `fluxmq-client` and
  `fluxmq-replication`, run over the default `fast` layer; the release check also runs them with
  `FLUXMQ_TLS_IMPL=ktls`.
- **Passing:**
  - `cargo fmt --all` and `cargo clippy --workspace --all-targets -- -D warnings`.
  - `cargo test --workspace`: 688 tests in 91 binaries, with the `tls` module loaded.
  - `fluxmq-tls` alone also passes without the module (fallback path).

## 5. Results

Docker A/B, 2026-10-12, `bench/results/20261012-v0.10-ktls` (`ab/`: `bench/runner.py --systems ktls --retention-mb 512
--bench-cpus 4`, same image, kernel TLS vs the userspace layer, broker and harness alike; at the time `fluxmq-*-tls` was kernel TLS
and `fluxmq-*-tls-user` the userspace layer, the labels in that result set). Host:
WSL2 kernel 6.18, 4 vCPUs, Docker Desktop; the kernel's `gcm(aes)` is `generic-gcm-aesni-avx` (no VAES), while aws-lc in
userspace uses VAES + VPCLMULQDQ on this CPU. 0 failures, every run drained, no acknowledged message missing.

| FluxMQ 1 node, TLS | kernel TLS | userspace | |
|---|---|---|---|
| saturation 1 KiB 4x4, msg/s (3 repeats) | 151k / 162k / 151k | 152k / 154k / 154k | equal |
| saturation 100 B 4x4, msg/s | 958k | 1 121k | −15 % (1 run) |
| catch-up 1 KiB, consume msg/s (4 runs) | 693k / 670k / 664k / 661k | 834k / 912k / 844k / 831k | **−20…−27 %** |
| catch-up 100 B, consume msg/s | 3.87 M | 4.28 M | −10 % (1 run) |
| latency 1k / 10k / 50k msg/s, p99 ms | 5.7 / 19.8 / 45 | 6.0 / 19.9 / 56 | equal |

3 nodes RF=3, full TLS: saturation and latency equal within noise; catch-up 1 KiB 645k vs 775k (−17 %).

Conclusion: on this host kernel TLS does not pay off. Bulk transfer (catch-up) is consistently slower, because the
kernel's AES-GCM is slower than aws-lc here and the copy saved is cheaper than that difference; the other rows are
equal. Kernel TLS can only win where the kernel's AES-GCM is as fast as aws-lc (or with NIC offload) or once
`sendfile` from the page cache removes the copy into userspace. **Decision:** the default is the userspace layer
(`fast`), kTLS is opt-in (`FLUXMQ_TLS_IMPL=ktls`); the code and tests stay. The TLS cost goal (≤ 15 % at 1 KiB on
one node) is still not met: 1 KiB 4x4 saturation 198k without TLS vs 152–162k with TLS on either path (−18…−23 %).

## 6. Operations

- The host kernel needs the `tls` module (`modprobe tls`; persistent: `echo tls > /etc/modules-load.d/tls.conf`).
  Containers use the host kernel, so Docker needs it on the host (on WSL2: in the WSL VM).
- Without the module, or without `FLUXMQ_TLS_IMPL=ktls`, everything works as in v0.9. With `ktls` and no module one
  `info` log line says kTLS is unavailable.

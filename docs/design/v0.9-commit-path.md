# v0.9 — leader commit path: per-partition completion and a per-partition pipeline

Scope: `fluxmq-core` (`channel.rs` writer, `fsync_pool.rs`, `storage/log.rs`), shared by single-node mode, the
replicated leader and followers. Goal: cut the leader's local publish → durable time, which v0.8 §5 item 2 found to be
the dominant share of the 3-node p99 at 50k msg/s (84–203 ms against a goal of ≤ 20 ms). Durability does not change. A
publish is acked only after its data is fsynced on the leader and on every ISR member.

**Status.** Both mechanisms shipped, default on with depth 1 (§2.4). On this Mac (native APFS, `F_FULLFSYNC`) the
uniform 8-partition latency is unchanged, because the local commit already sits at the floor of a serial barrier
device (§4.1) and v0.9 matches v0.8 there. When one partition's fsyncs are slow, the other partitions' p50 / p99 drop from 43 / 67 ms to
12 / 21 ms (§4.2). Closed-loop throughput is within noise of v0.8 (§4.3). In Docker (§7) the 3-node 50k p99 stays set by the shared disk (no measurable gain; differences are within the host's noise), while 4×4 saturation gains 11–15 %.

## 1. Root cause

In v0.8 the writer thread blocks on each commit's fsyncs (`FLUXMQ_COMMIT_PIPELINE` off, the default). The pipelined
mode allows one batch in flight, and a commit is published as one unit:

- **The commit waits for its slowest partition.** On Linux each data file is its own `fdatasync` chain. With 8 dirty
  partitions and a 4-thread pool (2-CPU brokers), the chains run in two waves, so every publish waits for the second
  wave and for the slowest file.
- **The writer serializes commits.** A publish that arrives while commit k fsyncs waits for the rest of k, then for
  its own commit k+1: about 1.5 × the fsync time on average and 2 × at worst.
- **A partition waits for other partitions' fsyncs.** Even when its own fsync finished, partition p cannot start its
  next fsync until the whole commit is done.

## 2. Change

### 2.1 Per-partition completion (`fsync_pool.rs`)

- `chains_for_groups(Vec<Vec<SyncOp>>) -> Vec<Chain>` builds one group per partition. Each `Chain` lists the groups
  that depend on it.
  - **Linux:** one chain per op (data file, sealed index, directory), all in the op's own group.
  - **Apple:** the real ops of all groups share one chain that ends in a single `F_FULLFSYNC` barrier, as in v0.6 to
    v0.8. Nothing is durable before the barrier, so splitting the chain would not help. Injected test ops (`Fail`,
    `Delay`) are separate chains of their own group, so tests behave the same on both platforms.
- `FsyncPool::submit_groups` returns a `Ticket` that reports each group as soon as every chain it depends on finished:
  `take_ready`, `wait_ready`, `poll_ready`.
  - An error reaches every group that depends on the failed chain.
  - Timed durations are recorded once, on the chain's first group.
  - `FsyncPool::run_inline` runs the chains on the caller's thread.
  - `submit`, `wait` and `chains_for` keep their v0.8 meaning.

### 2.2 Per-partition pipeline (`channel.rs`, `WriterState`)

- **Marks.** Each partition has a FIFO `marks[p]` of `PendingMark`s: taken `CommitMark`s that are not yet published.
  A commit (`Commit`: sequence number, ticket, group → partition) takes a mark of every dirty partition with fewer than
  `depth` marks in flight.
- **No waiting on other partitions.** A partition whose previous batch is still fsyncing keeps accumulating. It is
  submitted as soon as that batch is published, whatever the other partitions are doing. The writer never blocks on an
  fsync, except at barriers (`Truncate`, `Purge`, `Release`, `Close`) and when the batch is full (8 MiB / 4096
  requests).
- **Publishing a mark.** When a group is reported, its mark is flagged `synced`. Partition p then publishes from the
  front of `marks[p]` while the front is synced. Publishing does four things:
  - `PartitionWriter::publish_mark`: records become visible, and the mark becomes the rollback point;
  - tail;
  - `PartitionReplica::on_leo(mark end)`: the replica durable end and the HW;
  - acks.
- **Acks by offset.** A request waits in `acks[p]` with the end offset of its records, or in `multi` with one
  `(partition, end)` per partition if it spans several. It is acked once each partition's published end reaches its
  end. A multi-partition request is acked only when all its partitions are durable.
- **Inline commits.** A commit runs inline on the writer thread when nothing is in flight, it has a single chain and
  there is nothing to overlap with. This keeps v0.6's fast path at low rates.
- **Serial barrier (Apple).** Every commit ends in one whole-device `F_FULLFSYNC`, and the device serializes them. A
  new commit may therefore start only once no in-flight commit's barrier chain is still running
  (`Ticket::barrier_running`). A single-chain commit runs inline whenever nothing is in flight, as
  in v0.8. Partitions still complete individually: an injected slow op is its own chain.
- **Depth > 1.** Marks of one partition overlap. Their starts are staggered by (average mark time ÷ depth), so slots
  free up evenly instead of `depth` tiny commits starting back to back.
- **Pipeline off (`FLUXMQ_COMMIT_PIPELINE=off`)** reproduces v0.8 exactly: the writer waits for every commit, and a
  commit is published only once all its partitions are durable. This is the A/B baseline.

### 2.3 Errors

Same as v0.6 to v0.8:

1. On any fsync error, the writer first waits until no fsync of any in-flight commit is running.
2. It then rolls back every partition with an unpublished mark, plus the current batch, to its last published mark.
3. It fails every request not yet acked.

Nothing is published once a failure has been seen, not even marks whose own fsync succeeded. A write error in the
current batch first lets in-flight commits finish (`drain`). Rollback poisoning (`unsynced_served`, failed `set_len`)
is unchanged.

What differs: a partition that became durable **before** the failure keeps its acked data, because it was acked
after its own fsync. A multi-partition request with one failed partition is failed, but its records in partitions that
had already published stay stored. This is the at-least-once outcome a client gets on any failed publish.

### 2.4 Knobs and metrics

| CLI / env | default | meaning |
|---|---|---|
| `--commit-pipeline` / `FLUXMQ_COMMIT_PIPELINE` | `on` (was `off`) | `off` = v0.8 behaviour |
| `--commit-pipeline-depth` / `FLUXMQ_COMMIT_PIPELINE_DEPTH` | `1` (range 1..=16) | marks of one partition in flight |

`BrokerConfig::{commit_pipeline, commit_pipeline_depth}`. `deploy/docker-compose.yml` passes both through.

- **New:** `fluxmq_node_commit_latency_seconds`, a histogram of mark submitted → published, per partition and commit
  (`BrokerStats::commit_latency_us`, local node, not in cluster snapshots).
- **Kept:**
  - `fluxmq_channel_publish_latency_seconds` is the local publish → durable time (writer queue + commit). It is
    recorded per request when its partitions are durable, so it now reflects per-partition completion.
  - `fluxmq_node_fsync_latency_seconds`.

**Why depth 1.** On this Mac, depth 2 / 3 raised the uniform 50k p50 from 9.1 to 12.8–14.8 ms (§4.1).

- **macOS:** `F_FULLFSYNC` flushes are serialized by the device, so a second barrier in flight only queues behind the
  first. It also adds flushes.
- **ext4:** a `fdatasync` of an appended file must commit the jbd2 transaction that holds its `i_size` update, and
  jbd2 commits one transaction at a time. Two overlapping fsyncs of the same file are therefore mostly serial there
  too.

Depth 1 already gives what matters: no cross-partition waiting and a non-blocking writer. It never adds fsyncs per
partition, and it needs no extra file descriptors (§3). Depth > 1 stays available for a device whose flushes really
run in parallel.

## 3. Correctness

1. **A durable mark never passes an fsync.**
   - A mark is published only after every chain of its partition's group succeeded. The group holds all of the
     partition's ops for that commit: the data file, plus the deferred index and directory syncs of a roll.
   - `roll` itself syncs the sealed file before the next segment exists.
   - So the published end never covers bytes, segments or directory entries that are not durable. On Apple, the
     shared barrier covers every earlier plain fsync of the commit.
2. **Marks are monotonic and in order per partition.** `marks[p]` is a FIFO in the order the marks were taken, and only
   its front is ever published. `publish_mark` therefore sees marks in order, which it requires. `on_leo` and `high`
   only grow. A later mark whose fsync finished first waits.
3. **Why waiting is required.** An fsync covers all data written to the file before the call, so a later fsync's
   success often implies an earlier one's data is durable. Publishing in order still matters for two reasons:
   - an earlier mark can carry other ops (a roll's directory entry, a sealed index) that the later fsync does not
     cover;
   - after a writeback error Linux reports the error once and marks the pages clean. A later fsync can then succeed
     although earlier data was lost ("fsyncgate").

   So an earlier failure must stop every later mark of the partition, and it does (rule 5).
4. **Error reporting with overlapping fsyncs (`errseq_t`).** Linux records writeback errors per inode and reports each
   one once per open file description.
   - If two fsyncs of the same description overlap, the later one can consume the error of a page the earlier one
     covers, and the earlier one returns success. Its mark would then be published although its data was lost.
   - Fix: commit fsyncs of one file never share a description while they can overlap.
     - **Depth 1:** a partition's next mark is submitted only after the previous one was published. Its commit fsyncs
       are therefore sequential on the writer's description.
     - **Depth > 1:** every commit fsync opens its own description (`open_sync`). A fresh description reports every
       error recorded after it was opened, and any error that nobody had seen yet when it was opened.
     - `roll`'s synchronous sync of the sealed file can overlap an in-flight commit, so it now always uses its own
       description. v0.6 to v0.8's pipelined mode shared `self.file` there.
   - After a rollback, `set_active` reopens the writer's description, so an error already reported is not reported
     again.
5. **No ack after a failed fsync.** A failed group aborts before anything else is published (§2.3). Every request whose
   data was unpublished is failed, and its bytes are truncated off. A rollback runs only after every in-flight fsync has
   finished, as before, so it never truncates under a running fsync.
6. **Crash.** Every acked request lies at or below a published mark, and every published mark was fsynced (rule 1).
   Recovery is unchanged: it truncates torn tails to whole entries.

## 4. Local numbers (this Mac, native APFS)

Benchmark: `crates/fluxmq-core/tests/commit_latency.rs` (ignored, release).

- Open loop, 50,000 msg/s as 5,000 requests/s of 10 × 1 KiB, round-robin over 8 partitions, 8 s after 1 s of warm-up.
- Latency runs from each request's *scheduled* send time to its ack, so there is no coordinated omission.
- "v0.8" is a release build of HEAD `a393ddc`. Runs were interleaved.

### 4.1 Uniform load, 8 partitions

Client publish → ack in ms; 4 interleaved pairs; median (range):

| build | p50 | p99 | p99.9 |
|---|---:|---:|---:|
| v0.8 (`a393ddc`, pipeline off = its default) | 9.24 (8.78–9.49) | 14.6 (14.0–27.2) | 18.3 (17.6–35.6) |
| **v0.9 default** (pipeline on, depth 1) | **9.10** (8.87–9.24) | **14.0** (14.0–14.6) | **17.9** (16.9–19.1) |
| v0.9, depth 2 / depth 3 (one run each) | 12.8 / 14.8 | 19.2 / 28.6 | 23.1 / 34.8 |

The broker-side publish → durable time (`publish_latency`) matches: p50 8.3–8.5 ms in both builds.

During development, two variants had to be fixed:
- Without the serial-barrier rule (§2.2), commits for different partitions overlapped their barriers. The p99 was then
  22–23 ms in 2 of 3 runs.
- Without the inline rule, the pool hand-offs cost +0.4 ms at p50.

The device floor: each commit is one `F_FULLFSYNC` of about 5.8 ms (fsync p99), and the device serializes them. A
request arriving during a flush waits for it and then for its own: about 1.5 × the flush time, which is what both
builds show. All partitions share the barrier, so they complete together and there is nothing for per-partition
completion to gain here. The result is no regression, and depth > 1 is worse.

### 4.2 One slow partition

`BENCH_SLOW_MS=20`: every fsync of partition 0 takes 20 ms longer (injected `Delay` op); otherwise the same load.

Client publish → ack in ms, 2 interleaved pairs, same binary (`FLUXMQ_COMMIT_PIPELINE=off` is the v0.8 behaviour):

| | other 7 partitions p50 / p99 | slow partition 0 p50 / p99 |
|---|---:|---:|
| pipeline off (v0.8 behaviour) | 43.8 / 68.5, 43.8 / 67.0 | 43.8 / 68.3, 43.8 / 66.9 |
| **v0.9 default** | **9.3 / 14.5, 9.1 / 13.8** | 39.3 / 58.9, 39.0 / 58.7 |

A re-run on the final code (barrier tracking via `Ticket::barrier_running`) gave the other partitions 9.2 / 16.0 ms.
In the uniform pairs of §4.1, the final code gave 9.1 / 14.2 and 9.6 / 15.4 ms against v0.8's 8.8 / 14.7 and
9.4 / 14.4.

With v0.8 semantics every partition pays for the slowest one, and the blocked writer also caps the commit rate (about
2,500 fsyncs in 9 s against 11,300). With v0.9 the fast partitions see exactly the uniform numbers of §4.1.

This is the head-of-line effect that per-partition completion removes. It stands in for a commit's 8 Linux chains on a
4-thread pool finishing at different times, or for one file with a slow `fdatasync`.

### 4.3 Throughput, closed loop

`append_bench` (8 requests of 64 messages in flight per producer, one partition per producer), 3 interleaved rounds,
median msg/s:

| case | v0.8 | v0.9 |
|---|---:|---:|
| 100 B, 1 producer | 103.2k | 103.7k |
| 100 B, 4 producers | 337.2k | 331.7k |
| 1 KiB, 1 producer | 82.8k | 84.5k |
| 1 KiB, 4 producers | 231.3k | 229.8k |

All differences are within the run-to-run spread (±5 %). An earlier variant opened a fresh file description for every
commit fsync, and cost 5–10 % at 100 B × 4 in CPU per message. Descriptions are now opened only at depth > 1 (§3,
rule 4).

## 5. Tests

- **New, `crates/fluxmq-core/tests/commit_path.rs`:**
  - `durable_marks_publish_in_order_per_partition`: depth 3. Commit k's fsync is held for 400 ms while k+1 and k+2 of
    the same partition finish. Nothing is visible or acked before k, acks come in offset order, and another partition
    is not held back.
  - `durable_marks_are_monotonic_under_load`: 16 publishers, depth 3, 16 KiB segments (rolls inside commits), one
    partition 3 ms slower. A concurrent watcher sees every durable mark only grow, every acked offset is below the
    mark at ack time, offsets are `0..n`, and everything survives a reopen.
  - `slow_partition_does_not_delay_others`: partition 0's fsyncs take 600 ms longer. Partition 1 is acked in < 300 ms,
    both in the same batch and in later ones. With the pipeline off (v0.8) it waits ≥ 500 ms, which shows the test
    detects the difference.
  - `fsync_error_fails_publishes_and_never_acks`, at depth 1 and 3:
    - partition 0's fsync fails after 300 ms;
    - that publish fails, and so does a later batch of the same partition whose own fsync succeeded;
    - partition 1, durable before the failure, stays acked;
    - nothing failed is visible or survives a restart, and the partition accepts writes again.
  - `multi_partition_request_waits_for_every_partition`.
  - `abrupt_stop_with_deep_pipeline_keeps_acked_prefix`: crash-style drop without shutdown, depth 3, 8 KiB segments.
    Every acked message is present after reopening, and every partition is a gap-free prefix.
- **New, `fsync_pool.rs`:** `groups_complete_independently` (slow, fast and failing groups) and
  `shared_apple_chain_reports_every_member`.
- **Mutation check:** publishing synced marks out of order makes three of the new tests fail.
- **Existing:** `storage_pipeline.rs`, `storage::log` / `batch_tests` pipelined commit and crash recovery, and the
  replication suites (`fetch_ahead.rs` fsync hold and failure on the follower) all pass on the new path.
- **Passing:** `cargo fmt --all`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`.

Reading: the 1.5 s / 420 ms rows of the first set did not repeat. With the same image, on and off overlap round by
round, and each round's p99 follows that round's commit (fsync) time: on-r2's 6.8 ms commit gave 161 ms, off-r3's
3.6 ms gave 21 ms. The pipeline does not raise the commit rate (1100–1600/s against 1290–1700/s off), so it does not add
load to the shared SSD. At 50k on this host the p99 is still set by three brokers fsyncing on one laptop SSD inside one
VM, as in v0.8 §6. The ≤ 20 ms goal needs separate disks or hosts to judge.

Decision: ship pipeline on, depth 1. It removes the cross-partition head-of-line wait (§4.2), gains 11–15 % at 4×4
saturation, and its latency rows are within this host's run-to-run noise (single outliers on both sides; the 50k p50 is 1–3 ms higher in some rounds). `FLUXMQ_COMMIT_PIPELINE=off` stays as the fallback.
Bench system `fluxmq-cluster-nopipe` (A/B only) runs the off variant.

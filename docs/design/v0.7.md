# FluxMQ v0.7 design: the batch fast path ("beat Kafka on one node")

Status: draft. Implementation starts after the v0.6 benchmark is published. Nothing here may be built while a benchmark run is in progress: images are built from the working tree.

## Goal (product decision): better AND more reliable than Kafka, not "like Kafka"

**Durability is not traded for speed.** The default stays fsync before ack (group commit), and every reliability feature stays on the fast path: per-message ack, redelivery, nack, DLQ, filters. Speed has to come from doing less work per message, not from weaker guarantees. `FLUXMQ_FSYNC=os` remains only as an explicitly labelled comparison row.

Today Kafka is about 1.6–2.5× faster on one-node peak throughput, and its consumers about 10× faster when they lag. The reason is structural:

| Kafka | FluxMQ v0.6 | v0.7 answer (keeps our guarantees) |
|---|---|---|
| Stores a producer batch as an opaque blob | One record (32 B header + CRC) per message | Batch records (§1) |
| Consumers commit a position | Per-message maps, sets and timers | Range/bitmap ack state (§2): individual acks stay, cost O(1) amortized |
| Serves raw bytes (`sendfile`) | Decode, then re-encode | Raw batch delivery (§3) |
| Sequential catch-up reads | 4 MiB cache, then per-message disk fetches | Chunked catch-up reads, batch cache (§2a) |
| Compression | None | Per-batch lz4/zstd |

**Targets, measured with the v0.6 harness, window and limits:**
1. FluxMQ **group-commit (fsync before ack)** at least matches Kafka's **default** (page-cache acks) on one node, at 1 KiB and 100 B, 1p1c and 4p4c, in consumed msg/s. That is faster while more durable. Where physics (disk flush rate) prevents it, report the gap and the fsync-bound ceiling.
2. FluxMQ group-commit beats Kafka in the same durability (`log.flush.interval.messages=1`) by a wide margin.
3. Consumer throughput under producer overload is at least Kafka's, with zero true loss. A slow consumer never makes the broker drop data silently: retention skips are counted and alerted (v0.6).
4. 3-node RF=3: FluxMQ (fsync on every ISR member) at least matches Kafka acks=all (no fsync).
5. No regression in latency (p50 at 1k msg/s < 2 ms, p99 at 50k msg/s < 50 ms) or memory. Better than Kafka where it already is.
6. **Reliability proof is part of acceptance:** kill -9 and power-cut simulations (drop page cache / fault-inject unsynced writes) with zero acked loss for FluxMQ. The report shows the same test for Kafka defaults, which can lose acked messages, as the "more reliable" evidence.

## 1. Batch records: storage (`fluxmq-core::storage`)

- **New record kind "batch":** one envelope holds N messages from one publish request on one partition.
  - Envelope fields: `len, crc32c, base_offset, count, base_timestamp_ms, flags (compression), inner records`.
  - Inner records use varint deltas (Kafka v2-style): offset delta, timestamp delta, key, headers, payload.
  - One CRC per batch. Use CRC-32C, hardware accelerated, for new batches; legacy records keep CRC-32 IEEE.
- **Format compatibility:** the old single-record format stays readable, and a segment can mix both. Recovery validates per envelope. A torn batch is truncated as a unit, which is fine because it was never acked.
- **Index:** sparse, base offset → file position of the envelope. Reading offset X seeks to the envelope containing X and skips inside it.
- **Server parsing:** for keyless stream publishes the broker does not parse payloads. It validates the frame, assigns `base_offset` and timestamp, computes the CRC and writes the bytes.
  - Ideally the client sends a pre-encoded batch body (§3), so the broker only patches header fields.
  - Filters, size limits and per-message headers needed for indexing are still checked where a feature needs them. Without such features, there is no per-message work.
- **Compression:** per batch, `none | lz4 | zstd`, set by the producer (`ClientOptions::compression`). The broker stores compressed batches as they arrive. It decompresses only for features that must look inside: filters, the UI message inspector, the payload index, queue/keyed delivery.
- **Concurrency:** one writer per partition rather than per channel, with the v0.6 fsync pool shared. This removes the per-channel single-thread ceiling.

## 2. Cheap per-message ack state: core and group (keeps redelivery, nack, DLQ)

- **Replace per-message `HashMap` / `BTreeSet` / deadline entries with range-based state per partition:**
  - a committed low-watermark;
  - a compact acked bitmap or range set above it (roaring-style);
  - a delivered-not-acked set with **bucketed deadline wheels** (one timer per bucket, not per message);
  - attempt counts only for messages with more than one attempt (a sparse map).
- **Semantics unchanged:** individual ack, nack with delay, max attempts to DLQ, ack timeout, keyed ordering.
- **Batched acks:** the SDK already coalesces them. The server applies a whole `Ack{ids}` as range operations under one lock.
- **Optional `AckMode::Cumulative`** for consumers that want it (cheapest). The default stays individual.
- **Persisted group state:** checkpoint the low-watermark plus the bitmap, so redelivery after a restart is exact (no mass redelivery).

## 2a. Consumers falling behind under producer overload (found in the v0.6 bench)

- **Observation:** once producers are no longer throttled (v0.6 SDK coop fix), FluxMQ consumers collapse at 100 B 4p4c. 1.4M msg/s are published and only about 38k msg/s consumed. Kafka shows the same effect, less severely: 1.3M published, 374k consumed.
- **Hypothesis to confirm with profiling:**
  - Once a group falls behind the per-partition recent-message cache (4096 messages / 4 MiB), every delivery goes through `spawn_blocking` disk fetches with per-record decode.
  - The 2-CPU broker gives producers priority implicitly.
  - Kafka reads big sequential chunks through the page cache.
- **Fix:**
  - Catch-up reads in large sequential chunks (whole batches, §1/§3, readahead) instead of per-message fetches.
  - A configurable, larger recent-batch cache.
  - Fair scheduling between the publish and delivery paths: a bounded publish admission that applies backpressure to producers when the broker is CPU-saturated, so lagging consumers can't be starved indefinitely.
  - Metric: consumer lag and catch-up read rate.
- **Acceptance:** in the overload scenario, consumed msg/s ≥ Kafka's. Keep a dedicated "catch-up" bench scenario: preload N GB, then measure consume-only throughput.

## 3. Wire: proto, architect-owned (protocol v4)

- **`ClientFrame::PublishBatch`:** `channel, partition, compression, record_count, body: Bytes`. The body is pre-encoded inner records, so the broker writes them almost verbatim.
- **`ServerFrame::DeliverRecords`:** `subscription_id, partition, base_offset, records: Bytes`, carrying raw stored batch bytes, still compressed if they were stored that way. The client decodes and decompresses.
  - The server sends straight from the page cache or the recent-batch cache with no per-message work.
  - On Linux the plaintext path can use `sendfile` / `splice` (TLS needs kTLS; out of scope, it uses the copy path).
- **`ClientFrame::Commit`:** `subscription_id, partition, offset`, for cumulative ack.
- **Negotiation:** v4 is negotiated in `Hello`. v3/v2 clients keep `Publish`/`DeliverBatch`, and the broker converts between forms. The SDK falls back as in v0.6.

## 4. SDK

- `BatchingProducer` builds `PublishBatch` bodies (and compresses them) per partition while it lingers, so the broker never touches individual messages.
- Consumer: `SubscribeOptions::ack_mode(Cumulative)` with `commit()`, plus auto-commit every N ms or messages. It decodes `DeliverRecords` lazily (iterating zero-copy slices of the batch).

## 5. Replication (cluster)

- Followers already fetch byte ranges. Batches replicate as-is: no re-encoding, fewer records and less CRC work.
- Check that the replication fetch path doesn't decode records. If it does, switch it to raw ranges plus envelope validation.

## 6. Bench additions

- Kafka variant `kafka-*-fsync` with `log.flush.interval.messages=1` ("fsync before ack").
- **FluxMQ headline:** group-commit, individual acks (default semantics) on the v0.7 path (`PublishBatch` and raw delivery), compression off. Extra rows: lz4, and cumulative ack.
- **New scenarios:**
  - catch-up: preload N GB, then measure consume-only throughput;
  - overload: producers faster than consumers;
  - **crash durability:** kill -9 / VM-level crash during publish. Count acked-but-lost messages for each system (FluxMQ must be 0; Kafka defaults measured as-is).
- The same window, limits and drain/id checks as v0.6. A new frozen result set, with v0.6 → v0.7 history on the index page.

## Results — SDK

Measured 2026-10-09 on an Apple M1 Pro (8 cores), release builds. The machine was shared with other agents' builds, so absolute numbers are noisy. Compare the ratios, not the absolute values.

**Method.** A sink broker runs as a separate process and does minimal work: it answers `Publish`/`PublishBatch` at once and pushes pre-built deliveries under prefetch credit. The client is a separate process, and its CPU comes from `getrusage(RUSAGE_SELF)` over the measured window, after a 10 % warm-up. "Before" is the v0.6 SDK, i.e. HEAD plus the uncommitted coop fix, built from a snapshot. "After" is the v4 SDK. Both run against the same sink with 4 partitions.
- Publish: `BatchingProducer` (default options), 4 publisher tasks with a window of 5,000 each, a JSON-like payload, and stamping on. That's 2M messages at 100 B and 1M at 1 KiB.
- Consume: prefetch 2000, `ack()` per message. That's 3M messages at 100 B and 1M at 1 KiB. The sink sends `DeliverBatch` (≤ 256) on v3, and on v4 a 256-record envelope per frame delivering a partial range.

Client CPU in µs per message, median (range). Publish: 6 runs without compression, 5 runs with. Consume: 3 runs, plus 2 runs for each option variant:

| Path | 100 B before | 100 B after | 1 KiB before | 1 KiB after |
|---|---|---|---|---|
| Publish, no compression | 2.37 (1.72–3.18) | 0.94 (0.59–2.12) | 2.58 (1.95–3.31) | 1.21 (0.91–2.14) |
| Publish, lz4 | — | 0.69 (0.62–1.67) | — | 0.90 (0.85–1.30) |
| Publish, zstd | — | 0.67 (0.64–1.77) | — | 0.96 (0.90–2.31) |
| Consume + ack (raw records, CRC on) | 1.07 (0.94–1.10) | 0.86 (0.81–0.91) | 1.03 (1.00–1.20) | 1.03 (1.00–1.03) |
| Consume, CRC off | — | 0.85 (0.82–0.88) | — | 1.03 (1.01–1.05) |
| Consume, `raw_records(false)` (v3-style) | — | 1.05 (0.98–1.12) | — | 1.18 (1.15–1.21) |

Paired runs (same moment, same load) put the publish CPU per message at 0.32–0.67× of v0.6 at 100 B and 0.43–0.65× at 1 KiB. At 1 KiB, consume CPU is unchanged. What's left there is the per-message `Delivery`: owned header map, `Arc` clones, timestamp and the ack bookkeeping, which the public API requires.

Throughput: the sink (one connection, one task) is the bottleneck in most consume runs, so these are lower bounds. Publish went from 0.7–1.2M to 1.4–2.1M msg/s at 100 B, and from 0.45–1.1M to 0.9–1.7M msg/s at 1 KiB, with up to 2.8M msg/s with lz4. Consume was about 2.0M msg/s on both sides (sink-bound).

**Findings and recommendations.**
- **Publish.** The win comes from encoding each message once into the batch buffer, without per-message `PublishMessage` encoding at send. It also comes from no `flux-producer` map insert (the stamp is written straight into the record), one buffer allocation per batch, and the section shared with the socket write (no copy into the frame).
- **Compression.** It is cheap next to the rest of the per-message cost: one compression call per batch of about 1000 messages. lz4 and zstd at level 1 stayed within the run-to-run noise of no compression, because less data goes through the socket. Payloads in this bench are very compressible; real ratios vary. Recommended default for users: keep `None` (smallest latency, no surprise CPU on consumers), and suggest `Lz4` for JSON or log payloads.
- **CRC-32C verification.** Hardware CRC costs within noise: ≤ 0.03 µs/msg at 1 KiB, i.e. ≤ 3 % of consumer CPU and indistinguishable in most runs. **Keep `verify_crc` on by default.**
- **Raw records** save about 20 % of consumer CPU at 100 B compared with per-message delivery frames, and nothing measurable at 1 KiB. The real gain is on the broker (no per-message work), which this sink doesn't show.

Not measured here (needs the v4 broker): end-to-end throughput against the real broker, cumulative ack, and lag catch-up. The bench harness needs a switch for compression and ack mode; requested from bench/QA.

## Results — storage

### What changed (`fluxmq-core::storage`, `channel.rs`)

- **Entries.** A segment is a sequence of entries: batch envelopes exactly per `fluxmq_proto::batch` (32-byte header, records section verbatim, CRC-32C over `[8, total)`) and legacy v0.1–v0.6 records (CRC-32). Readers dispatch on bit 31 (`storage/entry.rs`). One segment may mix both. CRC-32C comes from the shared `fluxmq_proto::batch::codec` (`crc32c` crate: SSE4.2 / ARMv8 CRC instructions); compression codecs too (lz4_flex, zstd), so broker, replication and SDK can't diverge.
- **What gets written.** Everything new is an envelope:
  - `Broker::publish_batch` (`PublishBatch`): the producer's section is validated once (count/size limits, decompression with a 64 MiB cap, every record well formed, `offset_delta == index`, `timestamp_delta == 0`), then stored **as received** (compressed stays compressed); the broker only writes the header. `partition: None` routes the whole batch by `key_partition` or sticky; keys spanning partitions → `InvalidArgument`.
  - `publish(Vec<PublishMessage>)` (v2/v3 clients, REST, replay, DLQ retry): the writer encodes each partition's messages of a request into one envelope (cut at ~1 MiB and at segment roll points, so segments stay near their nominal size). The materialized `Message`s go into the recent cache with payloads sliced from the envelope (no second copy, the frame is freed).
  - Legacy records are still written in two cases: a message too large for an envelope (> 16 MiB, only possible via REST), and partitions whose `batch_writes` is off — set for every partition by `Broker::enable_replication` until the cluster confirms every replica reads envelopes (rolling upgrade from v0.6, `ReplicaHandle::set_batch_writes`).
- **Index and reads.** Sparse index entries point at entry positions (`rel_offset` = entry base). Reading offset X seeks the index, skips whole entries by header only (no CRC, no decode), then decodes the containing entry (CRC verified first) and skips inside it. Timestamps: one per envelope.
- **Raw reads** for the delivery engineer: `PartitionLog::read_envelopes(from, max_bytes)` / `cached_envelopes` → `EnvelopeChunk { first_base, next_offset, bytes, batches_only }`: whole entries, never crossing a segment, one positional read sized `max_bytes` (the seek's read-ahead is the read), zero-copy slice of it. `decode_chunk(partition, &Bytes)` turns any chunk into `Message`s (zero-copy payloads, decompression when needed).
- **Recent cache** is envelope-keyed (`--partition-cache-bytes`, default 16 MiB per partition, bytes only, no message cap). A producer batch is decoded at most once, lazily, on the first per-message access.
- **Recovery** validates per entry (CRC-32C / CRC-32, offset contiguity) and truncates a torn or corrupt tail entry as a unit. A v0.6 data dir opens unchanged and continues appending envelopes.
- **Replication.** Followers append fetched entries verbatim after per-entry CRC and contiguity checks (all-or-nothing per chunk). Truncation rounds down to an entry boundary. For the overlapped leader/follower fsync: `written_high()`, `read_envelopes_unsynced()`, `written_notify()`; a failed fsync after an unsynced read poisons the partition writer until restart (offsets that a follower may hold are never reassigned). Fault injection: `fail_next_fsync_for_tests[_after]`.
- **Not done: one writer thread per partition** (§1 "Concurrency"). Measured writer-thread CPU is 0.18–0.23 µs per 100 B message (mostly the `write(2)` copy) and 0.73–1.1 µs per 1 KiB message, so one channel writer saturates only beyond ~4M msg/s at 100 B — far above the fsync-bound rates below and above what a 2-CPU broker can feed. More writer threads would compete with delivery for those 2 CPUs. Fsyncs already run in parallel on the shared pool. Revisit if a profile shows the writer thread saturated.

### Measurement

Local, macOS (Apple Silicon, 8 cores), release builds, in-process `Broker` (no network), `crates/fluxmq-core/tests/append_bench.rs`: 8 partitions, each producer keeps 8 requests of 64 messages in flight on its own partition, group commit (fsync before ack, 2 ms interval), 1 s warm-up, 4 s window. CPU = whole-process user+sys (includes the bench's own producer tasks and tokio) per acknowledged message.

**Caveat:** the machine was shared with several concurrent agent builds (load average 6–20 on 8 cores) during every run. Throughput was dominated by that noise (the identical HEAD binary ranged 8k–118k msg/s at 100 B/1 producer across runs). | 100 B, 1 producer | 72k | 107k | 57k | 0.58 → 0.64 → 0.59 |

Bigger requests (200 × 100 B, 4 producers, 4 interleaved rounds): HEAD 706k–798k msg/s at 0.33–0.41 µs/msg; after `publish` 589k–822k at 0.36–0.48; after `publish_batch` 588k–837k at **0.19–0.22 µs/msg** (about half of HEAD's CPU).

Writer-thread CPU alone (thread CPU clock, `PartitionWriter` append + commit mark + publish, 200-message requests, `writer_cpu_microbench`): HEAD 221 ns/msg at 100 B, 873–921 at 1 KiB; after (`publish` path) 228 / 827–839; after (`publish_batch`) 184–213 / 726–1089. Conclusions:
- No regression of the per-message (`publish`) write path within this noise; CPU per message at parity.
- The `PublishBatch` path costs 16–25% less CPU per message at 64-message requests and about 50% less at 200-message requests, while keeping fsync-before-ack. Throughput here is fsync-bound (Apple `F_FULLFSYNC` barrier per commit), so CPU savings show up as throughput only on the 2-CPU bench broker.

### Risks and open points

- Payloads read from disk are zero-copy slices of the read buffer (64 KiB–1 MiB). A message held for long (retry backoff, DLQ) pins that buffer unless the group detaches it (`Pending::detach` exists for frames).
- `--partition-cache-bytes` default 16 MiB × partitions: 8 partitions = 128 MiB plus materialized messages for v2/v3 consumers. Accounting counts 64 B per materialized message; the real overhead with headers is higher.
- A producer batch can't be split, so a segment can exceed its roll size by up to one batch (≤ 16 MiB).
- Downgrade to v0.6 after envelopes were written is not supported (as documented in `batch.rs`).

## Results — cluster

### What changed

- **Verbatim replication (`fluxmq-replication`).** The leader serves whole stored entries (legacy records and batch envelopes) from a byte range; the follower walks only the entry framing (`chunk::verify`): contiguity plus CRC-32C per envelope (CRC-32 per legacy record), no decode, no decompression. It then hands the bytes to the core writer, which appends them as is (checking again). A corrupt fetch payload is **refetched** (`Retry`), never appended and never treated as divergence. A chunk whose first envelope starts below the follower's LEO (the follower's log ends inside a leader batch) makes the follower truncate to that envelope's base and refetch. Followers on any mix of legacy and batch segments stay byte-identical to the leader (tests compare the segment bytes).
- **Leader/follower fsync overlap (`fluxmq-core::replica`).** Followers fetch the leader's *written* tail (`read_envelopes_unsynced`, long-poll woken by `written_notify`), so the leader's fsync runs in parallel with theirs instead of before them. Acks are unchanged: HW = min(leader's durable LEO, durable LEO of every ISR / committed-ISR member). A follower reports its durable LEO in its fetch offset (followers publish only after their own fsync), and consumers see only offsets below the HW. Safety rests on two rules. First, a restarted leader is always demoted under a new epoch (controller), so followers truncate a tail it lost. Second, a failed fsync after an unsynced read poisons the leader's partition writer until restart (storage), so offsets a follower may hold are never reassigned to other data.
- **Cluster `PublishBatch` (`fluxmq-cluster::publish`).** `Cluster::publish_batch(channel, Option<u32>, RecordsSection)`. `Some(p)` is served only by `p`'s leader (`NotLeader` with the leader id otherwise, the same settle window as `Publish`). `None` routes the whole batch to one partition: the key partition when it has keys (every keyed record must map there, otherwise `BadRequest`; never split) or sticky round-robin when keyless. The section is forwarded raw to a remote leader (`POST /internal/v1/publish_batch`, postcard; one copy into the request, no per-message work). Compressed sections are decompressed only to read the keys of a partition-less batch.
- **Rolling upgrade v0.6 → v0.7.** A v0.6 follower can't parse envelopes, so:
  - *Writing:* a partition leader writes envelopes only while every replica in the assignment advertises the registry feature `batch-records` (`NodeRecord::features`). v0.6 nodes don't send it, and a v0.6 controller drops it when it rewrites a record; both read as "old". Until then `PublishBatch` is stored as legacy records (same offsets and acks). The reconciler applies the write format before the role, on every pass, so batches turn on once the last upgraded incarnation is registered. Replicated brokers start with batch writes off.
  - *Serving:* independent of the registry. Each follower declares its capabilities in the payload of its replication `Hello` (v0.6 leaders ignore it; v0.6 followers send none). The wire protocol stays v1 in both directions. A leader never sends an envelope to a follower that didn't declare `batch-records`: it serves the legacy prefix, then refuses with a rate-limited `error!` alert and a counter (`refused_old_follower_fetches`). This also covers an old node re-added to a partition that already wrote batches (downgrade is unsupported, but it can't corrupt the follower). The reconciler logs the same condition. Because serving doesn't depend on registry flags, a v0.6 controller dropping them after batches exist doesn't stall replication; only new writes go back to legacy.

### Measurement

Local macOS (Apple Silicon, 8 cores, one SSD), 3 processes on localhost, RF=3, `min_isr=2`, group commit (fsync before ack on every ISR member), 8 partitions, 4 producers × 4 in flight × 100 messages, 4 consumers, closed loop. Fresh cluster per run, runs interleaved v0.6/v0.7. Baseline is the HEAD binary 6d69c97 with its own bench client (v3 `Publish`). v0.7 is the working tree with the v0.7 client (`PublishBatch`).

| case | v0.6 msg/s | v0.7 msg/s | publish RTT p50 / p99 / min ms, v0.6 → v0.7 |
|---|---|---|---|
| 1 KiB (2 interleaved rounds) | 22.7k, 20.8k | 27.3k, 28.7k (+25–35%) | 67–74 / 132–140 / 46–50 → 51–56 / 123–130 / 20–25 |
| 100 B | 14.0k | 31.7k (2.3×) | 84 / 453 / 42 → 46 / 117 / 18 |

In-process `fluxmq-replication` bench (`tests/throughput.rs`, 6 partitions, RF=3, 8 publishers × 100 × 100 B): with group commit HEAD made 17.1–18.9k msg/s and v0.7 13–19k. With OS-buffered writes, HEAD 116k vs v0.7 209k on the quieter run.

**Caveats, read before quoting.**
1. The machine was shared with other agents' builds (load average 10–19 on 8 cores). Identical binaries varied up to 3× between runs: `FLUXMQ_FSYNC=os` gave 81k–235k msg/s on HEAD. Only the interleaved group-commit rows are meaningful, and only as a direction.
2. The three replicas share one SSD whose `F_FULLFSYNC` flushes serialize: one flush takes ~5 ms alone and ~12 ms each with 3 concurrent writers, about 250 flushes/s for the whole machine. With fsync on every ISR member, that device limit is the ceiling here (single node: 107k msg/s at 1 KiB). Overlapping the leader and follower fsyncs shows up mainly as the halved minimum RTT. On separate disks per node, the expected effect is ack latency ≈ max(leader fsync, follower fsync) + RTT instead of their sum.
3. Linux/Docker numbers (the reference for target 4 vs Kafka `acks=all`) come with the v0.7 Docker matrix after integration; this macOS setup is not representative of either system.

The structural bottleneck found and fixed: the leader fsync and the follower fetch → follower fsync → HW ran strictly in series. Followers could only fetch what the leader had already made durable. The remaining limit on a shared device is the number of flushes per acknowledged byte (one per partition file per node per commit). Bigger producer batches (`PublishBatch`) amortize it, which is why 100 B gains most.

  - leader loses its unsynced tail, both ways: when the ISR follower leads, the never-acked tail survives (allowed); when the restarted leader leads at a new epoch, the follower truncates it;
  - leader fsync fails (held 200 ms) after the follower fetched the unsynced batch: publish fails, HW never passes it, the leader is poisoned, then failover plus restart reconverges with nothing acked lost (10/10 runs);
  - envelopes are never served to a follower without the capability;
  - an old follower still replicates legacy records.
- `fluxmq-server/tests/cluster_batch.rs`:
  - `PublishBatch` routing: `NotLeader` with the leader id from non-leaders, keyless sticky spread, key partition from every node, spanning keyed batch refused, compressed sections; replicas byte-identical; every record readable;
  - a v0.6 controller dropping the features after batches exist: leaders go back to legacy writes, no ISR ever shrinks, replicas stay identical;
  - in-process rolling upgrade under load: two "v0.6" nodes, every node restarted in turn, no envelope while any replica is old, batches after the last upgrade, zero acked loss.
- `fluxmq-server/tests/rolling_upgrade_bin.rs` (ignored; needs `FLUXMQ_OLD_BIN` / `FLUXMQ_NEW_BIN`): real v0.6 binary → v0.7 binary, 3 processes, group commit, `min_isr=2`. It checks: zero acked loss (every acked id stored with its payload, read via every node), no envelope while any node is old, envelopes after. It passed 7 of 8 runs (7k–14k acked messages per run, 0 lost). The failing run timed out waiting for the cluster to report healthy after a kill -9, before the diagnostics were added; see risks.
- Existing replication, failover-property, move-property, rebalance and decommission tests run unchanged. With every node advertising `batch-records`, they now move batch segments.

### Risks and open points

- The one timed-out real-binary run (cluster not healthy within 90 s after a leader kill -9) is not explained yet. The test now prints the last observed metadata state on timeout.
- Downgrade to v0.6 after envelopes exist is unsupported. An old follower is refused loudly rather than corrupted, but the partition can't use it as a replica until it is upgraded or reassigned.
- `Cluster::publish_batch` with `partition: None` and a compressed section decompresses it once on the receiving node to read keys. SDKs always send `Some(p)`.
- The leader overlap relies on the controller bumping the epoch when a restarted node leads again (it is demoted on restart today). Any future fast-restart path that keeps a leader's epoch must keep that rule.

## Results — delivery

### What changed (`fluxmq-core::group`, `ackset`, `history`; `fluxmq-server::net`)

- **Range ack state** (`ackset.rs`). Per (group, partition): a committed low watermark plus finished offsets above it as disjoint ranges. The v0.6 `pending: BTreeSet<u64>` (one entry per in-flight message) is gone. An in-order ack is one increment of the watermark.
- **In-flight runs instead of per-message maps.** The deliveries of one poll (one `DeliverBatch`/`DeliverRecords` frame) share consecutive delivery ids, one subscription, one delivery instant and one ack deadline. So a run is one `BTreeMap` entry and one timer (deadlines are bucketed to 10 ms). The v0.6 `HashMap<id, InFlight>` + `BTreeSet<(deadline, id)>` per message is gone.
  - First attempts store nothing but the message `Arc`.
  - Messages with earlier attempts, DLQ retries and orphaned entries carry a boxed `Prior`: the sparse attempt records.
  - `Ack{ids}` (with a run hint, O(1) per id), `AckRanges` (proportional to covered ids, never to claimed range sizes) and `Commit` are applied under one lock acquisition.
  - Counters, processing-latency samples (`record_n` per run) and attempt history are applied once per batch.
  - Attempt history is updated after the group lock is released. It locks each history shard once per batch, keyed by a multiplicative hasher instead of SipHash.
  - Semantics are unchanged: individual ack, nack with backoff, `max_attempts` → DLQ, ack timeout, keyed ordering, offset reset, replicated-mode partition resets.
- **Exact restart.** `offsets.json` gains an optional `"acked": {group: [[[start, end], ...] per partition]}`, at most 1024 ranges per partition. Restored ranges are skipped by dispatch, so a restart redelivers exactly the unfinished messages.
  - Old files load (the field is optional), and old brokers ignore it.
  - **Cluster caveat:** replication still carries only the committed offset. After a leader failover, messages acked above the watermark may be redelivered once (at-least-once holds).
- **`AckMode::Cumulative`** (`SubscribeWith`, stream channels only; queue/keyed answer `BadRequest`).
  - No ack deadline. `Commit{partition, offset}` settles the subscription's deliveries below `offset`, and a lower offset is a no-op.
  - `Nack` answers `BadRequest`.
  - When the subscription ends, unsettled deliveries are redelivered from the committed position.
- **Raw delivery** (`DeliverRecords`) for v4 subscriptions with `raw_records`. When a partition has nothing that needs per-message handling (no due retry, no ready redelivery, no timestamp skip, batch envelopes only, stream mode), the group hands out a contiguous fresh range as whole stored envelopes:
  - Source: from the recent cache (one entry zero-copy; entries below 64 KiB are coalesced) or from the raw read-ahead.
  - Delivery ids are `first_delivery_id + (offset - from_offset)`. They are allocated from the same per-group counter as every other delivery, so they are unique per (channel, group).
  - The frame always holds every offset of `[from, from + count)` (it stops at gaps and restored ranges). The envelope slice is trimmed to the covering envelopes.
  - A raw in-flight run keeps the envelope bytes and decodes only what must be redelivered (nack, timeout, disconnect, reset).
  - A raw run that is ≥ 7/8 settled is compacted to its stragglers, with payload copies, so one slow message never pins a 1 MiB buffer.
  - Everything else (redeliveries, keyed/queue channels, legacy records, v2/v3 clients) goes out as `Deliver`/`DeliverBatch`, decoded from batches with zero-copy payload slices.
- **Catch-up reads.** A group behind the recent cache fetches with one positional read of whole entries (`read_envelopes`, 4 MiB, off the async runtime). The data is either kept raw for raw subscriptions, or decoded in the blocking task, not under the group lock.
  - A new fetch is issued once half of the previous one is used (double buffering).
  - Before, it was 512 records / 1 MiB per fetch, one at a time, decoded record by record.
- **Server (v4 enabled):** `MAX_ACCEPTED_PROTOCOL = PROTOCOL_VERSION`.
  - Handlers for `SubscribeWith` (ack mode, raw records, `prefetch_bytes` as a frame byte bound), `AckRanges`, `Commit` and `PublishBatch` (through `Cluster::publish_batch`).
  - v4 requests on a v2/v3 connection answer `ProtocolViolation`.
  - RBAC stays an exhaustive match.
- **Fair scheduling without throttling producers.** Subscription pumps and connection writers (group polling, frame encoding, socket writes) run on a dedicated delivery runtime: `--delivery-threads` / `FLUXMQ_DELIVERY_THREADS`, default 2, 0 = shared runtime.
  - Request handling (publish decode, append) stays on the main runtime, so the OS scheduler gives delivery its own CPU share when producers saturate the broker.
  - No publish admission or lag-coupled flow control was added: producers are never slowed down by consumers (product rule). The existing bounds still apply (`max_in_flight_requests` per connection, writer queues).
- **Metrics:** group lag (existing, now exact including restored ranges) and `fluxmq_group_catchup_read_bytes_total` (bytes read by catch-up read-ahead; its rate is the catch-up read rate).

### Risks and open points

- `prefetch_bytes` bounds frame size only. In-flight bytes are not tracked per subscription yet.
- Raw frames are encoded through postcard (one copy of the envelopes into the write buffer). `sendfile`/vectored writes would remove it and help at 1 KiB+.

- The delivery runtime is process-wide (first server in a process sets its thread count; tests share it).
- Acked-above-watermark ranges are not replicated (see the cluster caveat).

### Improvements (from `perf` profiles of the broker and the harness; full list with evidence in the report)

1. **Zero-copy outbound frames** — 1 KiB 1-node gap. 16.9 % of broker CPU is `memcpy` in `postcard::serialize_field::<Bytes>` ← `FrameCodec::encode` ← `connection::write_loop` (raw envelopes copied into the write buffer) + 3.1 % `BytesMut::reserve_inner`. Fix: header-only encode + `write_vectored` of the envelope `Bytes`, later `sendfile`. Expected +15–25 % at 1 KiB. No durability impact.
2. **Raw-run compaction inside an ack batch — quick fix done (uncommitted, working tree).** `GroupState::ack_at` compacted a raw run at 7/8 settled, decoding and CRC-checking the whole envelope chunk (`crc32c` ← `ChunkRecords::next` ← `Run::materialize` ← `ack_at` ← `ack_ranges`: 10 % of broker CPU at 1 KiB, ~23 % at 100 B 1×1) although the same `AckRanges` settled the rest. Now decided after the batch (`compact_runs`). Measured (`after-quick-fixes/`, 2 repeats): 1 node 1 KiB 1×1 231k → 277k (+20 %), 4×4 320k → 476k (+49 %, consumers keep up), 100 B 1×1 427k → 545k (+28 %), 100 B 4×4 +2 %; 3 nodes 1 KiB +10 % / +43 %; latency unchanged. With it, 1-node 1 KiB 4×4 beats Kafka-fsync (1.09×) and reaches 0.82× Kafka default; goal 2 becomes met at 1 KiB 4×4, goal 4 at 1 KiB 1×1 stays just short (0.94×).
3. **Per-message attempt history** (`AttemptHistory::on_deliveries` 10.3 % at 100 B 1×1): record only redelivered/nacked messages — product decision (retry-timeline UI).
4. **Inbound `PublishBatch` copy** (`Bytes::copy_from_slice` in `decode_frame`, 3.5 %): zero-copy `split_to().freeze()`.
5. **SDK consumer per-message cost** at 100 B 1×1 (single consumer task): batch-ack helper, fewer per-`Delivery` allocations.
6. **TLS at 1 KiB** (−46/−47 %): same CPU budget as item 1; kTLS later.
7. **3-node p99 at 50k msg/s** 131 ms (v0.6 61 ms): not profiled in this run; next step.
8. **Paced retention can't keep up at saturation** (≤ 16 segments/s/channel): disk overshoots the cap at 500–830 MB/s ingest; scale the per-tick budget with the overshoot.
9. **Producers outrun consumers on one node** (publish 1.7–2× consume): optional consumer-paced admission — product decision.
10. **Harness:** Kafka 3-node 100 B 4×4 client-bound (give clients 4 CPUs); audit cap raised to 600 s.

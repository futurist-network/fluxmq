# FluxMQ v0.5 design: important gaps, Docker, comparative benchmarks

The contracts live in code:
- `fluxmq_proto::wire`: protocol v3, `DeliverBatch`, `MIN_PROTOCOL_VERSION`, batch bounds.
- `fluxmq_proto::auth`: the v0.5 block (revocation, last-admin guard, certificate bindings).
- `fluxmq_proto::cluster`: `NodeStatus::Decommissioning` and the decommission block.

Read their docs first.

## 1. Batched delivery: `fluxmq-core` / `fluxmq-server` / `fluxmq-client`

- The broker coalesces deliveries ready for a subscription into `DeliverBatch` frames, sent only to clients that sent `Hello` with protocol v3.
  - Batches are bounded by the remaining prefetch credit, `MAX_DELIVER_BATCH` and `MAX_DELIVER_BATCH_BYTES`.
  - The broker never waits to fill a batch (no linger). It drains what is ready when the connection writer runs.
- v2 clients still get `Deliver`.
- The SDK speaks v3. It acks in batches (it already has `Ack { delivery_ids }`; make sure the consumer coalesces acks too, flushing on a short timer or a size bound, configurable, with acks on drop/close flushed).
- **Acceptance:**
  - consume throughput on the release bench measurably higher (report before/after);
  - p99 delivery latency at low rates not worse;
  - a v2 raw-protocol client still works (test);
  - all delivery semantics unchanged (redelivery, nack, DLQ, prefetch).

## 2. Security: `fluxmq-auth` / `fluxmq-server` / `fluxmq-api`

- **Revocation and expiry close live sessions on every node within 1 s:** client connections get `Goodbye`, WS gets close code 4401.
- **Last-admin guard:** 409 with `ERROR_LAST_ADMIN`.
- **Certificate bindings:**
  - meta `auth/cert-bindings/<cn>`, REST under `/api/auth/cert-bindings`;
  - a client-port mTLS CN maps to a principal when there's no token; the actor shows as `cert:<cn>`;
  - permission table entries (admin).
- Tests for each item, including a cluster test of revocation on another node.

## 3. Cluster operations: `fluxmq-cluster` / `fluxmq-api` / `fluxmq-notify`

**Node decommission and forget,** per the proto docs:
- uses the v0.4 rebalancer: repair-reason moves, plus a planner rule that a `Decommissioning` node is never a target and ends up with zero replicas;
- then Raft membership removal (openraft `change_membership`, which removes the voter or learner), and the registry entry is deleted;
- quorum safety checks; removing the controller makes it step down after its replicas are moved;
- integration tests: decommission a node under load with zero acked loss, the node ends up out of membership, and a restart with the same id joins fresh; forget a dead node after repair.

**Persistent notification history:**
- the history ring moves to the replicated system channel `$system.notifications`, which only the controller appends to, with retention of 7 days or 10 000 records;
- `GET /api/notify/history` reads it from any node (proxy to the leader like the events feed), so history survives a controller change or restart;
- test: history survives a controller failover.

## 4. UI

- **Access tokens:** a "Certificate bindings" section (list, create, delete, an inert warning when mTLS is off), a `last_admin` error message, and a note that revocation disconnects live clients.
- **Nodes:**
  - Decommission (confirm dialog explaining the moves, a progress chip from `GET …/decommission`, the plan link);
  - Forget (only for Down nodes with no replicas);
  - the `decommissioning` status chip.
- Mock and screenshots as usual.

## 5. Docker: `deploy/`

- **Images:**
  - a multi-stage `Dockerfile`: a Rust release build with a cargo cache mount, plus the UI build, into a small runtime image (debian-slim or distroless);
  - the `fluxmq` binary serves the UI;
  - `.dockerignore`;
  - the image also contains `fluxmq-bench`, `fluxmq-demo` and `fluxmq tls gen-dev`.
- **`deploy/docker-compose.yml` profiles:**
  - `single`;
  - `cluster`: 3 nodes with full TLS (a gen-dev init container writes certificates to a volume) and a healthcheck;
  - `demo`: load generator;
  - `kafka`: Apache Kafka in KRaft mode, 1 node and a 3-node variant;
  - `rabbitmq`: RabbitMQ with quorum queues, plus streams if useful;
  - `bench`: runner.
- `deploy/README.md` plus a GUIDE section in Russian.

## 6. Comparative benchmarks: `bench/`

**Same machine and same Docker resources for every system, one methodology.**

**Systems:**
- FluxMQ single node;
- FluxMQ 3-node RF=3 (plaintext and TLS);
- Kafka 1 node and 3-node RF=3 (`acks=all`, `min.insync.replicas=2`);
- RabbitMQ 1 node, and quorum queues on 3 nodes.

**Scenarios:**
- **Saturation ("на нагрузке"):** max publish+consume throughput, 1 KiB and 100 B messages, several producer and consumer counts.
- **Latency at fixed moderate rates ("без нагрузки"):** for example 1k, 10k and 50k msg/s open loop, measuring end-to-end p50/p99/p999.
- **Durability settings stated per system:** FluxMQ group-commit vs Kafka `acks=all` with the default flush vs RabbitMQ quorum queues with publisher confirms.
- **With and without TLS** for FluxMQ (and Kafka if feasible).
- **Resource use:** CPU and RSS per container (`docker stats`).

**Load tools:** each system's standard or official perf tools where they exist (`kafka-producer-perf-test` / `kafka-consumer-perf-test` or a common client harness; RabbitMQ `perf-test`), or one common harness if fairness needs it. Document the choice. Raw results are JSON in `bench/results/<date>/`.

**Report:** a self-contained HTML page at `bench/report/index.html`, generated from the JSON by a script. It holds:
- charts;
- tables;
- methodology, environment (CPU, RAM, Docker limits, versions) and caveats (macOS Docker VM, a single laptop, noisy neighbours);
- conclusions that are honest, including where FluxMQ loses.

## 8. Integration decisions

Made while integrating the engineers' work (commit `8df5f55`) into the 0.5.0 release.

**Proto items added by the architect after the engineers finished (additive):**
- `EventKind::{NodeDecommissionStarted, NodeDecommissioned, NodeDecommissionFailed,
  NodeForgotten}` are derived **cluster-wide**, like the rebalance events, not from the
  controller-local `Runtime::decommission_events` broadcast (that one only feeds the audit log).
  `Cluster::decommission_records()` exposes every record with its origin (`forget` lives only in
  the cluster-internal `DecommissionDoc`, so a small crate type `DecommissionRecord { status,
  forget }` carries it; no proto change). The telemetry poll adds it to `ClusterFacts`; the
  collector diffs it per tick (first observation = baseline; identity = node + `started_at_ms`,
  so a retried decommission is a new record). A forget emits no "started" event, only
  `node_forgotten` (or `node_decommission_failed` titled "Forget of …"). A record first seen
  already finished (the 1 s poll missed the steps) still emits its start and end once.
- `fluxmq_proto::notify::SYSTEM_NOTIFICATIONS_CHANNEL` replaces the local constant;
  `fluxmq_notify::history` re-exports it (`pub use`) so existing paths keep compiling.
- UI: the four kinds in `EventKind`, labels and icons; the mock emits them.

**Fixes with root causes:**
- *Unbounded metadata write.* openraft's `client_write` waits for the commit with no bound; a
  leader without a quorum (a restarted node that restored itself as leader, or a partitioned
  leader) blocked the caller forever, often with the controller lock held. `RaftMetaStore::
  propose_local` is now bounded by `LOCAL_PROPOSE_TIMEOUT` (4.5 s, below the 5 s forward
  timeout so a forwarding follower still gets the leader's answer) and returns
  `MetaError::Unavailable` ("outcome unknown"; not retried, the entry may still commit). The
  bound covers `put`/`delete`/CAS writes and the `/cluster/write` handler. Callers already map
  `Unavailable` (API 503, controller RPC `Unavailable`, background loops retry). Test:
  `cluster::metadata_write_without_quorum_fails_fast`.
- *Replica-less assignments (root cause of the `three_node_cluster_end_to_end` and
  `cluster_backup_restore_and_controller_history` flakes).* The system channels are created by
  the controller's ensure loop as soon as the node is the Raft leader — possibly before any
  heartbeat was received. `controller::create_channel` then placed the channel on an empty
  candidate set: partitions with no replicas and no leader, forever (`leader.unwrap()` panics,
  "no node led it during the backup"). Now `create_channel` leaves the channel unplaced when
  no node is alive (the controller tick already places unplaced channels once nodes are
  alive), and the tick re-places replica-less partitions written by older versions (no replica
  means no data anywhere, so this is safe). The tick also updates its leader-load map as it
  places channels, so channels placed in one pass (both system channels) spread their leaders.
  Right after an election a new channel is also not placed on fewer live nodes than the cluster
  is known to have (registered `Up`/`Joining` nodes plus initial peers not registered yet,
  bounded by the RF) until the controller has led for 5 s (`PLACEMENT_GRACE`): otherwise a
  channel created between the controller's own first heartbeat and its peers' got a reduced RF
  (seen as `under_replicated` system partitions with auto-rebalance off). The ensure loops now
  re-check every 250 ms until the channel exists (then every 2 s), so the system channels
  appear as soon as the cluster is placeable instead of up to 2 s later.
- *Finalize grace with a dead preferred leader.* A committed move waited 30 s for its
  preferred leader even when that node was down (seen when the controller is stopped mid-plan),
  holding up the plan. It now counts as done at once when `to[0]` is not alive; the tick's
  preferred election hands leadership back when the node returns.
- *Repairs held back by the failed-plan backoff* (found in the live forget check). A balance
  plan towards a node that then crashed rolls back and ends `failed`; the 10-interval (5 min)
  backoff after a failed plan then also blocked the repair of that dead node's replicas. The
  backoff now applies to balance moves only: during it, a plan with only the `repair` moves
  still starts.
- *Test-only races* (no product change): `dry_run_and_mode_off_change_nothing` snapshotted
  metadata before the system channels existed; `events_feed_is_served_by_every_node` compared
  the outsider's page before its metadata replica routed to the leader (it answers from its
  empty copy by design); `cluster_backup_restore_and_controller_history` used a fixed 500 ms
  sleep for config replication, read history from another node immediately, and ran the backup
  before the system channels were led; `forget_dead_node_after_repair` set
  `replace_after_secs = 3` before the cluster settled (a heartbeat missed under parallel load
  started repair moves); the cluster-TLS status check assumed every node leads one of the new
  channel's partitions (not guaranteed by leader balancing); `new_node_is_balanced_in_under_load_without_loss`
  asserted a replica spread ≤ 1 right after creation, but initial placement balances leaders,
  not replica counts (mode `full` evens it out; the test now waits for that); short 5–10 s
  readiness waits in `three_node_cluster_end_to_end` raised to 20 s.

**Release:** version 0.5.0 (workspace, `ui/package.json`, mock); the console's About page reads
its version from `package.json` (Vite `define`) instead of a hard-coded string.

**Comparative benchmark (Phase B):**
- *Harness fairness/safety fixes before the final run:* client resources per comparison (4 CPUs
  for single-node systems, 2 for 3-node systems so brokers + client fit the VM's 8 CPUs; recorded in
  every run JSON); `--repeat 3` interleaved saturation repeats with median/range in the report; a
  drain-mode leg in the batching comparison; Kafka disk bounding (1 s segment/file delete delay,
  16 MiB segments, 1 s retention check — the default 60 s delete delay filled the host disk in the
  first full run); a per-run disk guard (abort < 10 GB free), per-run broker data-dir size log with a
  5 GB abort, a Kafka topic-gone check, `down -v` per system; runs with a consumer that never received
  anything are excluded from medians (kept on record).
- *Result sets are immutable:* `20261008-171456-smoke`, `20261009-full` (first full run, partial;
  its deleted Kafka records were reconstructed from the runner log and marked invalid) and
  `20261009-full2` (complete) are frozen; `generate.py --all` renders a page per set plus an index
  with history / before→after.
- *Findings recorded as remaining work:* the retention-deletion ack stall at high write rates (A/B
  proven), the v0.5 SDK not negotiating down to a v0.4 broker, one unexplained not-drained FluxMQ
  cluster-TLS repeat (250 of 3.27 M within 15 s).

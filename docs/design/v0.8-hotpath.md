# FluxMQ v0.8: single-node hot path (publish / deliver)

Status: implemented in the working tree (not committed). Scope: one node, the publish and
deliver path. Replication/cluster and TLS/retention are other v0.8 work streams.

Rules kept: fsync before ack (group commit) stays the default; per-message ack, nack,
redelivery, DLQ, filters and consumer-side CRC verification (`verify_crc`) are unchanged. **No
wire change**: every frame is byte-identical to v0.7 (`PROTOCOL_VERSION` 4, `MIN` 2), so old
clients work as before. Zero copy is an implementation detail of the broker.

## Changes

### 1. Zero-copy outbound frames (`fluxmq-server::net::{codec, writer, connection}`)

v0.7: every `DeliverRecords` frame was postcard-serialized into the writer's `BytesMut`, so each
stored envelope was copied once in user space (`memcpy` in `serialize_field::<Bytes>`, 16.9 % of
broker CPU at 1 KiB 4×4), plus `BytesMut::reserve_inner` growth copies (3.1 %).

v0.8:
- `OutboundEncoder` writes a frame as a list of `Bytes` chunks: the length prefix, variant and
  varint fields go to a scratch buffer, and the stored envelope buffer itself (≥ 256 B) is the
  next chunk. `Deliver`/`DeliverBatch` payloads ≥ 2 KiB are chunks too (smaller ones are
  copied: an iovec costs more than copying 100 B). The scratch is allocated in 64 KiB blocks
  and is empty between frames, so it never grows by copying.
- `FrameWriter<W: AsyncWrite>` replaces `FramedWrite`: queued chunks go out with
  `poll_write_vectored` (up to 128 slices per call), partial writes resume mid-chunk. Same
  batching as before (up to 64 queued frames per flush, write early beyond 2 MiB queued, write
  timeout).
- Generic over `AsyncWrite`, so the TLS write path uses it too (tokio-rustls supports vectored
  writes; rustls copies into its record buffer, which encryption needs anyway). A writer without
  vectored writes gets small chunks coalesced into one 64 KiB buffer first.
- Tests: byte-identical to `wire::encode_frame` for every frame kind through writers that
  accept 3/7/1000 bytes per write, vectored and not; envelopes are the same allocation as the
  store's; backpressure stops at the limit.

`sendfile`: not done. Envelopes are served from the recent cache or a read-ahead buffer (both
memory), and the TLS path needs the bytes in user space anyway. A plain-TCP `sendfile` path for
disk catch-up would need file ranges in `RawDelivery` (storage change); left for later.

### 2. Attempt history without per-message work (`fluxmq-core::history`, `group.rs`)

v0.7 recorded every delivery and every ack in a per-message hash map (`AttemptHistory::
on_deliveries` 10.3 % of broker CPU at 100 B 1×1, plus `on_finishes`, the shard sort and two
`Arc` clones per message).

v0.8: first attempts store nothing per message.
- A delivery batch records its first attempts as offset spans (one entry per contiguous range of
  a partition: group, consumer, delivered-at). Raw runs are one span; decoded runs one span per
  partition (`Spans::push` extends a recent span of the same partition).
- An ack batch records acked first attempts the same way.
- Per-message records only for failed attempts (nack, ack timeout, disconnect —
  `on_failures` records the whole attempt with consumer and delivered-at), later attempts and
  DLQ retries.
- `get(id)` (the message inspector) derives the first attempt from the spans covering the id and
  merges the per-message records; output format and content are unchanged (a failed first
  attempt is listed once). Bounded like before: at most `attempt_history_capacity` messages
  covered by spans, oldest first.
- Redelivery counts, `max_attempts`, DLQ attempts (kept on the pending entry, not in the
  history) are untouched.
- Tests: unit tests (span coalescing, eviction bounds, failure/ack/DLQ-retry merging) and the
  broker-level history check in `delivery_v07.rs::raw_delivery_ids_and_redelivery` (nacked raw
  entry: nacked attempt 1 + acked attempt 2; every other message one acked attempt).

### 3. Zero-copy inbound `PublishBatch` (`fluxmq-server::net::codec`)

The reference decoder copied the records section (`Bytes` deserialization = copy, 3.5 %).
`ClientFrame::decode_frame` now decodes `PublishBatch` through a borrowing mirror and the section
body is `body.slice_ref(..)` of the received frame (as `Publish` payloads already were). The
storage still builds one contiguous envelope (one copy, needed for the cache/zero-copy delivery).
Test: agrees with the reference decoder, body points into the frame, truncation is an error.

### 4. Raw delivery: one frame per envelope, range acks as bit operations (`connection.rs`, `group.rs`)

Found while measuring: a raw-records subscription polled at most `MAX_DELIVER_BATCH` (256)
records, but a stored envelope cannot be split, so an envelope of N > 256 records went out
⌈N/256⌉ times, each time whole (and the SDK CRC-checked and skipped through it each time). At
100 B with 5 ms linger a producer batch per partition is typically several hundred records.
- The pump now asks for up to 64 Ki records per poll on raw subscriptions; the prefetch credit
  and `MAX_DELIVER_BATCH_BYTES` bound it in practice. The decoded part of a poll (`DeliverBatch`)
  stays capped at `MAX_DELIVER_BATCH`.
- `AckRanges` on a raw run is applied a 64-bit word at a time: live bits cleared with masks,
  offsets finished per contiguous stretch (`AckState::finish_range`), history spans and counters
  once, one latency sample with a count (`ack_raw_range`). Same effects as per-id `ack_at`.
- Tests: `v4_e2e.rs::large_envelope_goes_out_once` (1000-record envelope → exactly one frame;
  with 300 credit, exact parts, nothing lost; fails on the v0.7 bound),
  `delivery_v07.rs::raw_range_ack_state_matches_naive_model` (5 seeds; random multi-range
  `AckRanges` across words/runs, nacks, disconnects, ranges over settled ids; lag/in-flight after
  every step; committed = end) — checked to fail when the range finish is off by one.

### 5. Lagging consumers: deeper raw read-ahead (`group.rs`)

Producers outrun consumers on one node once consumers fall out of the recent cache (16 MiB per
partition ≈ 0.3 s at saturation): from then on they read from disk, where under heavy writes and
fsyncs (Docker Desktop's virtual disk) a 4 MiB fetch's latency bounded catch-up with one chunk in
reserve. The raw read-ahead now keeps up to 3 chunks (12 MiB) per (group, partition) ahead, one
more in flight. Delivery threads (`--delivery-threads`, default 2) and prefetch were checked:
with the changes above the broker is no longer CPU-bound at 1 KiB, see results.

### 6. Raw-run compaction deferred (`group.rs`)

The v0.8 profile at 100 B 1×1 (after items 1–5) still showed ~25 % of broker CPU in
`Run::materialize` → `ChunkRecords::next` / `Records::next` / CRC / `get_varint`: the v0.7 quick
fix decides compaction after each ack batch, but the SDK flushes acks every 64, so a run of
several hundred records reached "7/8 settled" in one batch and was decoded and CRC-checked whole
while its last eighth was acked milliseconds later. Now a mostly settled run is compacted only
once it is 250 ms old (`COMPACT_AFTER`): younger candidates are queued and compacted by a later
ack batch or the 10 ms reaper tick if still mostly settled. Memory bound unchanged in kind
(stragglers pin their envelope buffer for at most ~250 ms longer). Test:
`delivery_v07.rs::raw_stragglers_survive_compaction` now covers both the immediate path and a
run compacted by the reaper after the delay (stragglers redelivered intact).

### 7. SDK (`fluxmq-client`)

- `Delivery::ack_all(deliveries)`: batch ack helper — one clock read per call, one
  processing-time lock and one ack-buffer lock per run of deliveries of the same subscription
  (consecutive ids collapse into one `AckRanges` range). Cumulative mode falls back to `ack`.
  Test: `v4_e2e.rs::large_frames_zero_copy_and_ack_all` (raw and decoded consumers, 10 000
  messages of 1–5 KiB, CRC on, no redelivery after `ack_all`, lag 0).
- Receive path was already zero-copy (payloads slice the frame); it now also gets each envelope
  once (item 4), which removes the repeated CRC/skip work per envelope.

## Results

Docker Desktop, M1 Pro, broker 2 CPUs / 2 GiB, harness 4 CPUs, v0.7 harness settings (window
20 000, 16 MiB segments, 512 MiB/partition retention, 30 s windows), group commit (fsync before
ack). Baseline `fluxmq:v07-base` = cac69af. The host was shared with other agents' builds and
benchmarks (load average 10–17 on 8 cores), so absolute numbers are noisy; runs were interleaved
and broker CPU per message (from `docker stats` over the measured window) is reported as the
more robust metric. Raw data: a local working directory (`hotpath/ab1`, `ab2`, `ab3`, `prof/`).

### Saturation, consumed msg/s (median of 2) and messages per broker CPU-second

`ab2`: candidate = working tree with items 1–5 and 7 (also contains other agents' in-progress
changes); `ab1`: items 1–3 and 7 only. Item 6 (deferred compaction) was measured separately
(below).

| config | v0.7 base | v0.8 | broker CPU base → v0.8 | (pub+cons) per broker CPU-s |
|---|---|---|---|---|
| 1 KiB 1×1 | 304k | **431k** (+42 %) | 163 % → 110 % | 412k → 790k (1.9×) |
| 1 KiB 4×4 | 294k | **435k** (+48 %) | 176 % → 105 % | 370k → 849k (2.3×) |
| 100 B 1×1 | 538k | **715k** (+33 %) | 48 % → 29 % | 2.8M → 5.0M (1.8×) |
| 100 B 4×4 | 176k | 168k (=) | 38 % → 27 % | 3.4M → 4.4M |

`ab1` (items 1–3 + SDK only): 1 KiB broker efficiency 420k → 615k msg/CPU-s (+46 %), 100 B
2.5M → 4.6M; consumed 1 KiB 4×4 248k → 309k, 1×1 272k → 266k (consumers fell behind in both
images), 100 B 1×1 484k → 760k.

Reading the numbers:
- At 1 KiB the broker is **no longer CPU-bound** (≈105–110 % of 2 CPUs at saturation, v0.7
  ≈165–175 %), and consumers keep up (e2e p50 0.4–2.5 s vs 10–14 s in v0.7: consumers stay in or
  near the recent cache instead of falling into disk catch-up).
- At 100 B 4×4 both images are bound by the harness process (≈190 % of its 4 CPUs, producers and
  consumers share it; consumption jumps to 1.8M msg/s the moment producers stop). The broker is at
  27–38 % CPU. Not a broker limit; the v0.7 report's 632k for this cell came from a quieter host.
- Kafka targets (522k / 579k at 1 KiB): not reached in this noisy environment in absolute terms;
  the broker now has ~45 % CPU headroom at 435k, so the remaining limit is the harness/host. A
  rerun on a quiet host (as for the v0.7 report) is needed for the headline comparison.

### Latency (isolated: only this work stream's files on top of cac69af, `fluxmq:v08-mine`), 1 KiB 4p4c, p99 ms, 2 interleaved runs each

| rate | v0.7 base | v0.8 |
|---|---|---|
| 1k msg/s | 4.9 / 3.5 | 3.5 / 3.5 |
| 10k msg/s | 12.4 / 8.3 | 3.6 / 5.3 |
| 50k msg/s | 11.1 / 16.9 | 11.4 / 8.2 |

p50 1.8–2.5 ms in both. No regression. (Runs of the full working tree in `ab2` showed publish

not delivery — and the baseline had one 213 ms run too; the isolated image does not reproduce
them. Worth re-checking once the other v0.8 streams (retention pacing) are merged.)

### Item 6, deferred compaction (local, release build, macOS host, no Docker)

Prefill 6M × 100 B (1000-record batches), drain with one raw consumer (prefetch 4000), 2 runs:
compaction immediate 1.80M / 1.75M msg/s, deferred 250 ms **2.21M / 3.28M msg/s**; broker CPU
for the whole run (prefill + drain) 3.35 / 3.95 s → 2.99 / 2.34 s. A Docker A/B of this item was
started but stopped: host free disk fell below 10 GB during the run (rule).

## Results — final (set `bench/results/20261010-v0.8`)

Built from HEAD `95107b0` and measured on the same laptop with 34–43 GB free disk. The host was not quiet: the macOS
storage indexer ran at 50–90 % CPU, which affects latency tails, not throughput. Brokers had 2 CPUs / 2 GiB, the client
4 CPUs, with v0.7 harness settings and group commit. Saturation is the median of 2 for 1 KiB, otherwise 1 run. The report
is `bench/report/index.html`.

| 1 node | v0.7 set | v0.8 | Kafka default (same day) | Kafka fsync per message (same day) |
|---|---:|---:|---:|---:|
| 1 KiB 1×1, consumed msg/s | 231k | **489k** (drained) | 470k | 302k |
| 1 KiB 4×4 | 320k | **547k** (drained) | 538k | 395k |
| 100 B 1×1 | 427k | **702k** (drained) | 643k (v0.7) | 673k (v0.7) |
| 100 B 4×4 | 632k | **748k** (1.61M published) | 472k | 734k |
| Broker CPU at 1 KiB 4×4 | 2.01 cores / 310k | **0.85 cores / 511k** (3.9× msg per CPU·s) | 1.73 cores / 538k | 1.03 cores / 395k |
| Catch-up 1 GiB, 1 KiB / 100 B | 477k / 1.35M | **1.28M / 2.51M** | 395k / 608k (v0.7) | 1.69M / 587k (v0.7) |
| Overload 60 s, 1 KiB / 100 B consumed | 363k / 606k | **558k / 710k** | 616k / 201k (v0.7) | 418k / 628k (v0.7) |

- **Goal met:** 1 KiB saturation is now at Kafka's default, 1.04× / 1.02× against Kafka measured the same day (0.94×
  against the Kafka figures published for v0.7, which came from a quieter host). That is with an fsync before every ack.
- The host sanity check (v0.7 image, 1 KiB 1×1) gave 280k / 286k, the same as yesterday's 274k / 280k, so the gain is
  the code, not the host.
- Latency, 1 node, p50 / p99: 1.9 / 18, 1.8 / 10, 2.8 / 15 ms at 1k / 10k / 50k. The p99 is above v0.7's published
  3.5–8 ms, but the v0.7 image run alternately on this host showed the same or larger tails (p99 6.8–85 ms at 1k,
  122–221 ms at 50k).
- **The "publish p99 spikes 30–380 ms" item is resolved as environment.** They reproduce with the v0.7 image. Fsync is
  healthy inside the spiky windows (mean 0.6–1 ms). Retention deletes nothing in latency runs (Stream channels, data
  below the cap), and fetch-ahead is not active on one node. `docker exec` polling and host load raise them. Evidence:
  `investigation/latency-tails/` in the set. No code change.
